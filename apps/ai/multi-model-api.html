多模型 API 接入与选型 ​

背景与问题 ​

做 AI 内容生产这类业务，很少有"一个模型包打天下"的情况：剧本生成要长上下文和中文文笔，分镜抽要素结构化输出要稳，生图生视频又是完全不同的接口协议，翻译分类可能用小模型就够。于是代码里很快出现各家 SDK 的直接调用——OpenAI 的、云厂商的、开源部署的——每家的鉴权、重试、错误码、计费口径都不一样。

这种散装接入方式的代价会随业务增长迅速放大：

  • 换模型要改代码：某家涨价、限流、下线某个版本，得挨个业务模块改一遍；
  • 成本失控：明明分类任务用轻量模型就够，却一直在调旗舰模型，账单看不懂；
  • 故障扩散：某一家 API 抖动，所有依赖它的功能一起挂，没有降级；
  • 密钥管理混乱：密钥散落在各处配置里，轮换一次像做手术。

所以第一步不是"选哪个模型"，而是先把接入层收敛成一个统一网关。

方案设计 ​

核心思路：业务代码只依赖一个统一接口，模型差异在适配层消化。

业务模块 → 统一网关（路由/鉴权/限流/计费/降级） → 适配层 → 各家模型 API
                                              ↑
                                     模型注册表（配置驱动）

  • 统一接口：定义与厂商无关的请求/响应结构（messages、tools、JSON Schema 输出、usage），业务侧永远不 import 任何厂商 SDK；
  • 适配层：每家模型一个 Adapter，负责协议转换、错误码映射、流式格式统一；
  • 模型注册表：模型名、厂商、能力（长上下文/视觉/JSON 输出）、单价、限流配额、优先级，全部放配置，加模型不改代码；
  • 路由策略：按任务类型 → 模型别名（如 script.writer、classify.light）→ 具体模型，别名指向哪个模型由配置决定。

选型跟着任务走，而不是跟着热度走：生成类长文本看上下文长度和文风，结构化抽取看 JSON 稳定性和指令遵循，分类/改写这种简单任务用便宜的小模型，生图生视频单独评估（协议和成本口径完全不同）。一个实用原则：每个任务类型先用两个候选模型跑同一批评测集，看质量差距值不值价格差，再定默认路由。

关键实现 ​

1. 统一接口与适配层

python
class ModelGateway:
    def __init__(self, registry, adapters):
        self.registry = registry   # 别名 → 具体模型配置
        self.adapters = adapters   # 厂商 → Adapter

    async def chat(self, alias, messages, **opts):
        route = self.registry.resolve(alias)          # 配置驱动路由
        adapter = self.adapters[route.provider]
        for target in route.chain:                    # 主模型 → 降级模型
            try:
                resp = await with_retry(
                    lambda: adapter.chat(target, messages, **opts),
                    max_attempts=3)
                self.meter.record(target, resp.usage) # 计量：token/费用
                return resp
            except (RateLimited, Timeout) as e:
                self.metric.emit("gateway.fallback", target, e)
                continue                              # 降级到链上下一个
        raise AllModelsFailed(alias)

关键点：with_retry 只重试限流/超时这类可恢复错误；meter 每次调用记账，成本才能按业务模块拆分。

2. 失败降级

降级链按"质量降序、价格升序"配置在别名上。例如 script.writer 主模型不可用时先降同档备选，再降到轻量模型并在响应上打 degraded 标记——业务侧可以选择接受降级结果，或提示用户稍后重试。注意区分两种失败：可重试（限流、超时、5xx）走指数退避；不可重试（鉴权失败、参数错误、内容审核拦截）直接抛出，重试只会浪费配额。

3. 密钥与配额管理

  • 密钥统一放密钥管理（环境变量注入 / KMS / 云厂商 KMS），绝不进代码库和普通配置文件，支持无感轮换；
  • 按厂商管理配额：本地做全局限流（令牌桶）防止自我打爆，同时监控各家用量逼近配额时告警；
  • 每个业务模块分配调用预算，网关层按 key 计量，超预算熔断并告警，避免某个死循环把整月额度烧光。

落地效果 ​

例如内容生产链路接入了三四家模型服务之后，收敛到统一网关的典型变化：

  • 业务代码里不再出现任何厂商 SDK，新增一家模型只加一个 Adapter + 一段注册表配置；
  • 账单能按"剧本生成 / 分类 / 生图"拆开看，发现某类任务用错了模型档位，改配置切过去就完成降本；
  • 某家 API 半夜抖动时，请求沿降级链自动落到备选模型，业务无感知或仅标记 degraded，不再整条链路挂掉。

以上为示意效果——真实收益（可用性、成本降幅）取决于模型组合和流量结构，上线前建议用评测集验证降级后的输出质量是否仍可接受。

小结 ​

多模型接入的工程重点是三件事：统一接口把业务和厂商解耦，配置驱动的路由与降级链应对选型变化，网关层的计量与配额管理兜住成本。模型本身会一直变，接入层稳了，换模型才只是改一行配置。
