02 工业数字化应用 ​

MES 生产执行 · IIoT 工业物联网 · WMS 仓储 —— 现场三层，共用 OpenBiz 底座。

状态图例：✅ 已验证 · 🔧 在建 · 📋 规划中

初衷：为什么是工业，为什么是三个 ​

一句话：我做过这些，但带不走，所以重做一遍。

十年里跟工业真正沾边的是两段：钢瓶企业的轻量 MES（五端协同、设备采集，现场交付与联调），和更早的 IoT 项目。这两段是我简历里最有分量的业务经历，偏偏也是最难证明的——代码在客户机房，文档留在公司，面试时只能靠嘴说。

「我做过 MES」这句话，对方听完只能选择信或不信。我不想让人靠「信」。

所以做了个决定：把做过的东西，用能公开的方式重做一遍。同一类业务、同样的现场约束，换成自己的代码、自己的库表、自己能跑起来的 E2E。工单的七个状态、库存的三个数、设备断线后的补传，都不是为了凑项目数量——是现场真实卡过我的问题。

为什么是工业，不是电商或后台管理。 因为工业系统的难点不在技术栈，在业务规则：工单状态能不能乱、库存怎么才算对得上、设备断十分钟数据怎么补。规则写错，系统就没人敢用。能把这类规则讲清楚、写对，比多写几个 CRUD 更能说明问题——而工业恰好是我真有经验的地方。

为什么三个一起做。 工厂里设备、工单、库存是三段咬合的业务。只做一个 MES，讲出来是一张功能清单；三个一起，才讲得清边界在哪、协同怎么发生——IIoT 只管采集，MES 只管执行，WMS 只管账。而「谁都想要别人的数据」，恰恰是真实项目里最容易出事的地方。

为什么共用一套底座。 我做过四年 CRM / ERP / OA 的定制交付，习惯的工作方式就是「一套底座 + 多客户定制」。用 OpenBiz 的 saas-core 承载这三个系统，等于顺手验证一件事：这套底座能不能复制到第四个、第五个域。

最后把边界说清楚。 这三个是可复现的重建版本，不是公司项目的原件。规模、并发、客户现场的复杂度都不等同于真实交付；页面里每个「已实现 / 待做」都按实际状态标，没做完的不会写成做完了。把边界写明白，比把 Demo 吹成产品更可信——这也是我对自己交付习惯的要求。

业务全景 ​

这三个系统不是三个并列的 Demo，而是同一家工厂里同时发生、彼此咬合的三段业务：设备在转、单在产、料在动。客户一张订单进来，会在三个系统之间走一圈：

客户订单 → 生产计划 → 领料出库 WMS → 工单执行 MES → 质检放行 MES → 完工入库 WMS → 发货 WMS
                                          ↑
                            设备状态 / 产量 / 告警（IIoT 持续供数）

每个系统只回答一个业务问题，回答不了的交出去：

系统回答的问题不管什么
IIoT这台设备现在什么状态？这个参数刚才多少？不碰工单，不碰库存
MES这批货做到哪一步了？谁在做？合格没有？不碰设备协议，不碰库位
WMS料和货在哪、还有多少、先出哪一批？不碰工序，不碰工单进度

对应到人——工厂里六个角色，各看各的屏：

角色主要落在关心的事
计划员MES交期能不能赶上，哪张单卡住了
班组长MES · IIoT 看板今天要做几张单，设备有没有异常
操作工MES 报工这单做完了，报多少、合格多少
质检员MES 质检 · WMS 到货检这批能不能放行
仓管WMS账实对不对，先到期的是哪批
设备工程师IIoT哪台设备在报警，历史曲线长什么样

一句话概括这套东西：把一家工厂的三本账——设备账、生产账、库存账——做成能跑的系统。三本账各记各的，但一张订单穿过三本账时，数量和时间必须对得上。

这些系统为什么存在 ​

工业软件不是把纸单子搬到屏幕上。它接手的是人本来就做不好的三件事：记不住、算不准、跟不上。

人做不到的现场长什么样系统要接手的
记不住一个月后追一批货用了哪批料、谁经手的，只能靠回忆和对质全链路留痕：谁、何时、哪台设备、哪批料、做了什么
算不准账面一千、实际八百，月底盘亏查不出是谁弄错的每笔变动有流水兜底，库存三个数必须恒等
跟不上设备停了两个小时没人知道，等交期废了才发现状态实时可见，异常自动冒头，不用等人巡检

四层问题，层次决定它值多少钱 ​

工业软件解决的问题是分层的。停在哪一层，决定了它是个更贵的 Excel，还是真管理系统：

层次解决的问题典型能力只做到这层的后果
1 记录事实留痕，事后查得到报工记录、出入库流水、设备历史数据电子台账，比 Excel 好看一点
2 约束规则不许绕过工单状态机、库存不能为负、无质检不放行有了规则，数据才有人敢信
3 协同跨角色、跨系统对账一张订单穿过三本账，数量和时间对得上部门之间不再互相甩锅
4 判断数据变成决策依据交期预测、瓶颈识别、良率趋势从记录系统升级成管理系统

大部分工业软件死在第 1 层：功能清单很长，但每条规则都能被人为绕过，数据没人敢拿来做决定，最后就变成一个更贵、更难用的 Excel。这也是为什么下面三个系统我都要写状态机和流水——不是为了技术好看，是让规则绕不过去。

三个系统各守一道门 ​

系统没有它的时候它守的规则
MES计划下发之后就是黑箱：做到哪一步、谁在做、合不合格，全靠走到车间问工单状态不许跳；没有质检不能完工；报工数不能超计划
WMS库存是糊涂账，先进先出靠仓管记忆，发错批次没人察觉库存三个数恒等；流水只增不改；发货按批次先进先出
IIoT设备状态靠人巡检，故障靠等，产量靠手抄，抄完还不准断线要补传；超阈值必须告警；采集频率按用途分级

它解决不了什么 ​

把边界写清楚，比把功能吹满有用：

  • 不解决管理问题：现场没人愿意报工，系统再好也是一张空表
  • 不解决数据质量：物料编码一开始就乱，系统只会把这个乱放大得更快
  • 不解决人的习惯：让老师傅在屏幕上多点两下，比加十个功能难得多
  • 不替代工艺：系统不会告诉你这道工序该几度、几分钟——那是工艺员的事

一句话：工业系统的价值不在功能多少，在规则是否真的被执行。五个功能但绕不过去，比五十个功能但随时能被绕过值钱。

水平自评：覆盖到哪、面试够不够 ​

口径：「中小离散制造 / 自营仓 / 设备监控」 这一档客户的日常业务，不是汽车电子万级点位、也不是 3PL 多货主。百分比是「场景是否说得清、规则是否绕不过去」，不是功能清单完成度。

三系统分别到哪一档 ​

系统约覆盖已经站得住的还撑不住的
WMS~75–85% 自营仓日常收发存主链、三态+流水、FEFO、盘点/调拨/退货、RBAC/审计/备份、报表/PDA 壳、CI·Docker·Swagger波次/上架策略、库存冻结、批次全厂追溯 UI、正式 /open/v1 对外契约、万级 SKU
MES~55–65% 小批量装配执行七态工单、工序报工+WIP 不变量、质检明细、单工单追溯、完工→WMS、IIoT 计数报工、CAS 禁删工厂/产线主数据、班次、齐套领料、PDA/看板前端、跨工单批次追溯、排产
IIoT~70–75% 监控演示到可连真设备MQTT+Modbus TCP/RTU、S7 SoftPLC、OPC-UA Soft、点位/攒批/缓存/降采样、规则+通知、看板、P0-15 E2E、P1-16 协议环回完整 opc.tcp Binary、真 RS485/PLC、边缘离线、TDengine、OEE、万级点位、断库故障注入

合在一起：工厂「设备在转、单在产、料在动」的叙事与约束层大约到 60–70%；若只谈仓储交付，WMS 单独可冲到 约 80% 的中小仓场景。跨系统「一张订单穿三本账」的闭环有 MES↔WMS / MES←IIoT 实证，但还不是完整 ERP 级订单编排。

对应前面的四层模型：三系统都稳在 第 2 层（约束），WMS/MES 部分进入 第 3 层（协同），第 4 层（判断/预测）基本未做——面试时这样拆，比说「做了三个大系统」更可信。

还建议补什么（按面试性价比） ​

优先级补什么为什么
P0面试口述稿：三态库存、工单 CAS、告警迟滞各 90 秒对方问的是「你为什么这样设计」，不是功能数
P0本地一键演示路径（WMS verify_all / MES run_mes_e2e / IIoT verify-p0-15）练熟能当场打开比 PPT 强
P1WMS /open/v1 领料·完工入库正式端点（设计已有）把「跨系统」从 MES 侧单方调用讲成双边契约
P1MES 工序/追溯/集成的前端页（接口已有）避免「后端很全、页面只有两张表」被追问
P1IIoT 真设备或录像（一台 Modbus 从站/PLC）证明不是只跑内嵌模拟
P2断库补传/队列溢出故障演练、浏览器 E2E工程完整度加分，非入门门槛
不做也行APS、SCADA 组态、分库分表、3PL范围外；写进「明确不做」比硬做更加分

面试准备：够不够 ​

够做「有工业背景的后端 / 全栈」基本面试准备，前提是你能讲清下面几类问题（每条都有代码与断言可指）：

  1. 库存为什么是三个数（on_hand / reserved / locked），CAS 如何防超卖
  2. 工单状态机非法流转为什么必须 409，并发开工如何 AND status = from
  3. 告警为什么要持续时长 + 迟滞 + 收敛，和「阈值一过就刷屏」的差别
  4. 跨系统为什么用 outbox，WMS 挂了车间为什么还能报工
  5. 多租户 / 权限按动作切，和 CRUD 权限的差别

不够单独支撑的：大厂基础架构岗（中间件内核）、纯算法/APS、现场交钥匙总包（实施、培训、硬件联调占比极高）。那些要另备项目或经历，不要靠这三个 Demo 硬撑。
