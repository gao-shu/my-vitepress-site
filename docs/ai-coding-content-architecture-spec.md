# AI Coding 内容架构 Spec

修改契约。本文件不是文章，也不是下一轮的发挥许可。  
依据：`docs/ai-coding-content-analysis.md`（2026-09-20 只读盘点）+ 本阶段指令。  
本阶段不改站点正文、导航、配置、模板。

与上一阶段的冲突，按事实处理，不另起一套：

| 点 | 盘点 | 本指令 | 本契约 |
|----|------|--------|--------|
| Spec 要不要进导航 | 流程里要有，导航先不加 | 明确不加 | **不加。** 写进工作流和新/老项目 |
| Spec 章节有多长 | 不超过四项：目标、改动点、验收、不做 | 十个问题，用不到可省略 | **十问是检查清单，文件只有四个标题。** 见第 4 节 |
| 单次任务 Context | 贴进对话、不进仓库 | Spec 是冻结约定，要留下 | **对话里的那份任务 Context 退役，改成一篇短 Spec。** Context 页不再维护第二份 |
| 架构发生在何时 | 现文在写完代码之后做「人工架构判断」 | 开发前要有架构 | **架构挪到开发前。** 写完后的核对并进 Review，不保留两个架构阶段 |

## 1. 重构目标

把 AI Coding 栏目收成一条可重复的开发流程：

```text
需求 → 架构 → Context / Rules → Spec → 开发 → Test → Review → Debug / Regression → 交付
```

Cursor 只是执行工具。栏目不写成 Cursor 教程、Prompt 合集或 Vibe Coding。

成功标准只有三条：

1. 读者能指出 Spec 在流程里的位置，而不必新开一页。
2. 同一份约定（接口、验收、不做）不会在聊天里丢。
3. 落地包仍是唯一文件模板，文章数量不增加。

不做：企业级规格系统、每个阶段一篇、空目录、第二套工单示例。

## 3. 核心概念边界

六个概念各回答一个问题。不能互相替代。

| 概念 | 回答 | 留下什么 | 不留下什么 |
|------|------|----------|------------|
| Requirements | 要解决什么问题？ | 问题、给谁用、怎样算有用 | 表结构、类名、Prompt |
| Architecture | 系统准备怎么解决？ | 模块边界、技术栈、有哪些接口/表、状态机这种**系统级**约束 | 这一次的字段校验、验收命令 |
| Context | AI 需要知道这个项目现在是什么？ | 仓库里已成立的事实：`00-overview`、`01-modules`、`99-gotchas` | 这一次要改什么 |
| Rules | AI 在这个项目里必须遵守什么？ | `.cursor/rules/`，所有任务都适用 | 某一个功能的验收 |
| Spec | 这一次要实现什么，做到什么程度算完成？ | 一篇短文件，确认后才许改代码 | 项目永久说明、Rules 正文 |
| Prompt | 这一轮具体如何向 AI 下达任务？ | 对话。用完可扔 | 不能代替 Spec |

另外两个不是开发产物：

- **Agent** = 执行角色 / 工作方式。技术说明留在「技术 → Agent」，产品说明留在「Agent 应用」。AI Coding 不解释 Agent 是什么。
- **Skills** = 可复用能力，跟人走，不进客户仓库。不代替 Rules，也不代替 Review。

一句话：

> Rules 管所有任务。Context 是项目事实。Spec 是当前任务。Prompt 是这一轮怎么问。

AGENTS.md 是给 Agent 的项目卡片（名称、技术栈、禁止项）。它不是 Spec，不是 Rules 全文，也不是 Prompt。

## 4. Spec 定义

### 重量上限（下一轮不得突破）

- 一篇 Spec 目标 **40 行以内**。超过就说明把架构或 Rules 写进来了。
- **四个标题，不许再加。** 禁止出现：风险登记、里程碑、角色矩阵、非功能需求、测试用例表、版本号。
- 十个问题是动笔前的检查清单，不是十个 `##`。
- 某问用不到：不写空标题，也不写「无」。
- 新项目第一篇用现有 `ticket-admin`。不新造例子。
- 不建 Spec 索引、生成器、状态页。

### 十问怎么折进四个标题

| 检查清单 | 写进 |
|----------|------|
| 1. 背景 / 问题 | 目标（一两句，不单开「背景」） |
| 2. 目标 | 目标 |
| 3. 范围 | 范围 |
| 7. 涉及模块 | 范围 |
| 10. 不做什么 | 范围里的「不做」 |
| 4. 输入 | 做到什么 |
| 5. 输出 | 做到什么 |
| 6. 业务规则 / 约束 | 做到什么（只写**这一次**的规则） |
| 8. 接口 / 数据变化 | 做到什么；没有就不写 |
| 9. 验收标准 | 验收 |

长期都适用的约束（不改 URL、不加依赖）留在 Rules，不抄进 Spec。系统级状态机若已在架构里定死，Spec 只写「遵守该状态机」，不把架构再讲一遍。

### 文件长什么样

有具体任务时才新建，路径固定：

```text
docs/ai-context/specs/<短名>.md
```

空骨架（只此一份，放落地包，不要预建目录）：

```markdown
# <这次任务，一句话>

## 目标

## 范围
- 做：
- 模块：
- 不做：

## 做到什么

## 验收
```

新项目示例（下一轮写进新项目文，不写进落地包）：

```markdown
# 工单三个接口

## 目标
客服能新建工单、看列表、把状态从 OPEN 改到 DOING 再改到 DONE。

## 范围
- 做：POST/GET /api/tickets，PATCH /api/tickets/{id}/status
- 模块：TicketController、TicketService、TicketMapper；表 biz_ticket
- 不做：前端、登录、缓存、MQ

## 做到什么
- 创建：title 必填，初始 status=OPEN
- 列表：返回 id、title、status、created_at
- 改状态：只允许 OPEN→DOING→DONE，禁止跳步

## 验收
- mvn -q -DskipTests package 通过
- curl：能创建；非法跳转不会成功
```

老项目示例（只描述这一刀，不描述整个工单系统）：

```markdown
# 列表增加 status 过滤

## 目标
已有 GET /api/tickets 增加可选参数 status。

## 范围
- 做：这一条查询
- 模块：现有 Ticket 列表调用链（扫描结果里的那一条）
- 不做：新接口、改表、改状态机、改 URL

## 做到什么
- status 为空：结果与改前一致
- status=OPEN：只返回 OPEN
- 非法值：明确失败，不要当成「查全部」

## 验收
- 不传 status 与改前一致
- status=OPEN 只有 OPEN
```

原则：

> Spec 是一次任务的冻结约定，不是项目永久文档。任务做完可以留在 `specs/`，不要合并进 `AGENTS.md` 或 `00-overview.md`。

## 5. 新项目流程

文章：`docs/ai/ai-programming/cursor-new-project.md`  
目标：空仓按流程做出 `ticket-admin` 的后端三接口。不是 Cursor 按钮教程。

`ticket-admin` 本身就是一个小系统。架构和第一篇 Spec 都会很短，这是对的。不要为了「像架构」再虚构网关、登录、多模块。

下一轮章节（替换现在的「放文件 → 出方案 → 写代码」）：

| 节 | 产出 | 写法约束 |
|----|------|----------|
| 0. 当天做完什么 | 一个可演示的后端 | 保留现有范围：三接口。前端仍可选，且**不进第一篇 Spec** |
| 1. 需求 | 三句话：谁、什么问题、怎样算有用 | 不写表和类 |
| 2. 架构 | 一个后端模块、一张表、三个 URL、状态机 OPEN→DOING→DONE | 停在系统边界。字段校验不写在这里 |
| 3. Context | 按落地包填 `00-overview.md` | 人写已知事实。不粘贴落地包全文 |
| 4. Rules / AGENTS | 放入 `AGENTS.md`、`00-core.mdc` | 只写「从落地包复制并改名称」。禁止第二套模板 |
| 5. Spec | `docs/ai-context/specs/ticket-apis.md`，用第 4 节那个新项目示例 | 接口和「禁止跳步」写在这里。确认后才进入下一节 |
| 6. 开发 | 只实现该 Spec | Prompt 写「按该文件实现」，链到 Prompt Pattern「实现」，不复制模板 |
| 7. 测试 | 用 Spec「验收」里的命令和 curl | 不另写测试理论。可选链到 Prompt Pattern「测试」 |
| 8. Review | 只审这次 Diff | 链到 Code Review。不复制 Review Prompt |
| 9. Debug | 只有失败才做 | 链到 Prompt Pattern「Debug」。不建新页，不做成必写长文 |
| 10. 交付 | 对照 Spec 的「不做」打勾 | 保留现有交付清单的作用。不写发布流程 |

必须删除或改掉的现有写法：

- 第 1 步那种把包结构、表、接口、状态机塞进一次「方案」回复的 Prompt。拆开：架构一节、Spec 一节。
- 任何 AGENTS / rules / overview 的全文粘贴。

保留：示例项目名、包名、表名、三个 URL、先不装 Skill、先有约定再改代码。

## 6. 老项目流程

文章：`docs/ai/ai-programming/cursor-legacy-project.md`  
目标：接手已有仓，安全做完「列表加 status 过滤」这一刀。不重新设计系统。

下一轮章节：

| 节 | 产出 | 写法约束 |
|----|------|----------|
| 0. 禁止事项 | 保持现有禁令 | 不改 URL、不改表、不加依赖、不装 Skill、不编造 |
| 1. 扫描 | 三次扫描，一次一个文件 | **保留。** 写入 `00-overview`、`01-modules`、`99-gotchas`。标题与落地包锁定，不另起标题 |
| 2. 理解这一条调用链 | `01-modules` 里只写这次会碰的链 | 写明：这不是系统理解完成，只够这一刀 |
| 3. 修正 Context | 人删掉扫描里的猜测；gotchas 人写 | Context 来自代码，不是人按理想项目编 |
| 4. Rules | 用扫描到的技术栈填落地包里的 `00-core` / `AGENTS` | 不从零写理想规范。不在本文贴全文 |
| 5. Spec | `specs/list-status-filter.md`，用第 4 节老项目示例 | 只描述这一次过滤。禁止写成「重做工单系统」 |
| 6. 局部修改 | 按 Spec 改 | 保留现有停手表 |
| 7. Test | 对照 Spec 验收，含「不传参数与改前一致」 | 这就是回归的最小形式 |
| 8. Review | 链到 Code Review | 不复制 Prompt |
| 9. Regression | 专查没点名的行为没变 | 不新开文。和 Test 可以同一节，但必须点名「改前行为」 |
| 10. 验收 | 保留现有接手清单 | 对照 Spec，不对照一整份理想文档 |

不新增：全仓文档化、架构重设计、第二套文件模板。

### 和新项目共用的骨架

```text
Context → Rules → Spec → 实现 → Test → Review
```

来源不同，标题相同：

| | 新项目 | 老项目 |
|--|--------|--------|
| Context | 人按已知目标写 overview | 从代码、表、接口扫描，人删猜测 |
| Rules | 放入落地包，按示例改名 | 从现状填，不发明新规范 |
| Spec | 第一个功能怎么算做完 | 这一刀改什么、改前行为如何保持 |
| 架构 | 有，且很短 | **没有设计步骤。** 扫描只记录现状 |

## 7. 工作流职责

文章：`docs/ai/dev/coding/cursor-workflow.md`  
它是栏目里**唯一的阶段总地图**。不放工单示例，不放 Prompt 全文，不放文件模板。

现有 10 步不要推倒重写成另一套名词。按下面调整（名字尽量沿用现文）：

| 新顺序 | 来自现文 | 这一阶段解决什么 | 人 | AI | 链接 |
|--------|----------|------------------|----|----|------|
| 1. 明确需求 | 现步骤 1 | 要解决什么问题，怎样算有用 | 定 | 不决定做不做 | 无专页 |
| 2. 拆解任务 | 现步骤 2 | 一次只做可验证的一刀 | 定 | 可协助列步骤，人砍 scope | 无专页 |
| 3. 架构 | 现步骤 5 前移 | 系统边界：模块、栈、接口/表、系统级约束 | 拍板 | 可列选项，不拍板 | 新项目第 2 节是例子；老项目跳过设计 |
| 4. Context | 现步骤 3 的一半 | 项目现在是什么 | 提供或删改事实 | 老项目可扫描，人确认 | Context & Rules；文件在落地包 |
| 5. Rules | 现步骤 3 的另一半 | 所有任务必须遵守什么 | 定 | 遵守 | 落地包，不在此列规则正文 |
| 6. Spec | 新增名字 | 这一次做到什么算完 | 确认后冻结 | 可起草，人确认前不许改代码 | 无专页。形状见落地包骨架 |
| 7. 实现 | 现步骤 4 | 按 Spec 改代码 | 收口 | 写 | Prompt Pattern「实现」 |
| 8. 测试 | 现步骤 7 | 对照 Spec 验收 | 看结果 | 可写用例或命令 | Prompt Pattern「测试」 |
| 9. Review | 现步骤 6 | 审 Diff | 最终判断 | 提问题 | Code Review |
| 10. Debug / 回归 | 现步骤 8 | 失败才查；老项目要证明没点名的行为没变 | 定是否修 | 定位 | Prompt Pattern「Debug」 |
| 11. 交付 | 现步骤 10 | 对照 Spec 的「不做」收工 | 负责 | 不负责宣布完成 | 两篇实战的清单 |

从主链拿掉、不要删掉观点：

- **现步骤 5「写完再做架构判断」**：不单独成步。Diff 是否越界，写进 Review 的一句人的职责。
- **现步骤 9 重构**：改为交付之后的可选句：「没有新 Spec，就不重构。」不进实战必做，不建页。
- **文档 / 发布**：不进主链。`docs/ai-context/` 是给 AI 的事实，不是用户文档。现文没有发布方法，不要补。

工作流里每一节只留：这一步回答什么、人/AI、链到哪。现步骤 3 的材料清单删掉，改成上面两行链接。

## 10. 重复内容处理方案

### 工作流 vs 总览

- 总览删两段闭环（`index.md`「什么叫 AI Coding」「AI Coding 工作方式」里的流程块）。
- 工作流保留唯一阶段表。
- 「人对需求、架构、质量负责」这句话总览留一句即可，不展开。

### Context & Rules vs `00-core.mdc`

概念页下一轮删除或压成一句的现有块：

- 「单次任务 Context」整段代码块（约「贴进对话，不进仓库」至示例结束）。同一题改由老项目 Spec 承载。
- 「Rules 以落地包为准」下面那四条可粘贴规则。改成：边界原文只在落地包 `00-core.mdc`。
- 「修改边界」整段默认边界。与 `00-core` 同义。
- 「怎么用」里「没有就先写四条」「把 Context + 边界贴进 Prompt」。改成：开任务写 Spec，Prompt 里只给 Spec 路径。
