## 背景

设备数据同时有「最新一眼」和「事后可查」两种用法。

## 判断

| 存储 | 存什么 | 不存什么 |
|------|--------|----------|
| **Redis** | 设备在线状态、最新测点快照、短 TTL 会话/限流 | 不当事后审计库；不替代历史 |
| **MySQL** | 设备档案、点表配置、历史采样（V0 可先落同一库表）、后续工单等业务 | 不扛超高写入的无限明细（那是以后 TSDB 的事） |

读写路径（V0）：

```text
Gateway 上报
  → 写 Redis（最新值 / 在线）
  → 异步或同步写 MySQL（历史采样 + 业务）
  → 监控页：列表走 Redis，曲线走 MySQL
```

## 为何 V0 仍要 Redis

- 监控页高频刷「在不在线、当前值」时，避免每次打库  
- 为以后告警判定「当前状态」留统一入口  

若 Lab 001 设备量极小且无压力，可短期只用 MySQL，但模型上仍按上表分职责，避免业务表被当成缓存滥用。

## 结论

**Redis = 当前态；MySQL = 真相与历史（V0）。** 分工先于「要不要上更多中间件」。
