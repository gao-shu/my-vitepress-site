## 背景

工业 IoT 资料常默认：设备/网关必须 MQTT + Broker。

## 常见说法

> IoT 项目就该上 MQTT / EMQX。

## 判断

**不是标配，是需求驱动。**

V0 形态是「一个 Gateway → 一个后端」。HTTP 能完成上报、错误码清晰、排障简单。

MQTT 真正有价值的场景包括：多消费者（监控 + 报警 + 分析）、发布订阅解耦、弱网与会话、设备侧本就 MQTT。这些 **V0 都不成立**。

## 暂不用的原因

1. 多一个 EMQX = 多一套部署、权限、QoS、残留会话问题  
2. 尚未有「第二个订阅方」证明 Broker 必要  
3. 想先用 Lab 001 把采集与存储的问题暴露出来，避免和消息层问题缠在一起  

## 何时重新评估（V1 触发）

- 需要第二个独立消费者  
- 或 Lab 明确要做 QoS / 断线补传对照  
- 或 Gateway 数量与上报模型明显适合 pub/sub  

→ 对照实验：[Lab 001](../labs/lab-001) 之后的 Lab 002（规划中）

## 结论

V0 **不用** MQTT/EMQX；V1 用实验数据决定，不凭口号上。
