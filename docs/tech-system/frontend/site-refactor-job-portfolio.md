# 把个人网站从「学习站」改造成「求职作品集」

> 本文记录一次真实的信息架构重构：把一个堆了 445 篇笔记、顶部 6 个栏目（含 2 个下拉）、侧栏按旧目录散装的个人站，改造成面向求职的 5 栏目作品集。所有数字来自本次真实改动，方法可复现。

## 一、问题背景

原站点定位是「个人技术学习站」：顶部 6 个一级栏目、其中 2 个用下拉承载二级分类、还有一个独立的「开源拆解」栏目；左侧菜单按旧目录（guide / java / database / redis / framework / mq……）各配一套。结果是：

- **访客 10 秒内看不懂这个站是干什么的**——对求职毫无帮助；
- 同一个人的内容散在十几套侧栏里，Java 知识被拆到 `java/`、`framework/`、`springboot/` 三个目录；
- 早年一次目录迁移后，正文里残留了 **22 个死链**（指向已被删除的旧 AI 文档），没人发现；
- 公司项目（MES / CRM / AI 漫剧）和可公开验证的开源项目混在一起，没有区分。

**目标**：一天内完成页面框架改造，让站点能直接用于求职展示——顶部只留 5 个栏目、每栏目独立侧栏、首页突出个人定位与代表项目；**不动任何一篇文章的 URL**。

## 二、方案比较与关键决策

| 方案 | 做法 | 取舍 |
|---|---|---|
| A. 大搬家 | 按新分类物理移动/重命名 md 文件 | 目录整齐，但 **URL 全变、外链全失效、回归风险高** |
| B. 只改配置 | 不动文件，只用 VitePress 的 nav/sidebar 重新组织展示 | URL 零变更、可整体回退；代价是物理目录仍保留旧名 |
| C. 折中 | 配置重组 + 未归类内容用 `/more/` 兜底 | 兼顾「框架稳定」与「不丢内容」 |

选 **C**。核心原则：**改造第一天不迁移任何文件**，只改 `config.mts` 的导航与侧栏，让 445 篇文章「换件衣服」而不「搬家」。未归类的就业/成长/英语/资源类内容（约 150 篇）先通过一个低调的 `/more/` 入口保持可达，后续再治理。

## 三、关键实现

### 3.1 顶部收敛为 5 栏目、零下拉

```text
改造前：首页 / 技术体系(下拉) / 开源拆解 / 应用开发(下拉) / AI赋能 / 关于我   （6 项，2 个下拉）
改造后：首页 / 应用实例 / 功能开发 / 技术体系 / AI 实践 / 关于我               （6 项，0 下拉）
```

> 后续演进（2026-10-23）：新增「应用实例」一级栏目承载规划项目矩阵（5 模块 × 3 项目，均为配置与页面调整，无文件迁移）；原「应用开发」更名为「功能开发」，与「应用实例」形成「规划项目 ↔ 技术实践」的分工。URL 依旧零变更。

二级分类全部下沉到左侧菜单。「开源拆解」不再占一级入口，但其 4 个页面内容保留、仍可访问。

### 3.2 每栏目一套独立侧栏

- **功能开发**：企业业务 / 工业数字化 / AI 应用 / 办公自动化 / 个人工具
- **技术体系**：Java 后端 / 前端工程 / 数据库与中间件 / 系统集成 / 工业与物联网 / 部署与运维（把原先散在 `java` `framework` `springboot` `database` `redis` `mq` 的 38+34 篇归位）
- **AI 实践**：辅助编程 / Agent / 知识库与 RAG / 工作流 / 应用案例
- **关于我**：个人介绍 / 工作经历 / 技术能力 / 简历与联系

侧栏 link 仍指向**原 md 路径**，所以文章 URL 一个都没变。

### 3.3 未归类内容的「内容映射表」

没有为了填满菜单而造空页面。先建一张映射表（原路径 / 篇数 / 当前归属 / 目标归属 / 是否迁移 / URL 风险），没有明确归属的统一进 `/more/`，**原路径全部保留可达**。

## 四、验证：死链治理

改造最怕「改了导航却留下一堆死链」。我没有只信 VitePress 的 dead-link 警告，而是**从构建产物里实证**：

```bash
# 1. 提取所有渲染后页面的站内链接
grep -roh 'href="/my-vitepress-site/[^"#?]*"' dist --include="*.html" \
  | sed 's/href="//;s/"$//' | sort -u > links.txt

# 2. 逐个核对目标文件是否真实存在（.html 或 dir/index.html）
```

结果：约 **774 个唯一站内目标，22 个死链**。关键判断——这 22 个是否由本次改造引入？逐一查来源页面后发现，它们全部来自旧文章正文里指向「早年已删除的旧 AI 文档」的链接（在改造前的基线提交里目标就已不存在），**属于历史遗留，非本次引入**；新页面与 config 的死链为 0。

配套还有两条硬约束：

- **文章只增不减**：改造前 445 篇 → 改造后 449 篇（新增项目页/文章/模板等），删除 0、迁移 0；
- **可整体回退**：改造前单独打一个基线提交，出问题整单回退。

## 五、结果与经验

| 维度 | 改造前 | 改造后 |
|---|---|---|
| 顶部栏目 | 6 项含 2 下拉 | **5 项 0 下拉** |
| 侧栏 | 按旧目录十几套 | 每栏目一套，技术知识归位 |
| 首页 | 「个人技术学习站」 | 求职定位 + 代表项目 + 联系方式 |
| 文章 URL | — | **0 变更** |
| 死链 | 22 个历史遗留 | 新增 0（遗留项记录待治理） |

**几条可复用的经验**：

1. **先冻结范围再动手**：第一天只做框架，不迁文件、不补内容，避免无限装修挤占真正能证明能力的项目时间。
2. **用产物验证，别用警告验证**：dead-link 警告在带 `base` 的站点会误报，直接从构建产物 grep 链接再核对目标文件最可靠。
3. **「不搬文件」是迁移安全的最大杠杆**：只改配置，URL 就不变，外链和 SEO 不受影响，回退也只需一个 commit。
4. **映射表先行**：先盘清 445 篇的去向，再决定侧栏，避免「为了整齐而迁移」或「凭空造空页」。

## 六、局限与改进

- 物理目录仍是旧名（`java` `framework` 等独立目录），后续若要做真正的路径治理，需配 301/别名并评估外链影响。
- 22 个历史死链尚未清理，列入了后续治理清单。
- `/more/` 是过渡方案，未归类内容仍需逐步归位。
