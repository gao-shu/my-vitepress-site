# Flowable 企业二开（三层二开体系）

> **与入门衔接**：[Flowable 快速入门](/tech-system/backend/flowable-bpmn)（本站侧栏「技术体系 → … → 其他」内与之并列）
>
> **适合人群**：
> - 已能跑通「部署 → 起流程 → 查待办 → 完成任务」这一条主线  
> - 准备在企业里接 OA / 审批 / BPM 的需求，分不清「要写业务代码」还是「要动引擎」  
>
> **本篇刻意不做的事**：
> - 不从「某个 Java 类叫什么」讲起；需要对接源码时，只在引擎层一节说明**会碰到哪类机制**  
> - 不把二开讲成「背 API 列表」，而是按企业里真实分工拆成三层

---

## 本篇怎么读：先两个「模块」

### 模块一：Spring Boot 里先做到「简单能用」

企业里最常见的落地方式，是 **Spring Boot + Flowable Starter**：自动配置拉起来引擎，业务里只做四件事。

```text
部署流程定义（把 BPMN 落到库里的「模板」）
    ↓
启动流程实例（一次业务单据 = 一条「在跑」的流程）
    ↓
查待办 / 认领（回答：现在谁该办）
    ↓
完成任务（把当前节点办完，让引擎继续往下走）
```

依赖与配置按团队规范或官方 Starter 即可；关键是心里要有上面这条 **最小闭环**。  
更细的 BPMN 概念与 API 主线，见 [Flowable 快速入门](/tech-system/backend/flowable-bpmn)。

下面这种写法，本质就是 **「在 HTTP 层把业务选择写进变量，再交给引擎推进」**，多数项目够用很久：

```java
@PostMapping("/approve")
public void approve(@RequestParam String taskId,
                    @RequestParam boolean approved,
                    @RequestParam String comment) {

    Map<String, Object> vars = new HashMap<>();
    vars.put("approved", approved);
    vars.put("comment", comment);

    // 完成任务并传递变量：引擎据此走网关、创下一节点任务等
    taskService.complete(taskId, vars);
}
```

可以理解为：**网关上的条件、下一节点要什么数据，都在这里用变量「喂」给引擎**，而不是在每个 Controller 里手写「下一步该找谁」。

### 模块二：在同一套「完任务」能力上做二开——要动哪一层？

当你发现需求不限于「同意 / 驳回 + 意见」，而出现类似：

```text
谁批：按职级汇报链动态算？
走向：金额和风险组合后才决定支线？
交互：要能驳回到任意一环、发起人撤回、运行中加人减人？
还要有：在线画流程、每步不同表单、组织人事联动、钉钉/邮件通知？
```

就要把二开拆开看——下面 **三层**，对应企业里三组完全不同的心智负载。

---

## 一、为什么用「三层二开体系」来理解？

在企业项目里，二开往往不是「找一个万能扩展点」，而是三类问题叠在一起：

```text
业务规则到底听谁的？           → 第一层
人怎么画流程、怎么填表、怎么走组织？→ 第二层
流程在执行器内部能不能「破格」走动？→ 第三层
```

先分清层级，再决定招人、排期与技术方案，比自己搜到一个接口名就开始抄要稳得多。

---

## 二、第一层：业务规则层二开

### 这层在干什么？

这层回答的是：**在引擎照 BPMN 往下走之前 / 之中，企业的业务说了算的那部分逻辑**——谁办、过什么条件算通过、是否要临时改道、多人审批怎么结算。

典型包含：

```text
• 审批人策略：直属上级、部门负责人、角色候选人、候选组、矩阵岗、金额路由到不同职级……
• 条件规则：不仅网关里写表达式，还可能把一组规则外包成配置或脚本，由业务系统统一解释
• 动态节点：例如何时跳过某一环、是否在运行时插入一串「额外审批」（与「平台层建模能力」配套）
• 会签 / 或签：所有人过、任一过、按比例过、一票否决怎么处理
• Strategy 一类的结构化拆分：同一种「选人 / 算账 / 通过判定」，多种实现可插拔
```

### 怎么理解这层？

把你的业务系统想成：**在 Flowable 周围包了一层「企业规则引擎」**——引擎负责「按 BPMN 与变量推进令牌」，这层负责「算出变量、算出候选人、算出是否该拆会签」「把组织架构里的真相翻译成引擎能消费的 assignee/candidate」。  
它和「表单长什么样」「设计器画布」不强绑定，核心是 **规则与数据**。

### 这层强调什么？

> **本质上，这一层是企业规则引擎（含与人事/主数据耦合的那部分规则），不是在改 Flowable 内核。**

---

## 三、第二层：平台能力层二开

### 这层在干什么？

这层回答的是：**没有这些，业务规则再漂亮也落不了地**——人怎么维护流程、怎么用 IT 资产、怎么去协同。

典型包含：

```text
• 流程设计器：常见基于 bpmn.js 族系做画布、校验、租户隔离、自定义属性面板（扩展写进 BPMN 的自定义元素里）
• 表单系统：每步挂载不同表单（低代码 / JSON Schema）、只读快照、与业务主表关联
• 组织架构：岗位、部门树、兼任、代理人、班次——都会回流到第一层「选人策略」
• 消息通知：待办直达 IM / 邮件，链路与幂等一般由业务编排
• 流程中心：我的待办、已办、我发起的、抄送、委派、置顶、草稿等「壳」产品与权限模型
```

### 怎么理解这层？

这是 **企业对 BPM / 低代码 平台的投资**：Flowable 提供执行与持久化底座，但这一层决定了 **组织能不能自助演进流程、运维能不能控版本、合规能不能回溯表单与图**。

### 这层强调什么？

> **本质上，这一层是企业 BPM 平台（产品化能力），引擎只是其中的一个执行部件。**

---

## 四、第三层：Flowable 引擎层二开

### 这层在干什么？

当产品需求已经触及「**不改变 BPMN 结构就不舒服**」或「**标准完成 / 标准跳转语义不够用**」时，会进入引擎层二开，例如：

```text
• 任意节点驳回：不是简单变量分支，而是要把执行路径拉回到历史某点并保证数据一致
• 撤回：发起人或特定角色在尚未汇聚前收回令牌
• 动态跳转：在受控条件下改道（与审计、补偿强相关）
• 动态加签 / 减签：运行期改变多实例集合或插入并行审批枝
```

### 会涉及什么（只到「机制类型」，不展开类表）？

这类需求往往会碰到 **命令式事务边界**（一次操作里多表、多实例如何原子完成）、**节点行为**（某类 BPMN 元素在运行期如何推进）、**执行实例树**（父子执行、并行分支、多实例）等 **源码级概念**。  
它们不是「多写几个 Service 方法」一定能优雅解决的，要评估升级成本、回归成本与是否值得与官方演进路线并行维护。

### 这层强调什么？

> **这一层离「流程执行器」最近；动得越深，越要和团队明确：这是平台级投入，不是单个业务线的临时需求。**

---

## 五、三层怎么一起念（一句话对照）

```text
业务规则层   → 企业规则系统：把人、钱、风险翻译成变量与策略
平台能力层   → 企业 BPM 平台：画流程、挂表单、接组织、做通知与门户
Flowable 层  → 流程执行引擎：在语义不够时，才动命令、行为与执行模型
```

---

## 六、收尾：把认知对齐到「难在哪里」

```text
Flowable 本质上是流程执行引擎：
把 BPMN + 变量解释成「令牌怎么动、任务怎么生、历史怎么记」。
```

真正拖住工期和质量的，多半是：

```text
• 与企业人事、权责、矩阵组织纠缠在一起的规则系统
• 与合规、可追溯、千人千面表单相关的 BPM 平台
```

所以学习路线可以更诚实一些：**先把模块一闭环跑稳，再在模块二里对号入座——当前需求到底主要是哪一层？** 再找最小方案，而不是默认「我要去学改引擎源码」。
