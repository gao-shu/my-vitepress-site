# 编程开发提示词（29 条）

> 我自己写代码时反复用的 29 条。占位符【】换成真实信息（版本、报错原文、目录），用不上的约束直接删。
> 通用骨架：背景 → 现状 → 目标 → 约束 → 输出格式，见 [提示词库总览](/ai/prompts/)。

## 一、日常开发

### 1. 接手陌生模块：先读懂再动手

```text
背景：接手一个已有项目，技术栈【Spring Boot 2.7 + MyBatis-Plus + MySQL 8】，入口在【XxxApplication】，我要改的模块是【包路径】。
任务：不要改任何代码。先帮我搞清楚这个模块——
1) 对外暴露哪些接口，各自被谁调用；
2) 核心数据流从请求进入到落库经过哪些类；
3) 有哪些隐含约定（事务边界、缓存、异步、幂等）；
4) 哪些地方看着能改、实际不能动（历史包袱）。
输出：先给一份结构说明和调用链，标出你不确定的地方，我来确认。
```

### 2. 补单元测试

```text
背景：【类名】在【包路径】，职责是【一句话】，依赖【XxxMapper / Redis / 外部 HTTP】。
任务：为【方法名】写单元测试，覆盖：正常路径、边界值、空值与 null、异常分支、并发下的幂等（如果有）。
约束：用 JUnit 5 + Mockito，不启动 Spring 上下文；外部依赖全部 mock；断言要校验行为而不只是返回值。
输出：完整测试类，可直接放进【测试目录】；每个用例上方一行注释说明它守的是什么缺陷。
```

### 3. 重构但不改行为

```text
背景：这段代码【贴代码】在【类/方法】，现在的问题是【圈复杂度高/重复逻辑/命名混乱/职责不清】。
任务：在不改变外部行为的前提下重构。
约束：方法签名不变；异常类型和错误码不变；日志内容尽量不变；不引入新依赖；一次只做一类改动（先拆方法，再改名，最后抽类）。
输出：分步骤的重构计划 + 每一步的 diff，我逐步确认后再往下。
```

### 4. 审自己的 diff（没有同事时最有用）

```text
背景：这是我刚写的改动，spec 是【贴 spec 或需求描述】，diff 如下【贴 diff】。
任务：只做审查，不要改代码。按这个顺序检查——
1) 是否完整实现了 spec，哪条没实现；
2) 边界条件：空值、超时、重试、并发、幂等；
3) 异常是否被吞掉，错误信息是否可定位；
4) 权限校验是否缺失，是否有越权读写的可能；
5) SQL 是否 N+1、是否有全表扫描、事务范围是否过大；
6) 日志是否泄露敏感信息。
输出：按严重程度排序的问题清单，每条给出所在行和修改建议；没问题的项也要明确写“已检查，无问题”。
```

### 5. 提交信息与 PR 描述

```text
背景：这是一个【功能/修复/重构】提交，改动涉及【文件列表】，目的是【一句话】。
任务：写 commit message（Conventional Commits 格式）和一段 PR 描述。
要求：标题不超过 50 字符；正文说清“为什么改”而不是“改了什么”（diff 已经说明了）；PR 描述包含：背景、方案、影响面、验证方式、回滚方式。
输出：直接给可复制的文本，不要解释格式规范。
```

### 6. SQL 与索引

```text
背景：MySQL 8，表【表名】约【行数】行，字段【列表及类型】，现有索引【索引定义】。
慢 SQL：【贴 SQL】，执行计划：【贴 EXPLAIN】。
任务：分析慢在哪，给优化方案。
约束：不改表结构（除非确实必须，需说明代价）；不改变查询语义；索引不要超过【N】个。
输出：按收益排序的方案，每条写明预期效果和副作用（写入放大、索引失效场景）。
```

## 二、新功能扩展

### 1. 需求 → 技术方案

```text
背景：【项目/模块简述】，技术栈【…】。需求：想要【用户视角的描述】。
任务：给技术方案，先不要写代码。要覆盖：
1) 需要新增/修改哪些表、哪些接口；
2) 与现有模块的耦合点，怎么接进去最省事；
3) 至少两个方案的取舍（开发量、可维护性、扩展性），并给出推荐；
4) 明确不做什么（本期范围外）。
输出：结构化方案，控制在【N】字内，我要拿它去和需求方对齐。
```

### 2. 方案 → 开发 spec

```text
背景：方案已经定了：【贴方案】。
任务：把它整理成一份可直接开发用的 spec，包含——
1) 接口清单：路径、方法、入参、出参、错误码；
2) 数据模型：表结构、字段类型、索引、唯一键；
3) 状态机：状态、事件、允许的流转；
4) 边界与异常：空数据、重复提交、并发、超时、权限不足；
5) 不做的事。
约束：字段命名沿用现有风格【贴 2~3 个现有表或接口作为样例】；能复用现有能力就不要新建。
输出：markdown 文档，我要逐条改。
```

### 3. 表结构评审

```text
背景：这是新功能的建表语句：【贴 DDL】。现有库的规范是：【命名风格、主键策略、时间字段、软删除约定】。
任务：评审，不要直接改。检查：
1) 字段类型是否合理（金额、状态、时间、枚举）；
2) 索引是否覆盖实际查询，是否有冗余索引；
3) 唯一键是否足以防止重复数据；
4) 是否缺审计字段、是否有 NULL 陷阱；
5) 未来数据量【预估】下的分表/归档风险。
输出：问题清单 + 修改后的 DDL 建议，每条说明为什么改。
```

### 4. 前后端接口契约

```text
背景：后端【框架版本】，前端【Vue 3 + TS】。要做的接口是【功能描述】。
任务：给出接口契约，前后端都能照着写，包含：
1) TypeScript 的类型定义（含可选字段和联合类型）；
2) 请求/响应示例（成功、参数错误、无权限、服务异常各一份）；
3) 分页、排序、筛选参数的约定；
4) 时间、金额、ID 的序列化格式（避免 Long 精度丢失这类坑）。
输出：一份 markdown 契约 + 一段可直接放进前端 types 文件的 TS 代码。
```

### 5. 拆成可提交的小步

```text
背景：需求 spec 在【贴 spec】。
任务：拆成 5~8 个可以独立提交、每次都能跑通的步骤，每步不超过【200】行改动。
要求：每步写明——改哪些文件、验收方式（跑什么命令/看什么现象）、依赖前一步的什么产物；数据库变更和代码变更分步，保证任何一步中断都能回滚。
输出：按顺序的清单，我先做第 1 步。
```

## 三、Bug 修复

### 1. 报错定位（三件套）

```text
背景：【框架+版本】，运行环境【本地/测试/生产】。
现象：【什么操作触发了什么现象，前后端哪一侧】。
完整报错（原文，不要截断）：
【贴堆栈】
复现步骤：【1…2…3…】
我已经排查过：【看了哪些日志、试过哪些改动、排除了哪些可能】。
任务：先给根因假设，按可能性排序，每条说明依据和验证方法；不要直接给修复代码。
```

### 2. 最小复现

```text
背景：这个问题只在【特定条件】下出现，完整链路太复杂不好调。
任务：帮我把它缩小到最小复现——列出必要条件，逐个说明“去掉它还会不会出问题”，给一个 20 行以内能跑起来的复现代码。
约束：用【语言/框架】原语，不引入额外依赖；复现要能稳定触发，不能是偶发。
```

### 3. 并发与偶现问题

```text
背景：接口【接口名】在高并发下偶发【现象：超卖/重复数据/数据不一致/死锁】。
相关代码：【贴 Service 方法 + 事务注解 + 涉及的 SQL】。
现状：QPS 约【N】，库存/余额类字段更新方式是【先查再改 / 直接 UPDATE / 乐观锁】。
任务：1) 列出所有可能的并发窗口，标出代码行；2) 每个窗口给验证方法（怎么稳定复现）；3) 给修复方案并对比代价（悲观锁/乐观锁/唯一键/队列）。
约束：不改接口；锁定范围尽量小。
```

### 4. 慢接口排查

```text
背景：接口【路径】在【数据量】下响应【N 秒】，正常应【<N ms】。
已知：慢日志/火焰图/链路追踪如下【贴证据】。
任务：按“网络 → 应用 → 数据库 → 外部依赖”的顺序定位，指出最可能的 2~3 个瓶颈点，每个给出验证手段（打日志/计时/压测）。
输出：排查顺序表，先做哪个、看什么指标、判定标准是什么；先不要给优化代码。
```

### 5. 线上事故复盘

```text
背景：事故时间【…】，影响【范围/时长/用户量】，直接原因【已知信息】。
任务：帮我写复盘，结构：时间线（精确到分钟）、直接原因、根本原因（流程/设计/监控三层）、处置过程、改进项（每条带责任人和截止时间）。
要求：不要揽责也不甩锅，事实优先；改进项必须可验证，不能写“加强关注”。
```

## 四、功能完善

### 1. 边界与异常补齐

```text
背景：功能【描述】已跑通主流程，代码在【文件】。
任务：以“用户会怎么把它用坏”为出发点，列出缺失的边界处理，按优先级排序：
1) 空数据、超大输入、非法格式；
2) 重复提交、连续点击、刷新重放；
3) 网络超时、第三方失败、部分成功；
4) 权限越界、跨租户访问；
5) 数据迁移/历史数据兼容。
输出：清单 + 每条对应的最小改动，我先挑前三条做。
```

### 2. 权限与数据范围自查

```text
背景：系统用【RuoYi/Sa-Token/Spring Security】，角色有【角色列表】。
任务：检查以下接口是否存在越权：【贴接口清单或 Controller】。
检查项：能否越权访问他人数据、能否绕过前端直接调接口、数据范围（本人/团队/全部）是否在后端过滤、写操作是否校验归属、超管是否被意外限制。
输出：风险表（接口 / 风险等级 / 复现方式 / 修复点）。
```

### 3. 补测试与回归清单

```text
背景：这次改动涉及【模块】，历史回归靠手工点。
任务：给出两层产物——
1) 可以自动化的接口级测试用例（正常/边界/异常/权限各若干），用【pytest/RestAssured】写；
2) 无法自动化的手工回归清单，按“改动影响面”排序，每条写清操作步骤和预期结果。
约束：用例要能重复跑，不依赖固定自增 ID 和脏数据。
```

### 4. 交互与体验细节

```text
背景：页面【路径】已完成功能，用户反馈“用起来别扭”。
任务：从五个维度给改进建议，按投入产出排序：加载与空状态、错误提示（可操作而非“操作失败”）、表单校验时机、批量操作与快捷键、移动端/小屏适配。
约束：不改后端接口；改动优先在现有组件内完成。
输出：表格（问题 / 影响 / 改法 / 工作量 S-M-L），我先看低成本高收益的。
```

## 五、项目构建

### 1. 技术选型与骨架

```text
背景：要做【项目一句话】，使用者是【谁】，预期规模【并发/数据量】，我的技术栈是【Java/Vue 等】。
任务：给技术选型和脚手架方案，覆盖：语言与框架版本、数据库与缓存、消息队列要不要、鉴权方案、部署形态（单体/容器）、前端构建工具。
要求：每一项给“选它/不选它”的理由和替代方案；明确哪些是当前阶段不需要、可以以后再加的（避免过度设计）。
输出：选型表 + 一份可执行的初始化命令清单。
```

### 2. 目录结构与分层约定

```text
背景：新项目，技术栈【…】，团队规模【1 人 / 3 人】，预计【N】个模块。
任务：给一套目录结构和分层约定，要求：模块边界清晰、后续加模块不用改脚手架、单人和多人协作都能用。
输出：1) 目录树（带每个目录一句话说明）；2) 分层职责（Controller/Service/Mapper 各层能做什么、不能做什么）；3) 依赖方向规则（谁能依赖谁）；4) 直接可用的 CLAUDE.md 片段。
```

### 3. 数据库初始化

```text
背景：新库，MySQL 8，命名规范【下划线小写 / 前缀 xxx_】。
任务：按下面模型生成初始化脚本：【贴实体清单】。
要求：1) 建表语句含注释、字符集、引擎；2) 主键、唯一键、常用查询索引齐全；3) 时间字段统一【created_at/updated_at】；4) 附一份最小演示数据（每个表 3~5 行，外键能对上）；5) 脚本可重复执行（IF NOT EXISTS / 先 DROP）。
```

### 4. 容器化与部署脚本

```text
背景：项目【Spring Boot jar + Vue dist】，部署在【单机/麒麟/NAS】，用【Docker Compose】。
任务：给部署方案：Dockerfile（多阶段构建、非 root 用户、时区与字体）、docker-compose.yml（应用+MySQL+Redis）、启动脚本、日志落盘与轮转、健康检查。
约束：镜像尽量小；配置走环境变量；数据卷挂载宿主机目录；不要在生产镜像里塞构建工具。
输出：逐个文件给内容，并说明每个关键参数的用途。
```

### 5. CI 流水线

```text
背景：仓库在【GitHub/GitLab/Gitee】，技术栈【…】，分支策略【main + feature】。
任务：写一条最小可用流水线：构建 → 单测 → 静态检查 → 打包 → 部署到【测试环境】。
要求：缓存依赖；失败即停并输出可定位的日志；敏感信息走 secrets；只在 main 分支部署；给出回滚方式。
```

## 六、项目完善与上线

### 1. README（别人能跑起来的那种）

```text
背景：项目【名称】，技术栈【…】，实际入口和启动命令在【贴真实命令】。
任务：写 README，要求新人照着能在 10 分钟内跑起来：一句话定位、功能截图位、环境要求、启动步骤（逐条可执行）、配置项表、常见问题（至少 5 条真实踩过的坑）、目录结构、接口文档入口。
约束：命令必须来自我给的原文，不要自己编参数；不确定的地方留【待确认】标记，别猜。
```

### 2. 上线前检查清单

```text
背景：项目【名称】准备上线，部署环境【…】，预计首日流量【…】。
任务：给我一份上线前检查清单，按“配置 / 数据 / 依赖 / 安全 / 可观测 / 回滚”六类，每条是可勾选的、可验证的动作。
要求：包含——配置与密钥是否从代码里剥离、数据库是否已备份且能恢复、初始化数据是否就绪、第三方依赖的额度与超时、限流与降级开关、日志与告警是否接通、回滚方案和决策人。
```

### 3. 监控与告警

```text
背景：应用【技术栈】，部署【单机/集群】，已有【Prometheus/Grafana 或没有】。
任务：给出最小可用监控方案：必须采哪些指标（应用/数据库/主机三层）、阈值怎么定、告警发到哪里、什么情况不该告警（避免告警疲劳）。
输出：指标清单 + 采集方式 + 3 条最该先配的告警规则。
```

### 4. 技术债与重构优先级

```text
背景：项目【名称】已上线，代码约【N】行，我知道有问题的地方有：【列举】。
任务：帮我排技术债优先级，标准是“出故障的概率 × 影响面 ÷ 修复成本”。
输出：表格（债务项 / 风险 / 触发条件 / 修复成本 / 建议窗口），并给出“本期只做前三项”的理由。
```
