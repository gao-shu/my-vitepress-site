# AI 加持下的老项目开发完整流程（Cursor 实战版）

> **适用场景**：已有 Java / Spring Boot / 前后端项目,需要维护、迭代、重构或新增功能

---

## 一、前言:老项目开发的真正难点

很多开发者在老项目里效率低,并不是因为代码写不动,而是因为三个问题:

### 1. 代码理解成本高

- 模块多
- 调用链复杂
- 业务逻辑分散

### 2. 缺乏整体认知

- 不清楚系统全貌
- 不知道改动影响范围

### 3. AI 使用方式错误

- 直接让 AI 写代码
- 没有上下文(Context)
- 没有规则(Rules)约束

---

## 二、老项目 AI 开发的核心原则

在 Cursor 或任何 AI 编程工具中,老项目必须遵循一个核心原则:

> **先理解系统,再修改代码,而不是直接写代码**

可以拆成三层结构:

```
理解层(Understand)
    ↓
抽象层(Context / Rules)
    ↓
执行层(Code Generation)
```

---

## 三、标准流程总览

老项目 AI 加持开发分为 5 个阶段:

```
① 项目扫描(AI 分析现状)
② 构建 Context(系统认知)
③ 提取 Rules(开发约束)
④ 局部任务拆解(功能级)
⑤ AI 辅助改代码(执行层)
```

下面逐步讲清楚每一步怎么做。

---

## 四、第一阶段：项目扫描（AI 建立认知）

### 目标

让 AI 基于代码生成结构化系统文档（写入 docs 目录），用于后续开发快速定位。

---

### 操作方式（在 Cursor 中）

⚠️ **每一步对应一个文件，名称和内容完全一一对应**

---

#### 🟢 第1步：系统结构总览 → 对应 `00-system-overview.md`

👉 在 Cursor 输入：

```
请分析当前 Spring Boot 项目结构，并将结果写入文件 /docs/00-system-overview.md：

内容必须包含：

# 系统结构总览

## 分层结构
Controller → Service → DAO

## 模块划分
（按 Controller 划分模块，列出模块名 + 对应 Service）

## DAO 层
（MyBatis 或 JPA）

## 技术栈
（从依赖中判断）

要求：
- 不要猜测业务逻辑
- 只基于代码结构
- Markdown 格式
```

---

#### 🟡 第2步：数据库结构 → 对应 `01-database.md`

👉 在 Cursor 输入：

```
请分析当前项目数据库结构，并将结果写入文件 /docs/01-database.md：

内容必须包含：

# 数据库结构

## 核心表
（如 user、order）

## 表关系
（表之间关联）

## 核心业务表
（用户、订单等）

## 辅助表
（日志、配置等）

要求：
- 不要编造关系
- 基于代码推断
- Markdown 格式
```

---

#### 🔴 第3步：模块说明 → 对应 `modules/*.md`

👉 在 Cursor 输入（以用户模块为例）：

```
请分析【模块名】模块，并将结果写入文件 /docs/modules/【模块名英文名】.md：

内容必须包含：

# 【模块名】模块

## Controller
（列出所有接口方法，包含方法名）

## Service
（列出对应 Service 类和方法名，不要写业务解释）

## 相关表
（涉及的数据库表）

## 模块类型
（CRUD 或复杂业务，只做判断，不解释）

## 主要接口（重点）
（列出 2-3 个最核心接口，如 list / create / update）

## 推荐修改入口（关键）
（指出最适合修改的接口方法，如 UserController.list）

要求：
- 不要猜测业务逻辑
- 不要写职责解释
- 必须包含方法级别信息
- 用 Markdown 格式输出
```

👉 其他模块同理：

- `/docs/modules/order.md`
- `/docs/modules/product.md`
- ...

---

#### 🧠 第4步：系统地图（汇总）→ 对应 `02-system-map.md`

👉 在 Cursor 输入：

```
请基于项目结构分析，生成系统结构地图，并写入文件 /docs/02-system-map.md：

内容必须包含：

# 系统结构地图

## 模块划分
（按业务列出模块）

## 模块职责
（每个模块一句话）

## 核心模块
（必须熟悉）

## 辅助模块

## 推荐熟悉顺序

要求：
- 简洁
- 不要长篇解释
- Markdown 格式
```

---

### ✅ 最终完全对应关系（100% 对齐）

| 步骤 | 内容 | 文件 |
|------|------|------|
| Step 1 | 系统结构总览 | `/docs/00-system-overview.md` |
| Step 2 | 数据库结构 | `/docs/01-database.md` |
| Step 3 | 模块说明 | `/docs/modules/*.md` |
| Step 4 | 系统结构地图 | `/docs/02-system-map.md` |

## 五、第二阶段：构建 Context（系统认知层）

### 目标（修正版）

让 AI 基于第一阶段生成的结构文档，整理出系统级说明（Context），用于后续开发时统一认知。

👉 **本阶段本质是**：

- 从"结构信息" → 提炼"系统理解"
- 给 AI 一个稳定的"项目背景"

---

### 操作方式（在 Cursor 中）

⚠️ **只执行一次，不要反复生成（避免污染认知）**  
⚠️ **必须基于第一阶段 docs，不重新扫描项目**

---

#### 🟢 第1步：生成系统 Context

👉 在 Cursor 输入（复制下面完整内容）：

```
请基于以下已有文档，总结当前系统的 Context（系统说明），并直接写入文件 /docs/10-context.md（不存在则创建）：

参考文档：
- /docs/00-system-overview.md
- /docs/01-database.md
- /docs/02-system-map.md

输出内容必须包含：

# Context - 当前系统说明

## 系统类型
（如电商 / ERP / 内容系统，根据模块判断）

## 核心业务模块
（按业务总结，不要列类名）

## 技术栈
（从 system-overview 提取）

## 数据核心
（总结数据库核心表及作用）

## 系统特点
（根据模块复杂度 + 数据结构推断，如是否事务重 / 是否流程复杂）

要求：
- 不要照抄原文档
- 必须做总结和抽象
- 不要编造不存在的业务
- 使用 Markdown 格式
- 内容简洁清晰
```

---

### ✅ 你要的输出

**文件位置**：`/docs/10-context.md`

**内容包括**：

| 章节 | 说明 |
|------|------|
| 系统类型 | 如 CRM、OA、ERP 等 |
| 核心模块 | 按业务总结，不列类名 |
| 技术栈 | 从 system-overview 提取 |
| 数据核心 | 核心表及作用 |
| 系统特点 | 事务复杂度、流程复杂度等 |

---

### ⚠️ 注意（修正版）

- ❌ 不要重新扫描整个项目
- ❌ 不要让 AI 重新分析代码结构
- ❌ 不要生成长篇业务说明

👉 **本阶段只做**：

- ✔ 信息抽象
- ✔ 系统总结
- ✔ 认知统一

---

### ❗ 必须人工校正（这一点非常关键）

生成后你需要**手动确认两点**：

1. **系统类型**（AI 可能判断不准）
   - 例如：AI 可能将 CRM 误判为 ERP
   - 需要根据实际业务场景修正

2. **系统特点**（结合你经验修正）
   - 例如：AI 可能低估事务复杂度
   - 需要根据历史开发经验调整

**校正示例**：

```
## 系统类型
❌ AI 生成：电商系统
✅ 人工修正：CRM 客户管理系统

## 系统特点
❌ AI 生成：订单流程复杂
✅ 人工修正：客户跟进流程长，需记录多次沟通历史
```

---

### 💡 为什么需要人工校正？

- **AI 缺乏业务上下文**：只能看到代码结构，无法理解业务含义
- **命名可能误导**：`OrderController` 可能是"工单"而非"订单"
- **复杂度评估偏差**：AI 难以判断哪些业务流程真正复杂

**原则**：AI 负责**信息整理**，人负责**业务判断**。

---

## 六、第三阶段：提取 Rules（开发规则层）

### 目标（修正版）

让 AI 基于已有代码 + 第一阶段 docs + 第二阶段 Context，提取出当前项目真实的开发规范（Rules），用于约束后续 AI 生成代码。

👉 **本阶段本质是**：

- 从"代码实现" → 抽象"开发规则"
- 让 AI 写代码时不跑偏、不重构、不乱来

---

### 操作方式（在 Cursor 中）

⚠️ **不要凭空生成 Rules，必须基于代码和已有文档**  
⚠️ **不要追求一次完美，先生成"初版 Rules"**

---

#### 🟢 第1步：生成开发规范（Rules）

👉 在 Cursor 输入（复制下面完整内容）：

```
请基于当前项目代码 + 以下文档，提取当前项目的开发规范（Rules），并直接写入文件 /docs/99-rules.md（不存在则创建）：

参考文档：
- /docs/00-system-overview.md
- /docs/modules/*.md
- /docs/10-context.md

要求：所有规则必须"基于当前代码总结"，不要写理想化规范

输出内容必须包含：

# Rules - 开发规范

## 架构规范
（Controller / Service / DAO 各自职责划分）

## 接口规范
（接口返回格式、参数处理方式）

## 编码规范
（异常处理、日志记录方式）

## 数据库规范
（事务使用、数据库操作习惯）

## 命名规范
（类名、方法名、参数命名方式）

要求：
- 不要编造不存在的规则
- 必须贴近当前项目实际写法
- 使用 Markdown 格式
- 内容简洁清晰
```

---

### ✅ 你要的输出

**文件位置**：`/docs/99-rules.md`

**内容包括**：

| 章节 | 说明 |
|------|------|
| 架构规范 | Controller/Service/DAO 职责划分 |
| 接口规范 | 返回格式、参数处理 |
| 编码规范 | 异常处理、日志记录 |
| 数据库规范 | 事务使用、操作习惯 |
| 命名规范 | 类名、方法名、参数命名 |

---

### 🔄 后续迭代方式（必须执行）

**Rules 不是一次性产物，而是持续演进的文档。**

👉 **每做一个真实需求，补一条规则**：

**新增规则示例**：

```
## 业务规则（新增）
- 订单相关接口必须加事务
- 所有分页接口必须使用统一分页对象 PageResult
- 客户跟进记录必须记录操作人和操作时间
```

👉 **持续更新**：`/docs/99-rules.md`

**迭代流程**：

```
开发新需求
  ↓
发现新的编码习惯/约束
  ↓
补充到 99-rules.md
  ↓
下次 AI 生成代码时自动遵守
```

---

### 🔥 一句话收尾

> **Rules 不是写出来的，是从代码里提取、在开发中不断强化的。**

---

### 💡 为什么 Rules 如此重要？

- **避免 AI 乱来**：没有 Rules，AI 可能用你不喜欢的写法生成代码
- **保持代码一致性**：确保新生成的代码与现有代码风格一致
- **降低维护成本**：统一的规范让团队协作更顺畅
- **加速开发效率**：AI 遵守规则后，Code Review 更快

**原则**：Rules 越贴近实际，AI 生成的代码越可用。

---

## 七、第四阶段：原型驱动任务拆解

### 🎯 目的

把原型 / 需求转成结构化开发任务，让后续开发可以直接按模块执行：

- 页面是什么
- 功能是什么
- 数据怎么变
- 按什么顺序开发

---

### 🧭 操作方式（在 Cursor 中）

直接输入：

```
请基于当前原型/需求进行系统化拆解，并生成开发任务。

输出必须写入：
/docs/task/{YYYYMMDD}-task-{N}/

其中：
- YYYYMMDD = 今天日期
- N = 当天第几个任务（001开始递增）

必须生成文件：

00-summary.md（任务总览）
01-page-layer.md（页面结构）
02-function-layer.md（功能拆解）
03-data-layer.md（数据结构）
04-develop-order.md（开发顺序）

拆解要求：

页面层：
- 页面列表
- 页面跳转关系

功能层：
- 每个页面的操作行为
- 对应后端接口（如有）

数据层：
- 涉及数据库表
- 字段变化
- 表关系

开发顺序：
- 模块优先级
- 依赖关系

要求：
- 不写代码
- 不编业务细节
- 必须基于现有系统结构
- 结构化输出 Markdown
```

---

### ⚠️ 注意事项

- 任务目录必须按顺序递增（task-001、task-002）
- 不要让 AI 自己发挥业务逻辑
- **只做"拆解"，不做"实现"**
- **一定要先有原型/需求再执行**
- **这一阶段不写代码，只产出结构**

---

### ✅ 输出示例

假设今天是 2025年4月30日，第一个任务，会生成：

```
/docs/task/20250430-task-001/
├── 00-summary.md      # 任务总览：客户跟进功能
├── 01-page-layer.md   # 页面结构：列表页、详情页、编辑页
├── 02-function-layer.md # 功能拆解：查询、新增、修改、删除
├── 03-data-layer.md   # 数据结构：customer 表、follow_record 表
└── 04-develop-order.md # 开发顺序：先建表 → 后端接口 → 前端页面
```

---

### 💡 为什么需要这个阶段？

- **避免盲目开发**：先拆解清楚再动手，减少返工
- **明确依赖关系**：知道哪些模块必须先做，哪些可以后做
- **降低认知负担**：把大需求拆成小任务，逐个击破
- **便于协作**：不同开发者可以并行处理不同任务

**原则**：拆解越清晰，开发越顺畅。

## 八、第五阶段：AI 执行代码生成（完整版）

### 🎯 目的

基于 task 驱动，让 Cursor 完成：

- Controller / Service / Mapper 代码生成
- 数据库与配置变更处理
- 文档 + SQL 变更同步
- 保持项目结构一致

---

### 🧭 Cursor 执行指令（直接使用）

```
基于 /docs/task/{YYYYMMDD}-task-{N}/ 完成本次功能开发，要求如下：

---

### 1. 代码生成
- 生成 Controller + Service + Mapper 实现
- 严格基于 Context + Rules
- 必须复用已有代码
- 不允许重构现有架构
- 不允许新增无关业务设计
- 保持当前项目代码风格一致

---

### 2. 数据与逻辑实现
- 按 task 中 data-layer 完成数据库操作
- 保持当前 DAO / ORM 使用方式一致
- 不修改表结构（除非 task 明确要求）
- SQL 操作必须与现有项目规范一致

---

### 3. 数据库变更处理（必须执行）

如果本次开发涉及：
- 新增表
- 修改表结构
- 新增字段

必须执行：

1. 在 /db/ 目录生成 SQL 文件：
   /db/{YYYYMMDD}_task_{N}.sql

2. SQL内容必须包含：
   - CREATE TABLE（新增表）
   - ALTER TABLE（结构变更）
   - 字段注释说明

3. 同步更新：
   - /docs/task/{YYYYMMDD}-task-{N}/03-data-layer.md

---

### 4. 数据变更检查（必须执行）

开发完成后必须检查是否涉及：

- 数据库表结构变更
- 配置文件（application.yml / yml / properties）修改
- DTO / 枚举 / 常量新增或修改
- 新增工具类或通用组件

如存在变更必须同步标注在代码与文档中。

---

### 5. 文档同步

如果存在变更，请同步更新：

- /docs/task/{YYYYMMDD}-task-{N}/03-data-layer.md
- /docs/task/{YYYYMMDD}-task-{N}/00-summary.md（如影响范围变化）
- 如涉及开发规范变化，更新 /docs/99-rules.md

---

### 6. 约束

- 不允许自由设计业务逻辑
- 不允许脱离 task 范围开发
- 不允许一次性重构系统结构
- 不允许引入新的技术栈
- 必须严格遵循现有项目架构与风格
```

---

### ⚠️ 注意事项

- ✔ **一次输入即可完成完整开发流程**
- ✔ **必须基于 task 文件驱动**
- ✔ **Context + Rules 必须已存在**
- ✔ **数据库变更必须生成 SQL 文件**
- ❌ **不允许 AI 自行扩展业务**
- ❌ **不允许跳过 task 直接开发**
- ❌ **不允许引入新的技术栈或框架**

---

### 📁 输出示例

假设今天是 2025年4月30日，第一个任务，执行后会生成：

**1. 代码文件**：
```
src/main/java/com/example/controller/CustomerController.java
src/main/java/com/example/service/CustomerService.java
src/main/java/com/example/mapper/CustomerMapper.java
src/main/resources/mapper/CustomerMapper.xml
```

**2. SQL 文件**（如果涉及数据库变更）：
```
/db/20250430_task_001.sql
-- 包含 CREATE TABLE 或 ALTER TABLE 语句
-- 包含字段注释
```

**3. 文档更新**：
```
/docs/task/20250430-task-001/03-data-layer.md（更新数据结构说明）
/docs/task/20250430-task-001/00-summary.md（如有影响范围变化）
/docs/99-rules.md（如涉及开发规范变化）
```

---

### 🧠 本质说明

这一阶段本质是：

> **🟢 把 Cursor 从"写代码工具"变成"任务执行引擎"**

**之前的模式** ❌：
```
开发者：帮我写一个订单功能
AI：生成一堆代码，可能不符合项目规范
开发者：手动调整、修复、重构...
```

**现在的模式** ✅：
```
开发者：基于 task-001 完成任务
AI：严格按照 task 拆解的结构化需求执行
  - 读取 00-summary.md 了解任务目标
  - 读取 01-page-layer.md 了解页面结构
  - 读取 02-function-layer.md 了解功能点
  - 读取 03-data-layer.md 了解数据结构
  - 读取 04-develop-order.md 了解开发顺序
  - 结合 Context 和 Rules 生成代码
  - 自动生成 SQL 变更文件（如有需要）
  - 自动检查数据变更并更新文档
开发者：验证代码是否符合预期
```

---

### 💡 为什么需要这个阶段？

- **标准化输出**：每次开发都遵循相同的流程，减少人为差异
- **可追溯管理**：每个任务都有完整的文档记录，便于复盘
- **降低认知负担**：AI 已经理解任务结构，开发者只需验证结果
- **持续迭代优化**：通过文档同步机制，Rules 和 Context 不断进化
- **数据库版本控制**：SQL 文件统一管理，便于部署和回滚

**核心价值**：Task 驱动的开发方式，让 AI 从"创意生成者"变成"精准执行者"。

---

## 九、老项目 AI 开发的正确心智模型

### ❌ 错误认知

- AI 直接写完整项目
- Prompt 决定一切
- agent 能理解所有代码

---

### ✅ 正确认知

- AI 是"局部理解工具"
- Context 决定理解能力
- Rules 决定输出质量
- 人负责系统级决策

---

## 十、完整工作流总结

```
Step 1:AI 扫描项目(理解)
Step 2:整理 Context(系统认知)
Step 3:提取 Rules(开发规范)
Step 4:拆解任务(功能级)
Step 5:Cursor 执行代码生成
Step 6:人做验证与调整
```

---

## 十一、最终结论(非常重要)

老项目开发的本质不是"写代码",而是:

> **在复杂系统中,让 AI 参与理解 + 局部执行,而不是全权生成**
