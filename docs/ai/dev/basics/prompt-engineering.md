# Prompt 怎么写才像工程

> 打开这篇 → 套最小结构 → 复制模板 → 丢给 AI。先别背一百个技巧。

核心原则：

> **工程里够用的 Prompt，不是文采好，而是结构稳、约束清、输出可复用。**

---

## 适用场景

适合用「工程化 Prompt」的时候：

* 同一类任务要反复做（总结、Review、改 Bug、写测试）
* 输出格式必须稳定（表格、JSON、固定章节）
* 需要限制 AI 别乱改、别编造、别扩 scope
* 要把一次好用的问法沉淀成模板，给自己或团队复用

不适合：随口问一句、一次性探索。那种场景随便聊就行，不必硬套模板。

---

## 最小结构（背下来）

记住这几块就够用。日常四块；工程场景再补上下文和示例。

| 块 | 作用 | 一句话 |
| --- | --- | --- |
| 角色 | 设定视角 | 你希望模型扮演谁 |
| 任务 | 说清目标 | 要它完成什么 |
| 约束 | 画边界 | 不能做什么、不要编造、不要扩 scope |
| 输出格式 | 强约束结果形态 | 必须按什么结构输出 |
| 上下文（常用） | 提供材料 | Diff、报错、业务规则、相关代码 |
| 示例（可选） | 校准风格与粒度 | 给 1 个正例，必要时再给反例 |

最小可跑版本：

```text
角色：……
任务：……
约束：……
输出格式：……

[材料 / 上下文]
```

工程增强版再加：

```text
上下文：……
示例：……
```

## 使用前准备

写 Prompt 前先想清楚三件事：

1. **这次任务的验收标准是什么？**（什么叫「做完了」）
2. **必须提供哪些材料？**（缺上下文就只能得到泛泛回答）
3. **输出要拿去干什么？**（给人读、直接粘贴、还是再交给下一步 AI）

材料尽量具体：代码 Diff、报错原文、接口定义、业务规则、已知限制。不要只丢一句「帮我看看这段代码」。

---

## 注意事项

### 1. 先定结构，再堆技巧

「像工程」靠的是可复用结构，不是措辞花哨。角色、任务、约束、输出格式齐全，通常比堆形容词更稳。

### 2. 约束写清楚，比多说「请认真」有用

优先写：

* 不要修改代码 / 不要重构无关部分
* 不确定就标「需要确认」，不要编造
* 只输出指定格式，不要开场白和结尾客气话

### 3. 输出格式是稳定性的关键

让模型按你要的格式输出，不要让它自由发挥。常用约束：

* 必须用 Markdown / JSON
* 必须包含：结论 / 依据 / 风险 / 下一步
* 每条不超过 N 行
* 没有发现问题时直接说明，不要硬凑问题

### 4. 一次只做一类事

把「分析」和「修改」、「总结」和「扩写」拆开。混在一个 Prompt 里，最容易越改越大。

## 可直接复制：通用模板

```text
角色：你是一名资深工程师，负责[场景]。

任务：
[用一句话说清要完成什么]

上下文：
[粘贴 Diff / 报错 / 需求 / 相关代码]

约束：
- 只处理上述任务，不扩展范围
- 不确定的地方明确标「需要确认」
- 不要编造不存在的业务规则或 API
- 不要直接修改代码（若本轮只要分析）

输出格式：
1. 结论（3 行内）
2. 关键发现（按严重程度）
3. 建议下一步（可执行）
4. 需要我补充的信息（若有）
```

## 三个常见场景套用

### 1）技术总结

```text
角色：技术文档编辑
任务：把下面材料总结成可复用笔记
约束：不编造材料里没有的内容；不确定标出来
输出格式：
## 要点（5 条内）
## 例子（1～2 个）
## 常见坑（1～2 个）
## 我还需要确认什么
```

### 2）Code Review（只找问题）

```text
角色：Code Reviewer
任务：对下面 Diff 做问题优先的 Review，不要改代码
约束：
- 优先找本次修改引入的问题
- 不为风格差异提意见
- 不确定标「需要确认」
输出格式：严重问题 / 一般问题 / 可优化项 / Review 结论
```

### 3）改 Bug（先方案后动手）

```text
角色：负责定位与修复的工程师
任务：根据报错和相关代码定位根因，先给最小修复方案
约束：
- 本轮不要直接改代码
- 不进行无关重构
- 说明可能副作用
输出格式：
1. 根因判断
2. 依据
3. 最小修改方案
4. 风险与验证方式
```

更完整的 Review 工作流见 [用 AI 做 Code Review](/ai/dev/coding/ai-code-review)。

## 迭代方式（像调代码一样调 Prompt）

```text
跑一次
 ↓
看输出哪里不稳 / 跑偏
 ↓
只改一处：补约束 或 收紧输出格式 或 补上下文
 ↓
再跑，对比差异
```

不要一次改五处。和改代码一样：单变量调试，才知道哪句 Prompt 生效。

---

## 使用后的人工检查

拿到输出后，人至少看：

* 有没有编造材料里不存在的事实
* 有没有超出任务范围（顺手重构、扩需求）
* 格式是否可直接复用；若不能，把格式约束再写死一轮
* 不确定项是否已标出，还是被写成了肯定结论

## 我的判断

Prompt「像工程」，靠的不是技巧清单，而是：

> **最小结构固定 + 约束清晰 + 输出可验收 + 能沉淀成模板。**

日常记住四块：**角色 · 任务 · 约束 · 输出格式**；缺上下文就补材料，要风格稳定再加示例。够用了再谈高级技巧。
