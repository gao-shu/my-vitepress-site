# AI Coding 工作流

> 我如何把 AI 纳入真实的软件开发闭环。不是 Cursor 按钮说明书。

核心原则：

> **AI 可以提高代码生产速度，但不能替代开发者对需求、架构、质量和最终结果负责。**

完整闭环：

```text
1. 明确需求
2. 拆解任务
3. 准备上下文
4. 与 AI 协作实现
5. 人工架构判断
6. Code Review
7. 测试
8. Debug
9. 重构
10. 交付与复盘
```

---

## 1. 明确需求

动手前先写清三件事：

* **要解决什么问题**（用户/业务结果）
* **验收标准是什么**（怎样算做完）
* **边界在哪里**（不改什么、不做什么）

AI 最容易「自作主张扩 scope」。需求与边界不清时，生成再快也是在制造返工。

人负责：需求理解与验收定义。  
AI 不负责：替你决定「业务上该不该做」。

---

## 2. 拆解任务

把大需求拆成可验证的小步骤，例如：

```text
读懂现有调用链
 → 改一个接口 / 一张表 / 一个前端页
 → 补测试或手工验收路径
 → 再处理下一刀
```

原则：

* 一次只推进一类改动
* 每步有可观察的结果（编译过、用例过、页面能点）
* 先最小闭环，再谈优化与重构

拆解是工程能力，不是 Prompt 技巧。拆得清楚，AI 才稳。

---

## 3. 准备上下文

AI 只看得到你给它的材料。优先准备：

* 相关代码与调用链（不要只丢孤立片段）
* Git Diff / 当前改动范围
* 接口定义、表结构、错误日志（若涉及）
* 业务规则与约束（「不能改公共 API」「必须兼容旧数据」）
* 已有测试或验收步骤

上下文越具体，输出越像「在这个项目里写代码」，而不是「通用示例」。

通用 Prompt 结构见 [Prompt 怎么写才像工程](/ai/dev/basics/prompt-engineering)。

---

## 4. 与 AI 协作实现

推荐节奏：

```text
先让 AI 分析 / 给方案
 → 人确认方案与边界
 → 再让 AI 按确认项改代码
 → 人看 Diff，跑起来验证
```

尽量避免：

```text
一句话「帮我实现某某」
 → AI 直接大改几十个文件
 → 引入无关重构与新问题
```

人负责：范围、风格、是否允许重构。  
AI 负责：在约束内提高实现速度。

---

## 5. 人工架构判断

AI 生成之后，先问自己，而不是先问「还能不能再生成一点」：

* 模块边界是否被破坏？
* 是否引入不必要的抽象或依赖？
* 是否符合现有分层（Controller / Service / 仓储等）？
* 扩展点是否合理，还是在堆特例？
* 有没有为了「看起来高级」而过度设计？

这一步**不能外包给模型**。架构取舍依赖项目上下文与长期维护成本，属于开发者职责。

---

## 6. Code Review

AI 适合做第一轮广泛扫描；人做最终判断。

重点看：

* 本次修改是否引入缺陷
* 边界条件、空值、异常路径
* 权限、数据一致性、并发（若相关）
* 是否误报、是否漏报

工作方式与可复制 Prompt 见 [用 AI 做 Code Review](/ai/dev/coding/ai-code-review)。

记住：

> AI 发现的问题不一定是真的；AI 没发现也不代表没有问题。

---

## 7. 测试

能自动化的尽量自动化；没有现成测试时，至少固定一条人工验收路径。

优先验证：

* 主路径是否按验收标准通过
* 关键边界与失败路径
* 回归：改动是否影响相邻功能

AI 可以帮写测试草稿，但：

* 测什么、覆盖哪条业务规则 → 人定  
* 测试是否真能抓住风险 → 人判  

「测试绿了」不等于「业务对了」，尤其在 AI 大量生成代码时。

---

## 8. Debug

出问题时，仍按工程方式定位：

```text
复现
 → 缩小范围
 → 看日志 / Diff / 调用链
 → 形成假设
 → 最小验证
 → 再改
```

可以让 AI 辅助读栈、猜可疑点，但不要跳过复现与缩小范围。  
「再让 AI 整段重写」往往比「定点修」引入更多未知。

（`fix-one-bug` 等专项页有材料后再挂进来；本页先把 Debug 放进闭环。）

---

## 9. 重构

重构单独成步，不要和功能交付缠在一起。

* 功能未验收前：禁止顺手大重构  
* 验收后：只改结构、行为不变，并有测试或验收托底  
* 每次重构目标单一（命名、抽取、去重……）

AI 很擅长「看起来更优雅」的重写；人要负责判断值不值、风险大不大。

---

## 10. 交付与复盘

交付前至少确认：

* Diff 范围符合预期，无无关文件  
* 验收标准已勾完  
* 必要说明（PR / 变更说明）写清「改了什么、为什么、怎么验」

复盘只记对下次有用的：

* 哪类上下文一给就稳  
* 哪类任务不适合一次性丢给 AI  
* 哪次误报 / 漏报值得写进 Review 习惯  

复盘是把「用过 AI」变成「可重复的工程方法」。

---

## 人机分工（面试可直接说）

| 环节 | 更偏谁 |
| --- | --- |
| 需求与验收 | 人 |
| 任务拆解 | 人（可让 AI 帮忙列草案） |
| 上下文准备 | 人为主 |
| 代码实现草稿 | AI + 人约束 |
| 架构判断 | 人 |
| Code Review | AI 初扫 + 人终审 |
| 测试策略 | 人；用例草稿可 AI |
| Debug 结论 | 人 |
| 是否重构、重构范围 | 人 |
| 最终交付责任 | 人 |

---

## 和「会用 Cursor」的差别

| 会用工具 | AI Coding 工作流 |
| --- | --- |
| 会提问、会补全 | 有固定闭环与验收 |
| 生成得多 | 改得准、回得了滚 |
| 依赖某一款 IDE | 方法可迁移到别的工具 |
| 出问题再问 AI | 先复现、再定点、再让 AI 辅助 |

## 我的判断

工作流的价值不在步骤名称，而在强制一件事：

> **每一步都知道谁拍板、用什么验收、AI 准许动到哪里。**

做到这一点，AI 才是工程放大器；做不到，只是更快地制造技术债。
