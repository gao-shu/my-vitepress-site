# AI 辅助编程工作流

> 用 AI 写代码、改 bug、读旧项目的一套稳定流程：Spec 先行 → 交代清楚 → 管住上下文 → 人审 AI 写 → 跑过才算完。
> 另加一节「单人开发没有 review 兜底怎么办」——这是团队文章里通常不讲、但独立开发者天天遇到的问题。

## 场景与问题

用 Cursor 或 Claude Code 一段时间后，会遇到两种典型失败。一种是“改着改着崩了”：AI 一口气改了八个文件，跑不起来，你对着 diff 根本不知道它改了什么，只能回滚重来。另一种是“越聊越乱”：对话拖了两百轮，早期定下的约束早被冲掉，AI 开始翻出三轮之前的错误方案接着改。

这两种失败的根源一样：把 AI 当成替你写代码的人，而不是和你结对的助手。10 年开发经验里，我见过类似的问题——不是不会写，是没人告诉他边界在哪。对 AI 也一样，边界得由你来定。AI 的速度是你的十倍，但它的“责任心”是零，缺的那一半永远在你这边。

单人开发时这个问题更尖锐：没有同事帮你兜底，一次跑偏的改动没人拦，返工时间全算在你自己头上。所以下面这套流程的重点不是“怎么让它写得更多”，而是“怎么让返工更少”。

## 做法

### 1. Spec 先行，先写清楚再动手

动手前先让 AI 帮你把需求和方案整理成一份简短的 spec：要改什么、不改什么、接口长什么样、边界条件是什么。这份 spec 不用正式，几十行 markdown 就行，关键是它同时约束了你和 AI。

spec 没对齐之前，不让 AI 碰代码。具体做法：

- 先对话聊清楚：把背景、目标、约束丢给它，让它复述理解、提出它认为模糊的点。
- 让它把讨论结论整理成 spec 文档，你逐条修订，删掉它脑补的部分。
- spec 确认后，实现阶段每一轮都以 spec 为依据：“按 spec 第 3 条，这里应该……”

这本质上是把“先设计后编码”的老规矩搬过来，只是现在设计文档还要给另一个读者——模型——看。写 spec 的过程你自己也会想清楚很多事，这部分收益和 AI 无关，纯赚。

### 2. 交代任务的四段式：背景、目标、约束、输出

spec 管“做什么”，四段式管“怎么说”。同一件事，两种说法的结果差一个量级：

> 差：“这个接口好慢，帮我优化。”
>
> 好：“背景：Spring Boot 2.7 项目，/api/orders 在订单量 10 万时响应 3 秒（正常应 <300ms），慢日志指向一条全表扫描的 SQL。目标：压到 300ms 以内。约束：不加新依赖，不改出入参，分页保留。输出：先给方案和理由，我确认后你再改代码。”

四个要素各自管一件事：

- **背景**：技术栈、版本、上下文。它不知道你在 JDK 17 + MyBatis-Plus 里，就会给你一段 Hibernate 的写法。
- **目标**：一句话说清要什么，不要“帮我优化一下”这种模糊表述。
- **约束**：不能做什么。不能引依赖、不能改接口签名、不能动某个包——这些不说，它一定会好心办坏事。
- **输出格式**：要代码、要方案、要表格，要不要给理由，要不要分步。

再加两个几乎零成本的钩子：

- 开头：“先复述你对这个任务的理解，确认无误再开始。”——拦“开工前跑偏”。
- 结尾：“对照上面每一条约束检查你的回答，列出哪些满足、哪些没满足。”——拦“干完漏项”。

原理就是需求评审那一套：先对齐，再干活；干完再验收。约束越多，这两个动作越值钱。

### 3. 管理上下文，别让对话无限膨胀

- **一轮解决一件事**。一个问题解决后开新对话，别把上一个问题的残留带着走。
- **关键约定每轮重申**：技术栈、风格、禁改区域在新对话开头重新声明一次，不要假设 AI 记得。上下文窗口再大，关键信息也会被稀释。
- **识别失忆信号**：AI 开始重复问你已经说过的事、翻出旧方案接着改、忘记前面定下的约束，就是对话该重开的时候了。重开时把当前进度写成几句话带过去，比在旧对话里“唤醒”它高效得多。
- **用规则文件沉淀**：Cursor 的 `.cursorrules` / rules、Claude Code 的 `CLAUDE.md`，把项目级约定写进去，每个新会话自动带上，不用每次手动贴。

### 4. 分工明确：人审 AI 写

- **你负责**：定义问题、审方案、把关边界条件、跑测试、决定合不合。
- **AI 负责**：写样板代码、翻译、按 spec 实现明确的函数、补测试用例、解释代码。

配套的两条纪律：

- **小步改动**：一次一个函数或一个文件级别的改动，改完看 diff，看懂了再继续。看不懂的 diff 不要往下走——回滚的成本远低于 debug 一个你不理解的改动。
- **方案先过脑再实施**：AI 给的实现方案，先审“为什么这么改”，再看“改了什么”。听上去越顺的地方越要警惕，因为它最容易在顺畅的叙述里塞进想当然的假设。

### 5. 验证闭环不能省

改完就跑：编译、测试、复现原问题。AI 写的代码“看起来对”和“确实对”之间隔着一次真实运行。让它顺手补测试，或者自己补关键路径的测试，否则下次改动没人兜底。

一个实用的收尾动作：把 diff 和 spec 一起丢给另一个对话（或让它自查），“对照 spec 检查这个改动，哪些要求满足了、哪些没有”，相当于让另一个视角做 code review。

### 6. 两个日常高频场景

- **读陌生代码 / 接手旧项目**：别上来就让它改。先问“这个模块的入口在哪、核心数据流怎么走、有哪些隐含约定”，让它画出结构，你确认理解后再进入修改。先读懂再动手，对人对 AI 都是铁律。
- **修 bug**：给它完整报错栈 + 复现步骤 + 你已经排查过什么，让它先给根因假设再动手。“看起来像空指针，其实根因在上游数据”这类误判很常见，让它先列假设、说明依据，你用证据排除后再改。

## 单人开发：没有 review 兜底怎么办

团队里 AI 产出的代码至少有第二个人看一眼；独立开发、远程单干时没有这层，只能自己造一套替代品。三个动作最有效。

### 1. 把 review 变成流程

- **换视角审**：把 diff 和 spec 单独丢给一个新会话（最好换个模型），只给改动，不给你的推理过程。你先解释一遍“我为什么这么写”，它就容易顺着你点头。
- **固定自查清单**：每次提交前过一遍，八条够用——边界条件、空值 / 超时 / 重试、异常是否被吞、日志是否泄露敏感信息、并发与幂等、权限校验、SQL 是否 N+1、配置是否硬编码。
- **测试当门票**：没有测试覆盖的改动，先补测试再往下走。写不出测试，往往说明这块逻辑你自己也没想清楚。
- **错时审**：当天写的 diff 当天审容易自我确认，放一晚上，第二天第一件事看 diff，问题会自己跳出来。

### 2. 上下文切换是单人最贵的税

- **一个需求一个会话**，任务之间留三行交接笔记（做到哪、下一步、卡在哪），比在长对话里翻线索快得多。
- **长任务丢后台跑**：让它跑构建、跑测试的时候，你去写 spec 或看另一块代码，别盯着屏幕等。
- **并行用隔离目录**：`git worktree` 开一个独立目录让 AI 在里面折腾，主干继续可用，跑偏了直接删目录。
- **规则文件当团队约定**：目录结构、命名、禁改区域、构建与测试命令写进 `CLAUDE.md` / `.cursorrules`，等于把你脑子里的规范外化成每次会话都生效的“同事说明”。

### 3. 成本按任务分级

- **分级用模型**：样板代码、重命名、补注释、写测试骨架用便宜快的模型；架构讨论、疑难 bug、性能分析才上强模型。
- **按文件给上下文，别按仓库**：塞整个仓库既慢又贵，还更容易被无关代码带偏。
- **长会话是双输**：轮次一多，成本上升、质量下降，重开新会话往往比继续追问更便宜。

## 什么时候不用 AI

不是所有环节都该用：

- **核心算法和架构设计**：想清楚是你的活，AI 给的通用解法往往是平庸的平均值。
- **安全敏感代码**（鉴权、加密、支付）：AI 的产出必须逐行审，甚至宁可自己写。
- **一行就能改完的小改动**：打开 IDE 的时间比描述给 AI 还短。

认清“用它反而更慢”的场景，和认清“用它飞快”的场景同样重要。

## 关键要点

- Spec 先行：先对齐“改什么、不改什么”，再让 AI 写代码；spec 模糊的点让它自己提出来。
- 交代任务用四段式：背景、目标、约束、输出格式；开头让它复述，结尾让它自检。
- 小步提交，一次一个改动单位，看不懂的 diff 不继续。
- 对话有寿命，一个任务一个对话，关键约定每轮重申，项目约定沉淀到规则文件。
- 分工固定：AI 写，人审；方案、边界、合并决定权在人。
- 验证闭环：编译、测试、复现问题，跑过才算完；收尾用 spec 对照自查一遍。
- 单人开发要自建 review：换模型审 diff、八条自查清单、测试当门票、错时再审。

## 小结

AI 辅助编程的效率不是来自“它写得快”，而是来自“返工少”。Spec 先行管住方向，四段式管住输入质量，小步改动和人审管住质量，上下文管理管住连贯性，验证闭环管住底线。这套工作流和带新人、做 code review 是同一套管理逻辑——你不是在写代码，你是在管理一个速度快但没有责任心的执行者，责任心那一半得你自己补上；单人开发时，连“第二个人”也得你自己补。
