# AI 编程效率 SOP

> 一套可以直接用于 Cursor、WorkBuddy 等 AI 编程工具的实战操作手册。目标是减少重复沟通、开发弯路、无效修改和返工，让 AI 尽可能自主完成从任务理解到测试交付的全过程。

## 这套手册解决什么问题？

日常使用 AI 编程时，最浪费时间的往往不是写代码，而是：

- 反复解释项目背景和业务需求。
- AI 没理解项目就开始修改代码。
- 方案没有确定，写到一半才发现方向错误。
- 每完成一小步都要人工提醒下一步。
- AI 修改代码后没有主动编译和测试。
- 一个错误反复修复，甚至引入新的问题。
- 每个新项目都要重新告诉 AI 一遍开发规范。

这套 SOP 就是为了解决这些问题。

## 一、日常开发主流程

```text
接到开发任务
    ↓
判断任务类型与风险
    ↓
准备必要的项目上下文
    ↓
明确需求与验收标准
    ↓
分析影响范围
    ↓
制定技术方案和实施计划
    ↓
确认执行边界
    ↓
AI 连续执行开发
    ↓
编译、测试、问题修复
    ↓
代码审查与结果验收
    ↓
交付与经验沉淀
```

不是每个小任务都需要完整走一遍。

例如：

- 修改一个简单文案：直接定位、修改、检查即可。
- 修复一个明确的小 Bug：复现问题、定位原因、修改、回归测试。
- 增加一个业务模块：完整走需求分析、方案设计、开发和测试流程。
- 接手一个陌生老项目：先完成项目接入，再开始业务开发。

## 二、根据开发场景选择入口

| 当前场景 | 优先使用 |
| -------- | -------- |
| 全新项目，准备开始开发 | 01 项目初始化与 AI 接入 |
| 接手一个陌生项目 | 01 项目初始化与 AI 接入 |
| AI 总是理解错需求 | 02 开发任务输入规范 |
| AI 找不到正确的代码位置 | 03 项目分析与上下文准备 |
| AI 直接编码，导致方向错误 | 04 技术方案与任务拆解 |
| 想建立可复用的 AI 编程配置 | 05 Rules、Agent、Skills 实战配置 |
| 希望 AI 一次连续完成多个开发步骤 | 06 AI 连续开发与任务执行 |
| AI 修改后频繁报错、返工 | 07 报错排查、测试与自动修复 |
| 任务完成后需要检查和复用经验 | 08 交付验收与经验复用 |

## 三、不同任务采用不同执行强度

不要为了流程完整而增加不必要的操作。

| 任务类型 | 推荐执行方式 |
| -------- | ------------ |
| 简单修改 | 定位 → 修改 → 检查 |
| 小型 Bug | 复现 → 定位 → 修复 → 回归 |
| 普通功能 | 需求 → 分析 → 计划 → 开发 → 测试 |
| 复杂功能 | 需求分析 → 方案设计 → 分阶段开发 → 阶段验证 |
| 大型项目 | 项目接入 → 建立上下文 → 协作配置 → 任务执行 |
| 高风险改动 | 影响分析 → 备份或隔离 → 方案确认 → 实施 → 专项验证 |

判断标准：

1. 修改范围越大，前期分析越充分。
2. 影响数据、权限、资金、库存等核心业务时，提高验证强度。
3. 项目越陌生，越应该先理解现状。
4. 越简单的任务，越不应该引入复杂流程。

## 四、八个实战章节

### 01 项目初始化与 AI 接入

解决新项目和老项目如何快速建立 AI 开发环境的问题。

包括：

- 新项目初始化。
- 老项目接管。
- 项目基础信息收集。
- 项目规则文件准备。
- AI 接入验收。

进入第 01 章

### 02 开发任务输入规范

解决需求反复解释、AI 理解偏差的问题。

包括：

- 任务描述模板。
- 背景、目标、约束、验收标准。
- 新功能、Bug、重构等不同任务的输入方式。
- 需求澄清与提问规则。

### 03 项目分析与上下文准备

解决 AI 不知道该看哪些文件、不了解业务调用链的问题。

包括：

- 如何定位相关代码。
- 如何分析模块依赖。
- 如何识别接口、数据库和业务影响。
- 如何避免无效的全仓扫描。
- 如何向 AI 提供足够但不过量的上下文。

### 04 技术方案与任务拆解

解决 AI 没有方案就开始写代码的问题。

包括：

- 修改前影响分析。
- 技术方案比较。
- 实施步骤拆分。
- 任务依赖关系。
- 每个步骤的完成标准。

### 05 Rules、Agent、Skills 实战配置

解决 AI 开发规范无法复用、重复指挥的问题。

包括：

- Rules 配置。
- Agent 分工。
- Skills 封装。
- MCP 与 Hooks 的使用边界。
- Cursor、WorkBuddy 等工具适配。

### 06 AI 连续开发与任务执行

解决 AI 每完成一步都等待人工指令的问题。

包括：

- 连续任务执行。
- 阶段性检查点。
- 串行与并行执行。
- 修改范围控制。
- 长任务进度记录。
- 异常时暂停与恢复。

### 07 报错排查、测试与自动修复

解决 AI 修改代码后没有验证、错误反复出现的问题。

包括：

- 编译和测试。
- 错误定位。
- 根因分析。
- 自动修复循环。
- 回归验证。
- 防止无限修改。

### 08 交付验收与经验复用

解决 AI 只汇报代码写完，却无法证明任务真正完成的问题。

包括：

- 需求逐项验收。
- Git Diff 检查。
- 测试证据。
- 文档同步。
- 交付报告。
- Rules 和 Skills 经验沉淀。

## 五、使用原则

### 原则 1：先理解，再修改

AI 必须先了解与任务相关的现有代码和业务逻辑，不能只根据用户的一句话猜测项目结构。

### 原则 2：简单任务简单处理

不要为了完成一个小修改，先建立复杂的 Agent 团队或生成大量项目文档。

### 原则 3：能自主完成的事情不要交给用户

AI 应主动检查代码、执行命令、运行测试、分析报错。

只有权限不足、信息缺失、操作风险或关键决策需要人工确认时，才向用户求助。

### 原则 4：重要操作必须有证据

不能仅凭 AI 自己说完成了，就认为任务完成。

应该提供实际修改内容、命令执行结果、测试结果和未解决问题。

### 原则 5：有效经验才沉淀

一次性问题不一定需要增加 Rules 或 Skills。

只有具有重复价值的经验，才应该固化为可复用资产。

## 六、最终希望形成的工作方式

以后面对一个开发任务：

1. 我只需要把任务交代清楚。
2. AI 自己理解项目和需求。
3. AI 主动分析影响范围和实施方案。
4. AI 按计划连续完成开发。
5. AI 自己编译、测试、定位和修复问题。
6. AI 给出真实的完成情况和验收证据。
7. 有价值的经验自动进入后续优化流程。

这就是这套 SOP 的最终目标。
