# 01 项目初始化与 AI 接入

> 新项目开始前，让 AI 建立正确的项目开发环境；接手老项目时，让 AI 先理解现状再动手。目标是避免每次开发都重新解释项目，减少盲目扫描和错误修改。

## 一、先判断当前属于哪种情况

| 场景 | 操作方式 |
| ---- | -------- |
| 全新项目，代码还没开始写 | 新项目初始化 |
| 已有脚手架，但尚未正式开发 | 检查现有结构，补充项目约定 |
| 接手别人开发的项目 | 老项目接管 |
| 已经开发了一段时间，但 AI 经常理解错误 | 补充项目上下文与规则 |
| 小型一次性项目 | 只做最小必要准备，不建立完整体系 |

不要每个项目都创建一套庞大的文档。

项目初始化的核心任务只有三个：

1. 让 AI 知道项目是什么。
2. 让 AI 知道如何正确开发和验证。
3. 让 AI 知道哪些事情不能擅自做。

## 二、新项目初始化

### 2.1 执行步骤

| 步骤 | AI 要做什么 | 产出 |
| ---- | ------------ | ---- |
| 1 | 明确项目目标、用户和核心功能 | 项目目标 |
| 2 | 确认技术栈与运行环境 | 技术约定 |
| 3 | 检查或建立项目目录结构 | 项目骨架 |
| 4 | 确定开发、构建和测试命令 | 命令清单 |
| 5 | 确定代码规范和修改边界 | 项目规则 |
| 6 | 检查开发环境是否可用 | 环境检查结果 |
| 7 | 整理必要的项目上下文 | 项目说明 |

### 2.2 新项目初始化提示词

适用于 Cursor、WorkBuddy 等 AI 编程工具。

```text
现在准备开始一个新项目。

你的任务是协助我完成项目初始化，但暂时不要直接大规模编写业务代码。

第一步：明确项目目标
请先了解：
1. 项目要解决什么问题？
2. 主要用户是谁？
3. 核心业务功能有哪些？
4. 当前已经确定的技术选型是什么？
5. 有哪些明确的开发约束？

如果现有信息足够，不要重复询问。
如果存在关键缺失，一次性列出需要我确认的问题。

第二步：检查现有环境
检查当前工作目录：
- 是否已经存在项目文件？
- 是否已经有技术脚手架？
- 是否存在 Git 仓库？
- 是否已有项目规则文件？
- 是否已经安装必要依赖？

不要覆盖或删除已有内容。

第三步：提出初始化方案
给出：
1. 推荐目录结构。
2. 技术栈与依赖建议。
3. 开发、构建、测试命令。
4. 必要的项目规则。
5. 当前阶段需要创建的文件。

第四步：控制初始化范围
只创建当前阶段真正需要的内容。
不要预建大量空文档。
不要为了使用 Agent、Skills 或 MCP 而强行增加配置。

第五步：执行环境检查
在获得必要授权后，执行初始化和环境检查。

最终向我报告：
- 已完成的初始化内容。
- 项目目录结构。
- 技术栈。
- 开发和测试命令。
- 尚未解决的问题。
- 下一步建议。

特别要求：
不要把尚未确认的技术选型写成既定事实。
不要在没有确认的情况下执行高风险操作。
```

### 2.3 新项目初始化完成标准

- 项目目标已经明确。
- 技术栈已经确认。
- 项目目录结构合理。
- 开发环境可以正常运行。
- 开发和构建命令已验证。
- 测试方式已明确。
- 必要的项目规则已建立。
- 没有创建无意义的空文档或复杂配置。

满足当前阶段所需的项目条件即可开始业务开发，不必追求所有事项一次性完美。

## 三、老项目接管

老项目和新项目最大的区别是：

**新项目可以设计结构，老项目必须尊重现状。**

AI 不能因为认为某种架构更先进，就随意重构已有系统。

### 3.1 老项目接管步骤

| 步骤 | 检查内容 | 产出 |
| ---- | -------- | ---- |
| 1 | 项目目录与模块划分 | 项目结构 |
| 2 | 技术栈、依赖和版本 | 技术环境 |
| 3 | 启动、构建和测试方式 | 命令清单 |
| 4 | 核心业务模块与调用关系 | 业务地图 |
| 5 | 数据库、接口和外部依赖 | 关键依赖清单 |
| 6 | 代码规范和已有规则 | 开发约定 |
| 7 | 当前已知问题和风险 | 风险清单 |
| 8 | 与当前任务相关的代码位置 | 任务上下文 |
| 9 | 汇总并检查认知准确性 | 项目接入报告 |

不要求一次性理解整个系统。

先掌握项目整体结构，再围绕实际开发任务深入对应模块。

### 3.2 老项目接管提示词

```text
你现在需要接管一个已经存在的软件项目。

本轮任务是：理解项目现状，建立后续开发所需的上下文。

暂时不要修改业务代码，不要进行重构，不要安装新依赖。

请按以下顺序检查：

一、项目基本情况
- 项目技术栈及版本。
- 前后端架构。
- 模块划分。
- 目录结构。
- 主要依赖。

二、运行与开发方式
- 如何启动项目？
- 如何构建项目？
- 如何执行测试？
- 是否存在数据库及相关配置？
- 是否存在 Docker 或其他运行环境？

三、业务结构
- 核心业务模块有哪些？
- 模块之间如何调用？
- 关键接口在哪里？
- 重要数据实体有哪些？
- 是否存在第三方系统集成？

四、开发规范
- 是否存在 AGENTS.md、CLAUDE.md、.cursor/rules 等规则文件？
- 是否存在项目自己的代码规范？
- 是否有特殊的命名、目录或架构约束？

五、风险与注意事项
- 哪些模块不应该随意修改？
- 哪些操作可能影响生产数据？
- 是否存在已知问题？
- 哪些信息无法从代码中确认？

六、输出项目接入报告

请使用以下格式：

1. 项目基本信息
2. 技术栈与版本
3. 目录与模块结构
4. 项目启动、构建和测试方式
5. 核心业务模块
6. 重要接口与数据实体
7. 开发规范
8. 外部依赖
9. 已知风险与注意事项
10. 尚未确认的信息

每项信息标记为：
- 已确认：有代码、配置或文档证据。
- 待确认：目前无法从现有资料确定。
- 人工补充：需要项目维护人员提供。

执行约束：

1. 本轮只读分析，不修改任何文件。
2. 不扫描无关目录和大型依赖目录。
3. 优先检查项目入口、配置、README、模块结构和关键业务代码。
4. 不要把猜测当成事实。
5. 不要为了生成报告而重复读取大量相同内容。
6. 如果项目规模较大，先输出整体地图，再针对重要模块深入。
7. 不需要一次性理解整个项目的所有业务细节。

最后告诉我：
- 当前是否已经具备开发条件？
- 如果开始一个新功能，还缺少哪些必要信息？
- 哪些内容建议写入项目规则文件？
- 哪些内容应该等具体开发任务出现时再分析？
```

### 3.3 老项目接管硬性约束

以下规则默认适用于老项目：

1. 不擅自重构原有架构。
2. 不随意修改已有接口签名。
3. 不随意升级依赖和框架版本。
4. 不批量格式化无关文件。
5. 不把推测出来的业务规则当作真实业务规则。
6. 不擅自删除已有功能。
7. 不修改生产数据或执行不可逆操作。

如果某项开发确实需要突破上述限制，必须先说明原因、影响范围和替代方案，并取得必要授权。

### 3.4 老项目接管完成标准

- 已确认项目技术栈及主要版本。
- 已找到项目启动和构建方式。
- 已了解主要模块结构。
- 已找到当前任务相关的核心代码。
- 已了解必要的数据库和接口关系。
- 已识别已有项目规则。
- 已标记未知信息和潜在风险。
- 没有擅自修改业务代码。
- 没有将未经验证的猜测作为事实。

## 四、项目规则文件应该保存什么？

项目规则文件的作用不是保存整个项目的所有知识，而是让 AI 每次开发都遵守稳定的约束。

建议优先保存以下内容：

| 内容 | 是否建议写入 |
| ---- | ------------ |
| 技术栈和重要版本 | 是 |
| 项目目录约定 | 是 |
| 代码命名和开发规范 | 是 |
| 启动、构建、测试命令 | 是 |
| 禁止擅自修改的模块 | 是 |
| 数据库和接口的重要约束 | 视项目情况 |
| 某次 Bug 的具体排查过程 | 通常不需要 |
| 某次临时需求的业务细节 | 通常不需要 |
| 整个项目的所有代码解释 | 不需要 |

不要把所有项目知识都塞进一个规则文件。

稳定且每次开发都需要遵守的内容进入规则；具体任务信息随任务提供；专业流程进入 Skill。

具体配置方式将在第 05 章介绍。

## 五、推荐的最小项目资料

项目规模较大、需要长期使用 AI 开发时，可以逐步建立：

```text
项目根目录/
├── README.md
├── AGENTS.md                 # 项目级 AI 开发约定（按需）
├── docs/
│   └── development/
│       ├── project-overview.md
│       ├── architecture.md
│       └── known-issues.md
└── .cursor/
    └── rules/                # Cursor 专属规则（按需）
```

注意：

- 不要求所有项目都采用这个目录。
- 不要重复维护相同内容。
- 已有文档能承担职责时，优先复用。
- 不要为了目录看起来完整而创建空文件。
- 不同 AI 工具的配置格式不同，应按工具适配。

## 六、什么时候可以开始开发？

完成项目初始化或接管后，检查以下条件：

1. 知道项目是什么。
2. 知道项目如何运行。
3. 知道如何编译和测试。
4. 知道开发时需要遵守哪些规则。
5. 当前任务相关的信息能够继续获取。
6. 未确认的信息已经明确标注。

**不需要等整个项目完全理解后才开始开发。**

对于新功能，只需要在开始该任务前补充对应业务上下文即可。

## 七、常见错误

### 错误 1：让 AI 一次性扫描整个仓库

问题：耗费大量上下文，产生很多无关信息，反而不利于当前任务。

正确做法：先了解项目入口和模块地图，再根据任务定位具体代码。

### 错误 2：初始化阶段创建大量文档

问题：生成很多没有真实内容、后续也没人维护的文件。

正确做法：先确定哪些信息会被重复使用，再决定是否沉淀。

### 错误 3：AI 没有理解业务就开始开发

问题：技术实现可能正确，但不符合真实业务规则。

正确做法：将未知业务规则标记为待确认，不能自行编造。

### 错误 4：接手老项目时顺手重构

问题：原本只是增加一个功能，却引入大量无关变更和新风险。

正确做法：严格限制修改范围，先完成当前任务，再讨论独立重构。

## 八、本章最终检查

完成本章后，你应该拥有：

- 一个可运行、开发命令明确的新项目，或者一份可靠的老项目接入报告。
- 一套必要的项目级开发约定。
- 一份清楚的项目技术和业务上下文。
- 一份已知风险和待确认信息清单。
