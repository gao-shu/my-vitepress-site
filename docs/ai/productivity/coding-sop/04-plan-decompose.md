# 技术方案与任务拆解

> 上一章解决了「AI 该看哪里」，本章解决「看完之后怎么动手」。核心要求：先出方案再改代码，先把任务拆成可独立验收的步骤，再让 AI 一步一步执行——避免一句需求直接触发十几个文件的大改。

## 一、什么时候使用

以下情况必须先出方案、再拆解任务：

- 涉及三个以上文件的改动。
- 新增表、改字段、加索引，或有数据迁移。
- 新增或改动对外接口，涉及前后端契约。
- 涉及权限、资金、库存、订单状态等核心业务规则。
- 有多个可行实现，选错的代价高。
- 需求本身存在模糊点，不同理解会导致不同结果。
- 跨系统集成，涉及消息、超时、重试、幂等。

以下情况可以直接做：

- 单文件内、边界明确的小改动。
- 只改文案、样式、常量值。
- 已经有一份冻结的 Spec，且拆好的任务还没执行完。

**判断标准：如果改错了需要回滚多个文件，就先做方案。**

## 二、方案形成前的三件事

不要一上来就问 AI「这个需求怎么实现」。先做三件事，否则得到的方案是凭空设计的。

### 2.1 复述与澄清

让 AI 用自己的话复述需求，并列出仍模糊的点。重点澄清三类问题：

| 类型 | 例子 | 谁来定 |
| ---- | ---- | ------ |
| 业务规则 | 「不允许关闭」是指全部订单还是部分状态？ | 人 |
| 边界条件 | 批量关闭时部分失败，是全部回滚还是部分成功？ | 人 |
| 技术取舍 | 复用现有流程还是新建一条专用流程？ | AI 出选项，人拍板 |

### 2.2 把「不做」写进方案

方案里必须有一段「本次不做」。这一段是防止 AI 顺手扩大范围的闸门。

典型的不做项：不改现有接口签名、不动历史数据、不做架构升级、不顺手格式化无关文件、不引入新依赖。

### 2.3 明确方案的读者

方案同时给三个读者看：

- **人**——判断方向对不对、风险能不能接受。
- **AI**——按它实现，不靠对话里的口头约定。
- **验收者**——对照它判断「做完了没有」。

写进文件的方案才生效，只在对话里说过的方案不算。

## 三、方案设计的五个维度

方案不是一句「在 Service 里加个方法」。合格的方案要回答五个维度。

### 3.1 数据

- 用现有表还是新表？字段够不够？
- 是否需要索引？新查询条件命中哪个索引？
- 有没有唯一约束会被新逻辑破坏？
- 需不需要迁移历史数据？迁移脚本能不能重复执行？
- 事务边界在哪？失败时怎么回滚？

### 3.2 接口

- 路径、方法、入参、出参、错误码。
- 与现有接口命名和返回风格是否一致。
- 是否破坏兼容性——已上线的调用方能不能继续工作。
- 前端 API 定义要不要同步改。

### 3.3 模块与分层

- 代码落在哪个模块、哪个包。
- 是否跨模块依赖，依赖方向对不对。
- Controller 是否只做转发，业务逻辑放哪一层。
- 公共逻辑放 common 模块会不会污染其他模块。

### 3.4 兼容与影响

- 现有功能会不会被影响。
- 老数据能不能正常处理。
- 配置开关要不要加，默认开还是关。
- 定时任务、消息消费、报表统计是否也读这份数据。

### 3.5 验证方式

- 怎么证明做对了——哪些测试、哪些命令、哪些人工核对。
- 哪些场景必须覆盖（正常 / 边界 / 异常 / 并发）。
- 哪些场景本次不验证，原因是什么。

## 四、方案比较

**凡是「有多种做法」的地方，都不要只给一个方案。** 让 AI 列出两到三个选项并说明代价。

### 4.1 比较表模板

```text
| 维度 | 方案 A：<名称> | 方案 B：<名称> | 方案 C：<名称> |
| ---- | ------------- | ------------- | ------------- |
| 改动范围 | 涉及几个文件/模块 | | |
| 数据影响 | 是否改表/迁移 | | |
| 兼容性 | 对现有接口和调用方 | | |
| 性能 | 查询次数、数据量影响 | | |
| 可维护性 | 复用现有能力还是新增抽象 | | |
| 回滚成本 | 出问题后怎么退 | | |
| 验证难度 | 能不能写出测试 | | |
| 推荐结论 | 选哪个，为什么 | | |
```

### 4.2 取舍优先级

当选项各有优劣时，按这个顺序判断：

1. **业务正确性**——不满足业务规则的方案直接淘汰，不管代码多优雅。
2. **兼容性**——能不改现有接口就不改。
3. **改动范围**——能在本模块内解决，就不动公共模块。
4. **复用**——已有服务能用的不重新造。
5. **可验证性**——写不出测试的方案，风险要单独说明。
6. **代码美观**——排最后。为了「看起来更漂亮」扩大改动范围，是最常见的返工来源。

## 五、风险识别

方案里要有独立的风险清单，不许把风险藏在执行步骤里。

| 风险类别 | 典型信号 | 处理方式 |
| -------- | -------- | -------- |
| 业务规则冲突 | 需求与现有代码行为不一致 | 停手，交人确认，不自行选择 |
| 数据一致性 | 涉及状态流转、批量更新、并发扣减 | 明确事务边界和幂等方案 |
| 兼容性 | 改接口签名、改返回结构、删字段 | 列出现有调用方，逐个确认 |
| 不可逆 | 数据迁移、删除、覆盖生产配置 | 必须人工确认，先备份 |
| 性能 | 新增 N+1 查询、全表扫描、大批量同步 | 给出索引方案和数据量前提 |
| 安全 | 权限、鉴权、参数校验、敏感字段 | 纳入验收，必要时人工审 |
| 验证受限 | 没测试库、依赖外部服务、缺数据 | 明确写「未验证」及替代检查 |

**风险要标注等级和处理动作**，不要只写「可能有风险」。格式：`风险 → 触发条件 → 影响 → 处理 → 谁确认`。

## 六、确定修改范围

范围写不清楚，AI 就会按「它觉得合理」来扩。范围要分三栏写：

```text
允许修改：
- backend/src/main/java/.../service/WorkOrderService.java
- web/src/api/mes.ts
- sql/openbiz_mes_1_13.sql（新增，字段与索引）

禁止修改：
- 任何已有接口路径与方法签名
- legacy/ 目录下的历史逻辑
- pom.xml、package.json（本次不新增依赖）
- 任何生产配置

必须保持兼容：
- GET /api/mes/work-orders 的返回结构
- 现有状态机的流转规则
- 前端列表页的筛选参数
```

写不出「禁止修改」清单时，说明你对项目还不够熟——回到第 03 章补上下文。

## 七、任务拆解

### 7.1 拆到什么粒度

每个子任务满足三条才算拆好：

1. **可以独立完成**——不依赖还没完成的另一个子任务（依赖项要显式列出）。
2. **可以独立验收**——有明确的命令输出或 diff 特征能证明它做完了。
3. **一次提交能覆盖**——做完就能提交，不需要攒一堆半成品。

### 7.2 拆解顺序

按依赖顺序排，不要按「想到哪写到哪」排：

```text
数据层 → 后端服务 → 接口层 → 前端 → 测试 → 文档
   ↑          ↑         ↑        ↑       ↑       ↑
   └──────────┴─────────┴────────┴───────┴───────┘
              每一步完成都可单独验证
```

**前后端并行是有前提的**：接口契约必须先冻结。契约没定就并行，两边各写一套，合起来一定对不上。

### 7.3 任务拆解模板（可复制）

```markdown
# 任务拆解 · <任务短名>

## 任务目标
<一句话，与 Spec 一致>

## 不做项
- <明确列出>

## 修改范围
| 允许修改 | 禁止修改 | 必须兼容 |
| -------- | -------- | -------- |
| | | |

## 子任务清单

| 编号 | 子任务 | 涉及文件 | 依赖 | 完成标准 | 验收方式 |
| ---- | ------ | -------- | ---- | -------- | -------- |
| T1 | 数据库字段与索引 | sql/x.sql | 无 | 脚本可重复执行 | 本地库执行脚本 + 查 information_schema |
| T2 | 后端领域规则 | Service.java | T1 | 规则实现且有单测 | 单测通过 |
| T3 | 接口与 DTO | Controller.java、DTO | T2 | 返回结构符合契约 | 接口冒烟 |
| T4 | 前端列表与表单 | Vue 文件、api.ts | T3 | 页面取数正常 | 浏览器操作 + 编译 |
| T5 | 回归与文档 | 测试文件、README | T1–T4 | 既有测试通过 | 完整测试命令输出 |

## 执行顺序
T1 → T2 → T3 → T4 → T5（T3 与 T4 可并行，前提是接口契约已冻结）

## 检查点
- T1 完成后：人工确认迁移脚本
- T3 完成后：人工确认接口契约
- T5 完成后：人工对照验收清单判定完成
```

## 八、方案生成提示词（可复制）

这条提示词只让 AI 出方案，不让它改代码。

```text
你的任务只有一个：基于我已经提供的上下文，产出技术方案和风险清单。
本轮不要修改任何代码，不要创建任何文件。

任务：<一句话说明要做什么>

已有上下文：
- 涉及模块与文件：<来自第 03 章的分析结果>
- 相关调用链：<入口 → 服务 → 数据>
- 数据库与接口现状：<表、字段、接口契约>
- 已知约束与禁改区：<来自项目规则>

请按以下结构输出：

1. 需求复述（三句话内）
2. 仍模糊、会影响实现的问题（最多 8 条，按影响排序）
3. 本次不做项（至少 3 条）
4. 方案比较（2–3 个方案，逐项对比改动范围、数据影响、兼容性、回滚成本、验证难度）
5. 推荐方案与理由（按业务正确性 → 兼容性 → 改动范围 → 复用 → 可验证性排序）
6. 修改范围三栏（允许修改 / 禁止修改 / 必须保持兼容）
7. 风险清单（风险 → 触发条件 → 影响 → 处理 → 谁确认）
8. 子任务拆解（编号 | 任务 | 涉及文件 | 依赖 | 完成标准 | 验收方式）
9. 执行顺序与检查点
10. 需要我拍板的问题（没有就写「无，可以开始」）

特别要求：
- 不要输出实现代码。
- 不要为了让方案完整而编造项目里不存在的组件或服务。
- 无法判断的部分明确标「待确认」，不要自行假设。
```

## 九、执行前检查清单

方案确认后、动手前，逐条打勾。任何一条没过，都不要开始改代码。

### 9.1 方案层

- [ ] 需求已复述，模糊点要么已澄清、要么已标「不影响实现」。
- [ ] 「本次不做项」写出来了，至少三条。
- [ ] 有多种做法的地方给出了方案和代价，不是只给一个答案。
- [ ] 修改范围三栏齐全，能落到具体文件路径。
- [ ] 风险清单里每条都有处理动作和确认人。
- [ ] 涉及关键业务、不可逆操作、生产数据的部分已明确需要人工确认。

### 9.2 拆解层

- [ ] 每个子任务都能独立完成、独立验收。
- [ ] 子任务之间的依赖写清楚了，执行顺序可行。
- [ ] 每个子任务都有具体完成标准，不是「完成开发」这种空话。
- [ ] 检查点设置在风险最高的位置（数据迁移、接口契约、最终验收）。
- [ ] 没有把「顺手优化」塞进子任务清单。

### 9.3 环境层

- [ ] 构建命令、测试命令已确认可用。
- [ ] 测试库或测试数据已就绪；没就绪的已写明「未验证」及替代检查。
- [ ] 会改到的文件都有回归保护（有测试，或已列出人工回归步骤）。
- [ ] 回滚路径清楚：出问题怎么退回上一个可运行状态。

## 十、防止一次性大改

AI 最容易犯的错，是拿着一份方案一口气改完所有文件。控制手段有三层。

### 10.1 任务级控制

每次只派发一个子任务。完成、验收、提交之后，再派下一个。

```text
本轮只执行 T2：后端领域规则。
不要动 T3 的接口层，不要动 T4 的前端。
完成后给出 diff 和单测命令输出，等我确认后再继续。
```

### 10.2 数量级控制

给 AI 明确的改动上限：

```text
本次改动不得超过 5 个文件。
如果实现需要超过这个数量，先停下来说明原因，不要自行扩大。
```

### 10.3 检查点控制

在三个位置强制停下来人工确认：

| 检查点 | 为什么停 | 看什么 |
| ------ | -------- | ------ |
| 数据变更后 | 迁移不可逆 | 脚本内容、重复执行安全性、回滚脚本 |
| 接口契约后 | 前后端都依赖它 | 路径、入出参、错误码与冻结版本一致 |
| 最终验收前 | 最后一道闸 | 逐条对照验收清单，看证据不看自述 |

## 十一、什么时候必须人工确认方案

以下情况，AI 出完方案后必须等人拍板，不能直接进入实现：

- 业务规则有两种以上合理解释。
- 涉及数据库结构变更、历史数据迁移。
- 涉及权限、鉴权、资金、库存等核心逻辑。
- 涉及删除数据、改生产配置、不可逆操作。
- 要改已有接口签名或返回结构。
- 要新增核心依赖、升级框架版本。
- 要动禁改区或没有测试覆盖的老代码。
- 方案需要跨多个系统，且失败会影响其他系统。

确认时人只需要回答三件事：**选哪个方案、哪些边界要加、哪些风险不接受**。不需要替 AI 写代码。

## 十二、与提示词库的分工

本章提供的是**判断框架与产物模板**（方案怎么比较、风险怎么识别、任务怎么拆、何时人工确认）。

具体场景下可直接复制的提示词，在提示词库「新功能扩展」分类中已有：需求 → 技术方案、方案 → 开发 spec、表结构评审、前后端接口契约、拆成可提交的小步。详见 [提示词库 · 编程开发](/ai/prompts/coding)。

分工原则：**SOP 讲「怎么判断和验收」，提示词库给「可以直接复制的成品」。** 两边不维护相同的大段提示词，需要时用链接互相引用。

## 十三、常见错误

### 错误 1：只有方案，没有拆解

问题：方案看着完整，AI 一次改完十几个文件，出问题无法定位是哪一步错的。

正确做法：方案必须配一份逐文件、可独立验收的子任务清单，一次只执行一个。

### 错误 2：方案里没有「不做项」

问题：AI 按自己的理解「顺手优化」，改动范围失控。

正确做法：不做项至少三条，且在派发每个子任务时重申。

### 错误 3：比较方案时只看实现难度

问题：选了最容易写的方案，结果发现不满足业务规则或不兼容老数据。

正确做法：按业务正确性 → 兼容性 → 改动范围 → 复用 → 可验证性排序，实现美观度排最后。

### 错误 4：拆解时忽略依赖

问题：先写前端再改接口，或先写代码再改表，中途返工。

正确做法：显式列出依赖，按数据 → 服务 → 接口 → 前端 → 测试的顺序排。

### 错误 5：把风险写成「可能有风险」

问题：等于没写，执行时还是不知道该怎么处理。

正确做法：风险必须带触发条件、影响、处理方式、确认人四要素。

### 错误 6：任务完成标准写成「完成开发」

问题：AI 自己宣布完成，实际什么都没证明。

正确做法：完成标准写成具体命令、具体 diff 特征或具体页面行为。

## 十四、本章完成检查

- [ ] 需求已复述，模糊点已处理或明确标注。
- [ ] 有至少三条「本次不做项」。
- [ ] 五维度（数据 / 接口 / 模块 / 兼容 / 验证）都有结论。
- [ ] 多方案处有比较表，取舍理由符合优先级。
- [ ] 修改范围三栏落到具体文件路径。
- [ ] 风险清单每条都有处理动作和确认人。
- [ ] 子任务清单可独立执行、独立验收，依赖与顺序清楚。
- [ ] 每个子任务有具体完成标准，不是「完成开发」。
- [ ] 执行前检查清单全部打勾。
- [ ] 需要人工确认的事项已确认，没有让 AI 自行拍板。
