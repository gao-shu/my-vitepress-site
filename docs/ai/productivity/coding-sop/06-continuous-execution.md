# AI 连续开发与任务执行

> 前面几章解决了「怎么想清楚」，本章解决「怎么一口气做完」。连续执行不是发一段「你自己写完吧」的提示词，而是一套状态管理：任务有计划、执行有记录、失败有恢复、偏离有检测、关键节点有人审。

## 一、什么时候使用

适合连续执行：

- 任务已拆成多个子任务（第 04 章），且依赖顺序清楚。
- 子任务可以逐个验收，不需要等全部做完才知道对错。
- 同一个会话里上下文还够，或者已经建好可恢复的进度记录。
- 期望 AI 连续做完而不每步都回来问「要不要继续」。

不适合连续执行：

- 方案还没拍板、Spec 还没冻结。
- 任务之间有强耦合，前一个没验证完后一个没法开始。
- 涉及不可逆操作，且还没做备份或隔离。
- 上下文已经明显衰减（AI 开始重复问、翻旧方案、忘约束）。

**判断标准：你能不能把任务写成一张可打勾的清单，且每一项都能单独验证。** 写不出来，先回第 04 章拆解。

## 二、连续执行的三个文件

长任务最容易失控的地方是「状态只存在于对话里」。会话一断，做到哪、为什么这么做、下一步是什么，全丢了。

解决办法是把状态写进文件。三个文件就够：

| 文件 | 内容 | 谁写 | 什么时候读 |
| ---- | ---- | ---- | ---------- |
| `TASK-PLAN.md` | 子任务清单、依赖、完成标准、不做项、修改范围 | 方案阶段写，执行中只改状态 | 每轮开始 |
| `PROGRESS.md` | 每轮做了什么、验证结果、失败记录、下一步 | AI 每轮结束追加 | 每轮开始、恢复会话时 |
| `DECISIONS.md`（可选） | 执行中做的小决定及依据 | AI 遇到非阻塞取舍时追加 | 争议时回查 |

前两个是必需的。第三个只在复杂任务里用。

**为什么不让 AI 只维护一个文件？** 计划是相对稳定的约束，进度是不断追加的事实，混在一起会被越写越长的进度冲掉。分开存，AI 每轮只读计划 + 进度末尾几段。

## 三、任务状态机

每个子任务只有五种状态，不许出现「大概做完了」这种模糊状态：

```text
待执行 pending
    ↓ 开始
进行中 in_progress
    ↓ 验证通过           ↓ 验证失败且可重试
已完成 done          回到 in_progress（记录失败次数）
                         ↓ 同一错误达上限 / 需要人决策
                      阻塞 blocked
                         ↓ 人处理后
                      待执行 pending

任意状态 → 跳过 skipped（必须有明确原因）
```

### 3.1 状态变更的规则

- 一次只能有一个任务处于 `in_progress`。
- `done` 必须有证据——命令输出、diff、测试结果，不能只写「已完成」。
- `blocked` 必须写明阻塞原因和需要谁提供什么。
- `skipped` 必须写明原因，且不能跳过「验证类」任务。
- 状态变化时同步更新 `PROGRESS.md`，不允许只改计划不改日志。

## 四、每轮执行循环

AI 的每一轮工作严格按六步走，不能跳步：

```text
1. 读状态     读 TASK-PLAN.md 和 PROGRESS.md 末尾
2. 选任务     按依赖顺序选下一个 pending 任务，标为 in_progress
3. 执行       只做这一个子任务，遵守修改范围与不做项
4. 验证       跑这个任务的完成标准对应的命令
5. 记录       写 PROGRESS.md：做了什么、证据、失败、下一步
6. 提交       验证通过则提交，更新状态为 done，进入下一轮
```

### 4.1 为什么必须「一轮一任务」

一口气改完所有子任务，出问题你只能看到一大团 diff，无法定位是哪一步错的，也无法回滚到中间状态。一轮一任务换来的是：每个改动都能单独验证、单独提交、单独回滚。

### 4.2 每轮结束的固定交付

不管任务大小，每轮结束都要输出：

```text
本轮任务：T2 后端领域规则
状态：done / blocked
修改文件：列出具体路径
实际执行的命令：原样写出
命令输出：关键行原文（失败也要原样贴）
未完成 / 遗留：列出具体内容
下一轮任务：T3 接口与 DTO
```

## 五、任务计划文件模板（可复制）

```markdown
# 任务执行计划 · <任务短名>

## 目标
<一句话，与 Spec 一致>

## 不做项
- <至少三条>

## 修改范围
| 允许修改 | 禁止修改 | 必须兼容 |
| -------- | -------- | -------- |
| | | |

## 检查点（必须人工确认的位置）
- T1 完成后：迁移脚本
- T3 完成后：接口契约
- 全部完成后：验收清单

## 子任务

| 编号 | 任务 | 涉及文件 | 依赖 | 完成标准 | 状态 | 失败次数 |
| ---- | ---- | -------- | ---- | -------- | ---- | -------- |
| T1 | | | 无 | | pending | 0 |
| T2 | | | T1 | | pending | 0 |
| T3 | | | T2 | | pending | 0 |

## 停止条件
- 同一任务验证失败达 3 次
- 需要修改禁改区
- 需要改动生产数据或不可逆操作
- 实际改动文件超过计划范围
- 上下文明显衰减（开始重复问已说过的事）
```

## 六、进度日志模板（可复制）

```markdown
# 进度日志 · <任务短名>

## 环境
- 分支：<branch>
- 起始提交：<hash>
- 关键命令：<build> / <test>

---

## 轮次 1 · <时间>
- 任务：T1
- 状态：done
- 做了什么：<两三句>
- 修改文件：<路径清单>
- 执行命令：<原样>
- 输出摘要：<关键行原文>
- 遗留问题：<无 / 具体列出>
- 下一轮：T2

## 轮次 2 · <时间>
- 任务：T2
- 状态：blocked
- 失败记录：<第几次，错误原文>
- 阻塞原因：<具体>
- 需要谁提供什么：<具体>
- 已尝试的方案：<逐条列出，避免重复尝试>

---

## 当前状态快照（恢复会话时先看这里）
- 已完成任务：
- 进行中任务：
- 下一轮任务：
- 未解决问题：
- 当前分支与提交：
```

**「当前状态快照」放在最后**，每次追加新轮次时同步更新。恢复会话时只读这一段就能接上。

## 七、启动连续执行的提示词（可复制）

```text
接下来的任务按连续执行方式进行。本轮先不要开始写代码，只确认执行规则。

已提供：
- TASK-PLAN.md：<路径>
- PROGRESS.md：<路径>
- 全局 Rules：<路径>
- 本次 Spec：<路径>

请确认以下规则，然后开始第一轮：

1. 每轮只执行一个 pending 子任务，按依赖顺序选，不要跳。
2. 每轮开始先读 TASK-PLAN.md 和 PROGRESS.md 末尾的状态快照。
3. 严格遵守「不做项」和「修改范围」，超出范围先停下来说明。
4. 每个子任务完成后必须执行它的完成标准对应的命令，原样记录输出。
5. 每轮结束把执行结果写入 PROGRESS.md，更新状态快照，然后提交。
6. 验证失败时记录错误原文，同一错误尝试不超过 3 次；达到上限标为 blocked 并说明原因。
7. 到达检查点时停下来等我确认，不要自行通过。
8. 不要自己宣布整个任务完成——最终验收由我对照验收清单判定。

如果以上规则可行，请从 T1 开始执行第一轮。
```

## 八、中断与恢复

会话中断、上下文耗尽、第二天接着做——这些是长任务的常态，不是异常。

### 8.1 恢复提示词（可复制）

```text
我需要恢复一个中断的开发任务。

请先读取：
- <TASK-PLAN.md 路径>
- <PROGRESS.md 路径>
- 当前 git status 与 git log -3

然后只做四件事：
1. 复述当前状态：已完成哪些、进行中是哪个、下一轮是谁。
2. 核对文件状态与 PROGRESS.md 的记录是否一致；不一致的地方列出来，不要自行猜测原因。
3. 指出上一轮遗留的问题和未解决的阻塞。
4. 等我确认后，从下一轮任务继续执行。

不要重新做已经完成的任务，不要删除已有改动。
```

### 8.2 恢复时的三查

| 查什么 | 怎么查 | 不一致怎么办 |
| ------ | ------ | ------------ |
| 计划与进度是否一致 | PROGRESS 状态 vs TASK-PLAN 状态列 | 以 git diff 为准，把差异列出来交人确认 |
| 文件与记录是否一致 | git status vs 轮次记录里的修改文件 | 多出来的文件单独列出，不擅自回滚 |
| 上轮验证是否真的通过 | PROGRESS 里的命令输出原文 | 没输出就当作没验证，重跑一次 |

## 九、失败处理与恢复机制

### 9.1 失败先分类，不要直接重试

失败先分类，不要一律重试：

| 失败类型 | 判断信号 | 处理 |
| -------- | -------- | ---- |
| 代码错误 | 编译失败、断言失败、报错栈明确 | 可重试，最多 3 次，每次记录改了什么 |
| 环境问题 | 依赖服务不可用、缺权限、缺测试数据 | 标 blocked，不反复重试；写清替代检查 |
| 认知错误 | 反复改不对、改了 A 坏了 B | 停手，回第 03 章重新分析影响范围 |
| 需求冲突 | 测试通过但业务行为与预期不符 | 停手，交人确认，不是代码问题 |

### 9.2 三次规则

**同一个错误最多尝试三次。** 三次之后无论 AI 觉得多有把握都停手：

- 把三次的错误原文、尝试过的修改逐条列进 `PROGRESS.md`。
- 任务状态标 `blocked`，写明需要人提供什么。
- 不要「换一种写法再试第四次」——那通常是在同一个错误认知上打转。

### 9.3 回到上一个可运行状态

每个子任务验证通过后立即提交，本质就是在每个检查点留下一个可回退的位置。

需要回退时：

```text
1. 从 PROGRESS.md 找到最后一个 done 的轮次及其提交 hash
2. 确认这个 hash 之后的改动哪些要保留、哪些要丢弃
3. 用 git 的回退机制回到该位置（由人确认后执行）
4. 把被丢弃的轮次标为 skipped，写明原因
5. 从该位置重新规划，而不是在错误基础上继续叠修改
```

## 十、防止偏离目标

长任务跑偏的信号很典型：开始改没点名的文件、顺手格式化、为了「更合理」改接口、把「不做项」里的事做了。

三道防线：

### 10.1 每轮重申边界

在派发下一轮任务时，把「不做项」和「修改范围」再贴一次。上下文越长，早期约束越容易被稀释。

### 10.2 diff 范围检查

每轮结束检查实际改动文件是否在计划内：

```text
本轮实际修改文件 vs TASK-PLAN.md 的「允许修改」列：
- 在范围内：继续
- 不在范围内：说明原因，由人裁定「保留 / 回退」，不要自行决定
```

### 10.3 偏离信号清单

出现以下任一情况，立即停手：

- AI 说「顺手把……也改了」。
- 开始改依赖文件、配置文件、公共模块，而计划里没写。
- 同一个问题出现三种以上不同解释。
- AI 开始重复问已经回答过的问题。
- 完成标准被改写成了更宽松的版本。

## 十一、人工审核节点

不是每一步都要人看，但以下节点必须停：

| 节点 | 停下来的理由 | 人看什么 |
| ---- | ------------ | -------- |
| 方案确认后 | 方向错了后面全错 | 选哪个方案、哪些边界要加 |
| 数据变更后 | 迁移可能不可逆 | 脚本内容、回滚方案 |
| 接口契约后 | 前后端都依赖它 | 路径、入出参、错误码 |
| 检查点任务完成 | 风险最高的位置 | 证据原文，不是自述 |
| 出现问题无法归类 | 认知错误或需求冲突 | 由人判断属于哪类 |
| 最终验收 | 责任不能外包 | 逐条对照验收清单 |

**「要不要继续下一个任务」不需要问人**——这正是连续执行要省掉的往返。

## 十二、长任务的质量控制

### 12.1 每轮的门禁

一个子任务要标 `done`，必须同时满足：

- [ ] 实现了本任务的完成标准，不是「差不多」。
- [ ] 执行了对应的验证命令，输出原文已记录。
- [ ] 实际改动文件都在允许范围内。
- [ ] 「不做项」没有被触碰。
- [ ] 没有遗留未记录的问题。
- [ ] 已提交，有一个明确的提交 hash。

### 12.2 阶段性回归

不是每个子任务都要跑全量测试，但以下时机必须跑：

- 数据层改动后。
- 接口契约变更后的第一轮前端改动。
- 每完成 3 个子任务。
- 最终验收前。

### 12.3 上下文管理

- 一个任务一个会话窗口，跨任务用 `PROGRESS.md` 交接。
- 关键约束（技术栈、禁改区、命令）每轮开头重申，不假设 AI 记得。
- 发现 AI 开始「翻旧方案接着改」时，立刻开新会话并让它读进度快照。

## 十三、常见错误

### 错误 1：只发一段「你自己写完吧」

问题：没有状态文件，中途断了无法恢复；改偏了也发现不了。

正确做法：先建计划与进度两个文件，再启动。

### 错误 2：一轮改完所有子任务

问题：出问题无法定位，也无法回滚到中间状态。

正确做法：一轮一任务、一轮一验证、一轮一提交。

### 错误 3：失败后无限重试

问题：在同一个错误认知上打转，越改越乱。

正确做法：三次规则 + 失败分类；环境问题与认知问题不重试。

### 错误 4：让 AI 自己宣布整体完成

问题：它只能证明自己执行了步骤，不能证明业务正确。

正确做法：AI 只报告证据，最终验收由人逐条判定（第 08 章）。

### 错误 5：检查点也问「要不要继续」

问题：把连续执行又变回逐步等待，失去意义。

正确做法：只在高风险节点停；普通任务之间直接继续。

### 错误 6：进度记录只写「已完成」

问题：恢复会话时无法知道验证是否真跑过。

正确做法：记录命令原文、输出关键行、失败次数、遗留问题。

## 十四、本章完成检查

- [ ] 有 `TASK-PLAN.md`，含子任务、依赖、完成标准、不做项、停止条件。
- [ ] 有 `PROGRESS.md`，每轮记录命令与输出原文，末尾有状态快照。
- [ ] 状态只用五种，每个 `done` 都有证据和一个提交 hash。
- [ ] 一轮只执行一个子任务，验证通过才进入下一轮。
- [ ] 失败有分类，同一错误最多三次，达到上限标 `blocked`。
- [ ] 有中断恢复流程，恢复时核对计划、文件、验证记录三者一致。
- [ ] 每轮检查实际改动文件是否在允许范围内。
- [ ] 检查点清单明确，人只在必要节点介入。
- [ ] 上下文衰减时有明确的开新会话规则。
