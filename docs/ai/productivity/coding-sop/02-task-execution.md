# 02 任务执行

> 把需求交代清楚，让 AI 分析方案、拆解任务、连续编码，而不是每做一步都回来问一次「要不要继续」。人只在关键决策点拍板。

## 一、什么时候用

| 任务类型 | 执行方式 |
| -------- | -------- |
| 单文件小修改、文案、明确的小 Bug | 说清目标与边界 → 直接做 → 验证 |
| 新增接口、业务功能、跨文件修改 | 分析影响 → 简要方案 → 实施 → 测试 |
| 多模块改造、数据库变更、系统集成、核心业务重构 | 完整分析 → 方案拆解 → 风险检查 → 分阶段执行 |
| 已有一份冻结计划，要连续做完 | 按本页的连续执行机制推进 |

**判断标准：如果改错了需要回滚多个文件，就先做方案。** 修改一行代码，只要涉及订单状态、库存扣减或资金计算，也可能是高等级任务。

**不是输入越详细越好，而是影响 AI 正确完成任务的信息不能缺失。** 能从项目里查到的，不让用户重复写。

### 人什么时候必须参与

- 业务规则有两种以上合理解释。
- 涉及权限、支付、资金、库存等关键业务。
- 需要删除数据、改生产配置、执行不可逆操作。
- 要改已有接口签名或返回结构。
- 要新增核心依赖、升级框架版本。
- 要动禁改区或没有测试覆盖的老代码。

确认时人只需回答三件事：**选哪个方案、哪些边界要加、哪些风险不接受**。不替 AI 写代码。

## 二、操作步骤

### 2.1 任务输入结构

沿用四段式，再补两个真正影响效率的部分：

| 部分 | 需要回答的问题 | 是否必填 |
| ---- | -------------- | -------- |
| 背景 | 当前情况是什么？ | 视任务而定 |
| 目标 | 具体要实现什么？ | 必填 |
| 约束 | 哪些能改、哪些不能改？ | 必填，至少说明关键边界 |
| 输出格式 | 最终交付什么？ | 必填，默认输出执行结果 |
| 任务分级 | 需要多大程度的分析和验证？ | 由 AI 初步判断 |
| 验收标准 | 怎样才算完成？ | 必填，简单任务可简写 |

简单任务一句话加必要限制就够；复杂任务才补业务背景、流程和验收条件。

### 2.2 不同任务怎么交代

| 任务 | 重点 | 一句话要求 |
| ---- | ---- | ---------- |
| 新功能 | 明确功能行为、业务规则、与现有系统关系 | 优先沿用现有逻辑；规则冲突先集中提问，不自行编造 |
| Bug 修复 | 先找根因，不处理表面现象 | 给完整报错 + 复现步骤 + 已排查项，先定位再修 |
| 功能调整 | 明确变的部分和必须不变的部分 | 保持原有字段、排序、接口与流程 |
| 代码重构 | 重构内部实现，不改变业务行为 | 保持接口签名与数据结构兼容，先补行为测试 |
| 系统对接 | 数据结构、通信规则、失败与重复执行 | 接口调用成功 ≠ 业务数据同步成功；考虑幂等与超时 |

### 2.3 让 AI 主动发现缺失信息

把信息分三类，不要让用户事先想全：

| 类型 | 含义 | 处理方式 |
| ---- | ---- | -------- |
| 已确认 | 用户明确说明，或代码和项目资料能验证 | 直接采用 |
| 可推断 | 能从现有代码、配置、历史实现合理确认 | 查证据后采用 |
| 待确认 | 现有资料无法确定，且不同选择会影响结果 | 集中提问 |

**不能把自己的猜测当成已确认的业务规则。**

- 能从项目里确认的，不问用户。
- 不影响业务正确性的细节，按项目现有规范处理。
- 涉及业务规则、数据一致性、权限、安全、不可逆操作的，不能猜。
- 所有阻塞问题一次性提出；没有阻塞就直接执行，不逐步问「要不要继续」。

### 2.4 方案与拆解

方案要回答五个维度：**数据**（表、索引、约束、迁移、事务）、**接口**（路径、入出参、错误码、兼容性）、**模块与分层**（落在哪个包、依赖方向）、**兼容与影响**（老数据、调用方、开关、定时任务）、**验证方式**（哪些测试、哪些命令、哪些人工核对）。

凡有多种做法，给出 2–3 个方案并比较：改动范围、数据影响、兼容性、回滚成本、验证难度。取舍顺序是**业务正确性 → 兼容性 → 改动范围 → 复用 → 可验证性 → 代码美观**。

方案里必须有「本次不做项」和「修改范围三栏」：

```text
允许修改：
- backend/.../service/WorkOrderService.java
- web/src/api/mes.ts

禁止修改：
- 任何已有接口路径与方法签名
- legacy/ 目录下的历史逻辑
- pom.xml、package.json（本次不新增依赖）

必须保持兼容：
- GET /api/mes/work-orders 的返回结构
- 现有状态机的流转规则
```

拆解到什么粒度才合格：**能独立完成、能独立验收、一次提交能覆盖**。按依赖顺序排：`数据层 → 后端服务 → 接口层 → 前端 → 测试 → 文档`。前后端并行有前提——接口契约先冻结。

子任务表：

| 编号 | 子任务 | 涉及文件 | 依赖 | 完成标准 | 验收方式 |
| ---- | ------ | -------- | ---- | -------- | -------- |
| T1 | 数据库字段与索引 | sql/x.sql | 无 | 脚本可重复执行 | 本地执行 + 查 information_schema |
| T2 | 后端领域规则 | Service.java | T1 | 规则实现且有单测 | 单测通过 |
| T3 | 接口与 DTO | Controller.java、DTO | T2 | 返回结构符合契约 | 接口冒烟 |
| T4 | 前端列表与表单 | Vue 文件、api.ts | T3 | 取数正常 | 浏览器操作 + 编译 |

**完成标准不能写「完成开发」**，要写成具体命令、diff 特征或页面行为。

### 2.5 连续执行机制

连续执行不是发一段「你自己写完吧」，而是三样东西：

| 文件 | 内容 | 什么时候读 |
| ---- | ---- | ---------- |
| `TASK-PLAN.md` | 子任务、依赖、完成标准、不做项、停止条件 | 每轮开始 |
| `PROGRESS.md` | 每轮做了什么、命令输出、失败记录、下一步 | 每轮开始、恢复会话时 |
| `DECISIONS.md`（可选） | 执行中的小决定及依据 | 争议时回查 |

状态只有五种：`pending → in_progress → done / blocked / skipped`。`done` 必须有证据和一个提交 hash；`blocked` 必须写明原因和需要谁提供什么。

每轮六步，不能跳：

```text
1. 读状态    TASK-PLAN.md + PROGRESS.md 末尾
2. 选任务    按依赖顺序选下一个 pending，标 in_progress
3. 执行      只做这一个子任务，遵守范围与不做项
4. 验证      跑该任务的完成标准对应的命令
5. 记录      写 PROGRESS.md，更新状态快照
6. 提交      验证通过则提交，进入下一轮
```

**失败分类，不要一律重试**：代码错误可重试最多三轮；环境问题（缺服务、缺权限、缺数据）标 blocked；认知问题（反复改不对、改 A 坏 B）停手回项目分析；需求冲突交人确认。

每轮结束检查实际改动文件是否在允许范围内。出现这些立即停：AI 说「顺手把……也改了」、开始改依赖文件或公共模块、同一问题出现三种解释、开始重复问已回答的问题、完成标准被改宽松。

会话中断后，让它读 `PROGRESS.md` 末尾的状态快照接上，不要重做已完成任务。

## 三、提示词

### 3.1 最小任务输入

```text
任务：修复订单列表查询时状态筛选失效的问题。

目标：
让状态筛选按照实际订单状态返回正确结果。

约束：
只修改订单列表查询相关逻辑，不改变其他筛选条件和接口返回结构。

验收：
不同订单状态筛选结果正确，原有查询功能不受影响。

先检查现有实现，确认原因后直接修复并测试。
```

### 3.2 复杂任务输入

```text
【任务】
本次需要完成的具体事项。

【背景】
当前系统的业务情况、已有功能，以及为什么需要这次调整。

【目标】
1. 需要实现的功能。
2. 需要解决的问题。
3. 预期达到的效果。

【约束】
- 允许修改的范围：
- 不允许修改的范围：
- 必须保持兼容的内容：
- 技术或业务限制：

【验收标准】
1. 功能行为：
2. 数据正确性：
3. 接口兼容性：
4. 测试要求：

【交付要求】
- 完成代码修改。
- 执行必要的编译和测试。
- 说明修改文件、实现结果和验证证据。
- 汇总未解决的问题和风险。

先分析任务，识别必要信息和潜在风险，再制定执行方案。
不要为了补充无关信息而反复提问。
```

### 3.3 集中提问规则

```text
在执行任务前，请先检查现有代码、项目文档和相关业务实现。

对于缺失信息，按以下规则处理：

1. 能从现有项目中确认的信息，不要询问我。
2. 可以通过安全的代码检查验证的信息，先自行检查。
3. 不影响业务正确性的细节，可以采用符合项目现有规范的合理方案。
4. 涉及业务规则、数据一致性、权限、安全、不可逆操作或兼容性的重要问题，不能自行猜测。
5. 将所有真正阻塞执行的问题集中整理，一次性向我提问。
6. 如果没有阻塞问题，直接制定方案并执行，不要逐步询问我是否继续。

如果存在非阻塞风险，可以记录并说明处理依据，不要因此中断整个任务。
```

### 3.4 任务分级

```text
请先判断本次任务的执行级别：

L1：范围明确、影响较小，可以直接实施。
L2：涉及多个文件或业务逻辑，需要先分析影响并制定简要方案。
L3：涉及多模块、核心业务、数据结构、系统集成或高风险操作，需要完整分析和分阶段执行。

判断时考虑：
- 修改范围
- 业务复杂度
- 数据影响
- 接口兼容性
- 回归风险
- 是否存在不可逆操作

请说明判断结果和原因，然后采用对应的执行流程。

不要把简单任务复杂化，也不要把复杂任务当成简单任务直接修改。
```

### 3.5 方案生成

```text
你的任务只有一个：基于我已经提供的上下文，产出技术方案和风险清单。
本轮不要修改任何代码，不要创建任何文件。

任务：<一句话说明要做什么>

已有上下文：
- 涉及模块与文件：<来自项目准备页的分析结果>
- 相关调用链：<入口 → 服务 → 数据>
- 数据库与接口现状：<表、字段、接口契约>
- 已知约束与禁改区：<来自项目规则>

请按以下结构输出：

1. 需求复述（三句话内）
2. 仍模糊、会影响实现的问题（最多 8 条，按影响排序）
3. 本次不做项（至少 3 条）
4. 方案比较（2–3 个方案，逐项对比改动范围、数据影响、兼容性、回滚成本、验证难度）
5. 推荐方案与理由（按业务正确性 → 兼容性 → 改动范围 → 复用 → 可验证性排序）
6. 修改范围三栏（允许修改 / 禁止修改 / 必须保持兼容）
7. 风险清单（风险 → 触发条件 → 影响 → 处理 → 谁确认）
8. 子任务拆解（编号 | 任务 | 涉及文件 | 依赖 | 完成标准 | 验收方式）
9. 执行顺序与检查点
10. 需要我拍板的问题（没有就写「无，可以开始」）

特别要求：
- 不要输出实现代码。
- 不要为了让方案完整而编造项目里不存在的组件或服务。
- 无法判断的部分明确标「待确认」，不要自行假设。
```

### 3.6 启动连续执行

```text
接下来的任务按连续执行方式进行。本轮先不要开始写代码，只确认执行规则。

已提供：
- TASK-PLAN.md：<路径>
- PROGRESS.md：<路径>
- 全局 Rules：<路径>
- 本次 Spec：<路径>

请确认以下规则，然后开始第一轮：

1. 每轮只执行一个 pending 子任务，按依赖顺序选，不要跳。
2. 每轮开始先读 TASK-PLAN.md 和 PROGRESS.md 末尾的状态快照。
3. 严格遵守「不做项」和「修改范围」，超出范围先停下来说明。
4. 每个子任务完成后必须执行完成标准对应的命令，原样记录输出。
5. 每轮结束写入 PROGRESS.md，更新状态快照，然后提交。
6. 验证失败记录错误原文，同一错误尝试不超过 3 次；达到上限标 blocked 并说明原因。
7. 到达检查点时停下来等我确认，不要自行通过。
8. 不要自己宣布整个任务完成——最终验收由我对照验收清单判定。

如果以上规则可行，请从 T1 开始执行第一轮。
```

### 3.7 中断恢复

```text
我需要恢复一个中断的开发任务。

请先读取：
- <TASK-PLAN.md 路径>
- <PROGRESS.md 路径>
- 当前 git status 与 git log -3

然后只做四件事：
1. 复述当前状态：已完成哪些、进行中是哪个、下一轮是谁。
2. 核对文件状态与 PROGRESS.md 是否一致；不一致的列出来，不自行猜测原因。
3. 指出上一轮遗留的问题和未解决的阻塞。
4. 等我确认后，从下一轮任务继续执行。

不要重新做已经完成的任务，不要删除已有改动。
```

### 3.8 日常最简指令

```text
请根据我提供的任务，先检查项目现状并判断任务复杂度。

要求：
1. 优先从项目代码和文档中补全必要上下文。
2. 区分已确认信息、可验证信息和待确认信息。
3. 只有真正影响业务正确性或执行安全的问题才集中询问我。
4. 根据任务复杂度选择最轻量的合理执行流程。
5. 严格遵守修改范围，不擅自重构或扩大需求。
6. 完成后执行必要的编译、测试和回归检查。
7. 最终提供修改内容、验证证据和遗留风险。

如果没有阻塞问题，请直接执行，不要在每个小步骤都等待我的确认。
```

### 3.9 通用验收指令

```text
任务完成后，请不要直接宣布完成。

请按照本次任务的级别执行验收：

1. 检查实际修改是否符合任务目标。
2. 检查是否超出约定的修改范围。
3. 执行能够完成的编译、测试和静态检查。
4. 检查对原有功能和接口的影响。
5. 对无法验证的内容明确说明原因。

最终提供：
- 完成内容
- 修改文件
- 关键实现说明
- 实际执行的验证命令
- 验证结果
- 未解决的问题和风险

不得编造测试结果，不得将未执行的检查描述为通过。
```

## 四、验收标准

### 执行前检查

- [ ] 需求已复述，模糊点已澄清或标注。
- [ ] 有至少三条「本次不做项」。
- [ ] 多方案处有比较表，取舍理由符合优先级。
- [ ] 修改范围三栏落到具体文件路径。
- [ ] 风险清单每条有处理动作和确认人。
- [ ] 子任务可独立执行、独立验收，依赖与顺序清楚。
- [ ] 每个完成标准写成了命令、diff 特征或页面行为。
- [ ] 构建与测试命令已确认可用；缺测试环境的已写明替代检查。
- [ ] 需要人工确认的事项已确认。

### 任务分级验收

| 级别 | 必须做到 |
| ---- | -------- |
| L1 | 符合目标、没扩大范围、执行局部检查、说明结果 |
| L2 | 功能符合预期、相关模块正常、编译或测试通过、检查关键回归、说明遗留 |
| L3 | 核心业务规则验证、数据状态正确、接口兼容检查、异常场景验证、模块回归、迁移方案检查、证据与遗留齐全 |

### 每轮门禁

一个子任务要标 `done`，必须同时满足：完成标准达成、验证命令已执行且输出原文已记录、改动文件都在允许范围、不做项未被触碰、无未记录问题、已提交且有明确 hash。

### 执行阶段最容易犯的错

- **只有方案没有拆解**：AI 一次改十几个文件，出错无法定位。
- **方案里没有不做项**：AI 按自己的理解顺手扩大范围。
- **风险写成「可能有风险」**：执行时还是不知道怎么处理。
- **一轮改完所有子任务**：无法单独验证、单独回滚。
- **失败后无限重试**：在同一个错误认知上打转。
- **检查点也问「要不要继续」**：把连续执行变回逐步等待。

具体场景的可复制提示词见 [提示词库 · 编程开发](/ai/prompts/coding)；本页管流程与验收，不重复维护相同模板。

**执行完成、准备验收时进入 [第 04 页 · 交付验收](/ai/productivity/coding-sop/04-delivery-reuse)。遇到报错和测试失败先看 [第 03 页 · 问题解决](/ai/productivity/coding-sop/03-debug-fix)。**
