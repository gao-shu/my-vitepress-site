# 报错排查、测试与自动修复

> 前面几章让 AI 按计划连续开发，本章补上关键的一环：出了问题怎么自己发现、定位、修复、再验证。核心不是「让它多试几次」，而是一个可记录的闭环——发现问题 → 固定证据 → 根因假设 → 最小修复 → 测试 → 回归验证。

## 一、什么时候使用

以下情况应进入本章的闭环：

- 编译失败、单测失败、接口返回错误。
- 页面行为与预期不符。
- 生产或测试环境报异常，有堆栈或日志。
- 上一轮改动后，原本正常的功能出问题了。
- AI 说「已修复」但你不确定是不是真的修好了。

以下情况不要在这里处理：

- 问题还没复现——先固定复现条件，别直接改代码。
- 需求本身有冲突——那是第 02 章的阻塞问题，不是 bug。
- 涉及核心业务规则的判断——交人确认，不让 AI 自行选择。
- 环境问题（缺依赖服务、缺权限）——标为受限，不反复重试。

## 二、修复闭环的五步

```text
① 固定证据     复现步骤 + 完整报错 + 环境信息 + 当前改动
    ↓
② 根因分析     列假设 → 找证据 → 逐个排除 → 确认根因
    ↓
③ 最小修复     只改导致根因的那一处，不顺手重构
    ↓
④ 测试验证     跑相关测试 → 失败则回到 ②，最多三轮
    ↓
⑤ 回归验证     确认没引入新问题 → 记录已验证 / 未验证
```

**闭环的终点不是「代码改了」，而是「有证据证明改对了，且没改坏别的」。**

## 三、第一步：固定证据

大多数「反复修不好」是因为一开始证据就不全。AI 拿到一句「接口报错了」，只能猜。

### 3.1 必须收集的五类信息

| 信息 | 为什么要 | 怎么给 |
| ---- | -------- | ------ |
| 复现步骤 | 没有稳定复现就无法验证修好没有 | 从哪个页面、点什么、传什么参数 |
| 完整报错 | 截断的堆栈会隐藏真正的根因 | 贴首行异常、完整调用栈、Caused by 链 |
| 期望行为 | 不知道什么算对，就不知道修没修好 | 一句话说明正确结果 |
| 环境信息 | 版本、配置、数据量不同，结论可能不同 | 分支、提交、配置项、数据量级 |
| 最近的改动 | 大部分 bug 是上一轮改出来的 | `git diff` 或最近提交 hash |

### 3.2 不能稳定复现时

**先不要改代码。** 让 AI 输出三样东西：

1. 目前能确认的复现条件（哪怕只在某些数据下出现）。
2. 已排查过什么、排除了什么。
3. 可能原因的排序，以及每条需要什么证据来验证。

拿到这三样再决定下一步。直接上手改，通常改的是表象。

### 3.3 可复制：错误信息收集提示词

```text
当前有一个问题需要排查，但先不要修改任何代码。

问题现象：<一句话描述>
期望行为：<一句话描述>
发生环境：<分支 / 提交 / 配置 / 数据量级>

请只做三件事：
1. 列出固定这个问题还缺哪些信息（复现步骤、完整堆栈、相关配置、最近改动等），按影响排序。
2. 基于现有信息给出根因假设（至少两条），每条写明支持它的证据和反对它的证据。
3. 给出验证每条假设的最小检查动作（只读，不改代码）。

约束：
- 不要把推测写成事实。
- 不要输出修复代码。
- 不要为了让报告完整而编造没有的信息。
- 每条结论标明来源：用户描述 / 代码证据 / 推测。
```

## 四、第二步：根因分析

### 4.1 假设驱动，不是试错驱动

错误做法：改一个地方 → 跑一下 → 不行 → 再改一个地方 → 跑一下。

正确做法：先列假设，再用证据排除，最后只在剩下的假设上改。

```text
假设 A：前端传参类型不对
  证据支持：抓包显示 status 是字符串 "1"
  证据反对：后端 DTO 用的是 String，能接收
  验证动作：查 DTO 定义和 Controller 入参 → 排除

假设 B：SQL 条件没生效
  证据支持：同样的入参直接查库能查到正确结果
  证据反对：暂无
  验证动作：打印实际执行的 SQL 和参数 → 命中
```

### 4.2 区分表面问题与根本原因

| 表面问题 | 常见根本原因 |
| -------- | ------------ |
| 接口返回空列表 | 参数名不匹配、状态枚举值不一致、租户条件漏了 |
| 偶发失败 | 并发覆盖、缓存未失效、异步任务时序、共享状态 |
| 本地正常线上报错 | 配置差异、数据量差异、依赖版本差异、权限差异 |
| 改完 A 坏了 B | 共用方法被改、缓存脏数据、接口返回结构变化 |
| 测试通过但功能不对 | 测试数据没覆盖边界、断言写得太宽、业务规则理解错了 |

**判断是不是根因的标准**：修掉它之后，能不能解释「为什么之前会出现这个现象」。解释不了就还不是根因。

### 4.3 可复制：根因分析提示词

```text
请对以下问题做根因分析。本轮只分析，不改代码。

问题：<现象 + 完整报错原文>
复现步骤：<步骤>
相关改动：<git diff 或提交 hash>
相关文件：<来自第 03 章的调用链分析>

请按四段输出：

1. 事实（只写有证据的）
   - 现象、报错原文、实际执行的 SQL/参数、相关配置值
2. 根因假设（至少两条，按可能性排序）
   - 假设 / 支持证据 / 反对证据 / 验证动作 / 验证结果
3. 排除过程（逐条说明为什么排除）
4. 结论与修复范围
   - 确认的根因（如果还没有足够证据，写「未确认」）
   - 需要改的最小文件清单
   - 绝对不能改的地方

约束：
- 证据必须指到文件行号、日志原文或命令输出。
- 不要输出修复代码。
- 没有足够证据时明确说「未确认」，不要选一个最像的当结论。
```

## 五、第三步：最小修复

确认根因后，修复要满足四条：

1. **只改导致根因的那一处**——不顺手重构、不格式化、不改无关变量命名。
2. **不改变接口契约**——除非根因本身就是契约错误，且已获人工确认。
3. **保留已有测试**——不为了让测试通过而删断言、放宽条件。
4. **能解释现象**——改完之后能说清「为什么这个改动能解决那个现象」。

### 5.1 修复前的检查

```text
本次修复：
- 根因：<一句话>
- 改动文件：<具体路径，不超过 3 个>
- 改动方式：<具体改什么>
- 不改什么：<列出容易顺手改但不该改的地方>
- 验证方式：<哪个命令能证明修好了>
```

超过 3 个文件通常说明根因还没确认，回到第二步。

### 5.2 禁止的「修复」方式

- 硬编码特定值绕过问题。
- 吞掉异常让错误不出现。
- 放宽断言让测试通过。
- 删除失败的测试用例。
- 加 `if` 特判某条数据。
- 把 `qty` 之类的字段含义猜错继续往下算。

这些做法让错误消失，但不解决问题，还会在下个场景里以更隐蔽的方式回来。

## 六、第四步：测试与自动修复循环

```text
修复 → 跑最小测试集 → 通过？
                        ├─ 是 → 进入回归验证
                        └─ 否 → 回到根因分析，记录本轮尝试
                                 同一错误累计 ≤ 3 次
```

### 6.1 测试优先级

按这个顺序跑，先快后慢：

| 顺序 | 测试 | 目的 |
| ---- | ---- | ---- |
| 1 | 编译 / 类型检查 | 语法和依赖层错误 |
| 2 | 出问题的那一个单测 | 确认修复命中 |
| 3 | 相关模块的单测 | 确认没改坏邻近逻辑 |
| 4 | 接口冒烟 | 确认参数、返回、状态码 |
| 5 | 全量测试 | 最终门禁 |

不要一上来就跑全量——慢，而且失败信息不聚焦。

### 6.2 三轮上限

同一个错误最多三轮修复。每轮必须记录：

```text
轮次：第 N 轮
错误原文：<原样>
本轮假设：<改了什么，基于什么>
执行命令：<原样>
结果：<失败则贴输出关键行>
下一步：<继续 / 停手原因>
```

三轮仍未解决，停手并归类：是环境问题（缺依赖）、认知问题（影响范围判断错了），还是需求冲突（规则本身矛盾）。不同类别处理不同，不要混着试。

### 6.3 可复制：修复闭环提示词

```text
请按闭环方式修复以下问题。

问题：<现象 + 报错原文>
根因：<来自根因分析的结论，若未确认请注明>
允许的修改范围：<文件清单>
验证命令：<具体命令>

执行规则：
1. 只改导致根因的那一处，不顺手重构、不格式化、不改无关文件。
2. 每轮改完必须执行验证命令，原样贴出命令和输出关键行。
3. 测试失败时不要立即改代码，先说明本轮假设为什么错了。
4. 同一错误最多尝试 3 次；第 3 次仍失败就停手并说明原因。
5. 不要删除或放宽现有断言，不要硬编码特判，不要吞异常。
6. 每一轮结束后写入 PROGRESS.md（或本轮记录），再继续下一轮。

最终报告必须包含：
- 根因与修复对应关系
- 实际修改文件
- 每轮执行命令与输出原文
- 通过 / 未通过的测试清单
- 未解决的问题
```

## 七、第五步：回归验证

修好一个问题最容易引入另一个。回归验证回答的是：「除了修好的那个，其他东西还正常吗？」

### 7.1 回归的三个层次

| 层次 | 查什么 | 怎么做 |
| ---- | ------ | ------ |
| 同模块 | 共用方法、共用 DTO、同张表 | 跑该模块测试 + 手工点一遍关键路径 |
| 上下游 | 调用方、被调用方、消息消费方 | 按第 03 章的影响清单逐个核对 |
| 全局 | 权限、租户、状态机、事务 | 跑全量测试 + 关键场景冒烟 |

### 7.2 回归对照表

```text
| 场景 | 改前行为 | 改后行为 | 验证方式 | 结论 |
| ---- | -------- | -------- | -------- | ---- |
| 正常关闭订单 | 成功 | 成功 | 单测 + 页面操作 | 一致 |
| 无权限关闭 | 403 | 403 | 接口冒烟 | 一致 |
| 批量关闭部分失败 | 全部回滚 | 全部回滚 | 单测 | 一致 |
| 状态筛选 | 返回其他状态（bug） | 只返回目标状态 | 单测 | 已修复 |
```

**至少有一条「改前行为保持」的证据。** 只验证「修好了什么」不验证「没改坏什么」，不算完整回归。

## 八、已验证与未验证必须分开

这是本章最重要的一条纪律。

| 状态 | 含义 | 怎么写 |
| ---- | ---- | ------ |
| 已验证 | 实际执行命令且有输出证据 | 「单测 X 通过，输出见附件 / 日志」 |
| 未验证 | 有理由没跑，或跑了没证据 | 「测试库不可用，未跑集成测试；已用本地 H2 跑单测替代」 |
| 受限 | 环境或权限不允许 | 「生产配置只读，未做线上验证，需运维配合」 |
| 不适用 | 本次改动不涉及 | 「未涉及前端改动，无需浏览器验证」 |

**不能执行的测试不得写成通过。** 没有输出的「已测试」等于没测试。

### 8.1 验证报告模板（可复制）

```markdown
# 验证报告 · <问题短名>

## 根因
<一句话 + 证据链接>

## 修复
- 修改文件：
- 改动说明：

## 已验证（有证据）
| 项 | 命令 | 输出关键行 | 结论 |
| -- | ---- | ---------- | ---- |
| | | | 通过 / 失败 |

## 未验证（说明原因）
| 项 | 原因 | 替代检查 |
| -- | ---- | -------- |

## 回归对照
| 场景 | 改前 | 改后 | 结论 |
| ---- | ---- | ---- | ---- |

## 遗留问题
- <逐条列出，不藏>
```

## 九、与提示词库的分工

本章提供的是**修复流程与验证纪律**（证据收集、假设排除、三轮上限、回归对照、验证状态区分）。

具体排查手法类提示词在提示词库「Bug 修复」与「功能完善」分类中已有：报错定位三件套、最小复现、并发与偶现问题、慢接口排查、边界与异常补齐、补测试与回归清单。详见 [提示词库 · 编程开发](/ai/prompts/coding)。

分工原则：**SOP 管流程和门禁，提示词库给具体手法。** 遇到具体类型的 bug，从提示词库取手法，套进本章的闭环里。

## 十、常见错误

### 错误 1：没复现就改代码

问题：改的是猜测，改完无法确认是否真的修好。

正确做法：先固定复现步骤、完整报错、环境信息。

### 错误 2：边改边试，没有假设

问题：试对了也不知道为什么对，下次遇到同样问题还得重来。

正确做法：先列假设再用证据排除，记录排除过程。

### 错误 3：改了一堆文件「总有一个命中」

问题：无法确定哪个改动真正解决问题，也无法安全回滚。

正确做法：最小修复，改动文件不超过三个，一次只验证一个假设。

### 错误 4：三轮之后还在试

问题：在同一个错误认知上打转，越改越乱，diff 越来越不可读。

正确做法：三轮上限，停手归类，必要时回第 03 章重新分析影响范围。

### 错误 5：把没跑的测试写成通过

问题：交付报告失真，问题留到上线后暴露。

正确做法：四态区分——已验证 / 未验证 / 受限 / 不适用，每条都要有依据。

### 错误 6：只验证修好的场景

问题：修好了 A，把 B 改坏了。

正确做法：回归对照表至少有一条「改前行为保持」的证据。

### 错误 7：用硬编码和吞异常「修复」

问题：错误消失了，根因还在，下次以更隐蔽的形式回来。

正确做法：六类禁止做法写进规则，验证时检查 diff 里有没有出现。

## 十一、本章完成检查

- [ ] 有稳定的复现步骤；不能稳定复现时已输出排查证据和假设。
- [ ] 收集了完整报错、环境信息、最近改动。
- [ ] 有至少两条根因假设，且记录了排除过程。
- [ ] 确认的根因能解释原始现象。
- [ ] 修复只改了导致根因的那一处，改动文件不超过三个。
- [ ] 每轮修复都执行了验证命令，输出原文已记录。
- [ ] 同一错误尝试不超过三轮，达到上限已停手归类。
- [ ] 回归对照表包含「已修复」和「改前行为保持」两类证据。
- [ ] 验证结果按四态区分，没有把未执行写成通过。
- [ ] 遗留问题逐条列出，没有藏起来。
