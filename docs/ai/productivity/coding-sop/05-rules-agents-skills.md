# Rules、Agent、Skills 实战配置

> 前面四章的方法如果只活在对话里，下次开会就要重新交代一遍。本章把它们固化成三样能长期生效的东西：Rules 管约束，Agent 管角色，Skills 管重复出现的方法。配齐最小集就够，不要为了「体系完整」造一堆没人用的配置。

## 一、什么时候使用

**项目启动时建立最小集**，之后按需增补：

- 新项目接入完成，准备开始第一轮开发时。
- 老项目接管完成，已经知道禁改区和构建命令时。
- 同一类操作做了三次以上，每次都要重新说明做法时。
- 发现同一个错误反复出现，靠 Prompt 提醒已经不管用时。

**不要在这些时候配置**：

- 接手项目的第一天，连结构都没看清——先做第 01、03 章。
- 只有一个文件的改动。
- 某个做法只出现过一次，还不知道是否会复用。

### 1.1 启动必备清单（不超过五项）

| 必须有 | 内容 | 来源 |
| ------ | ---- | ---- |
| 1 | 项目认知资料（事实 / 待确认 / gotchas） | 第 01 章 |
| 2 | 一份全局 Rules（技术栈、命令、禁改区） | 本章第二节 |
| 3 | 一条开发主链 | 第 02、04 章 |
| 4 | 任务输入与验收习惯 | 第 02 章 |
| 5 | 连续执行时的进度记录方式 | 第 06 章 |

**不需要启动时就有**：全套 Agent、Skill 库、MCP 接入、Hooks 脚本。这些是遇到问题后才补的。

### 1.2 三者分工（一句话记牢）

| 机制 | 回答什么 | 自动生效 | 归属 | 能不能放业务事实 |
| ---- | -------- | -------- | ---- | ---------------- |
| Rules | 所有任务必须遵守什么 | 是 | 跟仓库走 | 只写约束，不复制说明 |
| Agent | 谁来做、权限到哪 | 按任务启用 | 跟仓库或人走 | 不存事实，只按输入工作 |
| Skills | 重复出现的方法怎么一步步做 | 触发才启用 | 跟人走，可跨项目 | **禁止** |

一句话：**Rules 是红线，Agent 是角色，Skills 是招式。**

## 二、Rules：把稳定约束写下来

### 2.1 该写什么、不该写什么

| 内容 | 是否写进 Rules |
| ---- | -------------- |
| 技术栈与重要版本 | 是 |
| 构建、测试、启动命令 | 是 |
| 命名与分层约定 | 是 |
| 禁改目录、禁改文件 | 是 |
| 安全红线（凭据、外发、权限） | 是 |
| 跨任务成立的业务约束 | 是，只写约束句，不复制业务说明 |
| 本次任务要做什么 | 否——写进 Spec |
| 完整业务流程说明 | 否——写进项目认知资料 |
| 分阶段操作步骤 | 否——写进 Skill |
| 某次具体改动的细节 | 否——它不属于长期约束 |

### 2.2 编写标准

1. **每条可验证**——能指向一个命令、一个 diff 特征或一个检查点。写「代码要写好」等于没写。
2. **每条禁止项配反例**——AI 需要看到「什么算越界」才能守住边界。
3. **写明来源**——哪份文档、哪次事故、谁的约定。半年后没人敢删无来源的规则。
4. **全局规则控制在 30 行以内**——超了就是混进了别的层。
5. **用「必须 / 禁止」陈述句**，不用「建议 / 尽量 / 最好」。

### 2.3 分层

| 层级 | 管什么 | 变更频率 |
| ---- | ------ | -------- |
| 全局 | 技术栈、构建测试命令、禁改区、安全红线 | 极低 |
| 项目级 | 分层约定、命名、错误码、接口风格 | 低 |
| 目录级 | 某模块特有约束（如无测试覆盖的 legacy 目录） | 中 |
| 业务约束 | 跨任务成立的业务红线 | 低 |

先在全局层写一份，能覆盖 80% 场景。目录级只在确有差异时才建。

### 2.4 Rules 模板（可复制）

```markdown
# <规则名> · <适用范围>

## 适用范围
- 生效范围：全局 / 项目 / <目录路径>
- 不适用：<明确写出例外>

## 事实依据
- <来源：项目认知资料第 X 节 / 某次事故复盘 / 团队约定>

## 必须遵守
| 编号 | 规则 | 验证方式 |
| ---- | ---- | -------- |
| C01 | | <命令或 diff 特征> |

## 明确禁止
| 编号 | 禁止项 | 反例（曾经或可能出错的写法） | 验证方式 |
| ---- | ------ | ---------------------------- | -------- |
| P01 | | | |

## 例外与审批
- 需要例外时，由 <角色> 确认，并记在 <位置>。

## 变更记录
| 日期 | 版本 | 改了什么 | 触发原因 |
| ---- | ---- | -------- | -------- |
```

### 2.5 填好的示例：Java + Spring Boot 项目

```markdown
# 00-core · 全局规则

## 适用范围
- 生效范围：全仓库所有开发任务
- 不适用：docs/ 下纯文档改动（仍需遵守 P03）

## 事实依据
- 《项目认知报告 · WMS 批次模块》第 2、8、9 节
- 2026-10 超卖事故复盘

## 必须遵守
| 编号 | 规则 | 验证方式 |
| ---- | ---- | -------- |
| C01 | 技术栈：Java 21 / Spring Boot 3.5 / MyBatis / MySQL 8 | pom.xml 未变更 |
| C02 | 提交前执行 mvn -q -DskipTests package 与 mvn test | 命令输出原文 |
| C03 | 新接口沿用 /api/<模块>/<资源>，错误码走统一包装类 | diff 检查 |
| C04 | 出库批次分配必须保持 FEFO 语义 | BatchAllocServiceTest 通过 |

## 明确禁止
| 编号 | 禁止项 | 反例 | 验证方式 |
| ---- | ------ | ---- | -------- |
| P01 | 不改已有 URL 与接口签名 | 把 /api/stock/outbound 改成 /api/stock/out | diff 检查 |
| P02 | 不自行新增依赖 | 为日期处理引一个新包 | pom.xml diff |
| P03 | 不外发客户物料编码、供应商价格、生产凭据 | 把生产配置贴进上下文文件 | 密钥扫描 |
| P04 | 不改动 legacy/inventory/ 下的旧结算逻辑 | 「顺手重构」无测试覆盖的代码 | 禁改区 diff 检查 |
| P05 | 不把 biz_stock.qty 当账面量使用 | 直接用 qty 做库存扣减 | 人工审 + gotchas 引用 |

## 例外与审批
- 需要例外时由项目维护人确认，并记入项目认知资料第 6 节。

## 变更记录
| 日期 | 版本 | 改了什么 | 触发原因 |
| ---- | ---- | -------- | -------- |
| 2026-11-16 | v0.1 | 初版 | 项目接入 |
```

注意 C04 与 P05：它们来自业务事实，但**只在项目认知资料里存一次**，Rules 里只写「必须遵守什么」和「怎么验证」，不复述整段业务规则。这是「唯一事实源」的落地方式。

## 三、Agent：把角色和权限写清楚

### 3.1 常见角色

绝大多数项目只需要「主执行者 + 按需一两个子角色」。

| 角色 | 职责 | 输入 | 输出 | 权限边界 |
| ---- | ---- | ---- | ---- | -------- |
| 主执行者 | 拆任务、传上下文、收口结果 | 需求 + Spec + 项目资料 | 任务分工表 + 汇总 | 可读全仓，写限任务范围 |
| 方案评审 | 出方案与代价对比，不动代码 | 需求 + 现状架构 | 方案 + 取舍 + 不做清单 | 只读，人拍板后才实现 |
| 后端执行 | 按 Spec 实现后端改动 | Spec + 规则 + 调用链 | diff + 测试 | 写后端目录 |
| 前端执行 | 按接口契约实现页面 | Spec + 接口契约 | diff | 写前端目录 |
| 测试执行 | 补用例、跑命令、汇总结果 | Spec 验收段 + diff | 测试结果（含失败项） | 写测试目录，不改实现 |
| 审查者 | 审 diff，输出问题清单 | 仅 diff + Spec | 问题清单 | 只读，**不判定通过** |

**一条硬规则：执行者不能当验收人。** 审查者只输出「问题清单和依据」，逐条对照验收清单判定是否完成，是人的动作。把这条写进权限边界，比在提示词里提醒十遍都有效。

### 3.2 什么时候才拆子角色

| 适合并行 | 必须串行 |
| -------- | -------- |
| 前后端共用已冻结的接口契约 | 需求澄清 → 方案拍板 |
| 多个互不重叠模块的同类改动 | 数据库变更 → 依赖它的接口 |
| 测试补充与文档整理 | 实现 → 审查 → 验收 |
| 独立模块的只读分析 | 同一文件的多处修改 |

**没有冻结的 Spec 就不要并行。** 拆得越细，上下文对齐成本越高；单文件改动搞多角色，纯属制造开销。

### 3.3 Agent 模板（可复制）

```markdown
# <角色名>

## 职责
<一句话，说明这个角色存在的唯一理由>

## 不负责
- <明确列出，尤其是"不做验收判定">

## 输入（缺一不可）
| 材料 | 来源 | 缺失时 |
| ---- | ---- | ------ |
| | | <停手索要，不自行脑补> |

## 输出
- 交付物与格式：
- 必须附带的证据：

## 权限边界
- 可读：
- 可写：
- 禁止：<文件 / 目录 / 操作>

## 协作方式
- 向谁交付：
- 何时升级给人：<触发条件>

## 停手条件
- <遇到什么必须停下来，不继续猜>

## 完成判定
- 由 <人 / 哪个环节> 判定，依据 <具体证据>；本角色不宣布完成。
```

### 3.4 填好的示例：审查者

```markdown
# 审查者

## 职责
只审本次 diff，输出可追溯的问题清单。

## 不负责
- 不修代码、不改 diff、不补测试。
- 不判定「可以合并 / 已完成」，那是人的动作。
- 不评价整体架构，只审这次改动是否越界。

## 输入（缺一不可）
| 材料 | 来源 | 缺失时 |
| ---- | ---- | ------ |
| 本次 diff | git diff | 停手索要 |
| 对应 Spec | specs/<短名>.md | 停手索要 |
| 全局 Rules 与禁改区清单 | 仓库 | 停手索要 |

## 输出
- 问题清单：编号 / 位置（文件:行）/ 违反了哪条规则或 Spec / 证据 / 严重级别。
- 每个问题必须指到具体行号，不接受「整体感觉」。

## 权限边界
- 可读：全仓只读
- 可写：无
- 禁止：修改任何文件、给出通过结论

## 协作方式
- 向人交付问题清单，人逐条裁定「改 / 不改 / 记入技术债」。
- 触发升级：禁改区被改动、发现凭据外泄、与 Spec 冲突且影响线上行为。

## 停手条件
- diff 与 Spec 明显不是同一个任务时停下。
- 无法判断规则是否适用时标「需人确认」，不自行解释。

## 完成判定
- 由人对照验收清单判定；本角色只输出清单。
```

## 四、Skills：把重复出现的方法封装起来

### 4.1 什么时候值得建 Skill

三个条件同时满足才建：

1. **同类操作已出现三次以上**——一次是特例，两次是巧合，三次才是模式。
2. **做法有稳定的步骤和检查点**——不是「随机应变」。
3. **至少在两个任务里验证过有效**——没验证过的方法只是设想。

### 4.2 与 Rules 的根本区别

| | Rules | Skills |
| - | ----- | ------ |
| 是否自动生效 | 是，每个任务都带 | 否，触发条件满足才启用 |
| 内容 | 约束（不能做什么） | 方法（怎么一步步做） |
| 归属 | 跟仓库走 | 跟人走，可跨项目复用 |
| 业务事实 | 只写约束句 | **禁止写入** |

**判断准则：Skill 里出现具体表名、客户名、业务字段，就是写错了地方。**

### 4.3 Skill 模板（可复制）

```markdown
# Skill · <方法名>

## 触发条件
- 用：<具体到可判断的场景>
- 不用：<列出容易误用的场景>

## 输入
| 材料 | 必须 | 缺失时 |
| ---- | ---- | ------ |
| | 是 / 否 | <停手 / 降级路径> |

## 执行流程
| 步 | 动作 | 中间产出 | 检查点 |
| -- | ---- | -------- | ------ |
| 1 | | | <谁确认> |
| 2 | | | |

## 输出
- 交付物与格式：
- 必须附带的证据：

## 验收标准
- [ ] <可打勾的具体条件>
- [ ] <可打勾的具体条件>

## 失败与降级
| 情况 | 处理 |
| ---- | ---- |
| 输入缺失 | 停手索要，不脑补 |
| 命令执行失败 | 原样贴出报错，不改写结论 |
| 中间产出不可信 | 退回上一步，标「需人确认」 |

## 不写入本 Skill 的内容
- 具体表名、客户名、业务字段 → 项目认知资料
- 长期约束 → Rules
- 本次任务范围 → Spec
- 工具目录与按钮 → 工具适配说明

## 复用记录
| 日期 | 项目 | 结果 | 据此改了什么 |
| ---- | ---- | ---- | ------------ |
```

### 4.4 填好的示例：老项目局部改动

```markdown
# Skill · 老项目局部改动

## 触发条件
- 用：已有仓库上范围明确的小改动（加过滤、加字段、修一个明确的 bug）
- 不用：新模块开发、架构调整、跨系统改造

## 输入
| 材料 | 必须 | 缺失时 |
| ---- | ---- | ------ |
| 项目认知资料 | 是 | 停手，先做第 01 章接入 |
| 本次 Spec（含验收与不做项） | 是 | 停手索要，不按口头需求开工 |
| 涉及的调用链 | 是 | 用第 03 章追踪提示词补一条 |
| 全局 Rules | 是 | 停手索要 |

## 执行流程
| 步 | 动作 | 中间产出 | 检查点 |
| -- | ---- | -------- | ------ |
| 1 | 复述改什么、不改什么 | 三句话 | 人确认 |
| 2 | 定位会碰的文件，列清单 | 文件清单 | 人确认范围 |
| 3 | 写或确认 Spec | specs/<短名>.md | 人冻结后继续 |
| 4 | 小步实现，一次一个改动单位 | diff | 人看 diff |
| 5 | 跑 Spec 里的验收命令 | 命令输出原文 | 对照验收段 |
| 6 | 查改前行为是否保持 | 回归对照结果 | 人确认 |
| 7 | 交审查者 | 问题清单 | 人裁定 |

## 输出
- diff + 命令输出原文 + 回归对照结果 + 未解决问题清单。

## 验收标准
- [ ] Spec 每条验收都有实际输出对应
- [ ] 未点名的行为与改前一致（至少验证一条）
- [ ] diff 未触及禁改区，依赖文件无变更
- [ ] 已有 URL 与接口签名未变

## 失败与降级
| 情况 | 处理 |
| ---- | ---- |
| 调用链超出本次范围 | 缩回范围，超出的记入待办 |
| 验收命令跑不通 | 原样贴报错，标「环境待确认」，不写成通过 |
| 发现需要先改架构 | 停手，退回第 04 章流程 |

## 复用记录
| 日期 | 项目 | 结果 | 据此改了什么 |
| ---- | ---- | ---- | ------------ |
| 2026-11-16 | WMS 批次模块 | 首用 | 初版 |
```

## 五、MCP 与 Hooks：别让它们越界

### 5.1 MCP 只解决外部能力

MCP 让 AI 拿到仓库之外的能力或数据，它不决定开发流程，也不替代项目认知资料。

| 适合接 | 不适合接 |
| ------ | -------- |
| 只读的测试库元数据查询 | 生产库（外发与权限风险） |
| 内部文档检索 | 把整个知识库塞进每次会话 |
| 构建与 CI 状态查询 | 用 MCP 代替本地跑命令 |
| 工单系统的只读同步 | 让 AI 直接写回工单系统 |

接入前过三项检查，缺一不接：

1. **必要性**——不接这个数据源任务真做不了吗？仓库内文件能解决就不接。
2. **边界**——能否外发、凭据放哪、权限最小化到什么程度、只读还是可写。
3. **降级**——服务不可用时是停下来还是走本地文件；不能出现「MCP 挂了整套 SOP 跑不动」。

### 5.2 Hooks 处理确定性检查

判断标准：**凡是「漏了就出事」且「能写成脚本判定」的检查，一律交给脚本，不交给 AI 自觉。** 提示词提醒会被长会话稀释，脚本不会。

| 检查 | 失败动作 |
| ---- | -------- |
| 格式 / lint / 构建 | 阻断提交 |
| 单测与最小冒烟 | 阻断并贴出输出 |
| 密钥 / 凭据扫描 | 阻断 + 报告 |
| 依赖文件变更检测 | 阻断，需人确认 |
| 禁改区 diff 检测 | 阻断 |
| 提交信息规范 | 提示或阻断 |

Hooks 不判断业务对错（例如「这个过滤逻辑符合 FEFO 吗」），那是 Spec 验收和人的判断。它只做确定性事实检查。

## 六、工具适配边界

本章所有文件名、目录名、层级划分都是**通用示意**，只表达「哪类内容放哪」，不代表任何 AI 编程工具的官方约定。

- Cursor、WorkBuddy、Claude Code 等工具的**目录结构、配置语法、加载优先级、调用方式**，以各自当前版本的官方文档为准。
- 不同工具对 Rules / Agent / Skills 的支持程度不同：有的没有目录级规则，有的 Skill 不进仓库，有的不支持 Hook。按能力映射，缺的能力不要用别的能力硬凑。
- 不把某个工具的目录结构当成行业规范，也不描述未经核实的工具特性。

## 七、维护与更新

配置不是写完就封存。维护规则：

| 触发 | 动作 |
| ---- | ---- |
| 同类错误第二次出现 | 给对应禁止项补一个反例 |
| 同类操作第三次出现 | 抽成 Skill 草案 |
| 项目技术栈升级 | 更新 Rules 的 C01 与验证命令 |
| 坑被踩到并解决 | 写入 gotchas，必要时升级为规则 |
| 某条规则半年没人触发 | 评审是否该删，避免规则膨胀 |
| 跨项目复用有效 | Skill 记一条复用记录 |

**每次更新都要记变更原因。** 没有原因的规则，半年后没人敢改也没人敢删。

## 八、常见错误

### 错误 1：Rules 里写本次任务

问题：规则文件越写越长，AI 只挑最后几行执行，真正的红线反而被淹没。

正确做法：任务写进 Spec，规则只写跨任务成立的约束。

### 错误 2：Skill 里塞业务字段

问题：Skill 跟人走，带着 A 项目的表名跑到 B 项目，输出全是错的。

正确做法：Skill 只放方法与检查点，业务事实留在项目认知资料。

### 错误 3：让审查者判定通过

问题：执行者当验收人，等于自己给自己打分。

正确做法：审查者只输出问题清单，完成判定留给人。

### 错误 4：启动前配齐全套

问题：花两周配了六个角色和十几个 Skill，第一轮开发一个都没用上。

正确做法：启动时只建 1.1 节的五项最小集，用到再补。

### 错误 5：靠提示词提醒做确定性检查

问题：「记得跑测试」「别提交密钥」在长对话里会被稀释。

正确做法：能脚本化的交给 Hooks，提示词只讲判断和取舍。

## 九、本章完成检查

- [ ] 全局 Rules 不超过 30 行，每条都有验证方式，禁止项都配了反例。
- [ ] Rules 里没有「本次」「这个需求」「先做……再做……」这类任务措辞。
- [ ] 实际启用的角色有书面职责与权限边界，审查者明确不判定通过。
- [ ] 每个 Skill 都写了触发条件、什么时候不用、失败降级、复用记录。
- [ ] Skill 里没有具体表名、客户名、业务字段。
- [ ] MCP 逐条过了必要性 / 边界 / 降级三项检查。
- [ ] 所有「漏了就出事」的检查已进入脚本，不靠提示词提醒。
- [ ] 启动必备清单没有超过五项。
- [ ] 所有配置都有来源和变更记录。
