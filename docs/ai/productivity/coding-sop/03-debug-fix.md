# 03 问题解决

> 让 AI 从被动挨错变成主动排查：固定证据 → 根因假设 → 最小修复 → 测试循环 → 回归验证。核心不是「多试几次」，而是每一步都有证据，同一错误不无限重试。

## 一、什么时候用

- 编译失败、单测失败、接口返回错误。
- 页面行为与预期不符。
- 测试或生产环境报异常，有堆栈或日志。
- 上一轮改动后，原本正常的功能出问题。
- AI 说「已修复」，但你不确定是不是真的修好了。

**以下情况不要在这里处理**：

- 问题还没复现——先固定复现条件，别直接改代码。
- 需求本身冲突——那是任务输入阶段的阻塞问题。
- 涉及核心业务规则的判断——交人确认。
- 环境问题（缺服务、缺权限、缺数据）——标为受限，不反复重试。

## 二、操作步骤

### 2.1 五步闭环

```text
① 固定证据     复现步骤 + 完整报错 + 环境信息 + 当前改动
     ↓
② 根因分析     列假设 → 找证据 → 逐个排除 → 确认根因
     ↓
③ 最小修复     只改导致根因的那一处，不顺手重构
     ↓
④ 测试验证     跑相关测试 → 失败回到 ②，最多三轮
     ↓
⑤ 回归验证     确认没引入新问题 → 记录已验证 / 未验证
```

**闭环的终点不是「代码改了」，而是「有证据证明改对了，且没改坏别的」。**

### 2.2 固定证据

必须收集五类信息：

| 信息 | 为什么要 | 怎么给 |
| ---- | -------- | ------ |
| 复现步骤 | 没有稳定复现就无法验证修好没有 | 从哪个页面、点什么、传什么参数 |
| 完整报错 | 截断的堆栈会隐藏真正根因 | 首行异常、完整调用栈、Caused by 链 |
| 期望行为 | 不知道什么算对，就不知道修没修好 | 一句话说明正确结果 |
| 环境信息 | 版本、配置、数据量不同，结论可能不同 | 分支、提交、配置、数据量级 |
| 最近改动 | 大部分 bug 是上一轮改出来的 | `git diff` 或最近提交 hash |

**不能稳定复现时，先不要改代码。** 让 AI 输出三样东西：目前能确认的复现条件、已排查过什么排除了什么、可能原因的排序及每条需要什么证据验证。

### 2.3 根因分析

**假设驱动，不是试错驱动。** 错误做法是「改一处跑一下，不行再改一处」。正确做法是先列假设，再用证据排除，最后只在剩下的假设上改。

```text
假设 A：前端传参类型不对
  支持：抓包显示 status 是 "1"
  反对：后端 DTO 用的是 String，能接收
  验证：查 DTO 定义和 Controller 入参 → 排除

假设 B：SQL 条件没生效
  支持：同样入参直接查库能查到正确结果
  反对：暂无
  验证：打印实际执行的 SQL 和参数 → 命中
```

常见表象与根因：

| 表面问题 | 常见根本原因 |
| -------- | ------------ |
| 接口返回空列表 | 参数名不匹配、枚举值不一致、租户条件漏了 |
| 偶发失败 | 并发覆盖、缓存未失效、异步时序、共享状态 |
| 本地正常线上报错 | 配置差异、数据量差异、依赖版本、权限 |
| 改完 A 坏了 B | 共用方法被改、缓存脏数据、返回结构变化 |
| 测试通过但功能不对 | 测试数据没覆盖边界、断言太宽、规则理解错 |

**判断是否根因的标准**：修掉它之后，能不能解释「为什么之前会出现这个现象」。解释不了就还不是根因。

### 2.4 最小修复

四条要求：只改导致根因的那一处；不改变接口契约（除非根因就是契约错误且已获确认）；不删除或放宽现有测试；能解释现象。改动文件超过三个，通常说明根因还没确认。

修复前写清楚：

```text
本次修复：
- 根因：<一句话>
- 改动文件：<不超过 3 个>
- 改动方式：<具体改什么>
- 不改什么：<容易顺手改但不该改的地方>
- 验证方式：<哪个命令能证明修好了>
```

**禁止的「修复」方式**：硬编码特定值绕过、吞掉异常让错误消失、放宽断言让测试通过、删除失败用例、给某条数据加 `if` 特判、把字段含义猜错继续算。这些让错误消失但不解决问题，下个场景会以更隐蔽的方式回来。

### 2.5 测试循环与三轮上限

按先快后慢跑：编译 / 类型检查 → 出问题的那一个单测 → 相关模块单测 → 接口冒烟 → 全量测试。一上来跑全量，慢且失败信息不聚焦。

**同一个错误最多三轮。** 每轮记录：错误原文、本轮假设（改了什么、基于什么）、执行命令、结果、下一步。三轮仍失败就停手并归类：

| 失败类型 | 信号 | 处理 |
| -------- | ---- | ---- |
| 代码错误 | 编译失败、断言失败、堆栈明确 | 可重试，最多三轮 |
| 环境问题 | 依赖服务不可用、缺权限、缺数据 | 标受限，不反复重试，写替代检查 |
| 认知错误 | 反复改不对、改 A 坏 B | 停手，回第 01 页重新分析影响范围 |
| 需求冲突 | 测试通过但业务行为不符预期 | 停手交人确认，不是代码问题 |

### 2.6 回归验证

三个层次：同模块（共用方法、共用 DTO、同张表）、上下游（调用方、消息消费方）、全局（权限、租户、状态机、事务）。

必须跑全量或阶段性回归的时机：数据层改动后、接口契约变更后的第一轮前端改动、每完成三个子任务、最终验收前。

回归对照表：

```text
| 场景 | 改前行为 | 改后行为 | 验证方式 | 结论 |
| ---- | -------- | -------- | -------- | ---- |
| 正常关闭订单 | 成功 | 成功 | 单测 + 页面 | 一致 |
| 无权限关闭 | 403 | 403 | 接口冒烟 | 一致 |
| 状态筛选 | 返回其他状态 | 只返回目标状态 | 单测 | 已修复 |
```

**至少有一条「改前行为保持」的证据。** 只验证「修好了什么」不验证「没改坏什么」，不算完整回归。

## 三、提示词

### 3.1 错误信息收集

```text
当前有一个问题需要排查，但先不要修改任何代码。

问题现象：<一句话描述>
期望行为：<一句话描述>
发生环境：<分支 / 提交 / 配置 / 数据量级>

请只做三件事：
1. 列出固定这个问题还缺哪些信息（复现步骤、完整堆栈、相关配置、最近改动等），按影响排序。
2. 基于现有信息给出根因假设（至少两条），每条写明支持它的证据和反对它的证据。
3. 给出验证每条假设的最小检查动作（只读，不改代码）。

约束：
- 不要把推测写成事实。
- 不要输出修复代码。
- 不要为了让报告完整而编造没有的信息。
- 每条结论标明来源：用户描述 / 代码证据 / 推测。
```

### 3.2 根因分析

```text
请对以下问题做根因分析。本轮只分析，不改代码。

问题：<现象 + 完整报错原文>
复现步骤：<步骤>
相关改动：<git diff 或提交 hash>
相关文件：<来自第 01 页的调用链分析>

请按四段输出：

1. 事实（只写有证据的）
   - 现象、报错原文、实际执行的 SQL/参数、相关配置值
2. 根因假设（至少两条，按可能性排序）
   - 假设 / 支持证据 / 反对证据 / 验证动作 / 验证结果
3. 排除过程（逐条说明为什么排除）
4. 结论与修复范围
   - 确认的根因（如果还没有足够证据，写「未确认」）
   - 需要改的最小文件清单
   - 绝对不能改的地方

约束：
- 证据必须指到文件行号、日志原文或命令输出。
- 不要输出修复代码。
- 没有足够证据时明确说「未确认」，不要选一个最像的当结论。
```

### 3.3 修复闭环

```text
请按闭环方式修复以下问题。

问题：<现象 + 报错原文>
根因：<来自根因分析的结论，若未确认请注明>
允许的修改范围：<文件清单>
验证命令：<具体命令>

执行规则：
1. 只改导致根因的那一处，不顺手重构、不格式化、不改无关文件。
2. 每轮改完必须执行验证命令，原样贴出命令和输出关键行。
3. 测试失败时不要立即改代码，先说明本轮假设为什么错了。
4. 同一错误最多尝试 3 次；第 3 次仍失败就停手并说明原因。
5. 不要删除或放宽现有断言，不要硬编码特判，不要吞异常。
6. 每一轮结束后写入 PROGRESS.md（或本轮记录），再继续下一轮。

最终报告必须包含：
- 根因与修复对应关系
- 实际修改文件
- 每轮执行命令与输出原文
- 通过 / 未通过的测试清单
- 未解决的问题
```

### 3.4 验证报告模板

```markdown
# 验证报告 · <问题短名>

## 根因
<一句话 + 证据链接>

## 修复
- 修改文件：
- 改动说明：

## 已验证（有证据）
| 项 | 命令 | 输出关键行 | 结论 |
| -- | ---- | ---------- | ---- |
| | | | 通过 / 失败 |

## 未验证（说明原因）
| 项 | 原因 | 替代检查 |
| -- | ---- | -------- |

## 回归对照
| 场景 | 改前 | 改后 | 结论 |
| ---- | ---- | ---- | ---- |

## 遗留问题
- <逐条列出，不藏>
```

## 四、验收标准

### 四态区分（最重要的一条纪律）

| 状态 | 含义 | 怎么写 |
| ---- | ---- | ------ |
| 已验证 | 实际执行命令且有输出证据 | 「单测 X 通过，输出见日志」 |
| 未验证 | 有理由没跑，或跑了没证据 | 「测试库不可用，未跑集成测试；已用本地库跑单测替代」 |
| 受限 | 环境或权限不允许 | 「生产配置只读，未做线上验证，需运维配合」 |
| 不适用 | 本次改动不涉及 | 「未涉及前端改动，无需浏览器验证」 |

**不能执行的测试不得写成通过。没有输出的「已测试」等于没测试。**

### 问题关闭清单

- [ ] 有稳定复现步骤；不能稳定复现时已输出排查证据和假设。
- [ ] 收集了完整报错、环境信息、最近改动。
- [ ] 有至少两条根因假设，记录了排除过程。
- [ ] 确认的根因能解释原始现象。
- [ ] 修复只改了导致根因的那一处，改动文件不超过三个。
- [ ] 每轮都执行了验证命令，输出原文已记录。
- [ ] 同一错误尝试不超过三轮，达到上限已停手归类。
- [ ] 回归对照包含「已修复」与「改前行为保持」两类证据。
- [ ] 遗留问题逐条列出，没有藏起来。

### 问题解决阶段最容易犯的错

- 没复现就改代码，改的是猜测。
- 边改边试，没有假设，试对了也不知道为什么对。
- 改一堆文件「总有一个命中」，无法定位和安全回滚。
- 三轮之后还在试，diff 越来越不可读。
- 把没跑的测试写成通过。
- 用硬编码和吞异常「修复」，根因还在。

具体排查手法（最小复现、并发偶现、慢接口、边界异常补齐、回归清单）见 [提示词库 · 编程开发](/ai/prompts/coding)；本页管闭环和门禁。
