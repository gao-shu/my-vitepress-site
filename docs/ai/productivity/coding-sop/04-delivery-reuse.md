# 04 交付验收

> AI 说「写完了」不算完成。完成要能逐条核对、有命令输出、有 diff 证据；验收通过后，还要判断这次经验值不值得沉淀，让下一次少走弯路。

## 一、什么时候用

- 一个子任务或整个任务执行完毕，准备标记完成。
- AI 报告「已完成」，你需要判断是不是真的完成。
- 准备提交、合并或部署之前。
- 一次开发结束后，判断哪些经验值得留下来。

**不要等到全部代码写完才第一次验收。** 每个执行检查点都该做局部验收——越晚发现问题，回滚成本越高。

**一条底线：完成由人判定，不由 AI 宣布。** AI 负责提供证据，人逐条核对。

## 二、操作步骤

### 2.1 四层验收

| 层次 | 回答什么 | 主要证据 |
| ---- | -------- | -------- |
| 功能验收 | 要求的功能实现了吗 | 页面操作、接口返回、业务规则核对 |
| 兼容验收 | 原有功能被影响了吗 | 回归对照、接口契约比对 |
| 技术验收 | 编译和测试通过了吗 | 命令输出原文 |
| 交付验收 | 结果可追溯、可接手吗 | diff、交付报告、遗留清单 |

按任务级别裁剪强度：

- **简单任务**：功能 + 局部检查 + 修改说明。
- **普通任务**：四层都过，兼容验收只看相关模块。
- **复杂任务**：四层全过，兼容覆盖上下游，技术验收包含全量测试。

### 2.2 功能验收

把任务输入里的「验收标准」逐条抄过来，每条填结果：

```text
| 验收项 | 预期 | 实际 | 证据 | 结论 |
| ------ | ---- | ---- | ---- | ---- |
| 不同状态筛选结果正确 | WAITING 只返回等待单 | 返回 3 条 WAITING | 单测输出 + 页面操作 | 通过 |
| 分页不受影响 | 第 2 页正常 | 页码正确、总数一致 | 接口返回原文 | 通过 |
| 不符合条件订单不能关闭 | 已发订单被拒 | 返回 409 | 接口冒烟 | 通过 |
```

**「看起来没问题」不是证据。** 每条都要指到具体命令输出、接口返回或页面行为。

业务规则单独核对：从项目认知资料取出本次相关规则（如「出库必须 FEFO」「关闭订单必须释放库存」），逐条确认实现是否保持。有疑问交业务确认，不让 AI 自行解释。

### 2.3 兼容验收

Git Diff 逐项检查：

- [ ] 改动文件都在允许范围内，没触碰禁改区。
- [ ] 依赖文件（`pom.xml`、`package.json` 等）没有意外变更。
- [ ] 没有批量格式化无关文件。
- [ ] 没有硬编码特判、吞异常、放宽断言。
- [ ] 没有删除或注释掉现有测试。
- [ ] 没有留下调试代码（打印、TODO、注释掉的分支）。
- [ ] 提交信息说清了改什么、为什么。

接口与数据兼容：

| 检查对象 | 核对什么 |
| -------- | -------- |
| 已有接口 | 路径、方法、入参、返回结构、错误码是否变化 |
| 已有字段 | 是否删除、改名、改类型、改含义 |
| 数据库 | 是否改字段类型、加非空约束，迁移能否重复执行 |
| 缓存 | 数据变更后缓存键是否失效 |
| 上下游 | 影响清单里的调用方是否逐个核对 |
| 前端契约 | `api/*.ts` 与后端 DTO 是否一致 |

兼容性结论写成三种之一：**没变 / 变了但已确认兼容 / 变了需要通知下游**。不写「应该没问题」。

### 2.4 技术验收

| 项 | 合格证据 | 不合格写法 |
| -- | -------- | ---------- |
| 编译 | 命令原文 + 成功输出 | 「编译通过」 |
| 单测 | 命令原文 + 通过数 / 失败数 | 「测试都过了」 |
| 接口冒烟 | 请求与返回原文 | 「接口正常」 |
| 类型检查 | 命令原文 + 输出 | 「类型没问题」 |
| 无法执行的检查 | 原因 + 替代检查 | 不写，或写成通过 |

### 2.5 遗留问题

遗留问题写清楚比假装没有更有价值。每条包含：**问题是什么、影响什么、建议怎么处理、谁来决定**。

「下次再说」不是处理方式——要么建待办，要么写进认知资料的 gotchas，要么在交付报告里留痕。

### 2.6 经验沉淀

**先问三个问题，全答「是」才动手**：

1. 这个问题还会再出现吗？
2. 不沉淀的代价是什么？
3. 有没有第二个项目能验证它？

沉淀位置：

| 经验类型 | 去哪里 | 例子 |
| -------- | ------ | ---- |
| 跨任务成立的约束 | Rules | 「禁止新增依赖」「出库保持 FEFO」 |
| 踩过的坑 | gotchas / 项目认知资料 | 「qty 是可用量不是账面量」 |
| 重复三次以上的做法 | Skill | 「老项目局部改动」 |
| 项目特有事实 | 项目认知资料 | 模块划分、字段含义、历史决策 |
| 一次性排查过程 | 不沉淀，留在交付报告 | 某次特定偶发问题 |
| 工具配置细节 | 工具适配说明 | 某工具的具体目录与语法 |

Skill 要在「复用记录」加一行：日期、项目、结果、据此改了什么。至少两个项目验证过才升级为通用方法。

**不要沉淀**：一次性 bug 的临时绕法、未验证有效的「好方法」、业务字段写进 Skill、本次任务范围写进 Rules、整段业务流程写进 Rules、过时的版本与命令、重复提示词库的大段模板、「尽量 / 建议」这类无法验证的软规则。

### 2.7 让下一次能直接复用

验收时问五个问题：

1. 下次开新会话，AI 能不能只读项目资料就知道禁改区和命令？
2. 同类任务再来，能不能直接套已有 Skill，不用从头讲步骤？
3. 上次踩的坑，下次还会不会踩？
4. 同类 bug 再出现，能不能直接套第 03 页的闭环？
5. 新人接手，能不能靠交付报告看懂这次改了什么、为什么？

两条答不上来，说明沉淀没做到位。

## 三、提示词

### 3.1 验收自查

```text
请对本轮改动做验收自查，不要修改任何文件，也不要宣布完成。

输入：
- 任务验收标准：<来自任务输入的验收段>
- 修改范围与不做项：<来自 TASK-PLAN.md>
- 本轮 diff：<git diff>
- 已执行的命令与输出：<原样>

请按四层输出：

1. 功能验收（逐条对照验收标准，每条给证据或标「缺证据」）
2. 兼容验收（逐项检查 diff、接口、字段、上下游，给出「没变 / 已确认兼容 / 需通知下游」）
3. 技术验收（已执行命令清单与输出关键行；未执行的明确标出，不得写成通过）
4. 交付验收（改动文件清单、遗留问题、是否可接手）

约束：
- 不编造测试输出，不把未执行的检查写成通过。
- 发现问题直接列出，不要替它找理由。
- 最后输出「可以进入人工验收 / 尚缺以下证据」二选一，不要输出「任务完成」。
```

### 3.2 交付报告模板

```markdown
# 交付报告 · <任务短名>

## 任务与范围
- 任务：<一句话>
- 任务级别：简单 / 普通 / 复杂
- 修改范围：<文件清单>
- 不做项执行情况：<是否全部遵守>

## 完成内容
- <逐条列出实现了什么>

## 修改文件
| 文件 | 改了什么 | 为什么 |
| ---- | -------- | ------ |

## 验证证据
| 层次 | 检查项 | 命令 / 操作 | 输出关键行 | 结论 |
| ---- | ------ | ----------- | ---------- | ---- |
| 功能 | | | | 通过 / 失败 |
| 兼容 | | | | 没变 / 已确认兼容 / 需通知下游 |
| 技术 | | | | 通过 / 未验证（原因） |

## 回归对照
| 场景 | 改前 | 改后 | 结论 |
| ---- | ---- | ---- | ---- |

## 遗留问题
| 编号 | 问题 | 影响 | 建议处理方式 |
| ---- | ---- | ---- | ------------ |

## 本次沉淀
- <写入了哪里，或「本次不沉淀」及原因>
```

## 四、验收标准

### 交付检查清单

- [ ] 四层验收逐条完成，每条都有证据。
- [ ] 功能验收逐条对照任务输入里的验收标准。
- [ ] diff 检查全部打勾，没有硬编码、吞异常、放宽断言。
- [ ] 接口、字段、数据库、缓存、上下游的兼容性结论明确。
- [ ] 技术验收的命令与输出原文已记录。
- [ ] 未验证项按四态区分，没有写成通过。
- [ ] 回归对照包含「已修复」与「改前行为保持」两类证据。
- [ ] 交付报告完整，遗留问题逐条列出且有处理方式。
- [ ] 沉淀经过三问筛选，放到了正确位置。
- [ ] 沉淀内容没有踩「不要沉淀」清单里的任何一条。

### 交付阶段最容易犯的错

- 以 AI 自述作为验收，「已完成」「已补充测试」不是证据。
- 只看功能不看兼容，新功能正常但老功能被改坏。
- 把没跑的测试写成通过。
- 遗留问题写「下次处理」，没有位置和责任人。
- 把一次性经验写成 Rules，规则越来越长。
- 把业务字段写进 Skill，污染下个项目。
- 没有回归对照证据，无法证明「没改坏别的」。

### 这套流程最终要回答的三个问题

1. **能不能少问？** 用户只交代目标和边界，AI 自己查项目、判断缺口、集中提阻塞问题。
2. **能不能少错？** 先理解再执行、方案先行、小步改动、每步有证据。
3. **能不能连续完成？** 有计划、有状态、有恢复、有检查点，不需要每步等待确认。

三条里还有做不到的，回到对应页补，不要靠增加文档数量制造「完整」的感觉。
