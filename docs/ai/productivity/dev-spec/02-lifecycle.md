# 开发中

> **一项开发任务从准备到交付的九个阶段。找到你现在所处的阶段，复制对应命令，按结果往下走。**

## 快速定位

| 我现在要做什么 | 使用 |
|---|---|
| 开新项目 / 接手老项目 | 01 项目准备 |
| 判断需求能不能做、把需求说清 | 02 需求分析 |
| 写代码前定方案、评方案 | 03 架构设计 |
| 按方案连续编码 | 04 功能开发 |
| 检查写完的代码、按问题整改 | 05 功能审查与完善 |
| 修业务逻辑错误、查 BUG 根因 | 06 逻辑与 BUG 修复 |
| 改善结构、不动行为 | 07 代码优化与重构 |
| 设计用例、执行测试、分析结果 | 08 代码测试 |
| 交付验收、沉淀经验、清理遗留 | 09 交付复用 |

> **原则：简单任务可跳过部分阶段，复杂任务完整走。测试必须有实际执行证据。**

---

## 01 · 项目准备

**让 AI 先懂项目、定好边界，再动手写代码。**

### 什么时候使用

- 全新项目要初始化
- 接手别人开发的项目
- AI 经常理解错、改错地方

### 操作

#### ① 新项目初始化

```text
现在准备开始一个新项目，请协助初始化，但暂时不要大规模编写业务代码。

1. 先确认：项目要解决什么问题、主要用户、核心功能、技术选型、开发约束。信息够就不要重复问，关键缺失一次性列出。
2. 检查当前目录：是否已有项目文件、脚手架、Git 仓库、规则文件、必要依赖。不要覆盖或删除已有内容。
3. 给出初始化方案：目录结构、技术栈与依赖、开发/构建/测试命令、必要规则、当前阶段要创建的文件。
4. 只创建当前真正需要的内容，不预建空文档，不为用 Agent / Skill / MCP 强行加配置。
5. 等我确认后再执行初始化和环境检查。

不要把未确认的技术选型写成既定事实，不要执行未经确认的高风险操作。
```

---

#### ② 老项目接管

```text
你要接管一个已有项目。本轮只读分析，建立后续开发需要的上下文。

暂时不要修改任何业务代码、不要重构、不要安装新依赖。

按顺序检查：技术栈与版本、前后端架构、模块划分；如何启动/构建/测试、有无数据库和 Docker；核心业务模块、模块间调用、关键接口、重要数据实体、第三方集成；已有规则文件和代码规范；哪些模块不能随意改、哪些操作影响生产数据、已知问题、代码里查不到的信息。

输出项目接入报告，每项标注：已确认（有证据）/ 待确认 / 人工补充。
最后说明：是否具备开发条件，开始新功能还缺什么信息，哪些建议写入规则。
```

### 完成标准

> **新项目能跑通构建和测试命令；老项目拿到一份带证据的接入报告和明确保护边界。**

## 02 · 需求分析

**把需求说清楚，并先判断可行性和风险——有重大问题先沟通，确认没问题再往下做。**

### 什么时候使用

- 收到新功能、改动、Bug 需求
- 需求描述模糊、怕 AI 理解错
- 不确定现有架构能不能实现

### 操作

#### ① 需求可行性分析

```text
请分析下面这个需求，本轮只分析和沟通，不要修改任何代码，也不要开始实现。

需求：<描述>

请输出：
1. 需求复述（三句话内），确认你理解对了
2. 可行性判断：基于当前项目结构、数据库、接口和现有能力，能不能做、要改哪些地方
3. 风险与阻塞：业务规则不清、数据一致性、权限、兼容性、不可逆操作等
4. 缺失信息：分「能从项目查到的」「必须问我的」两类；能从项目查到的你自己查，只把真正阻塞的集中问我
5. 初步影响范围：大致涉及哪些模块和文件

如果可行性有问题或存在重大风险，先列出来等我确认，不要给出实现方案。
确认无阻塞后，再问我是否进入方案设计。
```

---

#### ② 需求完善与任务输入

```text
需求已确认可行，请把它整理成可直接执行的任务输入。本轮只整理，不改代码。

需求：<描述>

按四段整理：
1. 目标：具体要实现什么
2. 约束：允许改什么、不能改什么、必须保持兼容什么
3. 验收：怎样算完成（写成能核对的行为、命令或 diff 特征，不写「完成开发」）
4. 任务分级：按修改范围、业务复杂度、数据影响、接口兼容、回归风险判断，说明是简单 / 普通 / 复杂

缺失信息按「能从项目查到的自己查、影响正确性的集中问我」处理，不要让我重写能从代码查到的内容。
```

### 完成标准

> **先得到可行性结论和风险清单（有风险就停下来沟通）；确认后得到一份目标、约束、验收都清楚的任务输入。**

## 03 · 架构设计

**在写代码前定方案，结合现有项目结构、数据库、接口和兼容性，避免方向错了返工。**

### 什么时候使用

- 涉及多文件或数据结构改动
- 有多种实现路径要取舍
- 改错了要回滚多个文件

### 操作

#### ① 技术方案设计

```text
请基于当前项目产出技术方案和风险清单。本轮只出方案，不要修改代码、不要创建文件。

任务：<一句话>
已有上下文：<涉及模块、调用链、数据表、接口、禁改区，或让 AI 自己读项目补全>

输出：
1. 需求复述（三句话内）
2. 现有结构影响：要改哪些模块、数据库、接口，与现状怎么衔接
3. 本次不做项
4. 方案比较（可选方案，逐项对比改动范围、数据影响、兼容性、回滚成本、验证难度）
5. 推荐方案与理由（业务正确性 → 兼容性 → 改动范围 → 复用 → 可验证）
6. 修改范围三栏：允许修改 / 禁止修改 / 必须保持兼容（落到具体路径）
7. 风险清单：风险 → 触发条件 → 影响 → 处理 → 谁确认
8. 子任务拆解：编号 / 任务 / 文件 / 依赖 / 完成标准 / 验收方式
9. 需我拍板的问题（没有就写「无，可以开始」）

不要编造项目里不存在的组件或服务，无法判断的标「待确认」。
```

---

#### ② 方案评审

```text
请评审下面这份技术方案，本轮只评审，不改方案、不改代码。

<粘贴方案>

检查：
1. 是否考虑了现有项目结构、数据库现状、接口契约和兼容性
2. 修改范围三栏是否落到具体文件、有无越界风险
3. 数据结构变更能否回滚、会不会影响已有数据
4. 风险清单是否每条都有处理动作和确认人
5. 子任务是否可独立验收、完成标准是否可核对
6. 有没有需要人拍板却没列出来的决策

输出：问题清单（带依据）+ 建议调整项 + 结论（可进入开发 / 需修改后再评）。
```

### 完成标准

> **一份结合现状、有范围约束和回滚考虑的方案，以及一份评审问题清单。**

## 04 · 功能开发

**按已确认的方案连续编码，每步守住修改范围，不扩大需求。**

### 什么时候使用

- 方案已定、子任务已拆
- 要让 AI 连续做多个步骤
- 中途可能中断、需要恢复

### 操作

#### ① 功能开发（守范围）

```text
请按已确认的方案开始开发，严格遵守下面的执行规则。

已提供：任务计划、修改范围三栏、不做项、验收标准。

执行规则：
1. 每轮只做一个子任务，按依赖顺序，不跳
2. 严格遵守修改范围，超出范围或要动禁改区 / 依赖 / 公共模块，先停下来说明，不要「顺手改」
3. 每个子任务完成后跑对应的验证命令，原样记录输出
4. 验证通过再进入下一个；失败先说明本轮假设为什么错了，同一错误建议最多试几轮，仍失败就停手标阻塞
5. 到检查点停下来等我确认，不要自行通过
6. 不要自己宣布整个任务完成，最终验收由我判定

如果以上规则可行，从第一个子任务开始。
```

---

#### ② 分阶段实施与进度记录

```text
请按分阶段方式推进，并维护进度状态，方便中断后恢复。

每轮固定动作：
1. 读上一轮进度状态
2. 选下一个待办子任务，标为进行中
3. 只做这一个子任务，跑验证命令并原样记录输出
4. 更新进度：已完成 / 进行中 / 下一轮 / 阻塞原因
5. 验证通过再提交

输出每轮的进度记录。遇到阻塞写清原因和需要我提供什么，不要猜测或跳过。
```

---

#### ③ 中断恢复

```text
我需要恢复一个中断的开发任务。

请先读取：进度记录、当前 git status、最近几条 git log。

然后只做四件事：
1. 复述当前状态：已完成哪些、进行中哪个、下一轮是谁
2. 核对文件状态与进度记录是否一致，不一致的列出来，不自行猜原因
3. 指出遗留问题和未解决的阻塞
4. 等我确认后从下一轮继续

不要重做已完成任务，不要删除已有改动。
```

### 完成标准

> **改动始终在约定范围内、每步有验证证据、中断后能准确接上，不重做不覆盖。**

---

## 05 · 功能审查与完善

**先检查已完成的代码是否符合规范，再决定要不要改——审查阶段不擅自重写。**

### 什么时候使用

- 一个功能或子任务写完
- AI 报告「已完成」，要判断是否真完成
- 想补边界、异常、权限但不确定改哪里

### 操作

#### ① 功能规范审查

```text
请对本次已完成的代码做规范审查。本轮只审查、只输出问题清单，不要修改任何文件，也不要重写代码。

输入：任务验收标准、修改范围与不做项、本轮 diff。

按清单检查，每条给「文件:行号 | 问题 | 依据」：
1. 功能是否符合验收标准、业务规则是否实现完整
2. 边界条件：空值、零值、重复、越权
3. 异常处理与事务边界
4. 接口、字段、数据兼容性
5. 权限与数据范围
6. 测试断言是否被放宽或删除
7. 改动范围：无关格式化、未用 import、调试打印、注释掉的分支、遗留 TODO

最后输出「问题清单」和「需我确认的疑点」两部分。不要写「整体没问题可以合并」这类结论，是否修改由我决定。
```

---

#### ② 问题整改

```text
请针对下面这份审查问题清单做整改，只改清单里的问题，不扩大范围。

问题清单：<粘贴>　修改范围：<粘贴>

要求：
1. 只处理清单里的问题，不顺手重构或加功能
2. 影响正确性 / 安全的优先；属于优化改进的单列出来，等我确认再处理
3. 每改一项跑对应验证，原样记录输出
4. 不删除或放宽现有测试，不硬编码绕过，不吞异常

输出：逐项整改结果 + 验证证据 + 未处理项及原因。
```

### 完成标准

> **一份带行号和依据的审查问题清单，确认后得到只针对问题的整改结果，没有被顺手重写。**

## 06 · 逻辑与 BUG 修复

**处理两类问题——结果与预期不符的逻辑错误，和有报错的 BUG，统一走「先定位根因、再最小修复、最后验证」。**

### 什么时候使用

- 编译失败、单测失败、接口报错
- 功能结果与预期不符
- 改完 A 坏了 B、偶发失败

### 操作

#### ① 业务逻辑修复（结果与预期不符）

```text
请处理一个业务逻辑错误，先定位根因，不要直接改代码。

现象：<期望 vs 实际>
复现步骤：<步骤>
相关改动：<git diff 或提交记录，可让 AI 自己查>

本轮只做：
1. 列事实（只写有证据的：现象、实际 SQL / 参数、配置值）
2. 列几条根因假设，每条写支持和反对的证据
3. 用最小只读动作验证并逐个排除
4. 给出确认的根因（证据不足写「未确认」）、最小修改文件清单、绝对不能改的地方

判断根因的标准：修掉它能解释原始现象。证据不足不要选最像的当结论，不要输出修复代码。等我确认后再修复。
```

---

#### ② BUG 根因分析与修复

```text
请按闭环方式修复一个 BUG。

问题：<现象 + 完整报错原文>
复现步骤：<步骤>
允许修改范围：<文件清单，或让 AI 先给建议>
验证命令：<具体命令>

要求：
1. 先收齐证据：复现步骤、完整堆栈、期望行为、环境、最近改动
2. 先分析根因再改，证据不足标「未确认」，不要猜着改
3. 只改导致根因的那一处，不顺手重构、不格式化、不改无关文件
4. 每轮改完跑验证命令，原样贴出命令和输出关键行
5. 失败先说明假设为什么错了；同一错误建议最多试几轮，仍失败就停手
6. 不删断言、不放宽测试、不硬编码特判、不吞异常、不加数据特判

输出：根因与修复对应关系 + 修改文件 + 每轮命令与输出 + 通过 / 未通过清单 + 未解决问题。
```

---

#### ③ 修复后回归验证

```text
请对本次修复做回归验证，只验证和报告，不改代码。

<粘贴修复内容和验证命令>

输出：
1. 已验证项：命令 + 输出关键行 + 结论
2. 无法验证的项：状态（未验证 / 受限 / 不适用）+ 原因 + 替代检查
3. 回归对照表：场景 | 改前行为 | 改后行为 | 结论，至少包含一条「改前行为保持」的证据

不能执行的测试写清楚原因，不要说成通过；没有输出的「已测试」等于没测试。
```

### 完成标准

> **先确认根因再修复，改动最小且有验证证据，回归能证明「修好了且没改坏别的」。**

## 07 · 代码优化与重构

**改善代码内部结构，不改变外部行为。要改行为就另开任务，不混在重构里。**

### 什么时候使用

- 功能正确但结构混乱、重复多
- 技术债影响后续开发
- 审查发现的改进点

### 操作

#### ① 代码优化

```text
请对下面这段代码做优化，目标是不改变外部行为的前提下改善可读性和结构。

代码：<粘贴代码或文件>

要求：
1. 先列出要补哪些行为测试来锁定当前行为，等我确认后再动手
2. 接口签名、返回结构、数据结构、字段含义、状态流转保持不变
3. 一次只改一个关注点，每步跑测试
4. 不夹带格式化、注释改写、无关调整
5. 不新增依赖，不改业务规则

输出：优化计划 + 行为测试清单 + 每步验证方式。本轮先不要改代码。
```

---

#### ② 重构不改行为

```text
请重构下面这段代码，严格保持外部行为不变。

代码：<粘贴>

必须保持不变：接口 / 返回结构 / 数据结构 / 字段含义 / 状态流转 / 错误码。

要求：
1. 先确认已有行为测试覆盖正常路径和关键边界；不足先补，补完给我确认
2. 小步改，每步跑一次行为测试
3. 不删除或放宽现有测试，不夹带无关改动
4. 不新增依赖，不顺手修业务问题
5. 完成后给出 diff 摘要，说明每处是结构改善还是行为变化——若有行为变化，单独标出并说明

输出：行为测试情况 + 重构步骤 + 验证证据。
```

---

#### ③ 技术债优先级

```text
请评估下面的技术债清单，给出处理优先级。本轮只评估，不改代码。

清单：<粘贴>

按「影响后续开发的程度 × 改动风险」给每项排序，说明：
1. 为什么现在处理 / 为什么可以暂缓
2. 处理前需要什么前置条件（比如先补测试）
3. 大致改动范围

输出：排序表 + 明确列出「暂不处理」的项及原因。不要为了美观把所有债都排进来。
```

### 完成标准

> **有行为测试保护、外部行为不变的重构结果，以及一份有依据的技术债优先级。**

---

## 08 · 代码测试

**设计用例、执行测试、分析真实结果——测试必须有实际执行证据。**

### 什么时候使用

- 功能开发 / 修复 / 重构完成后
- 交付前的必过环节
- 有测试结果但不确定可不可信

### 操作

#### ① 测试用例设计

```text
请为下面的改动设计测试用例。本轮只设计，不执行、不改代码。

改动：<描述或 diff>

要求：
1. 覆盖正常路径、失败路径、边界（空值 / 零值 / 重复 / 越权 / 状态不允许）
2. 断言精确，能区分对错，不写恒真断言
3. 标出每项用什么方式验证（单测 / 集成 / 接口冒烟 / 人工）
4. 标出哪些是「漏了就出事」、建议固化为脚本的检查

输出：用例清单（场景 | 输入 | 预期 | 验证方式）。
```

---

#### ② 测试执行

```text
请执行下面的测试，并原样记录结果。

命令：<粘贴具体命令，或让 AI 根据项目给出>

要求：
1. 按先快后慢顺序：编译 / 类型检查 → 相关单测 → 相关模块 → 接口冒烟 → 全量
2. 原样记录每条命令和关键输出
3. 失败就停下，先说明失败原因，不要擅自改代码让它通过
4. 不要放宽断言、删除用例、改测试数据掩盖问题

输出：命令 + 输出关键行 + 通过 / 失败清单。
```

---

#### ③ 测试结果分析

```text
请分析下面这份测试结果，判断哪些是真的通过。本轮只分析，不改代码。

<粘贴测试命令与输出>

检查：
1. 每条「通过」是否附了实际命令和输出证据
2. 有没有把未跑 / 受限 / 不适用写成通过
3. 断言是否被放宽、用例是否被删、测试数据是否被改得失真
4. 失败项是真问题还是测试本身的问题

输出：可信结果 + 可疑条目（原文 + 为什么可疑 + 需补什么证据）+ 建议动作。
```

### 完成标准

> **设计合理的用例、实际执行有输出证据、结果真实性经过核对，没跑的不算通过。**

## 09 · 交付复用

**交付要让结果可追溯、可接手；验收后判断哪些经验值得留下；同时清理本次开发产生的遗留文件。**

### 什么时候使用

- 任务完成、准备收工
- AI 说「已完成」，要判断是否真完成
- 本次开发产生了临时文件要清理

### 操作

#### ① 交付验收

```text
请对本轮改动做验收自查，不要修改文件，也不要宣布完成。

输入：任务验收标准、修改范围与不做项、本轮 diff、已执行命令与输出。

按四层输出：
1. 功能：逐条对照验收标准，每条给证据或标「缺证据」
2. 兼容：检查 diff / 接口 / 字段 / 上下游，给出「没变 / 已确认兼容 / 需通知下游」
3. 技术：已执行命令与输出关键行，未执行的明确标出、不得写成通过
4. 交付：改动文件清单、遗留问题、是否可接手

另查安全检查（敏感信息、破坏性操作、Git 状态）。
最后输出「可以进入人工验收 / 尚缺以下证据」二选一，不要输出「任务完成」。
```

---

#### ② 开发经验沉淀

```text
请判断本次任务有没有值得沉淀的经验。本轮只判断和建议，不创建文件。

先问三问：还会再出现吗？不沉淀的代价是什么？有没有第二处能验证？任一答不上来，就写「暂不沉淀」并说明留在哪。

三条都成立，按类型给沉淀建议：
- 跨任务约束 → 规则文件
- 踩过的坑 → 项目认知 / known-issues
- 反复出现的做法 → Skill（附稳定步骤和检查点）
- 项目特有事实 → 项目资料

不要沉淀一次性绕法、未验证的做法、业务字段写进 Skill、本次任务写进规则。
```

---

#### ③ 遗留文件清理

```text
请检查本次开发产生的遗留文件，给出清理建议。本轮只列出建议，不要删除任何文件。

检查范围：本次任务涉及的目录；参考本任务的起始提交或时间判断归属。

检查：
1. 临时文件、备份文件（.bak / .tmp / ~ / .orig 等）
2. 一次性调试脚本、临时日志、导出的数据文件
3. git status 里的未提交修改和未跟踪文件
4. 代码里注释掉的旧实现、遗留 TODO

关键约束：
- 只把能明确判断为本次产生的列为可清理
- 未提交 / 未跟踪文件里可能有用户自己的改动，绝不能一律当垃圾——逐项说明「是什么、是否本次产生、建议」
- 无法判断归属的一律标「需我确认」，不要列入自动清理
- 不要执行删除，等我逐项确认

输出：可清理清单（路径 + 依据）+ 需我确认的清单。
```

### 完成标准

> **一份可核对的验收结论、明确的沉淀去向，以及一份区分清楚、需要人确认才删的遗留文件清单。**

## 最后

### 开发中完成

九个阶段走完，至少确认：

- 需求先判可行性、有风险先沟通
- 写代码前有方案，方案定了守范围
- 写完先审查再整改，不擅自重写
- 修复先定位根因，不猜着改
- 测试有实际执行证据，没跑的不算通过
- 遗留文件清理区分归属，需人确认才删
