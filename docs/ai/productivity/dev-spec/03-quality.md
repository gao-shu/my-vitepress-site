# 第三层 · 质量与安全保障

> 确保结果可靠。这一层不是开发结束后才执行的收尾检查，而是从项目准备到最终交付**全程贯穿**的保障机制——每一轮改动都受它约束。

## 为什么贯穿全程

| 阶段 | 第三层在做什么 |
| ---- | -------------- |
| 项目准备 | 确认代码规范、禁改区、构建检查命令、生产资源标记 |
| 需求 / 架构 | 把质量要求写进验收标准和方案，数据变更先想回滚 |
| 开发 | 每轮改动做局部质量 + Git 检查 |
| 审查 / 修复 / 重构 / 测试 | 保证不引入新问题、不改行为、验证有证据 |
| 交付 | 四层验收、diff 全量检查、安全全项、遗留归零 |

六项保障：**代码质量 · 测试验证 · 数据安全 · Git 管理 · 变更控制 · 交付追踪回滚**。

## 1. 代码质量规范

**审查清单**：逻辑与业务规则完整性、边界条件（空值/零值/重复/越权）；异常不被吞、事务边界合理、失败不留半状态；接口/字段/返回结构变化已确认；测试覆盖关键与失败路径、断言没被放宽；改动范围无无关格式化、未用 import、调试打印、注释分支、遗留 TODO；命名分层符合现有风格。

**硬红线**（命中必须处理）：硬编码绕过、吞异常、放宽断言/删用例、给数据加特判、越界改动或触碰禁改区。

让 AI 自查时明确「只输出问题清单和依据，不修改、不宣布通过」，每条指到 `文件:行号`。能脚本化的检查（构建、lint、密钥扫描、禁改区 diff）交给脚本（见第一层 Hooks）。

> 提示词 · 代码质量自查
```text
对本轮改动做质量自查，只输出问题清单，不改文件、不宣布通过。改动：<diff>　约定：范围/禁改区/规范。
逐项查：逻辑与边界、异常与事务、兼容性、测试与断言、改动范围里的调试代码、可读性与重复。
每条给「文件:行号 | 问题 | 依据 | 建议改法」，单独列出硬红线命中项。没问题也逐项写「已检查，无问题」。
```

## 2. 测试与验证规范

**四态纪律**：已验证（实际执行 + 输出证据）、未验证（说明原因 + 替代检查）、受限（环境权限不允许）、不适用（本次不涉及）。**不能执行的测试不得写成通过，没有输出的「已测试」等于没测试。**

| 项 | 合格证据 | 不合格写法 |
| -- | -------- | ---------- |
| 编译 | 命令原文 + 成功输出 | 「编译通过」 |
| 单测 | 命令原文 + 通过/失败数 | 「测试都过了」 |
| 接口冒烟 | 请求与返回原文 | 「接口正常」 |

**回归三层次**：同模块（共用方法/DTO/同张表）、上下游（调用方/消息消费方）、全局（权限/租户/状态机/事务）。做对照表，至少留一条「改前行为保持」的证据——只验证「修好了什么」不验证「没改坏什么」不算完整。

> 提示词 · 验证结果真实性自查
```text
检查这份「已完成」报告里有没有把未验证写成通过，本轮只检查。报告：<粘贴>
检查：1 每条「通过」是否附命令和输出证据 2 是否把未跑/受限/不适用写成通过 3 回归是否含「已修复」和「改前行为保持」4 有无编造的测试输出。
输出可疑条目清单（原文 + 为什么可疑 + 需补什么证据）。
```

## 3. 数据与安全规范

**敏感信息**：密钥、令牌、密码、手机号、身份证号不写进代码/配置/日志/提交信息；`.env`、凭证不进版本库；日志不打印完整请求体、隐私、认证头；提交前跑密钥扫描。

**破坏性操作**（命中即停、需人确认）：删数据、清库、改生产配置、不可逆迁移；脚本写死生产地址或高权限账号；覆盖用户改动、强推、删分支；批量删除或格式化无关目录。能只读不写、能连测试库不连生产、能限定目录不开放全盘。

**输入与权限**：外部入参校验（类型/长度/格式/范围）；越权拦截（数据范围/租户/角色）；文件上传、路径/SQL/命令拼接风险；幂等与重复执行（接口重试、消息重复消费不出错数据）。

**依赖**：不新增来源不明的依赖或脚本，版本锁定，核心依赖需方案确认。

> 提示词 · 交付前安全检查
```text
对本次改动做安全自查，只输出检查结果，不修改。改动：<diff>
四块：1 敏感信息（密钥/隐私/凭证文件/日志打印）2 破坏性操作（删数据/清库/生产配置/写死生产资源）3 输入与权限（入参校验/越权/拼接/幂等）4 依赖（未知依赖/版本锁定）。
每项给「已检查/未检查/不适用」+依据，命中红线的单列并标「需人确认」。
```

## 4. Git 与版本管理

**提交前硬规矩**：

- 先看 `git status`，识别用户已有的改动、未跟踪文件、暂存区内容。
- **不覆盖用户已有改动**：同文件既有用户改动又有 AI 改动时停下说明，不擅自 `checkout --`、`reset --hard`、`stash`、强推或强行合并。
- 判断不了某处改动是谁改的，停下来问，不猜。
- 改动都在允许范围、没碰禁改区和依赖文件；不擅自 push、合并、删分支。

**diff 检查**：无批量格式化无关文件、依赖文件无意外变更、无硬编码/吞异常/放宽断言、无删除或注释掉现有测试、无调试打印/遗留 TODO，提交信息说清「改了什么、为什么」而非「update/fix」。一个提交对应一个能独立验收的子任务。

> 提示词 · 提交前 Git 安全检查
```text
对当前工作区做提交前检查，只输出检查结果，不执行任何 git 写操作（不 add/commit/checkout/reset/stash/push）。
先读 git status、git diff、git diff --cached、最近 log。
检查：1 用户已有改动/未跟踪/暂存内容与本次是否混在一起 2 改动是否在范围、是否触禁改区和依赖 3 diff 里有无硬编码/吞异常/放宽断言/删测试/调试打印/格式化 4 提交信息是否说清改了什么为什么。
输出：可安全提交清单 + 需人确认的冲突疑点 + 建议的提交拆分。不要替我判断性合并。
```

## 5. 变更控制

**修改范围三栏**（每次任务都写，落到具体路径）：

```text
允许修改：<文件路径>
禁止修改：<接口签名 / 历史目录 / 依赖文件>
必须保持兼容：<返回结构 / 状态机规则>
```
AI 说「顺手把…也改了」、开始改依赖或公共模块，立即停。

**检查点**：方案预先约定哪些是检查点（契约冻结后、数据层改完、接口联调前），到点必须停下等人确认，不自行通过。人只回答：选哪个方案、加哪些边界、哪些风险不接受。

**失败分类**：代码错误可重试有限轮次；环境问题标受限写替代检查；认知问题（改 A 坏 B）停手回分析；需求冲突交人确认。不一律重试。

**遗留文件清理**：交付前清理本次产生的临时文件（.bak/.tmp/~）、一次性调试脚本、临时日志、注释掉的旧代码、遗留 TODO、不该进版本库的构建产物。**只删这次任务产生的，判断不了归属就问。**

> 提示词 · 变更范围检查
```text
检查本次改动是否超出约定范围，只输出检查结果，不修改。
三栏（粘贴）：允许修改 / 禁止修改 / 必须保持兼容。当前 status 和 diff（粘贴）。
逐项查：实际改动是否都在允许内、是否触碰禁止、有无意外改动（依赖/公共模块/无关格式化）、必须兼容的内容是否真没变。
输出：合规清单 + 越界项（文件:行号）+ 需人确认疑点。
```

## 6. 交付追踪与回滚

**交付追踪**：报告留痕，最少含任务/级别/范围/不做项执行情况、修改文件（改了什么+为什么）、验证证据（命令+输出）、安全结论、遗留问题（是什么+影响+建议+谁决定）、沉淀去向。遗留必须有去处（建待办/写认知资料/报告留痕有人负责），「下次再说」不算处理。

**回滚方案**：复杂改动（数据结构、接口契约、多文件、迁移）在方案阶段就写好：

| 项 | 内容 |
| -- | ---- |
| 触发条件 | 什么情况必须回滚 |
| 粒度 | 按哪个提交/阶段回退 |
| 数据回滚 | 迁移能否逆执行、数据能否恢复 |
| 兼容兜底 | 新旧能否并存、是否需开关 |
| 回滚后验证 | 回到什么状态算成功 |

出问题先复现固定证据 → 判断前滚修复还是回滚（看改动范围、数据影响、时间成本）→ 按方案执行并保护未涉及改动 → 回滚后验证 → 在报告记录。

> 提示词 · 生成回滚方案
```text
为本次改动生成回滚方案，本轮只输出方案不执行。改动：<描述>　范围：<文件/接口/数据表/迁移>
输出：1 触发条件 2 回滚粒度（列相关提交）3 数据回滚（可逆性/恢复/丢失风险）4 兼容兜底 5 回滚步骤（标出需人确认的操作）6 回滚后验证。
无法回滚的部分明确标出并给替代处理（如只能前滚）。
```

---

## 交付前总检查清单

打钩前逐条核对，任何一条不过就不算完成：

- [ ] **质量**：审查清单逐项过完，硬红线命中为零。
- [ ] **验证**：每条通过都有命令和输出证据，四态分清，回归含「保持」证据。
- [ ] **安全**：敏感信息、破坏性操作、输入权限、依赖四项有明确结论。
- [ ] **Git**：用户已有改动完整保留，无擅自 checkout/reset/stash/push，diff 干净。
- [ ] **变更**：改动都在范围内，检查点未被跳过，遗留文件已清理（无误删用户文件）。
- [ ] **追踪**：报告完整，遗留有去处有人负责，复杂改动有回滚方案。
