# Skills · 专业技能

> 第一层 · 能力底座。解决「重复出现的方法怎么固化下来」——把验证有效的做法写成可调用的技能，让 AI 按固定步骤做，而不是每次重新发明。

## 解决什么问题

- 同类操作做过很多次，每次都要重新讲一遍步骤。
- 好的做法只存在于某次对话里，换个任务就丢了。
- 把一次性 bug 的临时绕法当成通用技能，越攒越脏。
- 技能里混进具体业务字段，污染下一个项目。

## 核心内容

### 什么时候才建 Skill

同时满足这几个条件再建：

1. 同类操作**反复出现**（不是做一次就结束）。
2. 有**稳定的步骤和检查点**，不是靠临场发挥。
3. 至少在**两处任务里验证有效**。

只做了一两次、还没验证有效的做法，先留在交付报告里，不要急着固化。

### Skill 写什么

- 适用场景：什么情况下调用这个技能。
- 前置条件：调用前需要准备什么（上下文、权限、输入）。
- 操作步骤：稳定、可复现的步骤。
- 检查点：每一步怎么判断做对了。
- 失败处理：常见失败和应对。
- 复用记录：日期、项目、结果、据此改了什么。

### Skill 不能写什么

| 不要写 | 原因 |
| ------ | ---- |
| 具体表名、客户名、业务字段 | 这些是项目事实，不是通用方法 |
| 一次性 bug 的临时绕法 | 不具复用价值 |
| 未验证有效的「好方法」 | 会固化错误做法 |
| 完整业务流程 | 属于 Project Context |

一句话：**Skill 存的是「怎么做」，不是「这个项目是什么」。**

### 与 Rules、Agents 的区别

| 机制 | 回答什么 | 归属 |
| ---- | -------- | ---- |
| Rules | 所有任务必须遵守什么 | 跟仓库走 |
| Skills | 重复方法怎么一步步做 | 跟人走，可跨项目 |
| Agents | 谁来做、权限到哪 | 跟仓库或人走 |

## 技能模板

```markdown
# <技能名>

## 适用场景
- 什么情况下调用：
- 不适用：

## 前置条件
- 需要的上下文：
- 需要的输入：

## 操作步骤
1. <步骤> → 检查点：<如何判断做对了>
2. <步骤> → 检查点：<如何判断做对了>
3. ...

## 失败处理
| 失败情况 | 应对 |
| -------- | ---- |

## 复用记录
| 日期 | 项目 | 结果 | 据此改了什么 |
| ---- | ---- | ---- | ------------ |
```

## 可复制提示词

<details>
<summary><strong>把一次成功做法固化为技能</strong></summary>

```text
我想把下面这套做法固化成一个可复用技能。请先评估它值不值得固化，再决定是否产出草稿。

做法记录：
<粘贴这次任务的步骤、检查点、踩过的坑>

请先回答三个问题：
1. 这类操作还会再出现吗？
2. 不固化的代价是什么？
3. 有没有第二个场景能验证它？

如果有任何一条答不上来，直接说明「暂不固化，留在交付报告」，不要产出技能草稿。

如果三条都成立，请产出技能草稿，包含：适用场景、不适用场景、前置条件、带检查点的操作步骤、失败处理表、复用记录表。
约束：只写「怎么做」的通用方法，不要写具体表名、客户名、业务字段。
```

</details>

<details>
<summary><strong>审查已有技能是否被污染</strong></summary>

```text
请检查下面这份技能是否适合跨项目复用，只输出问题清单，不修改内容。

<粘贴技能内容>

检查项：
1. 是否混入了具体表名、客户名、业务字段。
2. 是否混入了一次性 bug 的临时绕法。
3. 是否有未验证就写成通用做法的内容。
4. 步骤是否有明确检查点，还是靠临场发挥。
5. 是否写了复用记录，有没有至少两处验证。

每条问题给出原文片段、问题说明、建议改法。
```

</details>

## 验收要点

- [ ] 同类操作反复出现，且至少两处验证有效。
- [ ] 步骤有明确检查点，不是靠临场发挥。
- [ ] 技能里没有具体表名、客户名、业务字段。
- [ ] 有一次性的失败处理说明。
- [ ] 复用记录里写清了日期、项目、结果、据此改了什么。

技能是资产，不是垃圾桶。宁可少而精，不要多而脏。
