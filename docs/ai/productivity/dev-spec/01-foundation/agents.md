# Agents · 智能体协作

> 第一层 · 能力底座。解决「谁来做什么、权限到哪」——明确执行者、审查者、规划者的边界，让多个 AI 角色协作时不互相覆盖、不自己宣布完成。

## 解决什么问题

- 多开几个 AI 窗口同时改代码，结果互相覆盖。
- AI 既当执行者又当验收人，自己说「做完了」就算通过。
- 派活只给一句话，各角色理解不一致。
- 需求还没定就拆并行角色，越拆越乱。

## 核心内容

### 什么时候需要多个 Agent

多 Agent 不是「多开几个窗口」，只有在任务能切成相对独立的块、每块有明确验收接口时才划算。

**适合拆分**：

- 前后端按冻结的契约并行。
- 彼此不冲突的模块改造。
- 一个执行、一个按清单审查。
- 检索、分析类任务并行收集信息。

**不要拆**：

- 小任务、强耦合的改动。
- 需求还没冻结、上下文不足。
- 同一文件需要多人改。

这时候多 Agent 只会放大沟通成本。

### 三条硬边界

1. **文件所有权**：每个 Agent 明确负责哪些文件、哪些只读，同一文件不同时改。共用文件先约定谁改。
2. **契约先冻结**：接口、数据结构、字段名先定稿再并行；契约一变，所有人重读。
3. **审查者不判定通过**：执行者、审查者、规划者分开；审查者只输出「问题清单和依据」，最终验收由人做，AI 之间不能互相宣布完成。

### 每个角色都要给齐上下文

派给每个 Agent 的都要是同一份完整输入：**任务 + 修改范围 + 不做项 + 验收标准**，不接受「一句话派活」。

### 角色模板

```markdown
# <角色名>·<任务短名>

## 角色定位
- 职责：<规划 / 执行 / 审查>
- 权限：可改 <文件清单>；只读 <文件清单>
- 不做：<明确边界>

## 共同上下文
- 任务：<一句话>
- 修改范围：<允许改什么>
- 禁止修改：<不能碰什么>
- 必须保持兼容：<哪些不能变>
- 验收标准：<怎样算完成>

## 交付物
- <这个角色要输出什么>

## 完成判定
- 由人判定；本角色不宣布通过
```

## 可复制提示词

<details>
<summary><strong>多 Agent 分工（先出方案，不开始改）</strong></summary>

```text
这个任务需要多 Agent 并行。请先给出分工方案，不要开始改代码。

任务：<一句话>
冻结的契约：<接口/数据结构/字段名；若尚无，写「需先冻结」>

要求：
1. 按文件所有权划分，明确每个 Agent 负责哪些文件、哪些只读，确保同一文件不被同时改。
2. 如果契约尚未冻结，先只做契约设计，不要进入并行实现。
3. 每个 Agent 都收到同一份任务、修改范围、不做项和验收标准，不接受一句话派活。
4. 分工里包含执行者、审查者；审查者只输出问题清单和依据，不判定通过。
5. 说明结果如何收拢：各自 diff 越界检查、合并顺序、由谁做最终验收。

先输出分工表和风险点，等我确认后再启动。
```

</details>

<details>
<summary><strong>审查者角色（只报问题，不判通过）</strong></summary>

```text
你现在是审查者，只做审查，不修改任何文件，也不宣布通过。

审查对象：<改动描述 / diff>
任务验收标准：<粘贴>
修改范围与不做项：<粘贴>

请按以下清单输出问题（每条给文件:行号和依据）：
1. 是否超出修改范围、触碰不做项。
2. 业务逻辑和边界条件（空值、越权、重复、并发）。
3. 异常处理与事务边界。
4. 接口、字段、数据兼容性。
5. 测试是否被放宽或删除。
6. 是否留下调试代码、遗留 TODO、无关格式化。

最后输出「问题清单」和「需人确认的疑点」两部分。不要写「整体没问题，可以合并」这类判定结论。
```

</details>

## 验收要点

- [ ] 每个角色职责、权限、不做项写清，文件所有权无重叠。
- [ ] 契约已冻结才并行；未冻结就先做契约设计。
- [ ] 每个 Agent 都收到同一份完整输入，没有一句话派活。
- [ ] 审查者只输出问题清单，没有自行宣布通过。
- [ ] 结果收拢时做了 diff 越界检查，最终验收由人做。

多 Agent 的收益来自「边界清晰」，不是「数量多」。边界没清之前，宁可单 Agent 顺序做。
