# Rules · 项目规则

> 第一层 · 能力底座。解决「AI 如何遵守项目规则」——把跨任务成立、能验证的约束写成 AI 每次都会读到的规则，而不是每次对话反复口头交代。

## 解决什么问题

- 同一个项目，不同对话里 AI 的命名、分层、命令各不相同。
- 口头说过的禁令，换个会话就忘了。
- 规则写成一大篇，AI 记不住也执行不了。
- 把本次任务、临时想法混进规则，越积越乱。

## 核心内容

### Rules 写什么

只写**跨任务成立、能验证**的约束：

- 技术栈与版本。
- 开发、构建、测试命令。
- 命名与分层约定。
- 禁改目录、禁改接口。
- 安全红线（密钥、生产数据、破坏性操作）。
- 跨任务成立的业务约束。

### Rules 不写什么

| 不要写 | 原因 | 该放哪 |
| ------ | ---- | ------ |
| 本次任务、这个需求 | 任务结束就失效 | 任务描述 |
| 完整业务流程 | 太长，稀释关键约束 | Project Context |
| 分阶段操作步骤 | 那是 Skill | Skills |
| 「尽量」「建议」这类软规则 | 无法验证，等于没写 | 删掉 |

### 写作原则

- **可验证**：每条规则都要能说清「怎么算违反了」，最好能配一条命令或 diff 特征。
- **用强措辞**：用「必须 / 禁止」，不用「尽量 / 建议」。
- **禁止项配反例**：写清「曾经或可能出错的写法」，AI 才知道边界在哪。
- **控制篇幅**：全局规则建议控制在几十行内，只留真正高频、高影响的约束。
- **写例外与审批**：需要例外时，由谁确认、记在哪里，要写明。

### 工具适配边界

Rules 的具体文件名和目录（如 AGENTS.md、.cursor/rules 等）因工具而异。本规范只约定「规则该写什么、怎么验证」，具体放哪个文件、如何加载，以你所用工具当前版本官方文档为准。不要把某个工具的目录当成行业规范。

## 规则模板

```markdown
# <规则名> · <适用范围>

## 适用范围
- 生效范围：全局 / 项目 / <目录路径>
- 不适用：<明确写出例外>

## 事实依据
- <来源：项目认知资料第 X 节 / 某次复盘 / 团队约定>

## 必须遵守
| 编号 | 规则 | 验证方式 |
| ---- | ---- | -------- |
| C01 | | <命令或 diff 特征> |

## 明确禁止
| 编号 | 禁止项 | 反例（可能出错的写法） | 验证方式 |
| ---- | ------ | ---------------------- | -------- |
| P01 | | | |

## 例外与审批
- 需要例外时，由 <角色> 确认，并记在 <位置>。

## 变更记录
| 日期 | 改了什么 | 触发原因 |
| ---- | -------- | -------- |
```

## 可复制提示词

<details>
<summary><strong>把约束整理成规则</strong></summary>

```text
请帮我把下面这些项目约定整理成一份 AI 规则文件草稿。本轮只输出草稿，不写入任何文件。

项目约定：
<粘贴现有的口头约定、命令、禁令>

要求：
1. 只保留跨任务成立、能验证的约束；一次性的、业务流程、操作步骤不要放进来。
2. 每条用「必须 / 禁止」，配一条验证方式（命令或 diff 特征）。
3. 禁止项配一条反例，说明可能出错的写法。
4. 规则控制在必要篇幅内，高频高影响的优先。
5. 明确适用范围和例外审批方式。
6. 无法验证的软规则直接删掉，不要保留。

输出：规则草稿 + 被删掉的内容及原因。
```

## 验收要点

- [ ] 规则里没有「本次 / 这个需求 / 先做……再做……」这类任务措辞。
- [ ] 每条规则都能验证，禁止项都配了反例。
- [ ] 没有「尽量 / 建议」这类软规则。
- [ ] 例外与审批方式写明。
- [ ] AI 在新会话里能直接读到并遵守这些规则。

规则的价值在于「每次都生效」，不在于写得多。宁可少而硬，不要多而软。
