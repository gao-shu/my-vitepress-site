# Project Context · 项目上下文

> 第一层 · 能力底座。解决「AI 如何按需拿到准确的项目信息」——不是一次扫描整个仓库生成一堆没人看的文档，而是让 AI 在需要时能查到、查得准、有证据。

## 解决什么问题

- 每次开新对话都要重新解释项目背景。
- AI 扫一遍仓库，上下文被无关代码占满，关键信息反而被稀释。
- AI 靠命名和注释猜业务规则，把推测当成事实。
- 不知道哪些信息该长期保存、哪些该按任务临时提供。

## 核心内容

### 上下文分四层收敛

由外到内，每层有停止条件，能停就停，上一层没完成不进下一层：

| 层次 | 产出 | 可以停的条件 |
| ---- | ---- | ------------ |
| 项目地图 | 模块清单 + 入口 + 构建方式 | 能说出「项目由哪几块组成」 |
| 模块地图 | 本次任务涉及的目录与子模块 | 能指出「改动落在哪个包」 |
| 调用链 | 入口 → 服务 → 数据完整路径 | 能画出「请求经过哪几层」 |
| 相关文件 | 待读待改文件清单（含不改但受影响的） | 每个文件都能说出为何关心 |

**明确跳过**：`node_modules/`、`target/`、`dist/`、`.git/`、依赖目录、生成代码、大体积二进制。

追踪调用链时别只看同步调用，还要覆盖异步任务、消息消费、配置开关、动态 SQL。链条追到数据落点才算完：数据改在哪张表、事务边界在哪、异常最终怎么处理。

### 长期保存 vs 按任务提供

| 信息 | 放哪里 | 例子 |
| ---- | ------ | -------- |
| 跨任务成立、能验证的事实 | 项目资料（README / docs） | 技术栈、模块划分、构建命令、关键字段含义、历史决策 |
| 只有这次才有的信息 | 任务描述里给 | 本次目标、相关文件、验收标准 |
| 踩过的坑 | known-issues / gotchas | 某字段是可用量不是账面量 |
| 推测或未确认的信息 | 待确认清单 | 代码里查不到、需要人补充的 |

一句话：**能被证据验证且反复用到的，才沉淀；一次性的，留在任务里。**

### 项目资料最小集

```text
项目根目录/
├── README.md                 # 项目是什么、怎么跑
├── AGENTS.md                 # 项目级 AI 开发约定（按需）
├── docs/
│   ├── project-overview.md   # 模块、技术栈、关键设计
│   └── known-issues.md       # 已知问题与坑
```

已有文档能承担职责就复用，不要为了目录看起来完整而创建空文件。

### 结论要标状态

每条认知结论标注来源和状态：

- **已确认**：有代码、配置或文档证据。
- **待确认**：现有资料查不到。
- **人工补充**：需要项目维护者提供。

不要把「应该是」「一般是」写进正文。gotchas 由人写，不让 AI 代笔。

## 可复制提示词

<details>
<summary><strong>项目地图（只读，不改文件）</strong></summary>

```text
你的任务只有一个：产出一份项目地图。不要修改任何文件，不要提改进建议。

背景：我需要了解一个已有项目的整体结构，还没有开始任何开发。
目标：让我能回答「这个项目由哪几块组成、从哪里进入、怎么构建」。

约束：
- 只读分析，不修改任何文件。
- 跳过 node_modules、target、dist、build、.git、vendor、依赖和生成目录。
- 优先读依赖与构建文件、README、启动入口、前端入口、配置和目录结构。
- 不逐个文件通读；结论带证据路径，推断单独放进「待确认」。

请输出：
1. 项目类型与技术栈
2. 模块清单（模块 → 职责一句话 → 入口文件路径）
3. 入口清单（启动类、前端入口、可执行脚本）
4. 目录结构概览（只列到有业务含义的那一层）
5. 构建、启动、测试命令（附来源文件）
6. 配置文件清单（路径 → 管什么）
7. 外部依赖（数据库、缓存、消息队列、第三方接口）
8. 本轮未覆盖范围
```

</details>

<details>
<summary><strong>调用链追踪（追到数据落点）</strong></summary>

```text
你的任务只有一个：追踪一条完整调用链，输出链路和数据流。不要修改任何文件。

入口：<接口描述，如 POST /api/mes/work-orders/{id}/report，或前端某提交按钮>

约束：
- 从入口追到数据落点，中间不要停。
- 必须覆盖并说明：同步调用、异步任务、消息消费、配置开关、动态 SQL。
- 每步给出「文件路径:行号」和「方法名」。
- 找出事务边界和异常处理位置，指出这条链读写的表。
- 没找到的环节明确标「未找到」，不要跳过不提。
- 数据库结构以迁移脚本或实际库为准，不只凭实体类。

请输出：
1. 调用链总览（一行一步）
2. 逐层明细（层 | 文件:行号 | 方法 | 职责 | 数据变化）
3. 涉及的数据表（表名 | 读/写 | 关键字段）
4. 事务边界与异常处理
5. 隐藏路径（异步 / 消息 / 定时 / 动态 SQL）
6. 这条链上最容易出问题的几处及原因
```

</details>

<details>
<summary><strong>老项目接管（只读接入报告）</strong></summary>

```text
你现在需要接管一个已有项目。本轮只读分析，理解现状，建立后续开发所需的上下文。

暂时不要修改任何业务代码、不要重构、不要安装新依赖。

按顺序检查：
1. 技术栈及版本、前后端架构、模块划分、目录结构、主要依赖。
2. 如何启动、构建、测试，是否有数据库、Docker 等运行环境。
3. 核心业务模块、模块间调用、关键接口、重要数据实体、第三方集成。
4. 已有规则文件和项目代码规范。
5. 哪些模块不能随意改、哪些操作会影响生产数据、已知问题、代码里查不到的信息。

输出项目接入报告，每项信息标注：已确认（有证据）/ 待确认 / 人工补充。
最后说明：是否具备开发条件，还缺什么信息，哪些建议写入规则，哪些等具体任务再分析。
```

</details>

## 验收要点

- [ ] 每条认知结论都有来源，推测都在「待确认」里。
- [ ] 明确写出「未覆盖范围」。
- [ ] 能回答五问：改哪几个文件、谁受影响、涉及哪张表哪个接口、现有实现为什么这么写、哪些地方不能碰。
- [ ] 新项目命令已实际跑通；老项目确认没有架构级改动，diff 只有文档。
- [ ] 没有创建无意义的空文档。

五问里若有两条答不上来，回到对应层补，不要带着缺口改代码。
