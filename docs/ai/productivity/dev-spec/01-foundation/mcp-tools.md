# MCP / Tools · 工具与外部能力

> 第一层 · 能力底座。解决「AI 如何安全地连接仓库外的能力」——数据库、浏览器、外部 API、设计工具等，通过 MCP 或工具接入，但接入前要过必要性和边界检查。

## 解决什么问题

- 为了「看起来专业」接一堆用不上的工具，增加维护成本。
- 工具权限过大，AI 能读生产数据、能执行不可逆操作。
- 工具不可用时整个流程卡死，没有降级方案。
- 说不清某个工具到底给 AI 开放了什么能力。

## 核心内容

### MCP 解决什么

MCP（Model Context Protocol）让 AI 连接**仓库外的能力或数据**：数据库、文件系统、浏览器、第三方 API、设计工具等。它补齐的是「AI 靠读代码拿不到的信息」和「AI 光靠写代码做不了的动作」。

不是所有能力都要 MCP。能用文件、命令、脚本解决的，优先用更简单的方式。

### 接入前三问

| 检查 | 要回答什么 |
| ---- | ---------- |
| 必要性 | 这个能力是不是仓库内拿不到、又确实完成任务必须要的？ |
| 边界 | 它开放了什么权限？只读还是可写？能碰到生产环境吗？ |
| 降级 | 它不可用时怎么办？有没有替代检查或手动方案？ |

三条有一条答不上来，先不接。

### 权限最小化

- 能只读就不要可写。
- 能连测试库就不要连生产库。
- 能限定目录就不要开放整个文件系统。
- 涉及删除、写入、发送的动作，接入时就明确「需要人确认」。

### 记录能力清单

接了哪些工具、各自开放什么、谁配置、怎么降级，记在项目的工具说明里。避免「某次对话接过，后来没人知道」。

## 接入评估模板

```markdown
# <工具/MCP 名> 接入评估

## 必要性
- 解决什么问题：
- 为什么仓库内方式不够：

## 边界
- 开放的能力：
- 权限级别：只读 / 可写
- 访问范围：<库 / 目录 / 环境>
- 是否触及生产：<是 / 否>

## 降级
- 不可用时怎么办：
- 替代检查或手动方案：

## 确认
- 由谁配置：
- 哪些动作需要人确认：
```

## 可复制提示词

<details>
<summary><strong>评估是否要接入某个工具</strong></summary>

```text
我需要评估是否接入下面这个工具/MCP，请帮我做接入评估，本轮只输出评估，不做配置。

工具名：<名称>
想解决的场景：<要完成什么>
当前卡点：<为什么现在做不了>

请按三问评估：
1. 必要性：这个能力是不是仓库内拿不到、又确实完成场景必须要的？有没有更简单的替代？
2. 边界：它开放什么权限？只读还是可写？能碰到生产环境或敏感数据吗？
3. 降级：它不可用时怎么办？有没有替代检查或手动方案？

然后给出：权限最小化建议、哪些动作必须人确认、是否建议接入（建议 / 暂缓 / 不建议）及理由。
三问有答不上来的，直接标「待确认」，不要替我假设。
```

</details>

<details>
<summary><strong>梳理已有工具的能力边界</strong></summary>

```text
请梳理当前项目已接入的 AI 工具/MCP，输出一份能力边界清单。本轮只读分析，不修改配置。

对每个工具列出：
1. 开放了什么能力。
2. 权限级别（只读 / 可写）和访问范围。
3. 是否触及生产环境或敏感数据。
4. 哪些动作需要人确认。
5. 不可用的降级方案。

最后标出风险项：权限过大、触及生产、无降级方案的工具。
```

</details>

## 验收要点

- [ ] 每个工具都回答了必要性、边界、降级三问。
- [ ] 权限最小化：只读优先、不碰生产、范围受限。
- [ ] 删除、写入、发送等动作明确需要人确认。
- [ ] 工具不可用时能降级，不会整体卡死。
- [ ] 能力清单已记录，团队/后续会话能查到。

工具是手段，不是目的。接之前先问「没有它到底行不行」。
