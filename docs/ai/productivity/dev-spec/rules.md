# 通用项目 Rules · v1.0

> 一套可复用到 Java、Vue、MES、ERP、WMS、AI 企业应用等项目的通用 Rules 基础规范。它不是一条庞大的规则，而是一个规则集合：项目初始化时按实际情况选用，不适用的不必强行保留。

**定位：** 约束 AI Agent 在项目开发中的行为，明确技术边界、代码规范、数据安全和操作要求。

## 一、Rules 目录建议

```text
项目根目录/
├── AGENTS.md
├── .cursor/
│   └── rules/
│       ├── 01-project-boundaries.mdc
│       ├── 02-architecture.mdc
│       ├── 03-coding-standards.mdc
│       ├── 04-database.mdc
│       ├── 05-api-contracts.mdc
│       ├── 06-security.mdc
│       ├── 07-testing.mdc
│       └── 08-change-control.mdc
```

这里使用 Cursor Rules 的文件格式作为示例。其他 AI 工具应转换成各自支持的格式，不要直接照搬目录和扩展名。

## 二、通用 Rules 正文

下面是建议作为基础规则的内容。

### 01 · 项目边界规则

基础必备

**目的：防止 Agent 擅自改变项目现有技术方案、业务逻辑和修改范围。**

```text
1. 必须优先理解项目现有实现，不得在不了解现状时直接重构。
2. 必须遵循项目已确认的技术选型，不得擅自更换框架、组件或基础设施。
3. 不得擅自引入新的依赖、工具或第三方服务。
4. 修改范围必须与当前任务直接相关，不得随意修改无关文件。
5. 不得擅自删除已有功能、接口、字段或业务逻辑。
6. 发现现有设计存在问题时，应先分析影响范围，再提出调整建议。
7. 需求不明确、业务规则缺失或存在重大方案分歧时，必须先向用户确认。
8. 不得将推测的业务规则当作已经确认的项目事实。
```

### 02 · 架构与模块边界规则

**目的：保证项目架构一致，防止模块职责混乱和不合理耦合。**

```text
1. 必须遵循项目现有架构和模块职责划分。
2. 不得绕过既定模块边界直接访问其他模块内部实现。
3. 模块之间的交互必须遵循项目已有接口和依赖约定。
4. 不得随意增加跨模块依赖或形成循环依赖。
5. 公共组件、基础设施和核心业务模块的修改必须评估影响范围。
6. 不得为了少量代码复用而引入过度抽象。
7. 新增功能应优先复用现有架构和公共能力。
8. 涉及架构调整时，必须明确调整原因、影响范围和兼容性。
```

### 03 · 编码规范规则

**目的：保证代码可读、可维护，并与现有项目风格一致。**

```text
1. 必须遵循项目现有命名规范、目录结构和代码风格。
2. 新增代码必须保持职责清晰，避免单个类、函数或模块承担过多职责。
3. 不得重复实现项目中已经存在的公共能力。
4. 不得保留无用代码、无意义注释、调试代码和临时实现。
5. 不得使用空异常捕获、无意义默认值或静默忽略错误的方式掩盖问题。
6. 异常处理必须明确，不能随意吞掉异常信息。
7. 不得通过硬编码敏感信息、环境配置或易变业务参数解决问题。
8. 注释应解释必要的业务规则、复杂逻辑和设计原因，不重复描述代码本身。
9. 不得为了形式上的代码整洁而擅自扩大重构范围。
```

### 04 · 数据库与数据操作规则

基础必备

**目的：保护数据完整性，避免不安全的数据操作。**

```text
1. 必须遵循项目现有数据库类型、命名规范和数据访问方式。
2. 不得擅自修改已有表结构、字段类型、索引或约束。
3. 数据库结构变更必须提供对应的 SQL、迁移脚本或项目规定的变更交付物。
4. 不得在未经确认的情况下执行生产环境数据修改、删除或清理操作。
5. 涉及批量更新、批量删除和数据迁移时，必须评估影响范围。
6. 涉及事务的业务操作必须遵循项目事务管理约定。
7. 不得绕过项目既定的数据访问层和业务校验机制。
8. 必须关注数据一致性、唯一性、关联关系和并发问题。
9. 不得在代码、日志或提交文件中暴露真实敏感数据。
```

### 05 · 接口与数据交互规则

**目的：保证接口契约稳定，避免前后端及模块之间的数据交互不一致。**

```text
1. 必须遵循项目现有接口命名、请求方式和数据结构规范。
2. 不得擅自修改已有接口的请求参数、响应结构和字段含义。
3. 接口变更必须检查调用方及关联模块的兼容性。
4. 必须明确必要的参数校验、异常处理和错误返回。
5. 不得将数据库实体直接暴露给外部接口，除非项目明确采用该设计。
6. 前后端必须遵循统一的数据类型、字段命名和状态约定。
7. 不得使用未经确认的模拟数据代替真实业务数据。
8. 涉及公共接口时，必须考虑已有调用方的兼容性。
```

### 06 · 安全规则

基础必备

**目的：防止敏感信息泄露、越权操作和不安全的代码实现。**

```text
1. 禁止在代码仓库中提交密码、密钥、访问令牌和其他敏感凭证。
2. 敏感配置必须通过项目规定的安全配置方式管理。
3. 必须关注身份认证、权限校验和数据访问控制。
4. 不得仅依赖前端权限控制保护后端接口。
5. 涉及用户输入时，必须关注 SQL 注入、脚本注入和非法参数风险。
6. 不得绕过项目已有的认证、授权和审计机制。
7. 不得将敏感业务数据、用户隐私或凭证写入普通日志。
8. 执行外部命令、文件操作和网络请求时，必须考虑输入校验及操作范围。
9. 未经授权，不得访问、导出或传播项目中的敏感数据。
```

### 07 · 测试与质量规则

**目的：确保代码修改经过必要验证，而不是仅仅完成代码编写。**

```text
1. 新增或修改功能必须根据影响范围执行相应测试。
2. 修改已有功能时，必须关注相关功能是否受到影响。
3. 修复缺陷时，优先补充能够覆盖问题的测试。
4. 不得通过删除测试、跳过断言或修改测试预期来掩盖问题。
5. 测试失败时，必须分析原因并如实报告。
6. 不得将未执行的测试标记为通过。
7. 不得将编译成功等同于功能正确。
8. 对核心业务逻辑、异常场景和边界条件应进行必要验证。
9. 不得隐瞒已知缺陷、测试失败和未完成事项。
```

### 08 · 变更与操作控制规则

**目的：保护用户已有工作，避免未经授权的修改和不可逆操作。**

```text
1. 修改前必须检查当前工作区状态。
2. 不得擅自覆盖、删除或回滚用户已有修改。
3. 不得擅自执行 Git reset --hard、强制推送等高风险操作。
4. 不得擅自删除分支、提交历史或其他任务的工作成果。
5. 不得擅自执行生产环境部署、数据清理和不可逆操作。
6. 涉及批量文件修改时，必须确认修改范围。
7. 不得擅自修改与当前任务无关的环境配置。
8. Git 提交必须遵循项目提交约定，未经用户要求不得擅自推送远程。
9. 完成任务后，应能够说明实际修改内容和变更范围。
```

## 三、通用 Rules 应该如何使用？

不是每个项目都必须完整采用八类规则。

我建议分成两档：

| 类型 | 规则 | 建议 |
| --- | --- | --- |
| 核心基础规则 | 项目边界、数据库、安全、变更控制 | 所有项目优先建立 |
| 按需规则 | 架构、编码、接口、测试 | 根据项目技术和业务特点完善 |

## 四、Rules 与 AGENTS.md、Skills 的最终关系

**AGENTS.md**

项目入口：说明项目情况、协作约定和规则索引。

**Rules**

行为约束：规定必须遵守什么、禁止做什么。

**Skills**

执行方法：告诉 Agent 一项具体工作应该怎么做。

例如：

- Rule：未经授权禁止修改生产数据库。
- Skill：数据库结构变更与迁移流程。
- AGENTS.md：告诉 Agent 数据库规则和迁移 Skill 分别在哪里。

## 五、我的几个重要建议

这份通用 Rules 还需要注意三个问题：

1. **不要把所有规则都设为全局强制。** 有些项目不涉及数据库，有些项目不需要前后端分离，应该按适用范围加载。
2. **不要为了规则数量而增加规则。** 一条规则能够明确约束，就不必拆成五条相似规则。
3. **规则必须与工具加载机制匹配。** 文件写得再完整，如果 Agent 实际没有加载，也没有意义。

我的建议是先把这八类作为通用规则库，而不是要求每个项目原样复制八份。实际初始化时，先检查项目现状，选择适用规则，再补充项目特有约束。

这样才是真正能长期复用的 Rules 体系。
