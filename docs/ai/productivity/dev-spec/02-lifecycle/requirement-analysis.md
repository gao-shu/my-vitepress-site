# 02 需求分析

> 第二层 · 开发生命周期。解决「如何用尽可能少的文字，把任务准确交给 AI」——沿用背景、目标、约束、输出格式四段式，补上任务分级、验收标准、阻塞问题处理。

## 什么时候用

任何开发任务开始前。简单任务一句话加必要限制就够；复杂任务才补业务背景、流程和验收条件。

**不是输入越详细越好，而是影响正确性的信息不能缺。** 能从项目里查到的，不让用户重复写。

## 操作步骤

### 任务输入结构

| 部分 | 要回答什么 | 是否必填 |
| ---- | ---------- | -------- |
| 背景 | 当前情况是什么 | 视任务而定 |
| 目标 | 具体要实现什么 | 必填 |
| 约束 | 哪些能改、哪些不能改 | 必填，至少说清关键边界 |
| 输出格式 | 最终交付什么 | 必填，默认输出执行结果 |
| 任务分级 | 需要多大程度的分析和验证 | 让 AI 先判断 |
| 验收标准 | 怎样才算完成 | 必填，简单任务可简写 |

### 任务分级

| 级别 | 特征 | 执行方式 |
| ---- | ---- | -------- |
| L1 简单 | 范围明确、影响小 | 直接实施 + 局部检查 |
| L2 普通 | 多文件、有业务逻辑 | 先分析影响 + 简要方案 |
| L3 复杂 | 多模块、核心业务、数据结构、系统集成、高风险 | 完整分析 + 分阶段执行 |

判断时看：修改范围、业务复杂度、数据影响、接口兼容性、回归风险、是否不可逆。**改错了要回滚多个文件，就按 L3 走**；改动一行代码但涉及订单状态、库存、资金，也可能是 L3。

### 让 AI 主动发现缺失信息

把信息分三类，不要让用户事先想全：

| 类型 | 处理方式 |
| ---- | -------- |
| 已确认 | 用户说明或代码资料能验证，直接采用 |
| 可推断 | 查证据后采用，不凭猜测 |
| 待确认 | 资料查不到且会影响结果，集中提问 |

- 能从项目里确认的，不问用户。
- 不影响正确性的细节，按项目现有规范处理。
- 涉及业务规则、数据一致性、权限、安全、不可逆操作的，不能猜。
- 所有阻塞问题一次性提出；没有阻塞就直接执行，不逐步问「要不要继续」。

### 明确验收标准

验收标准要写成能核对的：功能行为、数据正确性、接口兼容性、测试要求。简单任务可简写成一句话，复杂任务逐条列。

**「完成开发」不算验收标准**，要写成具体命令、diff 特征或页面行为。

## 可复制提示词

<details>
<summary><strong>最小任务输入（日常最常用）</strong></summary>

```text
任务：<一句话说明要做什么>
目标：<预期结果>
约束：<允许改什么、不能改什么、必须保持兼容什么>
验收：<怎样算完成>

请先检查项目现状，从代码和文档补全必要上下文，不要让我重复写能从项目里查到的信息。
把缺失信息分成「已确认 / 可推断 / 待确认」：能从项目确认的不问我；不影响正确性的细节按项目规范处理；涉及业务规则、数据一致性、权限、安全或不可逆操作的，不能猜。
所有真正阻塞的问题一次性提出；没有阻塞就直接分析并执行，不要每个小步骤都问我。
严格遵守修改范围，完成后执行必要的编译、测试和回归检查，给出修改内容、验证证据和遗留风险。
```

</details>

<details>
<summary><strong>复杂任务输入</strong></summary>

```text
【任务】本次要完成的具体事项。
【背景】当前业务情况、已有功能、为什么这次调整。
【目标】要实现的功能、要解决的问题、预期效果。
【约束】允许修改范围 / 不允许修改范围 / 必须保持兼容 / 技术或业务限制。
【验收标准】功能行为 / 数据正确性 / 接口兼容性 / 测试要求。
【交付要求】完成代码修改；执行必要的编译和测试；说明修改文件、实现结果和验证证据；汇总未解决问题和风险。

先分析任务，识别必要信息和潜在风险，再制定执行方案。
不要为了补充无关信息反复提问；不要自行编造项目里不存在的规则。
```

</details>

<details>
<summary><strong>集中提问规则</strong></summary>

```text
在执行任务前，请先检查现有代码、项目文档和相关业务实现。

缺失信息处理规则：
1. 能从现有项目确认的，不要问我。
2. 可以通过安全检查验证的，先自行检查。
3. 不影响业务正确性的细节，按项目现有规范处理。
4. 涉及业务规则、数据一致性、权限、安全、不可逆操作、兼容性的重要问题，不能自行猜测。
5. 把所有真正阻塞的问题集中整理，一次性提问。
6. 没有阻塞问题就直接制定方案并执行，不要逐步问我是否继续。

非阻塞风险记录并说明处理依据，不要因此中断任务。
```

</details>

## 验收要点

- [ ] 需求已复述，模糊点已澄清或标注。
- [ ] 至少写出了本次不做项和关键边界。
- [ ] 验收标准可核对，不是「完成开发」。
- [ ] 阻塞问题已集中提出并得到答案，或确认无阻塞。
- [ ] 没有把推测写成已确认的业务规则。
- [ ] 任务分级合理，简单任务没有被复杂化。
