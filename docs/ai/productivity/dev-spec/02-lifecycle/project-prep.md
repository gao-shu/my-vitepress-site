# 01 项目准备

> 第二层 · 开发生命周期的起点。让 AI 先懂项目、定边界，准备到「能说清改哪里、影响谁、不能碰什么」就够了，不要先建一堆文档。

## 什么时候用

| 情况 | 怎么做 |
| ---- | ------ |
| 全新项目，还没开始写 | 先定边界，再让 AI 写代码 |
| 已有脚手架，尚未正式开发 | 检查现状，补项目约定 |
| 接手别人的项目 | 只读理解，建立最小上下文 |
| AI 经常理解错、改错地方 | 补上下文和规则，不必重做接入 |
| 改文案、小调整 | 跳过，直接派活 |

准备深度由任务决定：简单修改看当前文件即可；小 Bug 要一条调用链 + 复现条件；普通功能要模块地图 + 影响范围；复杂功能或老项目才做完整接入。

## 操作步骤

### 新项目：先定边界

1. 说清项目目标、用户和核心功能。
2. 检查已有文件，确认技术栈与运行环境，不覆盖已有内容。
3. 定下开发、构建、测试命令，并实际跑通一次。
4. 定代码规范、命名分层和禁改边界。
5. 只创建当前阶段需要的规则和资料（见第一层 [Project Context](/ai/productivity/dev-spec/01-foundation/project-context)、[Rules](/ai/productivity/dev-spec/01-foundation/rules)）。

**边界 → 结构 → 代码**。顺序反了，AI 会用「它认为合理」的结构替你做架构决策，而那个决策只活在那轮对话里。

### 老项目：先理解现状

按几块看，边看边记来源：结构与技术栈、启动构建测试方式、核心业务模块与调用、关键接口与数据实体、已有规则与规范、已知问题与风险、与当前任务相关的代码位置。

汇成一份简短的接入报告，每条标「已确认 / 待确认 / 人工补充」（详见 [Project Context](/ai/productivity/dev-spec/01-foundation/project-context)）。

保护边界（突破前要说明原因并取得同意）：

- 不擅自重构架构、改接口签名、升级依赖版本。
- 不批量格式化无关文件。
- 不把推测出来的业务规则当成真实规则。
- 不删已有功能，不改生产数据或执行不可逆操作。

### 什么时候可以开始开发

1. 知道项目是什么。
2. 知道怎么启动、编译、测试。
3. 知道开发要遵守哪些规则。
4. 当前任务相关信息能继续获取。
5. 未确认的信息已明确标注。

不需要等整个项目完全理解。新功能只需在开始该任务前补对应业务上下文。

## 可复制提示词

<details>
<summary><strong>新项目初始化</strong></summary>

```text
现在准备开始一个新项目，请协助初始化，但暂时不要大规模编写业务代码。

第一步：确认项目要解决什么问题、主要用户是谁、核心功能、技术选型和开发约束。信息够就不要重复问，有关键缺失一次性列出。
第二步：检查当前目录，看是否已有项目文件、脚手架、Git 仓库、规则文件、必要依赖。不要覆盖或删除已有内容。
第三步：提出初始化方案，包括推荐目录结构、技术栈与依赖、开发/构建/测试命令、必要项目规则、当前阶段要创建的文件。
第四步：只创建当前真正需要的内容，不预建大量空文档，不为使用 Agent、Skill、MCP 强行加配置。
第五步：在我确认后再执行初始化和环境检查。

报告已完成的初始化内容、目录结构、技术栈、开发测试命令、未解决问题和下一步建议。
不要把未确认的技术选型写成既定事实，不要执行未经确认的高风险操作。
```

</details>

<details>
<summary><strong>老项目接管</strong></summary>

```text
你现在需要接管一个已有项目。本轮只读分析，建立后续开发所需的上下文。
暂时不要修改任何业务代码、不要重构、不要安装新依赖。

按顺序检查：技术栈及版本、前后端架构、模块划分、目录结构；如何启动构建测试、是否有数据库和 Docker；核心业务模块、模块间调用、关键接口、重要数据实体、第三方集成；已有规则文件和代码规范；哪些模块不能随意改、哪些操作影响生产数据、已知问题、代码里查不到的信息。

输出项目接入报告，每项标注：已确认（有证据）/ 待确认 / 人工补充。
约束：不扫依赖和生成目录，不逐个文件通读，不把猜测当事实，项目较大时先给整体地图再深入重要模块。
最后说明：是否具备开发条件，开始新功能还缺什么信息，哪些建议写入规则。
```

</details>

## 验收要点

- [ ] 新项目命令已实际跑通；老项目有带来源的接入报告。
- [ ] 五问能答上：改哪几个文件、谁受影响、涉及哪张表哪个接口、现有实现为什么这么写、哪些地方不能碰。
- [ ] 禁改区和安全边界写明，并同步进规则。
- [ ] 推测都在「待确认」里，没有「应该是 / 一般是」。
- [ ] 没有架构级改动，没有无意义的空文档。
