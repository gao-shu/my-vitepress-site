# 07 代码优化与重构

> 第二层 · 开发生命周期。解决「怎么改善代码而不改变行为」——先补行为测试再动实现，接口和数据结构保持兼容，避免以重构之名引入新 BUG。

## 什么时候用

- 代码可读性差、重复多、职责混乱，但功能正确。
- 技术债积累到影响后续开发。
- 审查发现改进点，但不属于正确性 BUG。

**重构不是加功能，也不是修 BUG。** 目标是改善内部结构，外部行为不变。如果同时要改行为，先拆成两步：先重构（行为不变），再改行为。

## 操作步骤

### 重构前：先补行为测试

对要重构的部分，先补一组能覆盖当前行为的测试（正常路径 + 关键边界）。没有测试保护的重构等于盲改。

明确要保持不变的东西：

- 接口签名与返回结构。
- 数据结构与字段含义。
- 状态机流转规则。
- 对外可见的行为（排序、错误码、时序）。

### 重构中：小步、可回退

- 一次只改一个关注点，不做「大爆炸式」重写。
- 每步跑一次行为测试，确认没变。
- 不夹带格式化和无关改动，diff 要能看清语义变化。
- 依赖方向保持清晰，不引入新的循环依赖。
- 不新增依赖，除非方案已确认。

### 重构后：对照与清理

- 行为测试全绿。
- 接口契约比对无变化。
- diff 检查没有顺手改业务规则。
- 遗留文件清理：删掉重构产生的临时文件、无用注释、废弃代码（见第三层 [变更控制](/ai/productivity/dev-spec/03-quality/change-control)）。

### 技术债排序

不是所有技术债都值得现在还。按「影响后续开发的程度 × 改动风险」排序：经常改动又难懂的优先，稳定不动的可以暂缓。不为了美观重构冷门模块。

## 可复制提示词

<details>
<summary><strong>重构但不改行为</strong></summary>

```text
请对下面这段代码做重构，目标是改善内部结构，不改变任何外部行为。

代码：<粘贴代码或文件>

约束：
1. 接口签名、返回结构、数据结构、字段含义、状态流转全部保持不变。
2. 先列出你会补哪些行为测试来锁定当前行为，等我确认后再动手。
3. 一次只改一个关注点，每步跑一次测试。
4. 不夹带格式化、注释改写、无关调整。
5. 不新增依赖，不改业务规则。

输出：重构计划 + 要补的行为测试清单 + 每步的验证方式。本轮先不要改代码。
```

</details>

<details>
<summary><strong>技术债重构优先级</strong></summary>

```text
请评估下面这份技术债清单，给出重构优先级。本轮只评估，不改代码。

技术债清单：<粘贴>

按两个维度给每项打分：
1. 影响：是否经常改动、是否阻碍新功能、是否容易引发 BUG。
2. 风险：改动范围、是否有测试保护、是否触及核心业务。

输出按「影响高、风险低」优先排序的表，每项给：优先级、理由、建议的重构范围、前置条件（比如先补哪些测试）。
明确列出「暂不处理」的项及原因，不要为了美观把所有债都排进来。
```

</details>

## 验收要点

- [ ] 重构前有行为测试锁定当前行为。
- [ ] 接口、数据结构、状态流转保持不变。
- [ ] 每小步跑测试，diff 能看清语义变化。
- [ ] 没有夹带格式化和业务规则改动。
- [ ] 遗留文件已清理，技术债排序有依据。

重构完成进入 [08 代码测试](/ai/productivity/dev-spec/02-lifecycle/testing) 做完整验证。
