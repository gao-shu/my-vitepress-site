# 04 功能开发

> 第二层 · 开发生命周期。解决「让 AI 连续编码而不是每步都等确认」——用计划、状态、检查点支撑连续执行，人只在关键决策点拍板。

## 什么时候用

方案已定、子任务已拆解，进入实际编码。L1 简单任务可直接做；L2/L3 按连续执行机制推进。

## 操作步骤

### 连续执行靠三样东西

| 文件 | 内容 | 什么时候读 |
| ---- | ---- | ---------- |
| `TASK-PLAN.md` | 子任务、依赖、完成标准、不做项、停止条件 | 每轮开始 |
| `PROGRESS.md` | 每轮做了什么、命令输出、失败记录、下一步 | 每轮开始、恢复会话时 |
| `DECISIONS.md`（可选） | 执行中的小决定及依据 | 有争议时回查 |

状态用五种：`pending → in_progress → done / blocked / skipped`。`done` 要有证据；`blocked` 要写明原因和需要谁提供什么。

### 每轮固定动作

```text
1. 读状态    读 TASK-PLAN.md 和 PROGRESS.md 末尾
2. 选任务    按依赖顺序选下一个 pending，标 in_progress
3. 执行      只做这一个子任务，遵守范围与不做项
4. 验证      跑该任务完成标准对应的命令，记录输出
5. 记录      写 PROGRESS.md，更新状态
6. 提交      验证通过再提交，进入下一轮
```

### 人必须在场的情况

- 业务规则有多种合理解释。
- 涉及权限、支付、资金、库存，或要删数据、改生产配置、执行不可逆操作。
- 要改接口签名、新增核心依赖、升级框架。
- 要动禁改区或没有测试覆盖的老代码。
- 到达方案里约定的检查点。

确认时只需回答三件事：选哪个方案、加哪些边界、哪些风险不接受。不替 AI 写代码。

### 立即停手的信号

AI 说「顺手把……也改了」、开始改依赖文件或公共模块、同一问题出现多种解释、重复问已回答的问题、完成标准被悄悄放宽。

**失败先分类，不要一律重试**：代码错误可重试有限轮次；环境问题标 blocked；认知问题（改 A 坏 B）停手回分析；需求冲突交人确认。详见 [06 逻辑与 BUG 修复](/ai/productivity/dev-spec/02-lifecycle/bugfix)。

### 中断恢复

让 AI 读 `PROGRESS.md` 末尾状态接上，不要重做已完成的子任务，不要删已有改动。

## 可复制提示词

<details>
<summary><strong>启动连续执行</strong></summary>

```text
接下来的任务按连续执行方式推进。本轮先不要写代码，只确认执行规则。

已提供：TASK-PLAN.md、PROGRESS.md、全局 Rules、本次 Spec（填路径）。

请确认以下规则，然后从第一个子任务开始：
1. 每轮只执行一个 pending 子任务，按依赖顺序，不跳。
2. 每轮先读计划和进度末尾的状态，严格遵守不做项和修改范围，超出范围先停。
3. 子任务完成后执行完成标准对应的命令，原样记录输出。
4. 每轮结束写 PROGRESS.md、更新状态再提交。
5. 验证失败先说明本轮假设为什么错了，同一错误建议最多试几轮，仍失败标 blocked 并说明原因。
6. 到检查点停下来等我确认，不要自行通过。
7. 不要自己宣布整个任务完成——最终验收由人对照清单判定。

如果规则可行，从 T1 开始执行第一轮。
```

</details>

<details>
<summary><strong>中断恢复</strong></summary>

```text
我需要恢复一个中断的开发任务。

请先读取：<TASK-PLAN.md 路径>、<PROGRESS.md 路径>、当前 git status 和最近几条 git log。

然后只做四件事：
1. 复述当前状态：已完成哪些、进行中是哪个、下一轮是谁。
2. 核对文件状态与 PROGRESS.md 是否一致，不一致的列出来，不自行猜原因。
3. 指出上一轮遗留的问题和未解决的阻塞。
4. 等我确认后从下一轮继续执行。

不要重做已完成任务，不要删除已有改动。
```

</details>

## 验收要点

- [ ] 每轮只做一个子任务，完成标准达成且有命令输出证据。
- [ ] 改动文件都在允许范围，不做项未被触碰。
- [ ] 每轮写 PROGRESS.md 并提交，状态与实际一致。
- [ ] 失败先分类，没有在同一错误上无限重试。
- [ ] 检查点停下来等确认，AI 没有自行宣布整体完成。

开发中发现问题进入 [05 功能审查与完善](/ai/productivity/dev-spec/02-lifecycle/review) 或 [06 逻辑与 BUG 修复](/ai/productivity/dev-spec/02-lifecycle/bugfix)；每轮改动都要按第三层 [Git 与版本管理](/ai/productivity/dev-spec/03-quality/git-version) 检查。
