# 09 交付与复用

> 第二层 · 开发生命周期的终点。解决「怎么证明做完了、怎么让下次更省力」——交付要让结果可追溯、可接手，验收通过后判断哪些经验值得沉淀。

## 什么时候用

- 一个子任务或整个任务执行完毕，准备标记完成。
- AI 报告「已完成」，需要判断是否真的完成。
- 准备提交、合并或部署之前。
- 一次开发结束后，判断哪些经验值得留下来。

**一条底线：完成由人判定，不由 AI 宣布。** AI 负责提供证据，人逐条核对。

## 操作步骤

### 四层验收

| 层次 | 回答什么 | 主要证据 |
| ---- | -------- | -------- |
| 功能验收 | 要求的功能实现了吗 | 页面操作、接口返回、业务规则核对 |
| 兼容验收 | 原有功能被影响了吗 | 回归对照、接口契约比对 |
| 技术验收 | 编译和测试通过了吗 | 命令输出原文 |
| 交付验收 | 结果可追溯、可接手吗 | diff、交付报告、遗留清单 |

任务输入里的「验收标准」逐条抄过来，每条填预期、实际、证据、结论。「看起来没问题」不是证据。

简单任务做功能 + 局部检查 + 修改说明；普通任务四层都过；复杂任务四层全过且兼容覆盖上下游、技术验收含全量测试。

### 交付报告

报告至少包含：任务与范围、完成内容、修改文件（含「为什么改」）、验证证据（命令与输出关键行）、回归对照、安全检查结论、遗留问题、本次沉淀。

遗留问题要写清「问题是什么、影响什么、建议怎么处理、谁来决定」。「下次再说」不算处理方式——要么建待办，要么写进认知资料，要么在报告里留痕。

### 经验复用

验收完问三句，都答「是」才沉淀：这个问题还会再出现吗？不沉淀的代价是什么？能不能在别处也验证？

| 经验类型 | 去哪里 |
| -------- | ------ |
| 跨任务成立的约束 | Rules（见 [Rules](/ai/productivity/dev-spec/01-foundation/rules)） |
| 踩过的坑 | Project Context / known-issues |
| 反复出现的做法 | Skill（见 [Skills](/ai/productivity/dev-spec/01-foundation/skills)） |
| 项目特有事实 | 项目认知资料 |
| 一次性排查过程 | 不沉淀，留在交付报告 |

**不要沉淀**：一次性临时绕法、未验证的「好方法」、业务字段写进 Skill、本次任务写进 Rules、过时的版本与命令、和提示词库重复的大段模板。

## 可复制提示词

<details>
<summary><strong>验收自查（不宣布完成）</strong></summary>

```text
请对本轮改动做验收自查，不要修改任何文件，也不要宣布完成。

输入：任务验收标准、修改范围与不做项、本轮 git diff、已执行命令与输出（原样）。

按四层输出：
1. 功能验收：逐条对照验收标准，每条给证据或标「缺证据」。
2. 兼容验收：检查 diff、接口、字段、上下游，给出「没变 / 已确认兼容 / 需通知下游」。
3. 技术验收：已执行命令与输出关键行；未执行的明确标出，不得写成通过。
4. 交付验收：改动文件清单、遗留问题、是否可接手。

另外检查 Git 安全（是否保留用户已有改动、是否触及禁改区）和安全项（敏感信息、破坏性操作、输入校验）。
不编造测试输出，不把未执行的检查写成通过。
最后输出「可以进入人工验收 / 尚缺以下证据」二选一，不要输出「任务完成」。
```

</details>

## 验收要点

- [ ] 四层验收逐条完成，每条都有证据。
- [ ] 完成由人判定，AI 没有自行宣布完成。
- [ ] diff 检查通过，没有硬编码、吞异常、放宽断言。
- [ ] 交付报告完整，遗留问题逐条列出且有人负责。
- [ ] 沉淀经过三问筛选，放在正确位置。

第二层走完。整个过程中的质量、安全、变更、回滚要求，由第三层 [质量与安全保障](/ai/productivity/dev-spec/03-quality/code-quality) 全程约束。
