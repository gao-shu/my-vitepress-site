# 06 逻辑与 BUG 修复

> 第二层 · 开发生命周期。解决「报错如何定位、根因怎么找、如何修复并验证不反复」——逻辑错误和 BUG 放在同一阶段，但保留两套不同的处理方法。

## 什么时候用

- 编译失败、单测失败、接口报错。
- 页面行为与预期不符。
- 上一轮改动后原本正常的功能出问题。
- AI 说「已修复」但你不确定是不是真的修好。

**先别急着改**：问题还没复现就先固定复现条件；需求冲突回 [02 需求分析](/ai/productivity/dev-spec/02-lifecycle/requirement-analysis)；环境问题（缺服务、缺权限、缺数据）标为受限，不反复重试。

## 修复闭环

```text
① 固定证据     复现步骤 + 完整报错 + 环境信息 + 最近改动
     ↓
② 根因分析     列假设 → 找证据 → 逐个排除 → 确认根因
     ↓
③ 最小修复     只改导致根因的那一处，不顺手重构
     ↓
④ 测试验证     跑相关测试 → 失败回到 ②，建议最多几轮
     ↓
⑤ 回归验证     确认没引入新问题 → 记录已验证 / 未验证
```

终点不是「代码改了」，而是「有证据证明改对了，且没改坏别的」。

## 两套方法

### 方法一：逻辑错误（结果与预期不符，通常无报错）

典型表现：接口返回空列表、状态计算不对、数值偏差、筛选失效。

先做**根因假设**：列出几条候选假设，每条写支持和反对的证据，用最小只读动作验证，再在剩下的假设上改。判断是否真根因的标准——修掉它能不能解释「为什么之前会出现这个现象」，解释不了就还不是。

常见对应：返回空列表多是参数名、枚举值、租户条件；偶发失败多是并发覆盖、缓存未失效、异步时序；改完 A 坏 B 多是共用方法被改或返回结构变化。

### 方法二：BUG 与报错（有堆栈或明确失败）

先收齐五类证据：复现步骤、完整报错（首行异常 + 完整调用栈 + Caused by 链）、期望行为、环境信息、最近改动（`git diff` 或提交记录）。

不能稳定复现时，让 AI 输出三样东西：目前能确认的复现条件、已排查排除了什么、可能原因排序及每条要什么证据验证。

### 最小修复的共同要求

- 只改导致根因的那一处，改动文件尽量少。
- 不改变接口契约，除非根因就是契约错误且已获确认。
- 不删除或放宽现有测试。
- 能解释现象。

**这些不是修复**：硬编码特定值绕过、吞异常让错误消失、放宽断言让测试通过、删失败用例、给某条数据加特判。它们让错误消失但根因还在，下个场景会以更隐蔽的方式回来。

### 测试与回归

按先快后慢跑：编译/类型检查 → 出问题的那一个测试 → 相关模块 → 接口冒烟 → 全量测试。

同一错误建议最多试几轮，仍失败停手归类：代码错误可重试；环境问题标受限；认知问题（反复改不对）停手回分析；需求冲突交人确认。

回归做对照表，至少留一条「改前行为保持」的证据——只验证「修好了什么」、不验证「没改坏什么」不算完整。四态区分（已验证 / 未验证 / 受限 / 不适用）见第三层 [测试与验证规范](/ai/productivity/dev-spec/03-quality/test-verification)。

## 可复制提示词

<details>
<summary><strong>根因分析（本轮只分析不改）</strong></summary>

```text
请对以下问题做根因分析。本轮只分析，不改代码。

问题：<现象 + 完整报错原文>
复现步骤：<步骤>
相关改动：<git diff 或提交记录>
相关文件：<调用链分析结果>

按四段输出：
1. 事实（只写有证据的：现象、报错原文、实际 SQL 和参数、配置值）
2. 根因假设（列几条并排序，每条写支持证据、反对证据、验证动作、验证结果）
3. 排除过程（逐条说明为什么排除）
4. 结论与修复范围（确认的根因；证据不足就写「未确认」；需要改的最小文件清单；绝对不能改的地方）

证据必须指到文件行号、日志原文或命令输出。不要输出修复代码。没有足够证据时明确说「未确认」，不要选一个最像的当结论。
```

</details>

<details>
<summary><strong>修复闭环</strong></summary>

```text
请按闭环方式修复以下问题。

问题：<现象 + 报错原文>
根因：<来自分析结论，未确认请注明>
允许修改范围：<文件清单>
验证命令：<具体命令>

执行规则：
1. 只改导致根因的那一处，不顺手重构、不格式化、不改无关文件。
2. 每轮改完执行验证命令，原样贴出命令和输出关键行。
3. 测试失败时先说明本轮假设为什么错了，再改。
4. 同一错误建议最多试几轮，仍失败就停手说明原因，不要硬凑。
5. 不删除或放宽现有断言，不硬编码特判，不吞异常。
6. 每轮结束写入 PROGRESS.md 或本轮记录，再继续。

最终报告：根因与修复的对应关系、实际修改文件、每轮命令与输出原文、通过与未通过的测试清单、未解决问题。
```

</details>

## 验收要点

- [ ] 有稳定复现步骤；不能复现时已输出证据和假设。
- [ ] 收集了完整报错、环境信息、最近改动。
- [ ] 根因能解释原始现象；证据不足时明确写「未确认」。
- [ ] 修复只改根因那一处，改动文件尽量少。
- [ ] 每轮有命令输出证据，同一错误没有无限重试。
- [ ] 回归对照含「已修复」和「改前行为保持」两类证据。

修复完成进入 [07 代码优化与重构](/ai/productivity/dev-spec/02-lifecycle/refactor)（如是改进）或 [08 代码测试](/ai/productivity/dev-spec/02-lifecycle/testing)（如要回归验证）。
