# 05 功能审查与完善

> 第二层 · 开发生命周期。解决「功能写完了但边界、异常、权限没考虑全」——把审查与完善放在一起，按清单逐项核对并补齐，而不是只看功能能不能跑通。

## 什么时候用

- 一个子任务或功能开发完成，进入自检。
- AI 报告「已完成」，需要判断是不是真的完成。
- 交付之前的常规审查。

**不要等到全部写完才第一次审查。** 每个检查点都做局部审查，越晚发现问题，回滚成本越高。

## 操作步骤

### 审查清单

| 层次 | 看什么 |
| ---- | ------ |
| 逻辑与规则 | 业务规则有没有实现全，边界条件（空值、零值、重复、越权）有没有处理 |
| 异常与事务 | 异常有没有被吞掉，事务边界是否合理，失败时数据会不会处于半状态 |
| 兼容 | 接口签名、字段含义、返回结构有没有变，调用方是否受影响 |
| 权限与数据范围 | 越权访问有没有拦住，数据隔离条件有没有漏 |
| 测试 | 有没有覆盖关键路径和失败路径，断言是不是被放宽或删掉 |
| 改动范围 | 有没有混进无关格式化、未使用的 import、调试打印、注释掉的分支、遗留 TODO |

审查时让 AI **只输出问题清单和依据，不修改文件、不宣布通过**。完成判定由人做。

### 功能完善

审查发现的问题分两类处理：

- **影响正确性**：回到 [06 逻辑与 BUG 修复](/ai/productivity/dev-spec/02-lifecycle/bugfix) 走修复闭环。
- **属于改进优化**：放到 [07 代码优化与重构](/ai/productivity/dev-spec/02-lifecycle/refactor)，不在这轮顺手做大改。

完善时保持边界：不改变接口契约，不顺手重构无关代码，补了行为测试再改实现。

## 可复制提示词

<details>
<summary><strong>审自己的改动（没有同事时最有用）</strong></summary>

```text
请对本次改动做审查自查，不要修改任何文件，也不要宣布通过。

输入：任务验收标准、修改范围与不做项、本轮 git diff。

按清单输出问题（每条给文件:行号和依据）：
1. 业务逻辑与边界条件（空值、零值、重复、并发、越权）。
2. 异常处理与事务边界。
3. 接口、字段、数据兼容性。
4. 权限与数据范围。
5. 测试是否覆盖关键路径和失败路径，断言是否被放宽或删除。
6. 改动范围：无关格式化、未用 import、调试打印、注释掉的分支、遗留 TODO。

最后输出「问题清单」和「需人确认的疑点」两部分。
不要写「整体没问题，可以合并」这类判定结论。
```

</details>

<details>
<summary><strong>边界与异常补齐</strong></summary>

```text
请针对下面这段实现，补齐边界与异常处理。本轮只分析并给出要补的清单，不直接改代码。

实现：<粘贴代码或描述>

请列出：
1. 输入边界：空值、超长、非法格式、重复提交、并发。
2. 业务边界：状态不允许、权限不足、数据不存在、依赖不可用。
3. 异常路径：每类异常应该怎么处理，是否会被误吞。
4. 每条给出「建议处理方式」和「对应的测试用例」。

不要为不会发生的场景过度防御，只列真正影响正确性的。
```

</details>

## 验收要点

- [ ] 审查清单逐项过完，问题都列成了清单并带依据。
- [ ] 边界、异常、权限、数据范围都有结论。
- [ ] 没有把调试代码、无关格式化、遗留 TODO 带进来。
- [ ] 断言没被放宽，测试没被删。
- [ ] 审查者没有自行宣布通过，最终判定由人做。

审查发现问题进入 [06 逻辑与 BUG 修复](/ai/productivity/dev-spec/02-lifecycle/bugfix)。质量红线见第三层 [代码质量规范](/ai/productivity/dev-spec/03-quality/code-quality)。
