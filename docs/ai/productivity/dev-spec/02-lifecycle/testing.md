# 08 代码测试

> 第二层 · 开发生命周期。解决「怎么证明功能真的能工作」——按层次补测试、按证据报结果，把「测过了」变成可核对的结论。

## 什么时候用

- 功能开发、修复、重构完成后。
- 交付之前的必过环节。
- L1 简单任务做局部检查，L2/L3 按任务级别补全测试。

## 操作步骤

### 测试分层

| 层次 | 测什么 | 什么时候补 |
| ---- | ------ | ---------- |
| 单元测试 | 单个函数、规则、边界条件 | 业务逻辑改动必补 |
| 集成测试 | 模块间协作、数据库、接口 | 涉及数据或跨模块时 |
| 端到端 / 冒烟 | 关键用户路径、接口联通 | 交付前、前端改动时 |

按任务级别裁剪：简单任务跑局部检查即可；普通功能补单测 + 相关集成；复杂功能补全部分层 + 回归。

### 补测试的重点

- 覆盖关键路径**和失败路径**，不只测正常情况。
- 覆盖边界：空值、零值、重复、越权、状态不允许。
- 断言要精确，能确实区分对错，不写永远为真的断言。
- 不为了让测试通过而放宽断言、删除用例、改测试数据掩盖问题。

### 执行顺序

先快后慢：编译/类型检查 → 出问题的那一个测试 → 相关模块 → 接口冒烟 → 全量测试。一上来跑全量，慢且失败信息不聚焦。

### 四态报告

结果必须分清四种状态，不能把没跑的写成通过：

| 状态 | 怎么写 |
| ---- | ------ |
| 已验证 | 「单测 X 通过，输出见日志」 |
| 未验证 | 「测试库不可用，未跑集成测试；已用本地库跑单测替代」 |
| 受限 | 「生产配置只读，未做线上验证」 |
| 不适用 | 「未涉及前端改动，无需浏览器验证」 |

**没有输出的「已测试」等于没测试。** 详细规范见第三层 [测试与验证规范](/ai/productivity/dev-spec/03-quality/test-verification)。

## 可复制提示词

<details>
<summary><strong>补单元测试</strong></summary>

```text
请为下面这段代码补单元测试。

代码：<粘贴代码或文件>

要求：
1. 覆盖正常路径、关键边界（空值、零值、越界、重复）和失败路径。
2. 断言要精确，能区分对错，不写恒真断言。
3. 测试名说清「什么情况下应该怎样」。
4. 不修改被测试的业务代码。
5. 如果有难以测试的地方（依赖外部服务、静态调用），说明需要怎么隔离。

输出测试代码 + 每个用例覆盖的场景说明。
```

</details>

<details>
<summary><strong>补测试与回归清单</strong></summary>

```text
本次改动：<描述>
请基于改动内容，产出一份测试与回归清单，本轮只输出清单，不执行。

请列出：
1. 必跑项：编译/类型检查、相关单测、接口冒烟（写具体命令）。
2. 回归项：哪些原有功能必须保持不变，各自怎么验证。
3. 边界项：这次改动涉及的边界条件（空值、权限、状态、并发）。
4. 无法自动化的项：需要人工核对的页面行为或数据状态。

每项给「检查点 → 预期结果 → 验证方式」。
最后标出哪些属于「漏了就出事」的检查，建议固化为脚本（见 Hooks / Scripts）。
```

</details>

## 验收要点

- [ ] 测试覆盖关键路径和失败路径，断言精确。
- [ ] 按先快后慢顺序执行，有命令输出证据。
- [ ] 结果按四态区分，没跑的没写成通过。
- [ ] 回归项覆盖了「原有功能不变」。
- [ ] 没有通过放宽断言或删用例让测试变绿。
