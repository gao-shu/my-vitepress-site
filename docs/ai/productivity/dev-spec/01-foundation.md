# 开发前

> **让 AI 在开始开发前具备正确的项目认知、规则、技能、协作和工具能力。**

## 快速定位

| 我现在要做什么 | 使用 |
|---|---|
| 让 AI 快速了解项目 | Project Context |
| 建立 / 检查项目规则 | Rules |
| 把重复经验沉淀成 Skill | Skills |
| 一次提交任务，自动分工协作与验收 | Agents |
| 给 AI 增加外部工具能力 | MCP / Tools |
| 把重复检查自动化 | Hooks / Scripts |

> **原则：不是每个项目都需要全部配置。需要什么就用什么。**

---

## 01 · Project Context

**让 AI 快速了解项目，避免凭空猜测和反复解释。**

### 什么时候使用

- 第一次接手项目
- AI 不熟悉当前项目
- 开发涉及多个模块，需要先搞清楚影响范围

### 操作

#### ① 快速了解项目

```text
请分析当前项目，先不要修改任何文件。

重点检查：
1. 项目技术栈和目录结构
2. 核心模块及职责
3. 项目启动、构建和测试命令
4. 关键配置和外部依赖
5. 主要业务入口

输出：
- 项目结构
- 核心模块
- 启动/构建/测试命令
- 关键配置
- 待确认事项

所有重要结论尽可能提供文件路径作为依据。
不要猜测无法确认的信息。
```

**得到：** 一份可以直接用于后续开发的项目概览。

---

#### ② 分析指定模块

```text
请只读分析 <模块名/目录>，不要修改任何文件。

请说明：
1. 模块职责和边界
2. 对外入口
3. 核心文件及作用
4. 依赖和被依赖关系
5. 涉及的数据表、接口和外部服务

所有结论提供文件路径。
无法确认的内容标记为「待确认」。
```

**得到：** 指定模块的职责、边界、依赖和数据接口说明。

---

#### ③ 追踪业务调用链

```text
请只读追踪下面功能的完整调用链，不要修改任何文件。

入口：
<接口 / 页面操作 / 方法>

从入口追踪到最终数据落点，检查：
1. 同步调用
2. 异步任务 / 消息
3. 数据库读写
4. 事务边界
5. 异常处理
6. 配置开关

每个关键节点提供「文件路径:行号」。

输出：
调用链 → 数据表 → 事务/异常 → 可能风险。
找不到的环节明确标记「未找到」。
```

**得到：** 一条从入口到数据落点、带文件行号的完整调用链。
> **知道改哪里、影响谁、数据走到哪里；无法确认的内容已经明确标出。**

## 02 · Rules

**将项目中必须遵守的约束固化为 Rules，确保 Agent 按照项目要求执行。**

### 什么时候使用

- 新项目初始化，需要建立核心规则。
- 项目技术规范、架构或业务约束发生变化。
- 开发过程中发现 Agent 反复违反某项约定。
- 现有 Rules 需要补充、调整或验证。

### 操作

#### ① 创建与完善 Rules

```text
请分析当前项目，识别需要建立或完善的项目级 Rules，并完成规则整理。
重点检查：
1. 技术栈及技术选型约束
2. 项目架构与模块边界
3. 编码规范与实现约束
4. 数据库及数据操作约束
5. 接口规范与数据交互约束
6. 安全要求与禁止操作
7. 项目特有的业务约束
处理要求：
1. 只提炼必须长期遵守的约束。
2. 区分通用规则与项目特有规则。
3. 不将操作教程、开发流程和一次性任务写入 Rules。
4. 优先参考现有项目文档、代码和已确认的业务要求。
5. 检查现有 Rules，避免重复、冲突或相互矛盾。
6. 不确定的约束标记为待确认，不得自行编造。
7. 每条规则必须明确适用范围、约束对象和具体要求。
8. 根据当前 AI 工具支持的规则格式和加载机制创建或完善规则文件。
9. 必要时更新 AGENTS.md 中的 Rules 索引。
执行要求：
- 对有明确依据的规则，可以直接创建或完善。
- 对存在歧义或需要用户确认的规则，先列出问题，不要擅自固化。
- 不得为了追求规则数量而增加无实际价值的内容。
完成后输出：
- 新增及修改的 Rules
- 规则存放位置
- 适用范围
- 规则来源及依据
- 待确认事项
```

---

#### ② 检查与验证 Rules

```text
请检查当前项目的 Rules 是否合理、完整，并验证其加载和执行情况。
重点检查：
一、规则质量
1. 是否存在重复、冲突或相互矛盾的规则。
2. 是否存在模糊、宽泛或无法执行的规则。
3. 是否混入操作教程、开发流程或临时任务要求。
4. 是否存在项目无关或已经过时的规则。
5. 规则适用范围是否明确。
二、加载情况
1. 当前 AI 工具是否能够正确发现和加载 Rules。
2. 规则文件的路径、格式和作用范围是否正确。
3. 是否存在规则未加载、加载范围不正确或被其他配置覆盖的情况。
三、执行验证
1. 选择具有代表性的规则设计最小验证场景。
2. 检查 Agent 是否能够识别并遵守相应规则。
3. 对无法实际验证的规则，明确标记验证状态。
输出：
- 检查结果
- 加载验证结果
- 执行验证结果
- 发现的问题及风险
- 修改建议
- 尚未验证的事项
注意：
1. 不要仅凭文件存在或 Agent 自述，就认定 Rules 已经生效。
2. 不得将未实际验证的内容标记为通过。
3. 本次只输出检查报告和修改建议，不直接修改文件。
```

## 03 · Skills

**把开发过程中经过验证、可以重复使用的方法沉淀成 Skill。**

### 什么时候使用

- 开发过程中发现某种问题反复出现
- 某套操作方法已经验证有效
- 现有 Skill 需要补充、优化或修正
- 希望将项目经验转化为可复用能力

### 操作

#### ① 开发经验提炼与 Skill 沉淀

一次提交经验来源，自动完成「判断价值 → 提炼 → 检查完善 → 形成 Skill → 验证」的完整流程。

```text
请结合当前开发任务，识别是否存在值得沉淀或完善为 Skill 的经验。
经验来源：
<开发过程中遇到的问题、解决方案、操作流程或已有 Skill>

请按照以下流程处理：

第一步：判断沉淀价值
1. 是否具有重复使用的价值？
2. 是否形成了相对稳定的操作方法？
3. 是否经过实际任务验证？
4. 是否具有跨任务复用的可能？
如果不满足条件，输出「暂不沉淀」及原因，不要为了创建 Skill 而创建。

第二步：提炼经验
如果值得沉淀，请提炼：
- 适用场景
- 触发条件
- 前置条件
- 操作步骤
- 关键检查点
- 异常处理与失败场景
- 不适用场景

第三步：检查与完善
1. 去除具体项目、客户、表名和业务数据等专属信息。
2. 检查步骤是否明确、可执行。
3. 区分已验证方法与尚未验证的建议。
4. 检查是否与现有 Skill 重复。
5. 如果已有相关 Skill，优先评估是否应该完善原 Skill，而不是重复创建。

第四步：形成 Skill
1. 按当前 AI 工具支持的 Skill 规范生成内容。
2. 明确 Skill 名称、用途、触发条件和执行流程。
3. 保留必要的检查点和失败处理。
4. 输出完整 Skill 草稿。

第五步：验证与后续完善
1. 使用实际开发任务验证 Skill 是否有效。
2. 记录执行中发现的问题。
3. 根据验证结果决定是否正式沉淀或继续完善。
4. 未经实际验证的内容不得标记为已验证。

本次只输出分析结果和 Skill 草稿，不直接创建或修改文件。
```

## 04 · Agents

**适用于可以安全拆分、并行执行或需要独立审查的复杂任务。**

### 什么时候使用

- 前后端可以并行
- 不同模块可以并行
- 一个 Agent 开发、另一个 Agent 审查
- 任务复杂，需要多个专业角色

### 操作

#### ① 多 Agent 协作开发

一次提交完整任务，自动完成「评估分工 → 执行 → 统一验收」三个阶段。你只需发起一次任务，三个阶段是主 Agent 内部的工作流程，不需要手动分三次输入提示词。

```text
请评估下面的任务是否适合使用多 Agent 协作。如果适合，请自动完成任务拆分、分工、执行和最终验收；如果不适合，请说明原因，并建议使用单 Agent 完成。

任务：
<填写具体任务>

## 阶段一：任务评估与分工设计
1. 分析任务是否可以拆分为相对独立的子任务。
2. 检查任务之间的依赖关系、文件冲突和共享接口。
3. 判断多 Agent 是否比单 Agent 更高效。
4. 如果不适合多 Agent，说明原因并停止多 Agent 编排。
5. 如果适合，设计最小化分工方案。

分工要求：
- 明确每个 Agent 的职责和具体任务。
- 明确允许修改、只读和禁止修改的文件范围。
- 明确共享接口、数据结构和协作约定。
- 明确任务依赖和执行顺序。
- 指定主 Agent 负责协调、汇总和最终验收。

## 阶段二：执行任务
1. 按照分工启动各 Agent 执行任务。
2. 在任务允许的情况下并行执行，存在依赖时按顺序执行。
3. 各 Agent 严格遵守任务边界和项目开发规范。
4. 遇到重大设计问题、需求不明确或任务冲突时，暂停相关任务并反馈。
5. 主 Agent 持续协调进度，处理协作问题。
6. 各 Agent 完成后，汇报修改文件、实现内容、测试结果和遗留问题。

## 阶段三：汇总结果与统一验收
主 Agent 收集所有 Agent 的执行结果，并结合实际代码变更和 Git Diff 进行统一检查。

检查内容：
1. 是否完成原始需求。
2. 是否超出任务和文件修改范围。
3. 是否存在文件覆盖、修改冲突或重复实现。
4. 各模块之间的接口和数据结构是否一致。
5. 业务逻辑、异常处理和边界条件是否正确。
6. 是否存在代码质量问题。
7. 测试是否充分，是否有真实执行证据。
8. 是否存在遗留问题或潜在风险。

发现问题后：
- 明确且影响较小的问题，可以安排对应 Agent 修复。
- 涉及多个模块的问题，先协调相关 Agent 确认方案。
- 重大设计问题、需求偏差或超出原始范围的问题，先向用户说明。
- 修复完成后，重新检查代码并执行必要测试。

## 最终交付
请输出统一的执行报告：
1. 多 Agent 使用评估及分工情况。
2. 各 Agent 任务完成情况。
3. 实际修改文件及核心实现。
4. 发现的问题及修复情况。
5. 测试执行情况及结果。
6. 未解决的问题和遗留风险。
7. 最终验收结论：通过 / 有条件通过 / 未通过。

注意：
- 不得仅凭 Agent 自述判断任务完成。
- 不得将未执行的测试标记为通过。
- 不得擅自扩大修改范围。
- 不得隐瞒未完成事项。
- 最终验收由主 Agent 负责。
- 如果当前编程工具不支持子 Agent 创建、任务调度或并行执行，必须明确说明这一能力限制，不能假装已经启动了多个 Agent。
```

## 05 · MCP / Tools

**让 AI 获得项目外部能力，但优先考虑必要性和最小权限。**

### 什么时候使用

- 需要访问数据库
- 需要操作 Git / 浏览器 / API
- 需要连接外部系统
- 需要检查现有工具权限

### 操作

#### ① 判断是否需要工具

```text
请判断下面这个任务是否有必要接入外部工具。

工具：
<工具>

用途：
<想解决的问题>

请判断：
1. 当前能力是否已经足够
2. 接入后是否明显提高效率
3. 是否存在更简单的替代方案
4. 需要什么最小权限
5. 工具不可用时如何继续工作

输出：
建议接入 / 暂缓 / 不需要。

不要进行实际配置。
```

---

#### ② 检查现有工具

```text
请只读检查当前项目已经接入的 MCP / Tools。

检查：
1. 有哪些工具
2. 每个工具能做什么
3. 当前权限范围
4. 是否存在过度授权
5. 是否涉及生产环境或敏感数据
6. 是否存在人工确认机制
7. 是否有降级方案

只输出问题和建议，不修改配置。
```

## 06 · Hooks / Scripts

**把明确、重复、可自动判断的检查交给脚本，不靠 AI 和记忆。**

### 什么时候使用

- 每次开发都重复检查
- 检查结果可以明确判断
- 错误需要尽早阻止
- 希望减少人工检查

### 操作

#### ① 判断是否应该自动化

```text
请分析下面这些检查是否适合自动化。

检查：
<检查项>

逐项判断：
1. 是否重复出现
2. 是否可以明确判断通过/失败
3. 是否适合脚本执行
4. 是否需要业务判断
5. 失败后是否能明确告诉开发者如何修复

输出：
人工检查 / 脚本检查 / Hook 检查。

并说明原因。
```

---

#### ② 生成检查脚本

```text
请为下面的检查生成一个独立脚本。

检查：
<检查内容>

要求：
1. 不修改业务代码
2. 结果明确
3. 失败时说明原因
4. 给出修复建议
5. 给出运行命令
6. 给出退出码含义
7. 不依赖不可控的人工判断

输出：
脚本 + 使用方法。

先不要修改项目文件。
```

---

#### ③ 检查现有 Hooks

```text
请检查当前项目已有的 Hooks / 自动化检查。

判断：
1. 是否误报过多
2. 是否执行过慢
3. 是否重复
4. 是否应该改成手动执行
5. 是否存在值得增加的关键检查

输出：
保留 / 修改 / 删除 / 新增。

不要直接修改配置。
```
