# 第一层 · AI 工程基础

> 让 AI 正确工作。这一层是底座：把项目信息、规则、技能、分工、工具、自动化检查配置一次，长期复用，不用每次对话从头交代。

## 快速索引

| 模块 | 解决什么 | 核心产物 |
| ---- | -------- | -------- |
| Project Context | AI 怎么拿到准确的项目信息 | 分层扫描的项目资料 |
| Rules | AI 怎么遵守项目约束 | 一份可验证的规则文件 |

## 1. Project Context · 项目上下文

**解决**：反复解释项目背景；AI 全仓扫描把上下文占满；靠命名猜业务规则。

**四层收敛**——由外到内，能停就停：

| 层次 | 产出 | 能停的条件 |
| ---- | ---- | ---------- |
| 项目地图 | 模块清单 + 入口 + 构建方式 | 能说出「项目由哪几块组成」 |
| 模块地图 | 本次任务涉及的目录 | 能指出「改动落在哪个包」 |
| 调用链 | 入口 → 服务 → 数据完整路径 | 能画出「请求经过哪几层」 |
| 相关文件 | 待读待改清单（含受影响但不改的） | 每个文件都说得出为何关心 |

跳过 `node_modules/`、`target/`、`dist/`、`.git/` 等依赖和生成目录。调用链要覆盖异步任务、消息消费、配置开关、动态 SQL，追到数据落点和事务边界才算完。

**长期保存 vs 按任务提供**：

| 信息 | 放哪里 |
| ---- | ------ |
| 能验证、反复用到的事实（技术栈、模块、命令、字段含义、历史决策） | 项目资料（README / docs） |
| 本次才有的（目标、相关文件、验收） | 任务描述 |
| 踩过的坑 | known-issues |
| 推测、查不到的 | 待确认清单 |

结论标状态：**已确认**（有证据）/ **待确认** / **人工补充**。不写「应该是 / 一般是」，gotchas 由人写。

> 提示词 · 项目地图
```text
只读分析，不修改文件，不提改进建议。跳过 node_modules、target、dist、.git、依赖和生成目录。
优先读构建文件、README、启动入口、前端入口、配置、目录结构，不逐个文件通读。
输出：1 技术栈 2 模块清单（模块→职责→入口）3 入口清单 4 目录概览 5 构建/启动/测试命令（附来源）6 配置文件清单 7 外部依赖 8 未覆盖范围。
结论带证据路径，推断放进「待确认」。
```

> 提示词 · 调用链
```text
只读分析，从入口追到数据落点，不要停。必须覆盖同步调用、异步任务、消息消费、配置开关、动态 SQL。
每步给「文件路径:行号」和方法名；找出事务边界和异常处理；指出读写的表；找不到的标「未找到」。
输出：链路总览 / 逐层明细 / 涉及的表 / 事务与异常 / 隐藏路径 / 最易出问题的几处。
```

**检查点**：五问能答上——改哪几个文件、谁受影响、涉及哪张表哪个接口、现有实现为什么这样、哪些地方不能碰。两条答不上就补，别带缺口改代码。

## 2. Rules · 项目规则

**解决**：每次对话重复交代约束；AI 命名分层不一致；口头禁令换个会话就忘。

**写什么**：技术栈与版本、构建测试命令、命名分层、禁改目录、安全红线、跨任务成立的业务约束。
**不写什么**：本次任务、完整业务流程、分阶段步骤、「尽量 / 建议」这类无法验证的软规则。

**四条原则**：可验证（能说清怎么算违反）· 用「必须 / 禁止」· 禁止项配反例 · 全局控制在几十行内。例外写明「谁确认、记在哪」。

```
# <规则名> · <适用范围>
## 必须遵守
| 编号 | 规则 | 验证方式 |
| C01 |      | <命令或 diff 特征> |
## 明确禁止
| 编号 | 禁止项 | 反例 | 验证方式 |
| P01 |        |      |          |
## 例外与审批
- 需要例外时由 <角色> 确认，记在 <位置>。
```

> 提示词 · 把约定整理成规则
```text
把下面的项目约定整理成规则草稿，本轮只输出草稿，不写文件。
只保留跨任务成立、能验证的约束；每条用「必须/禁止」并配验证方式；禁止项配反例；删掉无法验证的软规则；写明适用范围和例外审批。
输出：规则草稿 + 被删内容及原因。
```

**检查点**：没有任务措辞、没有软规则、每条可验证、AI 新会话能直接读到。

## 3. Skills · 专业技能

**解决**：同类操作每次重讲步骤；好做法只活在某次对话；把一次性绕法固化成垃圾。

**何时建**（同时满足）：反复出现 · 有稳定步骤和检查点 · 至少两处验证有效。只做一两次的先留在交付报告。

**写什么**：适用场景、前置条件、带检查点的步骤、失败处理、复用记录。
**不写什么**：具体表名/客户名/业务字段、一次性绕法、未验证的做法、完整业务流程。

> 提示词 · 固化一个成功做法
```text
先回答三问：还会再出现吗？不固化代价是什么？有没有第二处能验证？任一答不上就写「暂不固化，留在交付报告」。
三条都成立才产出技能草稿：适用场景 / 不适用 / 前置条件 / 带检查点的步骤 / 失败处理表 / 复用记录表。
只写「怎么做」的通用方法，不要写具体表名、客户名、业务字段。
```

**检查点**：至少两处验证、步骤有检查点、没有业务字段污染、有复用记录。技能是资产不是垃圾桶，宁精勿滥。

## 4. Agents · 智能体协作

**解决**：多开窗口互相覆盖；AI 既当运动员又当裁判；一句话派活导致理解不一。

**何时拆**：前后端按冻结契约并行、互不冲突的模块、执行+审查、并行检索。**不要拆**：小任务、强耦合、需求没冻结、同一文件多人改。

**三条硬边界**：

1. **文件所有权**：每个 Agent 明确负责哪些文件、哪些只读，同一文件不同时改。
2. **契约先冻结**：接口、数据结构、字段名先定稿再并行；契约一变所有人重读。
3. **审查者不判定通过**：执行/审查/规划分开，审查只输出问题清单，最终由人判定。

派活要给同一份完整输入：任务 + 修改范围 + 不做项 + 验收标准。

> 提示词 · 多 Agent 分工
```text
先给分工方案，不要开始改代码。任务：<一句话>。冻结的契约：<接口/结构/字段，或「需先冻结」>。
要求：1 按文件所有权划分，同一文件不同时改 2 契约没冻结就只做契约设计 3 每个 Agent 收到同一份任务/范围/不做项/验收 4 含执行者和审查者，审查只报问题不判通过 5 说明结果如何收拢和最终谁验收。
先输出分工表和风险点，等我确认再启动。
```

**检查点**：文件所有权无重叠、契约已冻结、没有一句话派活、审查者没自行宣布通过。

## 5. MCP / Tools · 工具与外部能力

**解决**：接一堆用不上的工具；权限过大能读生产；工具挂了整个流程卡死。

**接入三问**（有一条答不上就不接）：

| 检查 | 要回答 |
| ---- | ------ |
| 必要性 | 仓库内拿不到、又确实必须的吗？有更简单的替代吗？ |
| 边界 | 开放什么权限？只读还是可写？能碰生产吗？ |
| 降级 | 不可用时怎么办？有替代检查或手动方案吗？ |

**权限最小化**：能只读不写、能连测试库不连生产、能限定目录不开放全盘；删除/写入/发送动作明确需要人确认。记录能力清单（接了什么、开放什么、谁配置、怎么降级）。

> 提示词 · 评估是否接入
```text
三问评估这个工具：必要性（仓库内是否拿不到且必须）、边界（权限/范围/是否碰生产）、降级（不可用怎么办）。
给权限最小化建议、哪些动作需人确认、结论（建议/暂缓/不建议）及理由。答不上的标「待确认」，不要替我假设。本轮只评估不配置。
```

**检查点**：三问都有答案、权限最小、有降级、能查到能力清单。

## 6. Hooks / Scripts · 自动化执行

**解决**：靠提示词提醒跑测试偶尔忘；红线只口头说过；Hook 装太多误报被忽略。

**什么交给脚本**（两条都满足）：漏了就出事 + 能明确判定。典型：构建、类型检查、单测、密钥扫描、禁改区 diff、遗留文件清理、lint。**需要业务判断的不交给脚本**。

**先写独立脚本，稳定后再挂到 Hook；不要一上来挂一堆。** 检查要快、准（少误报）、报错可解释、跳过有留痕。

> 提示词 · 把重复检查固化成脚本
```text
本轮只出方案不写代码。对每项检查判断：是否「漏了就出事且能明确判定」（否则留人工）。
给出脚本要做的事、输入输出、失败报错（说清怎么改）、建议触发时机（显式/提交前 Hook）。
只把最关键最稳定的挂 Hook，慢检查单独跑。输出：可脚本化清单 + 方案 + 建议挂 Hook 的最小集合。
```

**检查点**：自动化的都满足两条件、需要判断的留人工、Hook 最小且无误报、跳过有留痕。
