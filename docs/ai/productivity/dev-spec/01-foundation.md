# 开发前

> **让 AI 在开始开发前具备正确的项目认知、规则、技能、协作和工具能力。**

## 快速定位

| 我现在要做什么 | 使用 |
|---|---|
| 让 AI 快速了解项目 | Project Context |
| 建立 / 检查项目规则 | Rules |
| 把重复经验沉淀成 Skill | Skills |
| 让多个 Agent 分工协作 | Agents |
| 给 AI 增加外部工具能力 | MCP / Tools |
| 把重复检查自动化 | Hooks / Scripts |

> **原则：不是每个项目都需要全部配置。需要什么就用什么。**

---

## 01 · Project Context

**让 AI 快速了解项目，避免凭空猜测和反复解释。**

### 什么时候使用

- 第一次接手项目
- AI 不熟悉当前项目
- 开发涉及多个模块，需要先搞清楚影响范围

### 操作

#### ① 快速了解项目

```text
请分析当前项目，先不要修改任何文件。

重点检查：
1. 项目技术栈和目录结构
2. 核心模块及职责
3. 项目启动、构建和测试命令
4. 关键配置和外部依赖
5. 主要业务入口

输出：
- 项目结构
- 核心模块
- 启动/构建/测试命令
- 关键配置
- 待确认事项

所有重要结论尽可能提供文件路径作为依据。
不要猜测无法确认的信息。
```

**得到：** 一份可以直接用于后续开发的项目概览。

---

#### ② 分析指定模块

```text
请只读分析 <模块名/目录>，不要修改任何文件。

请说明：
1. 模块职责和边界
2. 对外入口
3. 核心文件及作用
4. 依赖和被依赖关系
5. 涉及的数据表、接口和外部服务

所有结论提供文件路径。
无法确认的内容标记为「待确认」。
```

**得到：** 指定模块的职责、边界、依赖和数据接口说明。

---

#### ③ 追踪业务调用链

```text
请只读追踪下面功能的完整调用链，不要修改任何文件。

入口：
<接口 / 页面操作 / 方法>

从入口追踪到最终数据落点，检查：
1. 同步调用
2. 异步任务 / 消息
3. 数据库读写
4. 事务边界
5. 异常处理
6. 配置开关

每个关键节点提供「文件路径:行号」。

输出：
调用链 → 数据表 → 事务/异常 → 可能风险。
找不到的环节明确标记「未找到」。
```

**得到：** 一条从入口到数据落点、带文件行号的完整调用链。

### 完成标准

> **知道改哪里、影响谁、数据走到哪里；无法确认的内容已经明确标出。**

## 02 · Rules

**把长期有效的项目约束交给 AI，不再依赖每次对话重复说明。**

### 什么时候使用

- 新项目建立 AI 开发规则
- 发现 AI 经常违反相同规范
- 需要检查已有规则是否有效

### 操作

#### ① 检查现有 Rules

```text
请只读检查当前项目已有的 AI 规则文件，不要修改。

检查：
1. 有哪些规则文件及生效范围
2. 是否存在重复或冲突
3. 是否包含一次性任务
4. 是否存在无法验证的规则
5. 是否缺少关键约束
6. 当前规则是否与项目实际情况一致

输出：
问题 → 依据 → 修改建议。

不要直接修改规则。
```

---

#### ② 生成项目 Rules

```text
请根据当前项目实际情况生成 AI 开发规则草稿。

先读取项目结构、技术栈和现有规范。

要求：
1. 只保留跨任务长期有效的规则
2. 明确「必须 / 禁止」
3. 每条规则尽可能可验证
4. 写清适用范围
5. 写清必要的例外情况
6. 不要编造项目不存在的技术约束

本轮只输出草稿，不写入文件。
```

---

#### ③ 验证 Rules 是否生效

```text
请检查当前项目的 AI Rules 是否真正生效。

检查：
1. 工具是否会读取这些规则
2. 文件位置和配置是否正确
3. 是否存在冲突或重复
4. 规则能否实际约束 AI 行为
5. 是否存在工具差异

只检查，不修改。
```

### 完成标准

> **规则少而明确、长期有效，并且 AI 确实能够读取和执行。**

---

## 03 · Skills

**把经过验证、会重复使用的方法沉淀成 Skill。**

### 什么时候使用

- 某种工作反复出现
- 已经形成稳定做法
- 希望以后直接复用

### 操作

#### ① 判断是否值得沉淀

```text
请判断下面这套做法是否值得沉淀为 Skill。

做法：
<描述>

检查：
1. 是否会重复出现？
2. 是否有稳定步骤？
3. 是否已经验证有效？
4. 是否可以跨任务复用？

如果不满足，请输出「暂不沉淀」并说明原因。

如果满足，请整理：
适用场景 → 前置条件 → 操作步骤 → 检查点 → 失败处理。
```

---

#### ② 创建 Skill

```text
请把下面已经验证有效的做法整理成 Skill 草稿。

做法：
<粘贴经验>

要求：
1. 面向重复使用，而不是一次性任务
2. 不写具体客户、项目、表名和业务数据
3. 步骤必须稳定、可执行
4. 每个关键步骤有检查点
5. 明确适用和不适用场景
6. 按当前使用的 AI 工具说明加载方式

只输出 Skill 草稿，不写文件。
```

---

#### ③ 检查 Skill

```text
请检查下面这个 Skill 是否适合长期复用。

重点检查：
1. 是否包含项目专属内容
2. 是否存在未验证的方法
3. 步骤是否明确
4. 检查点是否完整
5. 是否存在重复或无意义内容
6. 是否已经有实际任务验证

输出：
问题 → 风险 → 修改建议。

不要直接修改。
```

### 完成标准

> **只有稳定、重复、验证有效的方法才进入 Skill。**

## 04 · Agents

**当任务可以安全拆分或需要独立审查时，让多个 Agent 分工。**

### 什么时候使用

- 前后端可以并行
- 不同模块可以并行
- 一个 Agent 开发、另一个 Agent 审查
- 任务复杂，需要多个专业角色

### 操作

#### ① 判断是否适合多 Agent

```text
请分析下面任务是否适合使用多个 Agent。

任务：
<任务>

判断：
1. 是否可以独立拆分
2. 是否存在文件冲突
3. 是否存在共享数据或接口依赖
4. 是否需要独立审查
5. 使用多 Agent 是否真的比单 Agent 更高效

输出：
建议使用 / 不建议使用。

如果建议使用，给出最小分工方案。
```

---

#### ② 设计 Agent 分工

```text
请为下面任务设计多 Agent 分工方案，不要开始修改代码。

任务：
<任务>

要求：
1. 明确每个 Agent 的职责
2. 明确可修改文件
3. 明确只读文件
4. 明确禁止修改内容
5. 明确共享接口 / 数据契约
6. 避免多个 Agent 同时修改同一文件
7. 指定独立审查角色
8. 明确最终由谁验收

输出：
Agent → 职责 → 修改范围 → 只读范围 → 验收标准 → 协作关系。
```

---

#### ③ 审查 Agent 产出

```text
请独立审查以下 Agent 的开发结果和 Git Diff。

只审查，不修改，不宣布通过。

检查：
1. 是否超出各自修改范围
2. 是否存在互相覆盖
3. 接口 / 数据结构是否一致
4. 功能和边界是否正确
5. 是否存在调试代码、TODO 或临时代码
6. 是否存在测试遗漏

输出：
问题 → 文件 → 影响 → 建议。
```

### 完成标准

> **职责不冲突、修改范围明确、结果可独立审查。**

---

## 05 · MCP / Tools

**让 AI 获得项目外部能力，但优先考虑必要性和最小权限。**

### 什么时候使用

- 需要访问数据库
- 需要操作 Git / 浏览器 / API
- 需要连接外部系统
- 需要检查现有工具权限

### 操作

#### ① 判断是否需要工具

```text
请判断下面这个任务是否有必要接入外部工具。

工具：
<工具>

用途：
<想解决的问题>

请判断：
1. 当前能力是否已经足够
2. 接入后是否明显提高效率
3. 是否存在更简单的替代方案
4. 需要什么最小权限
5. 工具不可用时如何继续工作

输出：
建议接入 / 暂缓 / 不需要。

不要进行实际配置。
```

---

#### ② 检查现有工具

```text
请只读检查当前项目已经接入的 MCP / Tools。

检查：
1. 有哪些工具
2. 每个工具能做什么
3. 当前权限范围
4. 是否存在过度授权
5. 是否涉及生产环境或敏感数据
6. 是否存在人工确认机制
7. 是否有降级方案

只输出问题和建议，不修改配置。
```

### 完成标准

> **只接入真正需要的工具，并使用足够完成任务的最小权限。**

## 06 · Hooks / Scripts

**把明确、重复、可自动判断的检查交给脚本，不靠 AI 和记忆。**

### 什么时候使用

- 每次开发都重复检查
- 检查结果可以明确判断
- 错误需要尽早阻止
- 希望减少人工检查

### 操作

#### ① 判断是否应该自动化

```text
请分析下面这些检查是否适合自动化。

检查：
<检查项>

逐项判断：
1. 是否重复出现
2. 是否可以明确判断通过/失败
3. 是否适合脚本执行
4. 是否需要业务判断
5. 失败后是否能明确告诉开发者如何修复

输出：
人工检查 / 脚本检查 / Hook 检查。

并说明原因。
```

---

#### ② 生成检查脚本

```text
请为下面的检查生成一个独立脚本。

检查：
<检查内容>

要求：
1. 不修改业务代码
2. 结果明确
3. 失败时说明原因
4. 给出修复建议
5. 给出运行命令
6. 给出退出码含义
7. 不依赖不可控的人工判断

输出：
脚本 + 使用方法。

先不要修改项目文件。
```

---

#### ③ 检查现有 Hooks

```text
请检查当前项目已有的 Hooks / 自动化检查。

判断：
1. 是否误报过多
2. 是否执行过慢
3. 是否重复
4. 是否应该改成手动执行
5. 是否存在值得增加的关键检查

输出：
保留 / 修改 / 删除 / 新增。

不要直接修改配置。
```

### 完成标准

> **自动化只处理稳定、明确、有价值的检查，不为了自动化而自动化。**

---

## 最后

### 开发前准备完成

在开始开发前，至少确认：

- AI 已了解需要修改的项目范围
- 必要的 Rules 已生效
- 已有可复用 Skill 可以正常使用
- 多 Agent 任务已经明确分工（如需要）
- MCP / Tools 权限合理（如使用）
- 关键自动化检查已经准备好（如需要）

**准备完成 → 进入「开发中」** → [开发中](/ai/productivity/dev-spec/02-lifecycle)
