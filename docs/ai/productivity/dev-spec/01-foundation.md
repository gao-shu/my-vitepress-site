# 开发前

> **让 AI 在开始开发前具备正确的项目认知、规则、技能、协作和工具能力。**

## 快速定位

| 我现在要做什么 | 使用 |
|---|---|
| 让 AI 快速了解项目 | Project Context |
| 建立 / 检查项目规则 | Rules |
| 把重复经验沉淀成 Skill | Skills |
| 一次提交任务，自动分工协作与验收 | Agents |
| 给 AI 增加外部工具能力 | MCP / Tools |
| 把重复检查自动化 | Hooks / Scripts |

> **原则：不是每个项目都需要全部配置。需要什么就用什么。**

---

## 01 · Project Context

**让 AI 快速了解项目，避免凭空猜测和反复解释。**

### 什么时候使用

- 第一次接手项目
- AI 不熟悉当前项目
- 开发涉及多个模块，需要先搞清楚影响范围

### 操作

#### ① 快速了解项目

```text
请分析当前项目，先不要修改任何文件。

重点检查：
1. 项目技术栈和目录结构
2. 核心模块及职责
3. 项目启动、构建和测试命令
4. 关键配置和外部依赖
5. 主要业务入口

输出：
- 项目结构
- 核心模块
- 启动/构建/测试命令
- 关键配置
- 待确认事项

所有重要结论尽可能提供文件路径作为依据。
不要猜测无法确认的信息。
```

**得到：** 一份可以直接用于后续开发的项目概览。

---

#### ② 分析指定模块

```text
请只读分析 <模块名/目录>，不要修改任何文件。

请说明：
1. 模块职责和边界
2. 对外入口
3. 核心文件及作用
4. 依赖和被依赖关系
5. 涉及的数据表、接口和外部服务

所有结论提供文件路径。
无法确认的内容标记为「待确认」。
```

**得到：** 指定模块的职责、边界、依赖和数据接口说明。

---

#### ③ 追踪业务调用链

```text
请只读追踪下面功能的完整调用链，不要修改任何文件。

入口：
<接口 / 页面操作 / 方法>

从入口追踪到最终数据落点，检查：
1. 同步调用
2. 异步任务 / 消息
3. 数据库读写
4. 事务边界
5. 异常处理
6. 配置开关

每个关键节点提供「文件路径:行号」。

输出：
调用链 → 数据表 → 事务/异常 → 可能风险。
找不到的环节明确标记「未找到」。
```

**得到：** 一条从入口到数据落点、带文件行号的完整调用链。

### 完成标准

> **知道改哪里、影响谁、数据走到哪里；无法确认的内容已经明确标出。**

---

## 02 · Rules

**把长期有效的项目约束交给 AI，不再依赖每次对话重复说明。**

### 什么时候使用

- 新项目建立 AI 开发规则
- 发现 AI 经常违反相同规范
- 需要检查已有规则是否有效

### 操作

#### ① 检查现有 Rules

```text
请只读检查当前项目已有的 AI 规则文件，不要修改。

检查：
1. 有哪些规则文件及生效范围
2. 是否存在重复或冲突
3. 是否包含一次性任务
4. 是否存在无法验证的规则
5. 是否缺少关键约束
6. 当前规则是否与项目实际情况一致

输出：
问题 → 依据 → 修改建议。

不要直接修改规则。
```

---

#### ② 生成项目 Rules

```text
请根据当前项目实际情况生成 AI 开发规则草稿。

先读取项目结构、技术栈和现有规范。

要求：
1. 只保留跨任务长期有效的规则
2. 明确「必须 / 禁止」
3. 每条规则尽可能可验证
4. 写清适用范围
5. 写清必要的例外情况
6. 不要编造项目不存在的技术约束

本轮只输出草稿，不写入文件。
```

---

#### ③ 验证 Rules 是否生效

```text
请检查当前项目的 AI Rules 是否真正生效。

检查：
1. 工具是否会读取这些规则
2. 文件位置和配置是否正确
3. 是否存在冲突或重复
4. 规则能否实际约束 AI 行为
5. 是否存在工具差异

只检查，不修改。
```

### 完成标准

> **规则少而明确、长期有效，并且 AI 确实能够读取和执行。**

---

## 03 · Skills

**把经过验证、会重复使用的方法沉淀成 Skill。**

### 什么时候使用

- 某种工作反复出现
- 已经形成稳定做法
- 希望以后直接复用

### 操作

#### ① 判断是否值得沉淀

```text
请判断下面这套做法是否值得沉淀为 Skill。

做法：
<描述>

检查：
1. 是否会重复出现？
2. 是否有稳定步骤？
3. 是否已经验证有效？
4. 是否可以跨任务复用？

如果不满足，请输出「暂不沉淀」并说明原因。

如果满足，请整理：
适用场景 → 前置条件 → 操作步骤 → 检查点 → 失败处理。
```

---

#### ② 创建 Skill

```text
请把下面已经验证有效的做法整理成 Skill 草稿。

做法：
<粘贴经验>

要求：
1. 面向重复使用，而不是一次性任务
2. 不写具体客户、项目、表名和业务数据
3. 步骤必须稳定、可执行
4. 每个关键步骤有检查点
5. 明确适用和不适用场景
6. 按当前使用的 AI 工具说明加载方式

只输出 Skill 草稿，不写文件。
```

---

#### ③ 检查 Skill

```text
请检查下面这个 Skill 是否适合长期复用。

重点检查：
1. 是否包含项目专属内容
2. 是否存在未验证的方法
3. 步骤是否明确
4. 检查点是否完整
5. 是否存在重复或无意义内容
6. 是否已经有实际任务验证

输出：
问题 → 风险 → 修改建议。

不要直接修改。
```

### 完成标准

> **只有稳定、重复、验证有效的方法才进入 Skill。**

## 04 · Agents

**适用于可以安全拆分、并行执行或需要独立审查的复杂任务。**

### 什么时候使用

- 前后端可以并行
- 不同模块可以并行
- 一个 Agent 开发、另一个 Agent 审查
- 任务复杂，需要多个专业角色

### 操作

#### ① 多 Agent 协作开发

一次提交完整任务，自动完成「评估分工 → 执行 → 统一验收」三个阶段。你只需发起一次任务，三个阶段是主 Agent 内部的工作流程，不需要手动分三次输入提示词。

```text
请评估下面的任务是否适合使用多 Agent 协作。如果适合，请自动完成任务拆分、分工、执行和最终验收；如果不适合，请说明原因，并建议使用单 Agent 完成。

任务：
<填写具体任务>

## 阶段一：任务评估与分工设计
1. 分析任务是否可以拆分为相对独立的子任务。
2. 检查任务之间的依赖关系、文件冲突和共享接口。
3. 判断多 Agent 是否比单 Agent 更高效。
4. 如果不适合多 Agent，说明原因并停止多 Agent 编排。
5. 如果适合，设计最小化分工方案。

分工要求：
- 明确每个 Agent 的职责和具体任务。
- 明确允许修改、只读和禁止修改的文件范围。
- 明确共享接口、数据结构和协作约定。
- 明确任务依赖和执行顺序。
- 指定主 Agent 负责协调、汇总和最终验收。

## 阶段二：执行任务
1. 按照分工启动各 Agent 执行任务。
2. 在任务允许的情况下并行执行，存在依赖时按顺序执行。
3. 各 Agent 严格遵守任务边界和项目开发规范。
4. 遇到重大设计问题、需求不明确或任务冲突时，暂停相关任务并反馈。
5. 主 Agent 持续协调进度，处理协作问题。
6. 各 Agent 完成后，汇报修改文件、实现内容、测试结果和遗留问题。

## 阶段三：汇总结果与统一验收
主 Agent 收集所有 Agent 的执行结果，并结合实际代码变更和 Git Diff 进行统一检查。

检查内容：
1. 是否完成原始需求。
2. 是否超出任务和文件修改范围。
3. 是否存在文件覆盖、修改冲突或重复实现。
4. 各模块之间的接口和数据结构是否一致。
5. 业务逻辑、异常处理和边界条件是否正确。
6. 是否存在代码质量问题。
7. 测试是否充分，是否有真实执行证据。
8. 是否存在遗留问题或潜在风险。

发现问题后：
- 明确且影响较小的问题，可以安排对应 Agent 修复。
- 涉及多个模块的问题，先协调相关 Agent 确认方案。
- 重大设计问题、需求偏差或超出原始范围的问题，先向用户说明。
- 修复完成后，重新检查代码并执行必要测试。

## 最终交付
请输出统一的执行报告：
1. 多 Agent 使用评估及分工情况。
2. 各 Agent 任务完成情况。
3. 实际修改文件及核心实现。
4. 发现的问题及修复情况。
5. 测试执行情况及结果。
6. 未解决的问题和遗留风险。
7. 最终验收结论：通过 / 有条件通过 / 未通过。

注意：
- 不得仅凭 Agent 自述判断任务完成。
- 不得将未执行的测试标记为通过。
- 不得擅自扩大修改范围。
- 不得隐瞒未完成事项。
- 最终验收由主 Agent 负责。
- 如果当前编程工具不支持子 Agent 创建、任务调度或并行执行，必须明确说明这一能力限制，不能假装已经启动了多个 Agent。
```

### 完成标准

> **一次任务拿到完整执行报告：评估、分工、执行、统一验收全部完成；验收结合真实代码和 Git Diff，不靠 Agent 自述，未执行的测试不算通过。**

## 05 · MCP / Tools

**让 AI 获得项目外部能力，但优先考虑必要性和最小权限。**

### 什么时候使用

- 需要访问数据库
- 需要操作 Git / 浏览器 / API
- 需要连接外部系统
- 需要检查现有工具权限

### 操作

#### ① 判断是否需要工具

```text
请判断下面这个任务是否有必要接入外部工具。

工具：
<工具>

用途：
<想解决的问题>

请判断：
1. 当前能力是否已经足够
2. 接入后是否明显提高效率
3. 是否存在更简单的替代方案
4. 需要什么最小权限
5. 工具不可用时如何继续工作

输出：
建议接入 / 暂缓 / 不需要。

不要进行实际配置。
```

---

#### ② 检查现有工具

```text
请只读检查当前项目已经接入的 MCP / Tools。

检查：
1. 有哪些工具
2. 每个工具能做什么
3. 当前权限范围
4. 是否存在过度授权
5. 是否涉及生产环境或敏感数据
6. 是否存在人工确认机制
7. 是否有降级方案

只输出问题和建议，不修改配置。
```

### 完成标准

> **只接入真正需要的工具，并使用足够完成任务的最小权限。**

## 06 · Hooks / Scripts

**把明确、重复、可自动判断的检查交给脚本，不靠 AI 和记忆。**

### 什么时候使用

- 每次开发都重复检查
- 检查结果可以明确判断
- 错误需要尽早阻止
- 希望减少人工检查

### 操作

#### ① 判断是否应该自动化

```text
请分析下面这些检查是否适合自动化。

检查：
<检查项>

逐项判断：
1. 是否重复出现
2. 是否可以明确判断通过/失败
3. 是否适合脚本执行
4. 是否需要业务判断
5. 失败后是否能明确告诉开发者如何修复

输出：
人工检查 / 脚本检查 / Hook 检查。

并说明原因。
```

---

#### ② 生成检查脚本

```text
请为下面的检查生成一个独立脚本。

检查：
<检查内容>

要求：
1. 不修改业务代码
2. 结果明确
3. 失败时说明原因
4. 给出修复建议
5. 给出运行命令
6. 给出退出码含义
7. 不依赖不可控的人工判断

输出：
脚本 + 使用方法。

先不要修改项目文件。
```

---

#### ③ 检查现有 Hooks

```text
请检查当前项目已有的 Hooks / 自动化检查。

判断：
1. 是否误报过多
2. 是否执行过慢
3. 是否重复
4. 是否应该改成手动执行
5. 是否存在值得增加的关键检查

输出：
保留 / 修改 / 删除 / 新增。

不要直接修改配置。
```

### 完成标准

> **自动化只处理稳定、明确、有价值的检查，不为了自动化而自动化。**

---

## 最后

### 开发前准备完成

在开始开发前，至少确认：

- AI 已了解需要修改的项目范围
- 必要的 Rules 已生效
- 已有可复用 Skill 可以正常使用
- 多 Agent 任务已经明确分工（如需要）
- MCP / Tools 权限合理（如使用）
- 关键自动化检查已经准备好（如需要）

**准备完成 → 进入「开发中」** → [开发中](/ai/productivity/dev-spec/02-lifecycle)
