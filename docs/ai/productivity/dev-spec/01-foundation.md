# 第一层 · AI 工程基础

> 让 AI 具备正确工作所需的能力：读懂项目、遵守规则、复用技能、分工协作、连接工具、自动检查。每个模块给可直接复制的命令，介绍只讲用途。

## 快速定位

| 模块 | 什么时候用 |
| ---- | ---------- |
| Project Context | 让 AI 快速了解项目、模块、调用链 |
| Rules | 生成或检查 AI 必须遵守的项目规则 |
| Skills | 把重复做法固化成可复用技能 |
| Agents | 多 Agent 分工、配置与结果审查 |
| MCP / Tools | 评估、接入、检查外部工具能力 |
| Hooks / Scripts | 把确定性检查交给自动化脚本 |

---

## Project Context · 项目上下文

**功能介绍**：让 AI 按需拿到准确的项目信息，不靠猜、不做无意义的全仓扫描。

**使用场景**
- 接手陌生项目
- AI 频繁理解错模块或业务
- 准备改涉及多个模块的功能

### 命令 · 项目快速认知

```text
请分析当前项目，先不要修改任何文件。

重点检查：
1. 项目技术栈和目录结构
2. 核心模块及其职责
3. 项目启动、构建和测试命令
4. 关键配置文件和外部依赖
5. 核心业务入口和主要调用关系

输出一份简明项目说明，所有结论尽可能提供文件路径作为依据，无法确认的内容单独列出。
```

### 命令 · 模块分析

```text
请只读分析 <模块名或目录>，不要修改任何文件。

输出：
1. 这个模块的职责和边界
2. 对外暴露的接口 / 入口
3. 内部关键文件及各自作用
4. 依赖哪些模块、被哪些模块调用
5. 涉及的数据表或外部服务

结论带文件路径，推测标「待确认」。
```

### 命令 · 业务调用链分析

```text
请只读追踪一条完整调用链，不要修改任何文件。

入口：<接口路径或页面操作，如 POST /api/order/create>

要求：从入口追到数据落点，覆盖同步调用、异步任务、消息消费、配置开关；每步给出「文件路径:行号」；标出事务边界、异常处理和读写的表；找不到的环节明确写「未找到」。

输出：链路清单 / 涉及的表 / 事务与异常 / 最易出错的位置。
```

**预期结果**：一份带文件路径依据的项目说明、模块说明或调用链，能直接用来定位「改哪里、影响谁」。

## Rules · 项目规则

**功能介绍**：把跨任务成立的约束写成 AI 每次都会读到的规则，不用每次对话重复交代。

**使用场景**
- 新项目要建立开发约定
- AI 命名、分层、命令各做各的
- 口头禁令换个会话就失效

### 命令 · 检查现有规则

```text
请只读检查当前项目已有的 AI 规则文件（如 AGENTS.md、.cursor/rules 等），不要修改任何文件。

输出：
1. 找到了哪些规则文件、各自生效范围
2. 每条规则是否可验证（能否说清怎么算违反）
3. 是否混入了一次性任务、完整业务流程、操作步骤
4. 是否有「尽量 / 建议」这类无法验证的软规则
5. 缺失的关键约束（技术栈、命令、禁改目录、安全红线）

只列问题和依据，不要替我改写规则。
```

### 命令 · 生成项目规则

```text
请根据当前项目现状和下面的约定，生成一份 AI 规则文件草稿。本轮只输出草稿，不写文件。

项目约定：<粘贴口头约定、命令、禁令>

要求：
1. 只保留跨任务成立、能验证的约束
2. 每条用「必须 / 禁止」并配验证方式（命令或 diff 特征）
3. 禁止项配一条反例
4. 删掉无法验证的软规则
5. 写明适用范围和例外审批方式
6. 具体文件放哪、怎么加载，按我使用的工具说明，不要假设通用目录

输出：规则草稿 + 被删内容及原因。
```

### 命令 · 检查规则是否生效

```text
请验证当前 AI 规则是否真的对新会话生效，只做检查，不修改文件或配置。

检查：
1. 规则文件是否放在工具会读取的位置（按我使用的工具为准）
2. 规则内容是否自相矛盾或重复
3. 能否给出 2～3 个具体场景，说明每条关键规则会怎样约束 AI 的行为

输出：生效情况 + 存疑点 + 需要我确认的工具差异。
```

**预期结果**：知道项目有没有规则、规则写得好不好、要不要补,以及该放哪个工具目录。

> 不同 AI 工具的规则文件名、目录、加载方式不同。上面的命令不假定固定路径，需要时把「我使用的工具是 Cursor / WorkBuddy」补进命令。

## Skills · 专业技能

**功能介绍**：把反复用、验证有效的做法固化成技能，让 AI 按固定步骤做，而不是每次重新发明。

**使用场景**
- 同类操作做过很多次
- 好做法只活在某次对话里
- 要把个人经验沉淀成可复用能力

### 命令 · 识别可沉淀技能

```text
请回顾本次任务，判断有没有值得沉淀为 Skill 的做法。本轮只判断，不创建文件。

先回答三问：
1. 这个做法还会再出现吗？
2. 不沉淀的代价是什么？
3. 有没有第二处任务能验证它？

任一答不上来，就写「暂不沉淀」，并说明留在哪里（交付报告 / 认知资料）。
三条都成立，才列出可沉淀的做法和它稳定的步骤、检查点。
```

### 命令 · 创建 Skill

```text
请把下面这套做法整理成一个 Skill 草稿。本轮只输出草稿，不写文件。

做法记录：<粘贴步骤、检查点、踩过的坑>

要求：
1. 只写「怎么做」的通用方法，不要写具体表名、客户名、业务字段
2. 包含：适用场景、不适用、前置条件、带检查点的操作步骤、失败处理、复用记录表
3. 步骤要稳定可复现，不是靠临场发挥
4. 标注这个 Skill 放在哪里、怎么被工具加载（按我使用的工具说明）

输出：Skill 草稿。
```

### 命令 · 检查 Skill 质量

```text
请检查下面这个 Skill 是否适合跨项目复用，只输出问题清单，不改内容。

<粘贴 Skill 内容>

检查：
1. 是否混入具体表名、客户名、业务字段
2. 是否混入一次性临时绕法、未验证的做法
3. 步骤有没有明确检查点
4. 是否有复用记录和至少两处验证

每条给原文片段、问题、建议。
```

**预期结果**：判断出值不值得沉淀、拿到一份干净的 Skill 草稿，或明确「暂不沉淀」。

## Agents · 智能体协作

**功能介绍**：明确多个 AI 角色各做什么、能改哪些文件，避免互相覆盖、自己宣布完成。

**使用场景**
- 前后端或模块能并行、互不冲突
- 想让一个 Agent 执行、另一个审查
- 多人多 Agent 同时改一个项目

### 命令 · 任务分工

```text
这个任务需要多 Agent 并行。请先给出分工方案，不要开始改代码。

任务：<一句话>
冻结的契约：<接口 / 数据结构 / 字段名；若尚无，写「需先冻结」>

要求：
1. 按文件所有权划分，同一文件不被同时改，列出每个 Agent 负责的文件和只读文件
2. 契约没冻结就只做契约设计，不进入并行实现
3. 每个 Agent 都收到同一份任务、修改范围、不做项和验收标准
4. 分工含执行者和审查者，审查者只输出问题清单、不判定通过
5. 说明结果如何收拢、由谁做最终验收

先输出分工表和风险点，等我确认再启动。
```

### 命令 · 生成 Agent 配置

```text
请根据下面的角色职责，生成一份 Agent 配置草稿。本轮只输出草稿，不写文件。

角色：<名称>　职责：<规划 / 执行 / 审查>　权限：<能改哪些文件>

要求：
1. 写清职责、可改文件、只读文件、明确不做的事
2. 写清共同上下文：任务、修改范围、禁止修改、必须兼容、验收标准
3. 审查类角色必须写明「不判定通过，最终由人确认」
4. 配置语法、文件名和放置位置按我使用的工具说明，不要假设通用格式

输出：Agent 配置草稿 + 需要我确认的工具差异。
```

### 命令 · 协作结果审查

```text
请审查下面这些 Agent 的产出和 diff，只输出问题清单，不修改文件，不宣布通过。

<粘贴各 Agent 的产出与 diff>

检查：
1. 各自改动是否超出文件所有权、是否互相覆盖
2. 接口 / 数据结构是否按冻结的契约实现
3. 是否有 One Agent 改了另一个 Agent 负责的文件
4. 功能、边界、异常、兼容性问题
5. 是否留下调试代码、遗漏 TODO

输出：越界项 / 冲突项 / 质量问题 / 需人确认的疑点。
```

**预期结果**：一份边界清晰的分工方案、Agent 配置草稿，以及可核对的多 Agent 产出问题清单。

## MCP / Tools · 工具与外部能力

**功能介绍**：让 AI 安全地连接仓库外的能力和数据，接入前先判断值不值得、权限会不会过大。

**使用场景**
- 想接数据库、浏览器、外部 API 等能力
- 不确定某个工具该不该接
- 要检查现有工具权限是否过大

### 命令 · 工具需求评估

```text
请评估是否值得接入下面这个工具，本轮只评估，不做配置。

工具：<名称>　想解决的场景：<描述>　当前卡点：<描述>

按三问评估：
1. 必要性：这个能力是不是仓库内拿不到、又确实必须？有没有更简单的替代？
2. 边界：开放什么权限？只读还是可写？能碰生产环境或敏感数据吗？
3. 降级：它不可用时怎么办？有没有替代检查或手动方案？

输出：三问结论 + 权限最小化建议 + 哪些动作必须人确认 + 结论（建议 / 暂缓 / 不建议）。答不上的标「待确认」，不要替我假设。
```

### 命令 · 接入配置检查

```text
请只读检查当前已接入的 AI 工具 / MCP 配置，不要修改任何文件。

对每个工具列出：
1. 开放了什么能力
2. 权限级别（只读 / 可写）和访问范围
3. 是否触及生产或敏感数据
4. 不可用时有没有降级方案
5. 是否记录了谁配置、怎么降级

输出：能力清单 + 风险项（权限过大 / 触生产 / 无降级）。配置语法按我使用的工具核对。
```

### 命令 · 权限检查

```text
请检查下面这个工具的权限设置是否符合最小化原则，只输出检查结论，不修改配置。

工具：<名称>　当前权限：<描述>

检查：
1. 能否只读就不给写权限
2. 能否连测试库就不连生产库
3. 能否限定目录就不开放全盘
4. 删除、写入、发送等动作是否设为需要人确认

输出：不合规项 + 建议的最小权限配置。涉及生产凭据时，只描述配置方式，不要打印任何真实密钥。
```

**预期结果**：明确该不该接、接了哪些、权限是否最小、哪些动作需要人工确认。

## Hooks / Scripts · 自动化执行

**功能介绍**：把「漏了就出事、且能明确判定」的检查交给脚本和 Hook，不靠 AI 记得或人工盯。

**使用场景**
- 同样检查每次都要手动跑
- 密钥、禁改区这类红线没人自动拦
- Hook 装太多、误报不断

### 命令 · 自动化检查设计

```text
下面这些检查每次都要手动做，请设计成自动化方案。本轮只出方案，不写代码、不改配置。

检查清单：<粘贴>

对每项判断：
1. 是否「漏了就出事且能明确判定」——是则适合脚本化，否则说明留人工
2. 脚本的输入输出、失败时的报错（要说清怎么改）
3. 触发时机：显式运行还是提交前 Hook

输出：可脚本化清单 + 每项方案 + 建议挂到 Hook 的最小集合（只挑最关键最稳的，避免误报）。
```

### 命令 · 生成检查脚本

```text
请为下面这项检查生成一个可独立运行的脚本，并说明用法。

检查项：<描述>　项目技术栈：<描述>

要求：
1. 检查结果非黑即白，不依赖业务判断
2. 失败时报错说清「哪里不对、怎么改」
3. 不删除、不修改任何文件，除非我明确要求
4. 给出运行命令和退出码含义

输出：脚本内容 + 用法说明。
```

### 命令 · Hook 配置检查

```text
请只读检查当前 Hook / 自动化检查配置是否过载，不要修改配置。

<粘贴现有 Hook 清单，或让 AI 读取后列出>

检查：
1. 哪些检查误报多、很少拦住真问题
2. 哪些太慢、拖慢日常操作
3. 哪些需要业务判断、不该自动化
4. 有没有「漏了就出事且能判定」但没覆盖的检查

输出：建议移除 / 改为显式 / 新增的清单及理由。配置语法按我使用的工具核对。
```

**预期结果**：一份该自动化的最小清单、可运行的检查脚本，以及一份不误报的 Hook 配置建议。
