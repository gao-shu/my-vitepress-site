# Git 与版本管理

> 第三层 · 质量保障。解决「怎么保护已有改动、让每次变更可追溯」——Git 是项目资产的安全底线，AI 改动最容易在这里出事。

## 贯穿全流程的定位

Git 检查在每个产生改动的环节都要做，尤其是每轮开发提交前和最终交付前。

## 核心内容

### 提交前的硬规矩

- **先看 `git status`**，识别用户已有的修改、未跟踪文件、暂存区内容。
- **不覆盖用户已有改动**：AI 的改动和用户改动在同一文件时，停下来说明，不擅自 `checkout --`、`reset --hard`、`stash` 或强行合并。
- 判断不了某处改动是谁改的，停下来问，不猜。
- 改动文件都在允许范围内，没触碰禁改区和依赖文件。
- 不擅自 `push`、不擅自合并、不擅自删分支——这些由人决定。

### 提交信息

写清「改了什么、为什么」，不说「update」「fix bugs」这类空话。一个提交对应一个能独立验收的子任务，不把所有改动堆成一次提交。

### diff 检查

提交前逐项看 diff：

- [ ] 改动文件都在允许范围，没有批量格式化无关文件。
- [ ] 依赖文件（`pom.xml`、`package.json` 等）没有意外变更。
- [ ] 没有硬编码特判、吞异常、放宽断言。
- [ ] 没有删除或注释掉现有测试。
- [ ] 没有留下调试打印、TODO、注释掉的分支。
- [ ] 提交信息说清了改了什么、为什么。

### 保留用户改动的判断原则

宁可多问一句，不要覆盖用户写的东西。以下操作一律先确认：

- 同一文件既有用户改动又有 AI 改动。
- 需要 `git checkout`、`git restore`、`git reset` 才能继续。
- 暂存区里有不是这次任务的内容。

## 可复制提示词

<details>
<summary><strong>提交前 Git 安全检查</strong></summary>

```text
请对当前工作区做提交前检查，只输出检查结果，不执行任何 git 写操作（不 add、不 commit、不 checkout、不 reset、不 stash、不 push）。

请先读取：git status、git diff、git diff --cached、最近几条 git log。

检查项：
1. 有哪些用户已有的改动、未跟踪文件、暂存内容；和本次任务改动是否混在一起。
2. 改动文件是否都在允许范围，是否触及禁改区和依赖文件。
3. diff 里是否有硬编码、吞异常、放宽断言、删除测试、调试打印、遗留 TODO、批量格式化。
4. 提交信息是否说清「改了什么、为什么」。

输出：
- 可以安全提交的文件清单。
- 需要人确认的冲突或疑点（逐条说明）。
- 建议的提交拆分方式（如果一个提交混了多件事）。

不要替我做任何判断性合并，不要覆盖任何已有改动。
```

</details>

## 验收要点

- [ ] 提交前看过 status，用户已有改动被完整保留。
- [ ] 没有擅自 checkout / reset / stash / push / 合并。
- [ ] diff 检查全过，没有禁改内容混进来。
- [ ] 提交信息说清改了什么、为什么。
- [ ] 一个提交对应一个能独立验收的改动。

变更的更细控制（范围、检查点、回滚）见 [变更控制](/ai/productivity/dev-spec/03-quality/change-control)。
