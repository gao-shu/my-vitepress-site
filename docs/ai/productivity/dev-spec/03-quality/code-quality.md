# 代码质量规范

> 第三层 · 质量保障。这一层贯穿项目准备到最终交付的每一步，不是收工才执行。本页聚焦「怎么让代码本身可靠」——审查有清单、改动有边界、问题有依据。

## 贯穿全流程的定位

第三层不是第二层之后的「第九步」。它在每个阶段都生效：

| 阶段 | 代码质量在做什么 |
| ---- | ---------------- |
| 项目准备 | 确认代码规范、禁改区、构建检查命令 |
| 需求 / 架构 | 把质量要求写进验收标准和方案 |
| 开发 | 每轮改动做局部质量检查 |
| 审查 | 按清单逐项核对 |
| 修复 / 重构 / 测试 | 保证修复不引入新问题、重构不改行为 |
| 交付 | diff 全量检查、遗留问题归零 |

## 核心内容

### 代码审查清单

- **逻辑与规则**：业务规则实现完整，边界条件（空值、零值、重复、越权）处理到位。
- **异常与事务**：异常不被吞掉，事务边界合理，失败不留半状态数据。
- **兼容性**：接口签名、字段含义、返回结构变化已确认，调用方不受影响。
- **测试**：关键路径和失败路径有测试，断言没被放宽或删除。
- **改动范围**：没有无关格式化、未用 import、调试打印、注释掉的分支、遗留 TODO。
- **可读性**：命名和分层符合项目现有风格，没有明显重复或更简单的写法。

### 硬红线

发现以下情况必须处理，不能带过：

- 硬编码特定值绕过问题。
- 吞掉异常让错误消失。
- 放宽断言、删除失败用例让测试变绿。
- 给某条数据加特判掩盖规则问题。
- 改动超出约定范围、触碰禁改区。

### 让 AI 有效自查

- 明确要求「只输出问题清单和依据，不修改文件、不宣布通过」。
- 每条问题指到 `文件:行号` 和依据，不说「整体还行」。
- 审查者不判定通过，最终由人判定（见 [Agents](/ai/productivity/dev-spec/01-foundation/agents)）。
- 能脚本化的检查（构建、lint、密钥扫描、禁改区 diff）交给脚本（见 [Hooks / Scripts](/ai/productivity/dev-spec/01-foundation/hooks-scripts)），不靠提示词提醒。

## 可复制提示词

<details>
<summary><strong>代码质量自查</strong></summary>

```text
请对下面的改动做代码质量自查，只输出问题清单，不修改文件，不宣布通过。

改动：<粘贴 diff 或代码>
约定：修改范围、禁改区、项目规范（粘贴）

按清单检查：
1. 逻辑与业务规则完整性、边界条件。
2. 异常处理与事务边界。
3. 接口、字段、数据兼容性。
4. 测试覆盖与断言是否被放宽。
5. 改动范围：无关格式化、未用 import、调试打印、注释分支、遗留 TODO。
6. 可读性与重复代码。

每条问题给「文件:行号 | 问题 | 依据 | 建议改法」。
单独列出硬红线命中项（硬编码、吞异常、放宽断言、数据特判、越界改动）。
没有问题也逐项写「已检查，无问题」，不要只给结论。
```

</details>

## 验收要点

- [ ] 审查清单逐项过完，问题带文件行号和依据。
- [ ] 硬红线命中项为零，或已全部处理。
- [ ] 改动范围合规，没有遗留调试代码。
- [ ] AI 自查没有自行宣布通过，判定由人做。

质量检查的细节手法见 [提示词库 · 编程开发](/ai/prompts/coding)。
