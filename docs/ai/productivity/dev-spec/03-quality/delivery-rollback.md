# 交付追踪与回滚

> 第三层 · 质量保障。解决「交付后能不能追溯、出问题能不能回滚」——用交付报告留痕，用回滚方案兜底，让每次改动都可进可退。

## 贯穿全流程的定位

追踪和回滚的意识要从改动前就有，不是出问题才想：

| 时机 | 要做什么 |
| ---- | -------- |
| 改动前 | 记录起始状态（分支、提交、未提交改动） |
| 开发中 | 每轮提交，形成可回退的粒度 |
| 交付时 | 交付报告留痕，写清改了什么、证据、遗留 |
| 交付后 | 出问题能按提交定位、按方案回滚 |

## 核心内容

### 交付追踪

交付报告是追溯的核心。最少记录：

- 任务、级别、修改范围、不做项执行情况。
- 修改文件清单（改了什么、为什么）。
- 验证证据（命令与输出关键行）。
- 安全检查结论。
- 遗留问题（是什么、影响、建议、谁决定）。
- 本次沉淀去向。

遗留问题必须有去处：建待办、写进认知资料，或在报告里留痕并有人负责。「下次再说」不算处理。

### 回滚方案

复杂改动（涉及数据结构、接口契约、多文件、数据库迁移）在方案阶段就要写回滚方案：

| 项 | 内容 |
| -- | ---- |
| 回滚触发条件 | 什么情况下必须回滚 |
| 回滚粒度 | 按哪个提交 / 哪个阶段回退 |
| 数据回滚 | 迁移能否逆执行，数据能否恢复 |
| 兼容性兜底 | 新旧版本能否并存，是否需要开关 |
| 回滚后验证 | 回到什么状态算回滚成功 |

**不是所有改动都要真回滚**。有时前滚修复更快，但要先判断，不默认硬扛。

### 出问题后的处理顺序

1. 复现并固定证据（见 [06 逻辑与 BUG 修复](/ai/productivity/dev-spec/02-lifecycle/bugfix)）。
2. 判断是前滚修复还是回滚——看改动范围、数据影响、时间成本。
3. 按回滚方案执行，保护未涉及的改动。
4. 回滚后验证，确认回到可用状态。
5. 在交付报告里记录这次事故和处理方式。

### Git 层的可回退性

- 每轮子任务一次提交，粒度够细才能精确回退。
- 提交信息说清改了什么，方便定位。
- 不擅自 `reset --hard`、强推、删分支（见 [Git 与版本管理](/ai/productivity/dev-spec/03-quality/git-version)）。

## 可复制提示词

<details>
<summary><strong>生成回滚方案</strong></summary>

```text
请为下面这次改动生成回滚方案，本轮只输出方案，不执行。

改动内容：<描述>
涉及范围：<文件 / 接口 / 数据表 / 迁移>

请按以下结构输出：
1. 回滚触发条件：什么情况下必须回滚。
2. 回滚粒度：按哪个提交或阶段回退，列出相关提交。
3. 数据回滚：迁移是否可逆向，数据如何恢复，是否有丢失风险。
4. 兼容性兜底：新旧版本能否并存，是否需要开关。
5. 回滚步骤：按顺序写清每一步，标出需要人确认的操作。
6. 回滚后验证：怎么确认回到了可用状态。

无法回滚的部分明确标出，并说明替代处理方式（比如只能前滚修复）。
```

</details>

<details>
<summary><strong>交付追溯自查</strong></summary>

```text
请检查下面这份交付报告是否足以支撑后续追溯，只输出检查结果。

报告：<粘贴>

检查项：
1. 能否看清改了哪些文件、为什么改。
2. 验证结果是否有命令和输出证据，四态是否分清。
3. 遗留问题是否逐条列出、有人负责、有去处。
4. 是否记录了用户已有改动的处理情况。
5. 复杂改动是否有回滚方案或回滚说明。

每项给「满足 / 缺失 + 需要补什么」。最后判断：如果三个月后出问题，靠这份报告能不能定位到这次改动。
```

</details>

## 验收要点

- [ ] 复杂改动在方案阶段就有回滚方案。
- [ ] 每轮提交粒度细，提交信息可定位。
- [ ] 交付报告完整，遗留问题有去处、有人负责。
- [ ] 回滚方案写清触发条件、粒度、数据、验证。
- [ ] 出问题时能按提交定位、按方案回退。

到这里，三层体系完整闭环：**第一层**提供能力，**第二层**规范过程，**第三层**全程保障。整套规范的价值不在页数，而在每次开发都能少问、少错、可追溯。
