# 变更控制

> 第三层 · 质量保障。解决「怎么控制改动范围、让每一步可追踪可回退」——修改范围三栏、检查点、失败分类、遗留文件清理都在这里统一约束。

## 贯穿全流程的定位

变更控制从需求阶段定边界开始，贯穿开发每一轮，直到交付：

| 阶段 | 变更控制在做什么 |
| ---- | ---------------- |
| 需求 / 架构 | 定修改范围三栏、不做项、契约 |
| 开发 | 每轮只做范围内的一个子任务，越界先停 |
| 修复 / 重构 | 最小改动，不动无关代码 |
| 交付 | diff 全量核对，遗留文件清理 |

## 核心内容

### 修改范围三栏

每次任务都要写清三栏，落到具体文件路径：

```text
允许修改：
- backend/.../service/WorkOrderService.java
- web/src/api/mes.ts

禁止修改：
- 任何已有接口路径与方法签名
- legacy/ 目录

必须保持兼容：
- GET /api/mes/work-orders 的返回结构
- 现有状态机的流转规则
```

AI 说「顺手把……也改了」、开始改依赖或公共模块，立即停。

### 检查点

方案里预先约定哪些是检查点（如契约冻结后、数据层改完、接口联调前）。到检查点必须停下来等人确认，不自行通过。人只需回答：选哪个方案、加哪些边界、哪些风险不接受。

### 失败分类

不要一律重试。先分类再处理：

| 类型 | 信号 | 处理 |
| ---- | ---- | ---- |
| 代码错误 | 编译失败、断言失败、堆栈明确 | 可重试有限轮次 |
| 环境问题 | 缺服务、缺权限、缺数据 | 标受限，写替代检查 |
| 认知问题 | 反复改不对、改 A 坏 B | 停手回分析影响范围 |
| 需求冲突 | 测试过但行为不符预期 | 停手交人确认 |

### 遗留文件清理

开发过程中产生的临时文件、调试脚本、备份文件、生成物，交付前统一清理：

- 临时文件、`.bak`、`.tmp`、`~` 结尾的备份。
- 一次性调试脚本、临时日志。
- 被注释掉的旧代码、遗留 TODO。
- 构建产生的、不该进版本库的产物。

清理也要在范围内：只删这次任务产生的，不删用户已有的文件。判断不了归属就问。

## 可复制提示词

<details>
<summary><strong>变更范围检查</strong></summary>

```text
请检查本次改动是否超出约定范围，只输出检查结果，不修改任何文件。

修改范围三栏（粘贴）：
允许修改 / 禁止修改 / 必须保持兼容

当前 git status 和 git diff（粘贴）

请逐项检查：
1. 实际改动文件是否都在「允许修改」内。
2. 是否触碰「禁止修改」。
3. 是否有超出三栏的意外改动（依赖文件、公共模块、无关格式化）。
4. 「必须保持兼容」的内容是否真的没变（接口、字段、状态流转）。

输出：合规清单 + 越界项（文件:行号 + 说明）+ 需人确认的疑点。
```

</details>

<details>
<summary><strong>遗留文件清理清单</strong></summary>

```text
请扫描本次开发遗留的临时文件，输出清理清单，本轮只列清单，不删除。

扫描范围：<本次任务涉及的目录>
任务起始时间或提交：<用于判断哪些是本次产生的>

请列出：
1. 临时文件、备份文件（.bak / .tmp / ~ / .orig 等）。
2. 一次性调试脚本、临时日志、导出的数据文件。
3. 代码里注释掉的旧实现、遗留 TODO。
4. 构建产物中不该进版本库的部分。

每项标注：路径、判断为本次产生的依据、建议动作。
无法判断归属的一律标「需人确认」，不要列入自动清理。
```

</details>

## 验收要点

- [ ] 修改范围三栏写清并落到文件路径。
- [ ] 每轮改动在范围内，越界情况为零或已处理。
- [ ] 检查点停下来等确认，没有被跳过。
- [ ] 失败先分类，没有无限重试。
- [ ] 遗留文件清理完，没有误删用户文件。

回滚的方案与追踪见 [交付追踪与回滚](/ai/productivity/dev-spec/03-quality/delivery-rollback)。
