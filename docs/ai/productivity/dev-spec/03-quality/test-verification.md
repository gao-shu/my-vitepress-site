# 测试与验证规范

> 第三层 · 质量保障。解决「怎么证明结果正确」——用证据说话，分清已验证和没验证，保证每次交付都能回答「测了什么、结果怎样、什么没测」。

## 贯穿全流程的定位

测试验证不是开发结束才做。它在每个阶段有不同形态：

| 阶段 | 验证形态 |
| ---- | -------- |
| 项目准备 | 实际跑通构建、启动、测试命令 |
| 开发每轮 | 跑该子任务完成标准对应的命令 |
| 修复 | 修复闭环里每轮验证 + 回归对照 |
| 交付 | 按任务级别补全测试 + 四态报告 |

## 核心内容

### 四态纪律

| 状态 | 含义 | 怎么写 |
| ---- | ---- | ------ |
| 已验证 | 实际执行且有输出证据 | 「单测 X 通过，输出见日志」 |
| 未验证 | 有理由没跑，或跑了没证据 | 「测试库不可用，已用本地库跑单测替代」 |
| 受限 | 环境或权限不允许 | 「生产配置只读，未做线上验证」 |
| 不适用 | 本次改动不涉及 | 「未涉及前端改动，无需浏览器验证」 |

**不能执行的测试不得写成通过；没有输出的「已测试」等于没测试。** 这是整个规范里最重要的一条纪律。

### 验证证据要求

| 项 | 合格证据 | 不合格写法 |
| -- | -------- | ---------- |
| 编译 | 命令原文 + 成功输出 | 「编译通过」 |
| 单测 | 命令原文 + 通过数 / 失败数 | 「测试都过了」 |
| 接口冒烟 | 请求与返回原文 | 「接口正常」 |
| 类型检查 | 命令原文 + 输出 | 「类型没问题」 |

### 回归验证

三个层次：同模块（共用方法、共用 DTO、同张表）、上下游（调用方、消息消费方）、全局（权限、租户、状态机、事务）。

做对照表，至少留一条「改前行为保持」的证据：

```text
| 场景 | 改前行为 | 改后行为 | 验证方式 | 结论 |
| ---- | -------- | -------- | -------- | ---- |
| 正常关闭订单 | 成功 | 成功 | 单测 + 页面 | 一致 |
| 状态筛选 | 返回其他状态 | 只返回目标状态 | 单测 | 已修复 |
```

### 必须跑回归的时机

数据层改动后、接口契约变更后的第一轮前端改动、复杂任务的阶段性检查点、最终验收前。

## 可复制提示词

<details>
<summary><strong>验证报告模板</strong></summary>

```markdown
# 验证报告 · <任务短名>

## 已验证（有证据）
| 项 | 命令 | 输出关键行 | 结论 |
| -- | ---- | ---------- | ---- |
|    |      |            | 通过 |

## 未验证 / 受限 / 不适用
| 项 | 状态 | 原因 | 替代检查 |
| -- | ---- | ---- | -------- |

## 回归对照
| 场景 | 改前 | 改后 | 结论 |
| ---- | ---- | ---- | ---- |

## 遗留问题
- <逐条列出，不藏>
```

</details>

<details>
<summary><strong>验证结果真实性自查</strong></summary>

```text
请检查下面这份「已完成」报告里，有没有把未验证的内容写成通过。本轮只检查，不改内容。

报告：<粘贴报告>

检查项：
1. 每条「通过」是否附了实际执行的命令和输出证据。
2. 有没有把「未跑」「环境受限」「不适用」写成通过。
3. 回归对照是否同时包含「已修复」和「改前行为保持」。
4. 有没有编造的测试输出或结果。

输出：可疑条目清单（原文 + 为什么可疑 + 需要补什么证据）。
```

</details>

## 验收要点

- [ ] 每条通过都有命令和输出证据。
- [ ] 四态区分清楚，没跑的没写成通过。
- [ ] 回归对照含「改前行为保持」证据。
- [ ] 没验证、受限、不适用的都说明了原因和替代方案。
