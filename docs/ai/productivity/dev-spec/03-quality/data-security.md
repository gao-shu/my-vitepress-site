# 数据与安全规范

> 第三层 · 质量保障。解决「怎么保护项目资产和数据」——敏感信息、破坏性操作、输入与权限、依赖风险，从项目准备到交付全程检查。

## 贯穿全流程的定位

数据安全不是上线前才查。它在各阶段的关注点：

| 阶段 | 关注点 |
| ---- | ------ |
| 项目准备 | 标记生产资源、敏感目录、禁改区 |
| 架构 | 数据迁移、权限模型、敏感字段设计 |
| 开发 | 不写死密钥、不打印隐私、外部入参校验 |
| 修复 / 重构 | 保护已有数据，改动可回滚 |
| 交付 | 全项安全检查，命中红线先停 |

## 核心内容

### 敏感信息

- 密钥、令牌、密码、手机号、身份证号不写进代码、配置、日志、提交信息。
- `.env`、凭证文件不进版本库；提供示例文件而非真实值。
- 日志不打印完整请求体、用户隐私、认证头。
- 提交前过一遍密钥扫描脚本。

### 破坏性操作

以下操作命中即停，需人确认：

- 删除数据、清库、改生产配置、不可逆迁移。
- 脚本里写死生产地址或高权限账号。
- 覆盖用户已有改动、强推、删除分支。
- 批量删除文件、批量格式化无关目录。

**能只读就不写，能连测试库就不连生产库，能限定目录就不开放整个文件系统。**

### 输入与权限

- 外部入参校验：类型、长度、格式、范围。
- 越权访问拦截：数据范围、租户隔离、角色权限。
- 文件上传、路径拼接、SQL 拼接、命令拼接的风险检查。
- 幂等与重复执行：接口重试、消息重复消费不产生错误数据。

### 依赖与供应链

- 不新增来源不明的依赖或脚本。
- 依赖版本锁定，不随意升级框架。
- 新增核心依赖需方案确认。

## 检查清单模板

```markdown
## 安全检查（每次交付前）

| 项 | 结论 | 说明 |
| -- | ---- | ---- |
| 敏感信息 | 已检查 / 未检查 / 不适用 | |
| 破坏性操作 | 已检查 / 未检查 / 不适用 | |
| 输入校验 | 已检查 / 未检查 / 不适用 | |
| 权限与数据隔离 | 已检查 / 未检查 / 不适用 | |
| 依赖变更 | 无 / 有（已确认） | |

命中红线：<逐条列出，或「无」>
```

## 可复制提示词

<details>
<summary><strong>交付前安全检查</strong></summary>

```text
请对本次改动做安全自查，只输出检查结果，不修改文件。

改动：<粘贴 diff>

按四块检查：
1. 敏感信息：是否写入密钥、令牌、密码、隐私数据；是否打印完整请求体；凭证文件是否被跟踪。
2. 破坏性操作：是否有删数据、清库、改生产配置、不可逆迁移；是否写死生产地址或高权限账号。
3. 输入与权限：外部入参是否校验；越权和数据范围是否拦截；路径/SQL/命令拼接是否安全；是否考虑幂等。
4. 依赖与供应链：是否新增未知依赖或脚本，版本是否锁定。

每项给「已检查 / 未检查 / 不适用」和依据。命中红线的单独列出并标「需人确认」。
```

</details>

<details>
<summary><strong>权限与数据范围自查</strong></summary>

```text
请针对本次功能做权限与数据范围自查，本轮只分析，不改代码。

功能描述：<粘贴>

请检查：
1. 谁能访问这个功能，是否有越权风险。
2. 查询和写入是否带了必要的数据隔离条件（租户、用户、组织）。
3. 直接调用接口（绕过前端）能否看到不该看的数据。
4. 关键操作是否有二次校验。
5. 重复提交或重复消费会发生什么。

每条给「风险 → 触发条件 → 建议」。没问题的项写「已检查，无问题」。
```

</details>

## 验收要点

- [ ] 敏感信息、破坏性操作、输入权限、依赖四项都有明确结论。
- [ ] 没有密钥、隐私数据进入代码或日志。
- [ ] 破坏性操作都有人确认，没有写死生产资源。
- [ ] 外部入参校验、越权拦截、幂等处理到位。

Git 层面的资产保护见 [Git 与版本管理](/ai/productivity/dev-spec/03-quality/git-version)。
