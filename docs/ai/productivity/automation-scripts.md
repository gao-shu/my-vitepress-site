# 用 AI 写自动化脚本

## 场景与问题

自动化脚本是 AI 编程回报率最高的场景之一：脚本短、逻辑直、验证快，而且写脚本的人通常不是专业开发，从零学一门语言的性价比极低。清理文件、批量重命名、定时备份、抓数据、格式转换——这些“一次性但会重复”的活，正好让 AI 代劳。很多时候你甚至不需要看懂每一行，能把任务描述清楚就够了。

但自动化有个特殊风险：脚本跑起来人不在场，而且很多操作不可逆。`rm -rf` 拼错一个路径，或者定时任务每天凌晨静默执行一个有 bug 的删除逻辑，等你发现时损失已经造成。AI 写的脚本尤其要防这个——它对“危险”没有体感，只对“完成任务”有执念，你让它“清空目标目录里的旧文件”，它可能连目录本身一起处理了。

## 做法

### 1. 让 AI 生成脚本的标准流程

- **描述环境**：操作系统、有没有 Python/Node/PowerShell、涉及的工具和版本。不说清环境，AI 会给你一个在它想象的 Linux 上能跑的 bash。
- **描述数据流**：输入是什么、输出到哪、正常情况长什么样、异常情况有哪些。最好给一条真实的样例数据，包括边界样例（空文件、重名、超长路径）。
- **要求先给方案再写码**：让它先列出步骤和用到的命令，你确认逻辑无误再让它展开。逻辑错了，代码再漂亮也是错的。
- **要求可配置**：路径、数量、时间这类参数抽成变量或命令行参数写在文件头，不要硬编码在逻辑里。下次换目录不用改代码。
- **要求带注释和用法说明**：脚本头部写清楚用途、参数、示例。三个月后你自己回来，靠的就是这段说明。

### 2. 危险操作必须确认

在提示词里就写明安全要求，这是最重要的一条：

- 删除、覆盖、移动、格式化、发送请求等不可逆操作，默认只打印将要做什么（dry-run 模式），加 `--execute` 之类的开关才真执行。
- **先在小样本上跑**：先处理 3 个文件，人眼看过输出再放开到全部。
- **备份先行**：批量改动前，脚本第一步先把原数据复制到备份目录，或至少保证目标数据可恢复。
- **路径处理显式校验**：根目录非空判断、通配符展开结果打印出来确认，防止一个变量为空就扫到整个磁盘。
- 让 AI 自己 review 一遍：“检查这个脚本有没有不可逆操作、有没有路径处理漏洞、变量为空会怎样”，它的自查经常能抓出问题。

### 3. cron 与定时任务

- 定时任务先手动跑通至少三天，再进 crontab / 任务计划。
- **环境变量坑**：cron 里没有交互 shell 的 PATH 和 profile，绝对路径写死，或脚本开头显式 source 环境——这点直接让 AI 处理，它知道坑在哪。
- **失败可感知**：cron 出错默认没人看见，配合后面的日志和告警才有意义。
- 错峰执行，避开业务高峰；频率从低开始，够用就好，别一上来就每分钟跑一次。

### 4. 日志与告警

没有日志的定时任务等于黑盒。让 AI 顺手把这几样写进去：

- **带时间戳的日志**：记录每次执行的开始、结束、处理条数、结果，写入固定日志文件而不是 stdout。
- **非零退出码**：失败时 `exit 1`，cron 的 MAILTO、systemd 的 OnFailure、各种监控都依赖它。
- **关键节点通知**：失败发邮件或推送到 IM webhook，成功可以静默，避免告警疲劳。
- **日志轮转**：logrotate 或脚本内截断，否则半年后日志撑爆磁盘。
- **执行记录可追溯**：至少能回答“上周三凌晨那次跑了吗、处理了多少条、为什么失败”。

### 5. 一个具体例子：批量重命名脚本

把上面的流程落到一个真实任务上——把一个目录里 500 个 `IMG_xxxx.jpg` 按拍摄日期重命名：

1. **描述**：环境是 Windows + PowerShell；输入是目录里的 jpg；命名规则是“日期_序号”；给它两条样例文件名。
2. **先要方案**：它会列出“遍历 → 读 EXIF 日期 → 生成新名 → 检查冲突 → 重命名”的步骤，你确认规则里“没有 EXIF 日期怎么办”这类分支后再展开。
3. **安全要求**：先 dry-run 打印新旧文件名对照；先只处理 3 个文件看输出；确认无误才全量。
4. **验证**：随机抽查 10 个改名结果，故意放一个无 EXIF 的文件看它怎么处理。
5. **留日志**：写一份 rename.log 记录每次的映射关系，万一命名规则反了还能按日志改回来。

整个过程十几分钟，其中绝大多数时间花在描述和验证上——这两处正是最不该省的地方。

### 6. 脚本上线后的维护

脚本不是写完就完了：环境会变、路径会变、上游格式会变。让 AI 帮你做两件维护的事：

- **改需求时基于原脚本迭代**：把现有脚本 + 新需求丢进去，让它先说明改动点再动手，别每次从零生成。
- **定期自查**：每季度把脚本丢给 AI 问一遍“这个脚本现在有哪些失效风险”，它对路径依赖、废弃参数这类问题相当敏感。

## 关键要点

- 环境、数据流、样例数据先说清，先要方案后要代码，参数抽到文件头。
- 不可逆操作默认 dry-run，小样本先行，批量改动先备份，路径校验显式写。
- 定时任务先手动跑几天，注意 cron 环境的 PATH 坑。
- 日志记录执行过程与条数，失败给非零退出码并告警，日志要轮转。
- AI 负责写和自查，危险操作的开关永远握在人手里。

## 小结

AI 把写脚本的门槛降到“会描述需求”即可，但自动化放大的不只是效率，还有错误——脚本错了，定时任务会替你重复犯错。所以流程要卡死：先方案后代码、先 dry-run 后执行、先手动后定时、先有日志后上量。四道关过了，自动化才真正是省时间的东西，而不是埋在 crontab 里的雷。
