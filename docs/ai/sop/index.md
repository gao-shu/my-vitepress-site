# AI 软件工程 SOP：从项目接入到持续交付

> **AI Software Engineering SOP · V1.0**
> 一套面向 AI Agent 的通用软件工程标准作业体系 —— 让开发者面对新项目或老项目时，都能用同一套标准化流程完成项目认知、环境准备、AI 协作体系建设、任务执行、质量验收和经验沉淀。

## 这套 SOP 解决什么

用 AI 写代码一段时间后，真正费时间的不再是敲代码，而是这些事：

- 每次开新会话都要重新解释技术栈、目录、禁改区、构建命令；
- 换一个 AI 编程工具，之前攒的配置几乎全部作废；
- AI 说「已完成」，但没人能说清「完成」到底指什么；
- 项目里踩过的坑只存在聊天记录里，下一个项目重新踩一遍。

它的定位是**方法论，不是工具教程**。Cursor、WorkBuddy、Claude Code 只是执行工具，真正可迁移的是这套开发方法本身。所以这里不写任何工具的按钮和目录约定，具体落地办法单独放在工具适配层。

::: tip 核心原则
学习和理解是基础，项目实践是验证，通用方法论是最终沉淀。不能为了追求自动化，牺牲开发者对业务、架构和代码的理解。
:::

## 四阶段总览

```text
01 项目初始化          02 AI 协作体系          03 标准开发流程        04 持续改进
项目扫描、认知与建档 ─→ Rules / Agents ─────→ 需求 → 设计 → 开发 ─→ 经验沉淀、复盘
新项目 / 老项目双入口    Skills / MCP / Hooks   测试 → Review → 交付    规则迭代、版本升级
        │                      │                      │                    │
        └──────────────────────┴──────────────────────┴────────────────────┘
                    每一轮迭代结束后回到「持续改进」，再进入下一轮主链
```

新项目和老项目**入口不同、主链相同**：前者先定边界再建体系，后者先扫描理解再逐步接入，汇合点是《项目认知报告》，之后走完全一样的开发流程。

## 三层边界：别把工具当方法

| 层 | 内容 | 会随什么变化 |
|----|------|-------------|
| 通用方法层 | 项目认知、需求、架构、Rules/Agent/Skill 设计、开发流程、测试验收、复盘 | 基本不变 |
| 工具适配层 | 具体工具的目录名、配置语法、调用方式、能力边界 | 工具版本 |
| 项目特定层 | 业务规则、数据表、接口契约、历史决策、gotchas | 每个仓库 |

判断准则：**一段内容如果换个 AI 工具就得重写，说明它写错了层。** 因此本 SOP 涉及具体工具功能时，一律以对应版本官方文档为准，不把某个工具的目录结构当成行业通用规范，也不编造未经验证的特性。

## 怎么算「这套 SOP 用起来了」

不是看写了多少页，而是看这五条能不能在真实项目里打勾：

- [ ] 新开一轮会话时，不需要重新解释技术栈与禁改区（项目认知报告在仓库里）
- [ ] 换一个 AI 编程工具，只改适配层，通用方法层原样复用
- [ ] 每个任务有一份冻结的 Spec，开发和 Review 都对着它
- [ ] 「完成」由人对照验收清单判定，有命令输出或 diff 作为证据
- [ ] 重复出现的问题能被沉淀到明确位置，并在第二个项目里验证过

## 版本与迭代

采用版本化管理，先把 **V1.0 做到能独立使用**，不追求大而全：V1.0 通用 SOP → V1.1 多 Agent 协作与任务调度 → V1.2 工业数字化项目开发规范 → V2.0 更成熟的 AI Agent 自动化开发体系。详见 [版本记录与修订机制](/ai/sop/changelog)。

后续会拿真实项目的开发过程来验证：**哪一步不好用就改 SOP，哪种 Skill 反复有效就沉淀下来**。这里展示的应当是实践、验证、迭代出来的方法，而不是一次写成的文章集合。
