# 03 · AI 协作体系建设

> 本章是整套 SOP 的核心。目标不是配齐所有能力，而是把 Rules、Agent、Skills、MCP、Hooks 的职责钉死，让每一条约束、每一个角色、每一份方法都放对位置。

## 场景与问题

有三种很典型的「建了体系但没用」：

- **一份大杂烩规则**：技术栈、目录约定、业务流程、本次需求、安全红线全在一个文件里，两百多行。AI 每次只执行末尾几条，前面等于不存在。
- **Agent 拆得很热闹**：架构、后端、前端、测试、Reviewer 全配上，结果一个「改个字段校验」的任务要在五个角色之间传三轮，比自己改慢十倍。
- **Skill 和 Rules 互相打架**：Skill 里写着「按本项目三层架构实现」，换到另一个项目就带着上一个项目的业务事实跑，输出全是错的。

共同根因是第 01 章那张职责表没落地。本章把五个机制分别展开，给出**编写模板 + 填好的示例 + 验收方式**，全部与具体工具无关。

## 零、先定最小集，再谈完备

| 阶段 | 必须建 | 按需才建 | 明确不建 |
|------|--------|---------|---------|
| 项目接入后 | 全局 Rules 一份、项目认知报告、一条开发主链 | — | 全套 Agent、Skill 大全 |
| 第一次迭代 | 该任务的 Spec | 复用第二次出现的同类操作 | 为了「体系完整」补文件 |
| 重复 3 次以上 | — | 对应的 Skill | 只出现过一次就沉淀 |
| 确有并行收益 | — | 拆子 Agent | 单文件改动也搞多 Agent |
| 检查反复漏 | — | Hook 脚本化 | 靠 Prompt 反复提醒 |

判断顺序：**先 Rules，再 Spec，再 Skill，最后才考虑 Agent 和 MCP**。反过来做，你会得到一堆没人用的配置。

## 一、Rules：约束所有任务

### 分层

| 层级 | 管什么 | 示例 | 变更频率 |
|------|--------|------|---------|
| 全局 | 技术栈、构建测试命令、禁改区、安全红线 | 「不得自行新增依赖」 | 低 |
| 项目级 | 分层约定、命名、错误码、接口风格 | 「Controller 不写业务逻辑」 | 中 |
| 目录级 | 某个模块特有的约束 | 「legacy/inventory 无测试覆盖，禁止改动」 | 中 |
| 技术规范 | 语言/框架的具体写法 | 「MyBatis 不用注解写动态 SQL」 | 低 |
| 安全规范 | 凭据、外发、权限 | 「生产连接串禁止写进任何上下文文件」 | 极低 |
| 业务约束 | 跨任务成立的业务红线 | 「出库分配必须 FEFO，不得按 FIFO」 | 低 |

::: warning 三条不要写进 Rules
① 本次任务要做什么（那是 Spec）；② 完整业务流程说明（那是项目认知报告）；③ 分阶段的操作步骤（那是 Skill 或开发流程）。Rules 只回答「无论做什么任务都必须遵守什么」。
:::

### 编写标准

1. 每条规则**可验证** —— 能指向一个命令、一个 diff 特征或一个检查点，不能是「代码要写好」这种形容词。
2. 每条禁止项配一个**反例**，让 AI 知道边界在哪。
3. 写明**来源**（来自哪份文档、哪次事故、哪条约定），否则半年后没人敢删。
4. 全局规则控制在 **30 行以内**；超了就是混进了别层的东西。
5. 用「必须 / 禁止」陈述句，不用「建议 / 尽量」。

### Rules 编写模板（可复制）

```markdown
# <规则名> · <适用范围>

## 适用范围
- 生效范围：全局 / 项目 / <目录路径>
- 不适用：<明确写出例外>

## 事实依据
- <来源：项目认知报告第 X 节 / 某次事故复盘 / 团队约定>

## 必须遵守
| 编号 | 规则 | 验证方式 |
|------|------|---------|
| C01 | | <命令或 diff 特征> |

## 明确禁止
| 编号 | 禁止项 | 反例（曾经或可能出错的写法） | 验证方式 |
|------|--------|------------------------------|---------|
| P01 | | | |

## 例外与审批
- 需要例外时，由 <角色> 确认，并记在 <位置>。

## 变更记录
| 日期 | 版本 | 改了什么 | 触发原因 |
|------|------|---------|---------|
```

### 填好的示例（全局规则）

```markdown
# 00-core · 全局规则

## 适用范围
- 生效范围：全仓库所有任务
- 不适用：docs/ 下的纯文档修改（仍需遵守 P03）

## 事实依据
- 《项目认知报告 · WMS 批次模块》第 2、8、9 节

## 必须遵守
| 编号 | 规则 | 验证方式 |
|------|------|---------|
| C01 | 技术栈：Java 21 / Spring Boot 3.2 / MyBatis-Plus / MySQL 8 | pom.xml 未变更 |
| C02 | 提交前跑 `mvn -q -DskipTests package` 与 `mvn test` | 命令输出 |
| C03 | 所有新接口沿用 `/api/<模块>/<资源>`，错误码走统一包装类 | diff 检查 |
| C04 | 出库相关改动必须保持 FEFO 分配语义 | 单测 BatchAllocServiceTest |

## 明确禁止
| 编号 | 禁止项 | 反例 | 验证方式 |
|------|--------|------|---------|
| P01 | 不改已有 URL 与接口签名 | 把 /api/stock/outbound 改成 /api/stock/out | diff 检查 |
| P02 | 不自行新增依赖 | 为了一个日期工具引新包 | pom.xml diff |
| P03 | 不外发客户物料编码、供应商价格、任何生产凭据 | 把生产配置贴进上下文文件 | Hook 密钥扫描 |
| P04 | 不改动 legacy/inventory/ 下的旧结算逻辑 | 「顺手重构」无测试覆盖的代码 | 禁改区 diff 检查 |
| P05 | 不把 biz_stock.qty 当账面量用 | 直接用 qty 做库存扣减 | 人工审 + gotchas 引用 |

## 例外与审批
- 需要例外时，由项目维护人确认，并记在《项目认知报告》第 6 节。

## 变更记录
| 日期 | 版本 | 改了什么 | 触发原因 |
|------|------|---------|---------|
| 2026-11-16 | v0.1 | 初版 | 项目接入 |
```

注意 C04 与 P05：它们来自业务事实，但**在报告里只存一次**，Rules 里只写「必须遵守什么」和验证方式，不复述整段业务规则。这就是「唯一事实源」的落地方式。

## 二、Agent：角色与任务执行

### 角色清单

不要求每个项目都配全，绝大多数项目只需要「主 Agent + 按需的 1–2 个子角色」。

| 角色 | 职责（一句话） | 输入 | 输出 | 权限边界 | 协作方式 |
|------|---------------|------|------|---------|---------|
| 主 Agent | 拆解任务、传递上下文、收口结果，不写业务代码 | 需求 + Spec + 项目认知报告 | 任务分工表 + 汇总 | 可读全仓；写仅限任务文档 | 向人交付，不自行宣布完成 |
| 架构 Agent | 出方案与代价对比，不动代码 | 需求 + 现状架构 | 方案 + 取舍 + 不做清单 | 只读 | 人拍板后才进入实现 |
| 后端 Agent | 按 Spec 实现后端改动 | Spec + 相关规则 + 调用链 | 代码 diff + 测试 | 写后端目录 | 提交给 Reviewer 与测试 |
| 前端 Agent | 按接口契约实现页面 | Spec + 接口契约 | 代码 diff | 写前端目录 | 与后端并行，共用契约 |
| 测试 Agent | 补用例、跑命令、汇总结果 | Spec 的验收段 + diff | 测试结果（含失败项） | 写测试目录；不改实现 | 不修 bug，只报 |
| Reviewer Agent | 审 diff、提问题 | 仅 diff + Spec，不给推理过程 | 问题清单 | 只读 | **不判定通过** |

::: tip 为什么 Reviewer 不能判定通过
执行者不能当验收人。Reviewer Agent 只输出「问题清单和依据」，逐条对照验收清单判定是否完成，是人的动作。把这一条写进权限边界，比在 Prompt 里提醒十遍都有效。
:::

### 什么时候才拆子 Agent

| 适合并行 | 必须串行 |
|---------|---------|
| 前后端共用已冻结的接口契约 | 需求澄清 → 架构设计（人未拍板不能开实现） |
| 多个互不重叠模块的同类改动 | 数据库变更 → 依赖它的接口实现 |
| 测试补充与文档整理 | 实现 → Review → 验收 |
| 独立模块的只读分析 | 同一文件的多处修改 |

一条硬规则：**没有冻结的 Spec 就不要并行**。并行拆得越细，上下文对齐成本越高；单文件改动搞多 Agent，纯属用流程制造开销。

### Agent 编写模板（可复制）

```markdown
# <角色名> Agent

## 职责
<一句话，说明这个角色存在的唯一理由>

## 不负责
- <明确列出，尤其是"不做验收判定"这类边界>

## 输入（缺一不可）
| 材料 | 来源 | 缺失时 |
|------|------|--------|
| | | <停手并向主 Agent 索要，不自行脑补> |

## 输出
- 交付物与格式：
- 必须附带的证据：

## 权限边界
- 可读：
- 可写：
- 禁止：<文件 / 目录 / 操作>

## 协作方式
- 向谁交付：
- 何时升级给人：<列出触发条件>
- 与其他 Agent 的交接物：

## 停手条件
- <遇到什么情况必须停下来，不继续猜>

## 完成判定
- 由 <人 / 哪个环节> 判定，依据 <具体证据>；
  本 Agent 不宣布完成。
```

### 填好的示例（Reviewer Agent）

```markdown
# Reviewer Agent

## 职责
只审本次 diff，输出可追溯的问题清单。

## 不负责
- 不修代码、不改 diff、不补测试。
- 不判定「可以合并 / 已完成」，那是人的动作。
- 不评价整体架构好坏，只审这次改动是否越界。

## 输入（缺一不可）
| 材料 | 来源 | 缺失时 |
|------|------|--------|
| 本次 diff | git diff | 停手索要 |
| 对应 Spec | docs/ai-context/specs/ | 停手索要 |
| 全局 Rules 与项目认知报告第 8 节 | 仓库 | 停手索要 |

## 输出
- 问题清单：编号 / 位置（文件:行）/ 违反了哪条规则或 Spec / 依据 / 严重级别。
- 必须附带的证据：每个问题都要能指到具体行号，不接受「整体感觉」。

## 权限边界
- 可读：全仓只读
- 可写：无
- 禁止：修改任何文件、执行写操作、给出通过结论

## 协作方式
- 向人交付问题清单，人逐条裁定「改 / 不改 / 记入技术债」。
- 触发升级：发现禁改区被改动、发现凭据外泄、发现与 Spec 冲突且影响线上行为。
- 与测试 Agent 的交接物：测试未覆盖的边界条件，转交测试角色补用例。

## 停手条件
- diff 与 Spec 明显不是同一个任务时停下，不强行审。
- 无法判断某条规则是否适用时，标「需人确认」，不自行解释规则。

## 完成判定
- 由人对照验收清单判定；本 Agent 只输出清单，不宣布完成。
```

## 三、Skills：可复用的方法

### 与 Rules 的根本区别

| | Rules | Skills |
|---|-------|--------|
| 是否自动生效 | 是，每个任务都带 | 否，触发条件满足才启用 |
| 内容 | 约束（不能做什么） | 方法（怎么一步步做） |
| 归属 | 跟仓走，只属于这个项目 | 跟人走，可跨项目复用 |
| 能不能放业务事实 | 可以（但只写约束，不复制说明） | **禁止** |

一句话：**Skill 里出现具体表名、客户名、业务字段，就是写错了地方。**

### 通用 Skill 分类

| 类别 | 触发条件 | 典型产出 |
|------|---------|---------|
| 项目分析 | 接手陌生仓库 | 事实清单 + 待确认清单 |
| 需求分析 | 拿到一段模糊需求 | 澄清问题列表 + 范围草案 |
| 架构设计 | 需要定模块边界 | 方案与取舍对比（不拍板） |
| 数据库设计 | 新增表/改字段 | 表设计 + 迁移与回滚要点 |
| API 设计 | 新增/改接口 | 接口契约（路径、入出参、错误码） |
| 后端开发 | 有冻结 Spec | 小步 diff + 单测 |
| 前端开发 | 有接口契约 | 页面 diff + 交互说明 |
| 测试 | 实现完成 | 用例 + 实际命令输出 |
| Bug 排查 | 有完整报错与复现步骤 | 根因假设 + 证据排除记录 |
| 代码审查 | 有 diff | 问题清单（不判定通过） |
| 文档生成 | 交付前 | README / 变更记录 / 交接说明 |
| 项目交付 | 验收通过后 | 交付报告 |

### 设计标准

1. **触发条件写「什么时候不用」**，比只写什么时候用更能防止滥用。
2. 执行流程每一步都有**可检查的中间产出**，不能是「分析一下」这种黑盒。
3. 写清**失败与降级**：缺输入、命令跑不通、AI 输出不可信时怎么办。
4. 必须有**复用记录**：至少在两个项目里跑过，才升级为通用能力。
5. Skill 不写业务事实、不写工具按钮、不复制 Rules 全文。

### Skill 编写模板（可复制）

```markdown
# Skill · <方法名>

## 触发条件
- 用：<具体到可判断的场景>
- 不用：<列出容易误用的场景>

## 输入
| 材料 | 必须 | 缺失时 |
|------|------|--------|
| | 是 / 否 | <停手 / 降级路径> |

## 执行流程
| 步 | 动作 | 中间产出 | 检查点 |
|----|------|---------|--------|
| 1 | | | <谁确认> |
| 2 | | | |

## 输出
- 交付物与格式：
- 必须附带的证据：

## 验收标准
- [ ] <可打勾的具体条件>
- [ ] <可打勾的具体条件>

## 失败与降级
| 情况 | 处理 |
|------|------|
| 输入缺失 | 停手索要，不脑补 |
| 命令执行失败 | 原样贴出报错，不改写结论 |
| 中间产出不可信 | 退回上一步，标「需人确认」 |

## 不写入本 Skill 的内容
- 具体表名、客户名、业务字段 → 项目认知报告
- 长期约束 → Rules
- 本次任务范围 → Spec
- 工具目录与按钮 → 工具适配指南

## 复用记录
| 日期 | 项目 | 结果 | 据此改了什么 |
|------|------|------|-------------|
```

### 填好的示例（Skill · 老项目局部改动）

```markdown
# Skill · 老项目局部改动

## 触发条件
- 用：在已有仓库上做一个范围明确的小改动（加过滤、加字段、修一个 bug）
- 不用：新模块开发、架构调整、跨多个系统的改造

## 输入
| 材料 | 必须 | 缺失时 |
|------|------|--------|
| 项目认知报告 | 是 | 停手，先做接入（第 02 章） |
| 本次 Spec（含验收与"不做"） | 是 | 停手索要，不按口头需求开工 |
| 涉及的调用链 | 是 | 用扫描 Prompt 补一条链 |
| 全局 Rules | 是 | 停手索要 |

## 执行流程
| 步 | 动作 | 中间产出 | 检查点 |
|----|------|---------|--------|
| 1 | 复述改什么、不改什么 | 三句话复述 | 人确认 |
| 2 | 定位会碰的文件，列清单 | 文件清单（不超过 N 个） | 人确认范围 |
| 3 | 写/确认 Spec | specs/<短名>.md | 人冻结后才继续 |
| 4 | 小步实现，一次一个改动单位 | diff | 人看 diff |
| 5 | 跑 Spec 里的验收命令 | 命令输出原文 | 结果对照验收段 |
| 6 | 查「改前行为」是否保持 | 回归对照结果 | 人确认 |
| 7 | 交 Reviewer | 问题清单 | 人裁定 |

## 输出
- diff + 命令输出原文 + 回归对照结果 + 未解决问题清单。

## 验收标准
- [ ] Spec 中每条验收都有对应的实际输出
- [ ] 未点名的行为与改前一致（至少验证一条）
- [ ] diff 未触及禁改区，pom.xml / 依赖文件无变更
- [ ] 已有 URL 与接口签名未变

## 失败与降级
| 情况 | 处理 |
|------|------|
| 调用链超出本次范围 | 缩回范围，把超出的记入待办，不扩大改动 |
| 验收命令跑不通 | 原样贴报错，标「环境待确认」，不写成「通过」 |
| 发现需要先改架构 | 停手，退回技术设计流程，不在本任务里顺手重构 |

## 不写入本 Skill 的内容
- 具体表名、字段、客户名 → 项目认知报告
- 禁改区清单 → Rules
- 本次改哪个接口 → Spec
- 某工具怎么配置 → 工具适配指南

## 复用记录
| 日期 | 项目 | 结果 | 据此改了什么 |
|------|------|------|-------------|
| 2026-11-16 | WMS 批次模块 | 首用 | 初版 |
```

## 四、MCP：外部能力连接

MCP 只解决一件事：**让 AI 拿到仓库之外的能力或数据**。它不决定开发流程，也不替代项目认知报告。

| 适合接 | 不适合接 |
|--------|---------|
| 只读的测试库元数据、表结构查询 | 生产库（外发与权限风险） |
| 内部文档/知识库检索 | 把整个业务知识库塞进每次会话上下文 |
| 构建与 CI 状态查询 | 用 MCP 代替本地跑命令 |
| 工单/需求系统的只读同步 | 让 AI 直接写回需求系统 |

接入前三项检查，缺一不接：

1. **必要性**：不接这个数据源，任务是不是真做不了？能靠仓库内文件解决的，不接。
2. **边界**：数据能不能外发、凭据放哪、权限最小化到什么程度、只读还是可写。
3. **降级**：服务不可用时，流程是停下来还是走本地文件；不能出现「MCP 挂了整套 SOP 就跑不动」。

## 五、Hooks：确定性自动化

判断标准很简单：**凡是「漏了就出事」且「能写成脚本判定」的检查，一律交给 Hooks，不交给 AI 自觉**。Prompt 提醒会被长会话稀释，脚本不会。

| 检查 | 为什么必须脚本化 | 失败动作 |
|------|----------------|---------|
| 格式 / lint / 构建 | 每次提交都要过，AI 会忘 | 阻断提交 |
| 单测与最小冒烟 | 「已完成」必须有证据 | 阻断并贴出输出 |
| 密钥 / 凭据扫描 | 外发不可逆转 | 阻断 + 报告 |
| 依赖文件变更检测 | 防止 AI 自行引包 | 阻断，需人确认 |
| 禁改区 diff 检测 | 无测试覆盖的老代码不能被顺手改 | 阻断 |
| 提交信息规范 | 便于回溯与回滚 | 提示或阻断 |

Hooks 不判断业务对错（例如「这个过滤逻辑符合 FEFO 吗」），那是 Spec 验收和人的判断。它只做确定性事实检查。

## 六、一个需求，五个机制各做什么

需求：**WMS 出库列表增加「效期不足 30 天」过滤**（老项目，第三次做同类局部改动）。

| 机制 | 这一刀里管什么 | 不管什么 |
|------|---------------|---------|
| Rules | 禁改 `/api/stock/outbound` 签名、禁止把 `qty` 当账面量、禁改 legacy 目录、禁止新增依赖 | 这个过滤怎么实现 |
| Agent | 主 Agent 拆任务；后端 Agent 实现；Reviewer 只出「问题清单」 | 判定能不能合 |
| Skills | 复用「老项目局部改动」Skill 的 7 步流程与回归对照 | 存 `biz_stock` 字段含义 |
| MCP | 若需核对测试库表结构，只读接入；不可用时降级到本地 DDL 文件 | 决定开发顺序 |
| Hooks | 提交前跑 `mvn test`、密钥扫描、禁改区 diff 检测 | 判断 FEFO 有没有被破坏 |
| 人 | 确认规则 R02 未被改动、逐条对照验收清单判定完成 | 写实现代码 |

看出职责边界的意义：如果把「必须 FEFO」写进 Skill，换到 ERP 项目就会带着 WMS 的业务事实跑；如果让 Reviewer 判定通过，验收就外包给了执行者。

## 七、工具适配边界声明

本章所有文件名、目录名、层级划分都是**通用示意**，只表达「哪类内容放哪」，不代表任何 AI 编程工具的官方约定。

- Cursor、WorkBuddy、Claude Code 等工具的**目录结构、配置语法、加载优先级、调用方式**，以对应版本的官方文档为准。
- 不同工具对 Rules / Agent / Skills 的支持程度不同：有的没有目录级规则，有的 Skill 不进仓库，有的不支持 Hook。适配时按能力映射，缺的能力不要用别的能力硬凑。
- 本 SOP 不编造未经验证的工具特性。具体落地办法在 **M3 工具适配指南**中单独给出（Cursor、WorkBuddy 各一篇），通用章节里不混写。

## 八、建设验收清单

- [ ] 全局 Rules 不超过 30 行，每条都配了验证方式，禁止项都有反例
- [ ] 任取一条规则，能说清它属于哪个层级、来源在哪
- [ ] Rules 里没有出现「本次」「这个需求」「先做…再做…」这类任务/流程措辞
- [ ] 实际启用的 Agent 有书面职责与权限边界，Reviewer 明确不判定通过
- [ ] 每个 Skill 都写了触发条件、什么时候不用、失败降级、复用记录
- [ ] Skill 中没有具体表名、客户名、业务字段
- [ ] MCP 接入逐条过了必要性 / 边界 / 降级三项检查
- [ ] 所有「漏了就出事」的检查已进 Hooks，不靠 Prompt 提醒
- [ ] 启动必备清单没有超过 5 项（防过度设计）

## 九、常见问题

**Q：只有一个 Agent 算不算建了协作体系？**
算。单 Agent + 一份可验证的 Rules + 一条主链就是最小可用体系。角色数量不是成熟度指标。

**Q：Rules 和项目认知报告都提到 FEFO，算重复吗？**
不算，但职责不同：报告里写「规则是什么、来源在哪」，Rules 里只写「必须保持、怎么验证」。不要两边都贴整段业务说明。

**Q：Skill 什么时候从项目专属升级成通用？**
同类操作在**第二个不同项目**里跑通、且删掉所有业务事实之后仍然可用，才升级。只出现过一次就沉淀，通常会沉淀出一份没人用的模板。

**Q：工具不支持 Hooks 怎么办？**
把检查降级为 CI 步骤或提交前手动脚本，并在验收清单里点名「必须跑」，不要假装 AI 会记得。适配层能力缺失要如实记录，不要用别的能力硬凑。

## 关键要点

- 建设顺序：Rules → Spec → Skill → Agent / MCP；启动必备不超过 5 项。
- Rules 管约束且自动生效，Skill 管方法且触发才用；Skill 里禁止出现业务事实。
- Agent 必须有权限边界，Reviewer 不判定通过，验收始终在人。
- 没有冻结的 Spec 不并行；单文件改动不拆多 Agent。
- 确定性检查交给 Hooks，MCP 接入前过必要性 / 边界 / 降级三关。
- 所有目录与语法均为示意，具体工具以官方文档为准，M3 单独适配。

## 小结

协作体系的成熟度不看配置数量，看**职责有没有混**。一份 30 行可验证的 Rules、一个明确的 Reviewer 边界、一份在两个项目里验证过的 Skill，比十个 Agent 加两百行规则有用得多。建完这一层，就具备进入需求、设计、开发、测试主链的条件了 —— 那是 M2 的范围。
