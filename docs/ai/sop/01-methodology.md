# 01 · 方法论与总体架构

> 先分清「方法」「工具」「项目事实」三层，再谈协作。这一章是后面七章的地基，也是整套 SOP 里唯一不随工具版本变化的部分。

## 场景与问题

用 AI 写代码半年后，最容易攒下这四个毛病：

- **每次开新会话都要重新解释一遍**：JDK 几、分层怎么走、哪个包不能动、构建命令是什么。解释成本比自己改还高。
- **换工具就作废**：花两周攒的 Rules、Skills、Agent 配置，从 Cursor 换到另一个工具时几乎全要重写，于是开始怀疑之前那两周是不是白干了。
- **"已完成"没有定义**：AI 说做完了，你问测试跑了吗，它说"已补充测试"；上线一跑才发现边界条件漏了。没有人能说清"做完"到底指什么。
- **规则越写越长，越长越没人遵守**：技术栈、目录约定、业务流程、安全红线、本次任务需求，全塞进一份规则文件。最后连你自己都不看，AI 更是只挑最后几行执行。

这四个问题的根子是同一件事：**把工具配置当成了方法，把规则当成了流程，把一次性的对话当成了项目资产。**

SOP 要解决的不是"怎么让 AI 写更多代码"，而是"怎么让一个项目在被 AI 参与之后，仍然可理解、可复现、可验收"。

## 一、为什么需要一套 SOP

| 维度 | 传统软件开发 | 随手用 AI 辅助 | SOP 化的 AI 开发 |
|------|-------------|---------------|-----------------|
| 上下文在哪 | 人脑 + 文档 | 单轮对话，会话结束即丢 | 仓库里的项目认知报告 + 规则文件 |
| 谁做决策 | 人 | 常常是 AI 顺手替你定了 | 需求、架构、验收由人拍板，有书面依据 |
| 产出物 | 代码 + 文档 | 代码 + 一段聊天记录 | 代码 + Spec + 验收记录 + 沉淀项 |
| 典型失败 | 需求理解偏差 | 改崩了看不懂 diff、越聊越乱 | 流程被跳过，能定位到是哪一步没做 |
| 换工具成本 | 低 | 高（配置全绑在工具上） | 低（换的只是适配层） |
| 可复现性 | 靠规范 | 靠运气 | 靠输入、输出、验收三件套 |

一句话：AI 把**执行**变得极便宜，于是**定义问题**和**判断结果**成了瓶颈。SOP 就是把这两件事固化下来。

::: tip 核心原则
学习和理解是基础，项目实践是验证，通用方法论是最终沉淀。不能为了追求自动化，牺牲开发者对业务、架构和代码的理解。
:::

## 二、五条原则

1. **理解和判断在人，执行在 AI。** 需求取舍、架构决策、验收判定不出让。AI 可以列选项、写草稿、跑检查，但不替你拍板。
2. **通用优先，工具适配分离。** 方法论不能长在某个工具的目录结构上；目录名、配置语法、调用方式全部下沉到适配层。
3. **新项目和老项目分入口，汇合到同一条主链。** 新项目先定边界再建体系，老项目先扫描理解再逐步接入；进了开发阶段，两者走同一套流程。
4. **前期最小必备，过程中按需补充。** 不要求开工前把 Rules、Agents、Skills 全部配齐。过度设计比缺配置更常见。
5. **完成以证据为准。** 编译、测试、diff、验收清单是可核验的证据；"AI 声称完成"不是。

## 三、总体架构：三层

```text
┌─ 通用方法层 ─ 跨项目、跨工具、长期不变 ──────────────────┐
│ 项目认知 · 需求分析 · 架构设计 · 任务拆解                 │
│ Rules 设计 · Agent 职责 · Skill 设计 · 测试验收 · 复盘沉淀  │
└──────────────────────┬─────────────────────────────────┘
                       │ 适配（工具版本变了只改这一层）
┌──────────────────────▼─────────────────────────────────┐
│ 工具适配层 ─ 以对应版本官方文档为准                      │
│ Cursor / WorkBuddy / Claude Code / 其他支持 Agent 的工具  │
│ 只负责：目录名、配置语法、调用方式、能力边界              │
└──────────────────────┬─────────────────────────────────┘
                       │ 落地到具体仓库
┌──────────────────────▼─────────────────────────────────┐
│ 项目特定层 ─ 只属于这一个仓库                            │
│ 业务规则 · 数据表 · 接口契约 · 历史决策 · gotchas          │
└────────────────────────────────────────────────────────┘
```

一条判断准则：**如果一段内容换一个 AI 编程工具就得重写，那它写错了层。**

这也是本 SOP 不叫《Cursor 使用教程》的原因。Cursor、WorkBuddy、Claude Code 只是执行工具，工具特性以各自官方文档为准，本 SOP 不把某个工具的目录结构当成行业通用规范。涉及具体配置的落地办法放在 [M3 的工具适配指南](./index)（建设中），不在方法论章节里混写。

## 四、五个协作机制，各管一件事

这是最容易混淆的地方，也是整套体系的支点。

| 机制 | 回答什么问题 | 约束/作用于 | 生命周期 | 粒度 | 不负责 |
|------|-------------|------------|---------|------|--------|
| **Rules** | 所有任务必须遵守什么 | AI 的行为边界 | 长期，随项目迭代 | 全局 / 项目 / 目录级 | 本次任务要做什么 |
| **Agent** | 谁来做、按什么职责做 | 执行角色 | 按阶段启用 | 一个角色 | 定规则、写规范 |
| **Skills** | 重复出现的方法怎么复用 | 可复用流程 | 跨项目积累，跟人走 | 一个方法 | 存业务事实 |
| **MCP** | 需要接哪些外部能力/数据 | 连接边界 | 按需接入 | 一个外部系统 | 决定开发流程 |
| **Hooks** | 哪些检查必须确定性执行 | 自动化脚本 | 长期 | 一条检查 | 判断业务对错 |

一句话记住：

> **Rules 负责约束，Agent 负责角色与任务执行，Skills 负责可复用的方法，MCP 负责外部能力连接，Hooks 负责确定性自动化。**

职责混淆自查表 —— 这些是真实项目里最常见的错放：

| 常见写法 | 问题 | 应该放哪 |
|---------|------|---------|
| Rules 里写「本次给工单列表加 status 过滤」 | 规则管所有任务，这条只管一次 | Spec / 任务文档 |
| Rules 里写整套业务流程说明 | 规则会膨胀到没人读 | 项目认知报告 |
| 把客户业务表、字段含义写进 Skill | 跟人走的 Skill 会污染下一个项目 | 项目特定层 |
| 让 Reviewer Agent 自己决定「这样可以合」 | 执行者不能当验收人 | 人的验收环节 |
| 靠 Prompt 提醒「别提交密钥」 | 提醒会被上下文稀释 | Hooks 做确定性拦截 |
| 一开始就接五六个 MCP 数据源 | 没验证过需要，只增加排障面 | 按需，接入前先过三项检查 |

## 五、人与 AI 的职责边界

| 环节 | 人（拍板） | AI（执行） | 留下的证据 |
|------|-----------|-----------|-----------|
| 需求取舍 | 定做什么、不做什么 | 提澄清问题、列模糊点 | 需求澄清记录 |
| 架构设计 | 定模块边界、技术栈、系统级约束 | 列备选方案与代价 | 技术设计文档 |
| 业务规则 | 确认规则来源与例外 | 从代码/文档里抽取候选 | 规则清单 + 来源 |
| 代码实现 | 审方案、砍 scope、看 diff | 按 Spec 实现 | 小步提交 + diff |
| 测试用例 | 定验收条件 | 补用例、跑命令 | 测试结果 |
| 质量验收 | 逐条对照清单判定 | 自查、提问题 | 验收报告 |
| 交付上线 | 决定合不合、什么时候发 | 汇总文档与变更 | 交付报告 |

注意最后一行：**AI 不负责宣布完成**。这不是不信任模型，是责任没法外包 —— 出了线上问题，回滚和复盘的是人。

## 六、完整工作流程图

```text
[ 入口分叉 ]
新项目 ── 目标 / 范围 / 技术栈 / 目录 / 模块边界 ──┐
                                                  ├─→ 《项目认知报告》
老项目 ── 扫描 / 识别栈 / 理解架构 / 业务规则 / 债 ─┘          │
                                                              ▼
                                              [ 最小 AI 协作体系 ]
                                          全局 Rules + 一条开发主链
                                                              │
                                                              ▼
              ┌──────────── 标准开发主链（单次迭代）──────────────┐
              │ 需求澄清 → 技术设计 → 任务拆解 → 实现              │
              │     → 测试 / Review → 交付                        │
              │   （新项目与老项目在这里合流，步骤完全一致）        │
              └──────────────────────┬───────────────────────────┘
                                     ▼
                 [ 阶段性复盘 ] 发现重复问题 → 分析根因
                                     │
                        ┌────────────┼────────────┐
                        ▼            ▼            ▼
                   Rules / Agent / Skill / Docs / 脚本
                        └──── 复用验证 → 更新通用方法库 ────┘
                                     │
                                     └──→ 下一迭代回到主链
```

四阶段对应「项目初始化 → AI 协作体系 → 标准开发流程 → 持续改进」，八章内容都挂在这张图的某一段上，不会多出一条孤立流程。

## 七、避免过度设计：什么时候才补

| 时机 | 启动必备 | 明确不做 |
|------|---------|---------|
| 项目启动 | 项目认知报告、全局 Rules（技术栈 / 禁改区 / 构建测试命令）、一条开发主链 | 全套 Agent、Skill 大全、接满 MCP |
| 开发过程中 | 同类操作重复 3 次以上才建 Skill；确有并行收益才拆子 Agent | 为展示多 Agent 而拆任务 |
| 阶段复盘 | 根因 → 判断沉淀位置 → 小范围复用验证 | 把所有经验一股脑写进 Rules |
| 跨项目复用 | 通用方法库、模板库、版本记录 | 把项目业务事实带进通用库 |

判断「值不值得沉淀」只需要三个问题：这个问题还会再出现吗？不沉淀的代价是什么？沉淀之后有没有第二个项目能验证它？三个都是肯定，才动手。

## 八、本章输入 / 输出 / 验收标准

| 项 | 内容 |
|----|------|
| 输入 | 一个准备引入 AI 协作的项目（新或老）；现有工具清单 |
| 输出 | 三层架构划分结论、五个机制的职责划分表、人/AI 分工表、本项目适用的流程图 |
| 验收 | ① 能说清哪些内容属于工具适配层；② 任取一条现有规则，能判断它是否放错了层；③ 能指出「完成」由谁判定、以什么为证据；④ 启动必备清单不超过 5 项 |

::: warning 验收不通过的信号
如果讨论完还是「先把 Rules 写全再开工」，说明过度设计没挡住；如果所有内容都指向某一个工具的目录名，说明三层没分开。这两种情况都不要进入第 02 章。
:::

## 九、常见问题

**Q：不配 Agent 也能叫 AI 协作体系吗？**
能。单 Agent + 清晰 Rules + 一条主链，就是可用的最小体系。多 Agent 是任务并行度上来之后的结果，不是起点。

**Q：工具更新了，这套 SOP 会不会失效？**
通用方法层不会。失效的只会是适配层的目录名和语法，改一处即可。这也是要求「具体配置以官方文档为准」的原因 —— 本文不写任何工具的目录结构。

**Q：Rules 和 Spec 有什么区别？**
Rules 管**所有任务**（不改 URL、不加依赖、分层约定）；Spec 管**这一次任务**（改什么、验收是什么、明确不做什么）。Spec 冻结后开发和 Review 都对着它，任务做完可以归档，但不要合并进 Rules。

**Q：小项目也要写项目认知报告吗？**
要，但可以很短。哪怕只有技术栈、模块边界、构建命令、禁改区四行，也比每次会话重新解释强。老项目尤其不能省 —— 见第 02 章。

## 关键要点

- 三层架构：通用方法层 / 工具适配层 / 项目特定层；换工具只改中间那层。
- 五个机制各管一件事：Rules 约束、Agent 执行、Skills 复用方法、MCP 连外部、Hooks 做确定性检查。
- 新项目和老项目入口不同，但汇合到同一条标准开发主链。
- 人对需求、架构、验收负责；AI 对自己的「已完成」不负责判定。
- 启动只做最小必备，重复三次以上才沉淀，沉淀前先想清楚验证场景。

## 小结

这套 SOP 的价值不在于让 AI 写得更多，而在于让协作结果**可复现、可验收、可迁移**。先把三层分开，再把五个机制的职责钉死，后面七章都只是在这张图上填细节。做对这一步，换工具、换项目、换模型都不会让你从零开始。
