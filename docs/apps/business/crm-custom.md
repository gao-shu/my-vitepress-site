# CRM 定制改造实践

CRM 是定制化最重的一类系统：每个客户的销售流程都不一样，字段、阶段、报表各有说法。做开发组长那几年带过多客户定制，最贵的教训不是写不出功能，而是升级时把二开代码冲掉。这篇记录差异化处理的策略。

## 背景与问题

- 一套 CRM 卖给 N 个客户，A 客户要「线索→商机→合同」，B 客户加了「渠道返点」，C 客户销售阶段叫法都不同。
- 直接改核心代码满足客户，代码分叉：修一个 bug 要改 N 份，升级等于重做。
- 完全配置化又不现实：有些差异是流程逻辑（审批条件、分成计算），配置表达不了。
- 需求来自销售、实施、客服多头，客户口头需求直接进开发排期，做到一半发现和标准路线冲突。

核心问题只有一个：**差异放在哪里**。

## 方案设计

### 配置化 vs 二开的判断标准

| 差异类型 | 处理方式 | 例子 |
|----------|----------|------|
| 展示类 | 配置 | 字段增删、名称叫法、列表列、字典值 |
| 流程走向类 | 配置（规则/引擎） | 审批条件、阶段名称与必填项 |
| 业务逻辑类 | 二开（扩展点） | 分成计算、特殊校验、外部系统对接 |
| 数据模型类 | 二开（扩展表/扩展字段） | 客户独有的业务对象 |

判断口径：**能用数据描述的进配置，必须用代码表达的进扩展点，绝不直接改核心链路。**

### 扩展机制设计

- 自定义字段：`ext_c01 ~ ext_nnn` 预留列 + 字段元数据表，类型、校验、可见性都由配置驱动。
- 扩展表：客户级一对一扩展表（如 `crm_customer_ext_{client}` 或统一表 + client_id），放核心表不该背的字段。
- 扩展点：核心流程里留 hook（接口 + Spring 装配），二开以独立 jar/模块提供，核心代码只声明「此处可扩展」。
- 客户开关：`sys_client_config` 记录每个客户开了哪些功能开关，代码里按开关走分支，而不是复制整个模块。

### 升级冲突避免

- 二开代码与核心代码**分仓或分模块**，核心只通过版本化的扩展接口暴露钩子。
- 扩展接口一旦发布不轻易改签名，废弃走标记 + 过渡版本。
- 每个客户的差异清单（配置 + 二开模块）进版本管理，升级前先跑一遍差异回归用例。
- 数据库变更用版本化脚本（Flyway/Liquibase 思路），客户库结构可追溯到具体版本。

### 需求管理

- 需求先分类：标准功能（进产品路线）/ 配置可满足（实施配）/ 二开（立项排期）/ 拒绝（说明替代方案）。
- 每个客户建「差异台账」：需求来源、处理方式、落在哪个配置项或哪个扩展模块。
- 与客户约定：改核心的需求要么走产品版本，要么加钱进二开，不做「悄悄改一下」。

## 关键实现

自定义字段取值（示意）：

```java
public Object getFieldValue(Customer c, String fieldCode) {
    FieldMeta meta = fieldMetaService.get(fieldCode);
    if (meta.getIsCustom()) {
        return c.getExtValue(meta.getExtColumn()); // ext_c01...
    }
    return ReflectUtil.getFieldValue(c, meta.getColumn());
}
```

要点：

- 列表筛选、导出、报表读取统一走 `getFieldValue` 这类入口，否则自定义字段一多，散落的 `if (client == xx)` 会失控。
- 审批条件用规则表达式（如 SpEL / 简单 DSL）落在配置表，改条件不改代码、不重启。
- 扩展点实现按客户打包部署，核心版本升级时先在测试环境跑全量客户开关组合的回归。
- 差异台账与配置表同源，新人接手时先看台账，再看代码。

## 落地效果（示意）

以下为模式效果示意，非生产数据：

- 字段、字典、列表差异基本不再进开发排期，实施人员配置即可交付。
- 核心升级时，二开模块只需按扩展接口重新编译验证，不再整包合并。
- 需求分类后，约一半的客户需求在配置阶段被消化，开发只处理真正要写代码的部分。
- 新客户上线时，按差异台账复制一份配置基线，起跑时间明显缩短。

## 小结

CRM 定制的核心不是「会不会做这个功能」，而是差异放哪。配置管展示与流程走向，扩展点管业务逻辑，差异台账管预期——三者齐了，多客户才不至于把一套系统改成分叉的 N 套。直接改核心代码是短期最快、长期最贵的路。
