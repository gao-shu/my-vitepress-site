# 管理后台设计与开发

管理后台几乎是所有业务系统的「底座」：登录、权限、菜单、增删改查、导出。做悟空 CRM/ERP/OA 那几年，前后端接了十几个后台，踩的坑大同小异。这篇把可复用的设计整理出来。

## 背景与问题

- 后台本质是重复的：每个模块都是「列表 + 表单 + 权限」，每个页面都手写一遍，开发量和维护量都会爆炸。
- 权限需求会长出来：从「谁能进哪个页面」，长到「哪个角色能看哪些列、改哪些字段、审哪些单」。
- 多客户定制时，同一个后台在不同客户那里长得一样、字段不一样，硬编码会改不动。
- 前后端分离后，接口约定不清晰，联调靠吼，翻页、筛选、导出各写各的。

结论：先定权限模型和接口约定，再谈页面效率。

## 方案设计

### 权限模型：RBAC 加两层扩展

经典 RBAC 够用：用户 → 角色 → 菜单/按钮权限。实际项目再加两条扩展：

| 扩展 | 解决什么 |
|------|----------|
| 数据权限（dept_id / owner_id 范围） | 销售只能看本部门客户 |
| 字段权限（列级、表单级） | 同一页面，财务能看到成本价，销售看不到 |

权限点挂在「资源 + 动作」上（如 `crm:customer:export`），而不是挂在页面上，按钮和接口共用同一套编码。

### 菜单与路由

- 菜单存库（sys_menu），支持目录 / 菜单 / 按钮三级。
- 后端返回菜单树，前端据此生成路由；隐藏页面不下发，越权访问直接 403。
- 路由 path 与菜单编码解耦，改菜单名不炸收藏的 URL。

### 通用 CRUD 与字典

- 后端一套 BaseCRUD：分页、条件查询、批量删除，业务模块继承即可。
- 字典（sys_dict）统一管理下拉、状态、类型，前端按编码渲染，避免枚举硬编码散落前后端。
- 校验规则放后端（JSR-303），前端校验只做提示优化，不能当唯一防线。

### 列表筛选与导出

- 筛选条件统一走一个 query 对象：字段名与列名一致，后端用 QueryWrapper 拼条件。
- 导出走异步：提交任务 → 轮询或推送下载链接，大表同步导出会拖垮请求线程。
- 导出列 = 列表可见列 = 字段权限过滤后的列，三者必须同源，否则一定对不上账。

### 前后端分离约定

| 约定 | 内容 |
|------|------|
| 返回结构 | `{ code, msg, data }`，code=0 成功，业务错误码分段 |
| 分页 | `page`/`size` 入参，返回 `total` + `list` |
| 认证 | JWT 放 Header，刷新与踢出策略明确 |
| 错误 | 参数校验 400 + 字段明细，未登录 401，无权限 403 |
| 文档 | 接口文档先行，改动先改文档再改码 |

## 关键实现

权限校验拦截器（示意）：

```java
public boolean preHandle(req, resp, handler) {
    String code = resolvePermissionCode(handler); // 注解或路由映射
    if (code == null) return true;
    if (!permissionService.has(loginUser, code)) {
        throw new BizException(403, "无权限");
    }
    return true;
}
```

要点：

- 权限码优先从注解 `@RequiresPerm("crm:customer:export")` 解析，没有注解再退化到菜单映射。
- 用户权限缓存进 Redis，改角色权限时按用户维度失效，缓存 key 带公司/租户维度。
- 数据权限不靠前端传参，后端根据当前用户的角色范围自动追加 `dept_id IN (...)`。
- 通用 CRUD 的字段用配置声明（列名、类型、是否可查、是否导出），一份配置同时驱动列表、表单、导出。
- 菜单与按钮权限在登录时一次性下发，页面渲染时只读前端缓存，避免每个按钮都请求后端。

## 落地效果（示意）

以下为模式效果示意，非生产数据：

- 新增一个标准业务模块：后端 1 个 Service + 1 个 Controller + 1 份字段配置，前端 1 个列表页 + 1 个表单弹窗，半天内可联调。
- 换角色看同一页面，可见菜单、列、按钮自动收敛，不需要为每个角色复制页面。
- 导出结果与列表一致，因为走的是同一份筛选条件和字段配置。
- 客户定制字段走字典与扩展字段表，核心表结构不用跟着改。

## 小结

管理后台的复用点不在页面，而在三样东西：权限模型、字典与字段配置、接口约定。先把这三样定下来，CRUD 页面就是流水线产物；反过来先堆页面，后期加数据权限、字段权限时基本要推倒重来。
