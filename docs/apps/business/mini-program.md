# 微信小程序开发实践

小程序看着简单：页面、接口、发布。真做一遍会发现，坑集中在登录态、联调和审核三处。这篇按一个后端出身的全栈视角，记录小程序开发里最费时间的几件事。

## 背景与问题

- 登录不是「调个接口」：wx.login 拿 code 换 session_key，再和自有账号体系打通，中间还有过期、静默登录、unionid 一堆分支。
- 小程序和后端联调环境多：开发版连本地、体验版连测试、正式版连生产，配置错了排查半天。
- 体验版到发布之间有审核：类目、资质、内容合规都可能被打回，发布节奏被卡。
- 性能问题在低端机上才暴露：包体积超限、setData 太频繁、图片太大，首屏白屏用户直接走。

结论：把登录态、环境配置、发布流程先跑通，再堆功能页面。

## 方案设计

### 登录态与授权

推荐的主流方案（code2session）：

```
小程序 wx.login() → code
    ↓ 后端 code2session → openid + session_key
    ↓ 后端校验/创建自有用户 → 签发自定义登录态(token)
小程序存 token → 后续请求带 Authorization
```

- 登录态用**自定义 token**，不要直接拿 openid 当通行证。
- 静默登录（无感）与授权登录（手机号等）分开：先能进，再要敏感信息。
- session_key 由微信侧维护过期，与自建 token 的过期策略解耦，别混为一谈。
- 敏感操作（支付、改手机号）单独做二次校验，不复用普通 token。

### 与后端接口联调

- 环境配置收敛到一个 `config.js`：开发/体验/正式三个 baseUrl，构建时按环境注入。
- 请求统一封装成 `request()`：自动带 token、统一处理 code/401/网络错误，页面只写业务。
- 401 统一走静默重登 + 重放原请求，不要每个页面自己写登录逻辑。
- 联调用体验版或开发版连测试环境，本地真机预览只解决 UI，接口联调走同一套封装。

### 体验版 / 发布流程

| 阶段 | 用途 | 要点 |
|------|------|------|
| 开发版 | 自测 | 可开调试，连本地/内网 |
| 体验版 | 内部验收 | 上传后设体验成员，连测试环境 |
| 审核版 | 提审 | 选对类目与资质，提供测试账号 |
| 正式版 | 灰度/全量 | 先灰度，观察反馈再全量 |

- 每次提审准备一个**已存在的测试账号**，审核人员进不去页面是常见驳回理由。
- 版本号与描述写清楚改了什么，方便回滚对照。

### 常见审核与性能问题

审核高频雷区：

- 内容类目缺资质（食品、医疗、教育）。
- 页面内出现引导分享/关注的诱导文案。
- 支付功能未接入微信支付或类目不符。
- 测试数据没清、页面报错直接提审。

性能高频雷区：

- 分包加载：主包控制在 2MB 内，把非首屏页面扔进 subpackages。
- setData 只传变化字段，别把整个大对象塞进去；长列表分页 + 虚拟滚动。
- 图片压缩 + 懒加载 + CDN，首屏图片控制尺寸。
- wx:key 必须给，列表渲染没有 key 会出诡异的复用 bug。

## 关键实现

请求统一封装（示意）：

```js
async function request(opts) {
  const token = wx.getStorageSync('token');
  const res = await pRequest({ ...opts, header: { Authorization: `Bearer ${token}` } });
  if (res.code === 401) {           // token 过期：静默重登后重放
    await silentLogin();
    return request(opts);
  }
  if (res.code !== 0) throw new BizError(res.msg);
  return res.data;
}
```

要点：

- silentLogin 要加锁（Promise 缓存），并发多个 401 时只发一次 code 换 token，否则 session_key 打架。
- 登录态持久化存 `wx.setStorageSync`，启动时读取并校验，失败再走登录。
- 后端按 `openid + appId` 建用户唯一索引，防止重复注册。
- 真机测一遍低端安卓：iOS 开发者工具流畅不代表线上流畅。

## 落地效果（示意）

以下为模式效果示意，非生产数据：

- 统一 request 封装后，页面代码不再关心登录与错误处理，联调基本只看业务参数。
- 三个环境配置集中管理，切环境不再改散落各处的 URL。
- 提审前有清单（类目、资质、测试账号、清数据），驳回次数明显下降。
- 分包 + 图片治理后，首屏打开时间在低端机上可感知地变快。

## 小结

小程序的难点不在页面写法，在三件事：登录态的完整闭环（静默、过期、并发）、环境与请求的统一收口、审核与性能的提前清单。这三件事在项目第一天就定，后面的功能开发就是常规体力活；拖到提审前再补，几乎必返工。
