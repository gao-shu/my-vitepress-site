# 多租户 SaaS 架构

做过多客户定制之后，很容易走向另一条路：与其维护 N 套部署，不如做成一套 SaaS——多租户。这篇整理租户隔离、权限差异、计费配额和数据迁移这四件绕不开的事。

## 背景与问题

- 一套系统服务多个企业，**A 公司的数据绝不能被 B 公司看到**，这是底线，出一次事故客户就没了。
- 每个租户的组织结构、字段、功能开通不一样，既要隔离又要有差异。
- 商业模式要落地：免费试用、按人数/功能订阅、超配额怎么办，这些必须在架构里留位置。
- 老客户从私有部署迁到 SaaS，或反过来，数据怎么搬、搬完怎么对账，是最容易翻车的环节。

先回答最根本的问题：**数据隔离放在哪一层**。

## 方案设计

### 租户隔离方案

| 方案 | 做法 | 适用 |
|------|------|------|
| 独立库 | 每租户一个 database | 大客户、强隔离、数据主权要求 |
| 独立 schema/实例 | 每租户一套 schema | 中等隔离，运维成本居中 |
| 共享表 + tenant_id | 一张表，行上带租户字段 | 中小租户、规模化首选 |

实践上多用**混合**：默认共享表 + `tenant_id`，大客户切独立库。关键要求是一致的：

- 所有业务表带 `tenant_id`，且默认查询必须自动追加租户条件。
- 租户条件来自登录上下文（token 里的 tenant），**不接受前端传参指定租户**。
- 唯一索引、外键、关联查询都要带 tenant_id，否则跨租户串数据。
- 归档、备份、删除按租户粒度操作。

### 权限与配置差异

- RBAC 按租户建角色模板：租户内自己管角色，平台提供可复制的默认模板。
- 功能开关分两级：平台级（全局能力）+ 租户级（订阅开通）。
- 字段与界面差异沿用 CRM 的思路：自定义字段 + 配置驱动，租户配置存在租户维度。
- 租户间物理隔离，租户内按角色隔离——两层不要混在一个 if 里。

### 计费与配额

- 订阅表：套餐、周期、到期时间；配额表：用户数、存储、API 调用量。
- 用量**记账式累计**（流水 + 定时汇总），不要每次请求实时 COUNT 大表。
- 超限策略明确：硬限制（拒绝）还是软限制（告警 + 限速），按资源类型定。
- 到期处理走状态机：正常 → 试用到期 → 降级（只读）→ 冻结 → 删除（有保留期）。
- 支付回调要幂等，订阅状态以自己库里为准，不轻信前端跳转。

### 数据迁移

- 迁移工具：导出 → 校验 → 导入 → 对账，四步分开，可重跑。
- 租户标识、关联关系（部门、角色、单据外键）整体映射，不能只导业务数据。
- 停机窗口 + 增量同步：先全量，切流前补增量，对账通过再切。
- 保留旧环境只读一段时间，出问题能回退。

## 关键实现

租户上下文自动过滤（示意）：

```java
@Component
public class TenantLineInterceptor implements Interceptor {
  public void beforeQuery(Executor exec, MappedStatement ms, BoundSql sql, Object param) {
    Long tenantId = TenantContext.get();          // 从登录态取，非请求参数
    if (tenantId == null && isTenantTable(ms)) {
      throw new BizException("缺少租户上下文");
    }
    ms.getBoundSql(...) // 追加 tenant_id = ?
  }
}
```

要点：

- 用 MyBatis 拦截器统一加租户条件，比每个 SQL 手写 `where tenant_id=?` 可靠；同时保留手写兜底审查。
- `TenantContext` 用 ThreadLocal/TransmittableThreadLocal，异步线程、线程池场景要传递，否则串租户。
- 提供租户维度的「越权自测」用例：A 租户 token 拼 B 租户 id 访问，必须 403/404。
- 记账流水表带唯一键（tenant + 维度 + 周期），防重复记账。
- 独立库租户走同一套迁移脚本，只是 datasource 路由不同。

## 落地效果（示意）

以下为模式效果示意，非生产数据：

- 统一租户拦截器后，新增业务表自动纳入隔离，漏写 tenant 条件的问题在评审阶段就能查出来。
- 功能开关与自定义字段让新租户开通从「部署一套」变成「配置一遍」。
- 用量记账与配额校验上线后，超卖资源、超限扯皮有据可查。
- 迁移流程标准化，私有部署客户上云按四步走，对账项提前定义，切流争议少。

## 小结

多租户架构的优先级很清晰：隔离是底线（统一上下文 + 统一拦截，别靠人肉记），差异靠配置（角色模板、功能开关、自定义字段），商业化靠记账（配额、到期状态机、幂等回调），迁移靠流程（可重跑、可对账、可回退）。先做对隔离，再谈规模。
