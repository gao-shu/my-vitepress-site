# 知识库问答（RAG）搭建实践

## 背景与问题

中小企业里不缺文档，缺的是"能问得出来的文档"。产品手册散落在网盘，制度文件在飞书里，历史工单在 Excel 里——新人遇到问题第一反应还是"问人"。做一个内部知识库问答系统，让员工用自然语言提问、系统基于企业自己的文档回答，是 AI 落地里性价比最高的一类需求。

直接把文档喂给大模型行不通：上下文窗口有限，文档一多就装不下；更重要的是，模型没有你的私有资料，只能靠"编"。所以常规做法是 RAG（Retrieval-Augmented Generation，检索增强生成）：先从知识库里检索出与问题相关的片段，再把片段连同问题一起交给大模型生成回答。

这条路能走通，但每个环节都有坑，下面按我们实际搭建的顺序展开。

## 方案设计

整体链路分两条：离线的**入库流水线**和在线的**问答链路**。

- 入库流水线：文档解析 → 切分（Chunking）→ 向量化（Embedding）→ 写入向量库（附带原文与元数据）
- 问答链路：问题向量化 → 向量检索（召回 Top-K）→ 重排（Rerank）→ 拼装 Prompt → 大模型生成回答（带引用）

技术选型上不追新：向量库用 Qdrant 或 pgvector（如果已有 PostgreSQL，pgvector 能省一套运维），Embedding 用国内云厂商的中文向量模型或开源 BGE 系列，大模型按任务走多模型接入那一套统一路由。核心精力应该花在**切分质量和检索效果**上，这两点决定了上限，模型只是把上限兑现。

```
文档 → 解析 → 切分 → Embedding → 向量库
                                      ↓
用户问题 → Embedding → 检索 Top-K → 重排 → Prompt 拼装 → LLM → 回答（带引用）
```

## 关键实现

**1. 切分：按结构优先，不要无脑定长**

切分粒度是最容易踩坑的一步。推荐按文档结构（标题、段落）切，切完再按 token 上限拆分，块之间留 10%~15% 的重叠，避免语义被拦腰截断。每块带上来源元数据（文件名、章节、更新时间），回答时才能给出引用。

```python
def chunk_document(doc):
    sections = split_by_heading(doc)          # 先按标题结构切
    chunks = []
    for sec in sections:
        parts = split_by_tokens(sec.text, max_tokens=500, overlap=60)
        for p in parts:
            chunks.append({
                "text": p,
                "source": doc.filename,
                "section": sec.heading,
                "updated_at": doc.updated_at,
            })
    return chunks
```

**2. 检索与重排：先召回再精筛**

单靠向量检索，Top-5 里经常混进"主题相近但答非所问"的块。两段式是标配：先用向量检索召回 Top-20~50，再用 Cross-Encoder 重排模型对（问题, 块）打分，取 Top-3~5 进入 Prompt。有条件的再加一路 BM25 关键词检索做混合召回，专有名词、型号、单号这类查询靠向量很容易丢。

```python
def retrieve(question, top_k=5):
    q_vec = embed(question)
    candidates = vector_store.search(q_vec, limit=30)      # 召回
    candidates += bm25_search(question, limit=10)          # 混合召回
    ranked = reranker.rank(question, dedupe(candidates))   # 重排
    return ranked[:top_k]
```

**3. 接入大模型：Prompt 里写死"只依据资料回答"**

拼装 Prompt 时把检索片段编号放进去，明确要求：只依据给出的资料回答；资料里没有的，直接说"资料中未提及"；回答末尾列出引用来源。这三条约束对抑制造幻觉非常有效。

```
你是企业知识库助手。仅依据以下资料回答问题，资料未提及的内容明确说明"未提及"，不要推测。
资料：
[1] {chunk.source} / {chunk.section}\n{chunk.text}
...
回答时标注引用编号，如 [1][3]。
```

## 落地效果

例如一个 200 篇文档的产品知识库，做完结构化切分 + 混合检索 + 重排之后，典型问答的效果大致是：

- 产品参数、操作步骤这类有明确出处的问题，回答基本能命中正确片段并给出引用；
- 引入重排后，"召回了相似主题但不是用户要问的那条"这类错误明显减少；
- 对于资料里确实没有答案的问题，加了约束的 Prompt 会让模型老实回答"未提及"，而不是顺口编一个。

注意这些是"例如"性质的示意——真实效果取决于文档质量和领域，上线前必须拿 30~50 个真实业务问题做评测集，人工标注期望答案，跑准确率基线，再迭代切分与检索参数。

## 常见坑

- **切分过大**：一块塞几千 token，检索召回了但信噪比极低，模型找不到重点；还会挤占上下文。宁可小块 + 重排补救。
- **检索不准**：问题和文档用词不一致（口语 vs 专业术语）、专有名词查不到，靠加混合检索、同义词扩展、查询改写来解；重排不是可选项，是必需品。
- **幻觉**：模型答了资料里没有的内容。三板斧——Prompt 硬约束、回答强制带引用便于抽查、上线前用评测集回归。引用对不上就说明检索或生成有问题，定位也快。
- **文档更新不生效**：入库是一次性的，源文档改了库没改。入库要按文档版本做增量更新，删旧块重插。

## 小结

RAG 的工程重心不在调模型，而在**数据处理和检索质量**：结构化切分、混合召回、重排、带引用的受约束生成，这四件事做扎实，问答准确率就能到可用水平。先拿评测集把基线量出来，再谈优化，否则全是感觉。
