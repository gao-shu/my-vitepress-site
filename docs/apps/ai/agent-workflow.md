# 智能体工作流设计与落地

## 背景与问题

Demo 阶段的 Agent 很容易做：丢一个 Prompt 给模型，让它自己决定调什么工具、走什么路径，跑通一两个例子效果惊艳。但要放到业务里跑，问题立刻来了——路径不可控、失败不可重试、出错无法定位、成本无法预估。中小企业做 AI 落地，最怕的就是"演示很智能，上线很玄学"。

核心矛盾在于：**自由度越高，可控性越差**。纯粹的 ReAct 式 Agent（模型自主循环决定下一步）自由度最高，但业务流程往往是有明确步骤的——工单分类有固定分支，内容审核有固定环节，这些流程不需要模型"自由探索"，需要的是在关键环节借模型的判断力。

所以第一个要想清楚的问题是：你的场景到底需要 Agent 还是工作流。

## 方案设计

**Agent 与工作流的区别，可以粗暴地这样理解：**

- **工作流（Workflow）**：流程由代码定义，模型只在固定节点上做"判断"或"生成"。路径确定、可测试、成本可估。适合流程清晰的场景——审批流转、内容生产流水线、数据清洗。
- **Agent**：流程由模型自主决定，代码只提供工具和终止条件。路径不确定、难测试、成本波动大。适合开放性任务——多轮客服、探索式分析。

**实践中的结论是：能用工作流解决的，不要上 Agent。** 我们的做法是"工作流打底，节点内嵌模型判断"：主干状态机用代码写死，只在分类、抽取、改写这类节点调用大模型。既拿到了智能化的收益，又保住了工程可控性。真正需要多步自主决策的场景（比如一个任务要模型自己决定查哪些系统），再把某一段换成 Agent 子任务，用完收回来。

整体架构：

```
任务入口 → 状态机调度（代码） → [节点A: 规则] → [节点B: 模型判断] → [节点C: 工具调用]
                ↑                    ↓ 失败/超时
                └── 重试队列 ←────────┘
任务表（状态、上下文、每步输入输出、trace_id） 贯穿全程
```

## 关键实现

**1. 任务拆解与状态机**

把业务流程画成状态机，每个节点有明确的输入输出契约，状态落库。这样任何时刻任务卡在哪一步、重试过几次，查表就知道，不用翻日志猜。

```python
# 状态机定义：流程是代码，模型只在带 llm 标记的节点介入
FLOW = {
    "parse_ticket":  {"on_success": "classify",   "on_fail": "failed"},
    "classify":      {"on_success": "dispatch",   "on_fail": "classify_retry", "llm": True},
    "dispatch":      {"on_success": "done",       "on_fail": "dispatch_retry"},
}

def run(task_id):
    task = task_store.get(task_id)
    while task.state not in ("done", "failed"):
        node = FLOW[task.state]
        try:
            result = execute_node(node, task)     # 规则节点走代码，llm 节点走模型
            task.append_step(node, result)        # 每步输入输出落库，便于回溯
            task.state = node["on_success"]
        except RetryableError as e:
            task = backoff_retry(task, node, e)   # 指数退避，超限转 failed
        task_store.save(task)
```

**2. 工具调用设计**

工具是模型与真实系统的接口，设计要点：

- **Schema 严格**：参数用 JSON Schema 定义，必填项、枚举值写清楚，模型填错直接校验拒绝并返回错误信息让它重试；
- **幂等**：工具可能被重复调用（重试场景），写操作带业务幂等键，防止重复下单、重复发消息；
- **权限收敛**：Agent 能调的工具按任务类型白名单放行，不让模型碰它不该碰的系统；
- **返回可读**：工具返回给模型的文本要精简、结构化，别把整个数据库表结构扔进去。

**3. 失败重试与可观测**

大模型调用的失败分三类，处理方式完全不同：网络/超时/限流（可自动重试）、模型输出不符合 Schema（带错误信息重试一次，再失败转人工）、业务性失败（不重试，直接走补偿分支）。不要写一个笼统的 catch-all 重试三次。

可观测上，每个任务一条 trace：节点序列、每步的 Prompt 摘要、模型响应、耗时、token 消耗。出问题先看 trace 定位到节点，再看该节点的输入输出——这比对着一个黑盒 Prompt 调试高效得多。

## 落地效果

例如一个工单自动分派流程，把原来"全靠模型自由发挥"的单体 Agent 拆成状态机 + 三个模型节点之后：

- 流程走向固定了，测试用例可以直接断言"该走到哪个状态"，回归测试能自动化；
- 单个节点失败不影响整体，重试和降级（比如模型超时就走规则兜底）都有了明确位置；
- 运维同学看任务表就能回答"这个任务为什么卡住"，不用拉工程师查日志。

这些同样是示意——真实收益主要体现在**可控性和排障效率**上，成功率的提升要靠评测集和线上数据说话。

## 从 Demo 到可用的差距

这块最容易被低估，列一下必须补的东西：

- **评测**：固定一批典型输入 + 期望输出，Prompt 或模型一改就回归。没有评测集，所有优化都是盲调；
- **降级路径**：模型服务挂了怎么办？关键节点要有规则兜底或转人工，不能整条链路瘫痪；
- **成本闸门**：单任务 token 上限、并发限流、每日预算告警，防止一个死循环烧钱；
- **人工介入点**：低置信度、高风险操作（退款、删除）要留人工确认，不要全自动；
- **Prompt 版本管理**：Prompt 改动要像代码一样有版本、可回滚，出问题能定位是哪次改动引入的。

## 小结

Agent 落地的关键不是让模型更自由，而是**给它套上工程的笼子**：流程用状态机圈住，工具用严格 Schema 和幂等约束住，失败分类处理，全程 trace 可回放，再配上评测集和降级路径。模型负责判断，代码负责确定性——分工清楚了，Demo 才能变成能交付的系统。
