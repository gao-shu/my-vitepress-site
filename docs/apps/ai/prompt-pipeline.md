# Prompt 编排与生成流程自动化

## 背景与问题

AI 漫剧这类内容生产业务，本质上不是"一次调用大模型"，而是**一条多步流水线**：剧本 → 分镜脚本 → 关键帧生图 → （可选）生视频 → 合成。每一步的输出是下一步的输入，每一步调用的模型和参数还不一样——剧本要长文本生成，分镜要结构化抽取，生图是另一个 API 协议。

这类需求如果用"一个大 Prompt 一把梭"的方式做，会遇到几个典型问题：

- **单次生成质量不稳**：剧本和分镜的写作要求完全不同，混在一个 Prompt 里互相干扰；
- **不可复用、不可调优**：Prompt 写死在代码字符串里，改一个词要发版，出了问题不知道是哪个版本的 Prompt 生成的内容；
- **失败无法局部重试**：第 3 步生图失败，难道整个剧本重新生成？前面成功的步骤白白浪费；
- **没有人工介入点**：模型生成的剧本如果直接进入生图，一个方向性错误会放大到后面每一步。

所以关键不是"写一个好 Prompt"，而是**把 Prompt 和流程都当成可管理的工程资产来编排**。

## 方案设计

把流水线拆成"步骤"，每个步骤有明确的定义：

- **模板（Template）**：这一步的 Prompt 模板，带变量占位符，独立于代码管理；
- **模型路由**：这一步走哪个模型别名（接到多模型网关）；
- **输入/输出契约**：上一步产物的 Schema、本步输出的 Schema（如分镜必须是 JSON 数组）；
- **审核策略**：自动通过 / 抽检 / 必须人工确认。

```
任务创建
  → [步骤1] 剧本生成    （模板 script.v3 + 长文本模型）      → 人工审核点①
  → [步骤2] 分镜拆解    （模板 storyboard.v2 + JSON 输出）   → 规则校验
  → [步骤3] 关键帧生图  （并行 N 个分镜 → 生图 API）
  → [步骤4] 视频合成    → 任务完成
```

流程编排用异步任务做：任务表记录整体状态，每个步骤一条执行记录（输入、输出、模板版本、模型、耗时、状态），步骤间通过任务产物传递数据。任一步失败只重试该步，且能从任意步骤**断点续跑**——这在生图动辄超时的场景里是刚需。

审核节点放在"错误会被放大"的位置：剧本方向错了，后面全白做，所以剧本后设人工确认；分镜有 JSON Schema + 规则校验兜底，可自动放行或抽检。

## 关键实现

**1. 模板版本管理**

Prompt 模板不写在代码里，放文件并带版本号，任务执行时锁定版本——同一个任务从头到尾用同一套模板版本，保证可复现、可归因。

```
prompts/
  script/v3.md          # 变体：{{genre}} {{episode_no}} {{synopsis}}
  storyboard/v2.md       # 输出要求：JSON Schema 内嵌
  storyboard/v2.schema.json
```

```python
def run_step(task, step_def):
    tpl = template_store.load(step_def.template, version=step_def.locked_version)
    prompt = tpl.render(**task.context)
    result = gateway.chat(step_def.model_alias, prompt,
                          output_schema=step_def.schema)   # 走统一网关
    task.record_step(step=step_def.name,
                     template_version=tpl.version,
                     model=result.model,      # 记录实际用了哪个模型
                     input=task.context,
                     output=result.data,
                     status="done")
    return result.data
```

每步落库的记录就是审计线索：内容出了问题，能查到当时用的哪个模板版本、哪个模型、原始输入是什么。

**2. 人工审核节点**

审核不是"停下来等人点按钮"那么简单，要定义清楚：审核什么（剧本全文？分镜表？）、超时怎么办（默认打回还是默认通过）、审核意见怎么回流（修改后重跑当前步骤还是回退上一步）。实现上就是任务状态机里的一个 `waiting_review` 状态，审核通过才推进。

**3. 异步任务编排**

- 任务入队（Redis Stream / MQ 均可），worker 按步骤推进，生图这类长耗时步骤天然适合异步重试；
- 步骤幂等：以 `(task_id, step, attempt)` 做幂等键，重试不会产生重复产物；
- 并行扇出：多个分镜的生图并发执行（控制并发度 + 处理限流），全部完成再汇聚到下一步；
- 全局超时与预算：单任务有总时长和 token/费用上限，超限终止并告警，防止死循环烧钱。

## 落地效果

例如一条"3 分钟漫剧、约 40 个分镜"的生产任务，串成带审核的流水线之后的典型形态：

- 剧本人工确认后，分镜拆解和生图自动跑，运营从"每步盯着"变成"只审关键节点"；
- 某个分镜生图失败只重试该分镜，前面的剧本和分镜结果全部保留，不用整单重跑；
- 出了质量争议，按任务记录能查到每一步的模板版本和模型，复现当时的生成过程。

以上为示意——实际提效幅度取决于审核环节的设置和模型稳定度，建议先小规模跑通一条完整链路、记录每步耗时和失败率，再逐步放开自动通过的节点。

## 小结

内容生产自动化的要点：**Prompt 模板版本化管理，流程拆成带契约的步骤，审核点放在错误放大之前，执行用异步任务编排并支持断点续跑**。模型负责生成，流水线负责可控、可复现、可归因——这才是一条能长期跑的生产链路。
