# Web 与 PDA 数据协同

## 背景与问题

典型现场是这样的：计划员在 Web 后台排产、下发任务，班组长和仓管在 PDA 上领任务、扫码执行、回传结果；Web 端再看进度和异常。两套端、一个后台，协同做不好会出现这些问题：

- **任务状态对不上**：Web 上显示「进行中」，PDA 上早做完了没传；或者两个 PDA 同时领了同一条任务，重复干活。
- **回传时机混乱**：有人做成「每扫一条同步一条」，弱网下卡成幻灯片；有人做成「最后一次性传」，中途退出全丢。
- **冲突处理没有规则**：任务被 Web 端改了数量、PDA 端又扫了超量，谁让步没有定义，最后靠人工对账。
- **条码数据流不统一**：Web 端生成的二维码和 PDA 端解析出的内容格式不一致（前缀、校验位、分隔符），扫码后匹配不到单据。

本质问题不是「前端怎么写」，而是**一套数据、两个写入方、网络还不稳定**，需要先定协议再写代码。

## 方案设计

**数据流总览**：

```
Web 后台                    后台服务                     PDA 端
排产/下发任务  ──任务快照──▶  任务表(状态机)  ──claim──▶  领取本地缓存
查看进度      ◀──状态订阅──  ◀──批次回传(幂等)──  扫码采集/校验
异常处理      ◀──异常队列──  ◀─────────────────  冲突/失败标记
```

**三个设计决定**：

1. **任务是状态机，不是自由编辑的表**：`已下发 → 已领取 → 执行中 → 已完成 → 已关闭`，每条流转由服务端校验，两端都只能发起合法流转。
2. **下发走快照，回传走批次**：Web 下发时把任务所需的物料、库位、数量固化成快照，PDA 离线也按快照干活；回传按批次提交，每条带幂等键。
3. **冲突有显式规则**：见下文「冲突处理」，能在服务端判定的自动判，判不了的进异常队列由人在 Web 端处理，**绝不静默覆盖**。

**任务分发方式**：量小用 PDA 主动拉（`GET /tasks?since=` 增量拉取），量大或需要即时提醒再加推送（长连接/厂商推送）。拉取模型简单、断线天然可补偿，作为默认方案。

## 关键实现

**1. 任务分发与领取（防重复领取）**

```sql
-- 服务端：领取动作用条件更新做原子锁
UPDATE task SET assignee = #{pdaId}, status = 'EXECUTING', ver = ver + 1
WHERE id = #{taskId} AND status = 'DISPATCHED';
-- affected = 0 → 任务已被别人领取，返回 409
```

PDA 领到后整包快照写本地，后续扫码校验全走本地，不再依赖网络。

**2. 回传批次与状态一致性**

```json
POST /task-results/batch
{
  "batchId": "b-20261014-8f3a",     // 整批幂等键
  "taskId": "T-1001",
  "ops": [
    { "opId": "o-001", "type": "SCAN", "code": "PART00123", "qty": 10, "ts": 1790000001 },
    { "opId": "o-002", "type": "SCAN", "code": "PART00456", "qty": 5,  "ts": 1790000002 }
  ]
}
```

服务端规则：`batchId` 已处理 → 直接返回上次结果（整批重试安全）；`opId` 唯一索引兜底单条重复；处理结果**逐条返回**（成功/冲突/非法），PDA 只删除成功的 op，冲突项标 `NEED_REVIEW` 留在本地并提示。任务完成以服务端聚合的数量为准，PDA 显示的是「已回传视图」，避免两端各算各的。

**3. 冲突处理**

- **数量类冲突**（超交、重复扫码）：服务端聚合时校验，超限直接拒绝该条，返回剩余可扫数量；PDA 界面按返回值即时纠正。
- **版本类冲突**（任务在 Web 端被改过）：快照带 `ver`，回传时比对，`ver` 不一致返回 `STALE_TASK`，PDA 提示「任务已变更，需重新拉取」，已采数据保留待人工确认。
- **双端同时写同一单据**：服务端状态机挡住非法流转，冲突进异常队列，Web 端提供「采纳 PDA / 采纳 Web / 手工调整」三个操作，处理动作留审计日志。
- 原则：**自动裁决只用于能用规则判定的场景，其余显式抛给人**，宁可多一步人工确认，不要悄悄丢数据。

**4. 条码/二维码数据流**

统一「编码规范 → 生成 → 解析 → 匹配」一条链：

| 环节 | 约定 |
|------|------|
| Web 码生成 | 约定格式，如 `BIZ|taskId|lineNo|qty|check`，二维码用 `\|` 或 `^` 分隔 |
| PDA 解析 | 剥离 GS1 前缀（`]C1`）、去回车换行，按分隔符切字段并校验校验位 |
| 匹配 | 先按 `taskId+lineNo` 匹配本地快照，匹配不到再查服务端主数据 |
| 兜底 | 非法码进「异常扫码」列表，不弹窗打断流水作业，事后统一处理 |

编码规则放在一个共享的常量/文档里，Web 生成和 PDA 解析用同一份测试用例回归，避免「Web 改了分隔符 PDA 没跟上」这种低级事故。

**5. 状态推送回 Web**

Web 端进度页用轮询（`GET /tasks/summary?ids=` 每 5~10s）或 SSE 推送；关键不是实时性多高，而是**状态语义统一**——进度百分比一律由服务端按聚合结果计算，两端展示同一来源。

## 落地效果（示意）

| 维度 | 协同混乱时（示意） | 建立协议后（示意） |
|------|--------------------|--------------------|
| 任务领取 | 双人重复干活，事后对账 | 原子领取，409 拦截 |
| 回传 | 重复提交产生重复记录 | batchId/opId 双层幂等，逐条结果 |
| 码不匹配 | 现场拿手工单绕过系统 | 统一编码规范 + 异常码队列 |
| 进度查看 | Web、PDA 各显示一套 | 服务端聚合为唯一进度来源 |

实际效果需上线后统计重复任务率、异常队列处理时长来验证。

## 小结

Web 与 PDA 的协同，难点在**协议而非界面**：任务用状态机和原子领取保证不重不乱，回传用批次 + 幂等键保证不断不丢，冲突用显式规则加异常队列保证不静默覆盖，条码用统一编码规范保证两端说一种语言。把这四件事写成接口文档和测试用例，两端各自开发也不会跑偏；缺了任何一条，现场一定会用「手工单」把系统绕过去。
