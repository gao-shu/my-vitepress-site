# 离线优先的终端应用设计

## 背景与问题

仓库、车间、野外巡检这类场景，网络断续是常态而不是异常。多数应用的默认写法是「在线为主、缓存兜底」：数据从服务端拉下来放内存，断网时界面转圈，恢复后整页刷新。这种写法在终端场景会出三类事故：

- **断网期间用户动作丢失**：扫了码、点了确认，提示「网络异常」，人一急重复操作，恢复后数据又乱。
- **恢复后整包覆盖**：重新拉取时把本地改动冲掉，或者把别人的新数据冲掉——同步=覆盖，没有冲突概念。
- **回补逻辑临时补**：断网两周的设备上线时一次性灌几万条，超时、内存爆、顺序错乱。

离线优先（offline-first）换个思路：**本地存储是数据的主副本，网络只是同步通道**。界面永远读写本地，同步在后台异步进行，冲突按规则处理。这个思路不是新概念（PWA、RxDB、CRDT 讨论了很多年），落到工程上真正要做的是四件事：本地优先存储、变更队列、冲突策略、重连补偿。

## 方案设计

**核心模型**：

```
UI（永远读本地，永远写本地）
  ↓
本地库（SQLite/Room：业务表 + 变更队列 outbox + 同步游标）
  ↓
同步引擎（按游标拉增量、按队列推变更、冲突裁决、记录结果）
  ↓
服务端（全量/增量接口 + 冲突裁决 + 操作日志）
```

**四个设计决定**：

1. **本地优先存储**：业务数据落 SQLite（关系型、可查询、可事务），所有写操作先在本地事务里完成，UI 立即可见——本地写成功就是「保存成功」，与网络无关。
2. **变更队列（outbox）**：每次业务写在**同一事务**里生成一条变更记录（表、行、操作类型、前后镜像或增量、opId、时间戳），同步引擎只搬运 outbox，业务代码不直接碰网络。
3. **冲突策略先定规则**：按数据类型分层——能幂等的用幂等消掉；能字段合并的合并；有业务语义冲突（数量、状态）的抛给人工。**没有万能策略，按表定策略**。
4. **重连补偿**：上线后按游标增量拉 + 分批推 + 断点续传，禁止全量覆盖和一次性回灌。

**同步协议（示意）**：

- 下行：`GET /sync/pull?cursor=&limit=` 返回变更列表 + 新游标；服务端发的每条变更也带 opId。
- 上行：`POST /sync/push` 提交 outbox 批次，逐条返回 `applied / duplicate / conflict / rejected`。
- 两端都记录对方的 opId，实现**双向去重**——防止「我推上去的变更又被拉回来当成对方的新变更」。

## 关键实现

**1. 本地写 + outbox 同事务**

```sql
BEGIN;
  UPDATE task SET done_qty = done_qty + 10 WHERE id = 'T-1001';
  INSERT INTO outbox(op_id, table_name, row_id, op, payload, created_at, status)
  VALUES ('o-20261014-0001', 'task', 'T-1001', 'UPDATE',
          '{"done_qty": 110}', strftime('%s','now'), 'PENDING');
COMMIT;
```

同步引擎只认 `status = 'PENDING'` 的记录，按 `created_at` 顺序分批（如 50 条）推送；成功置 `SYNCED`，冲突置 `CONFLICT` 并带原因。**业务代码永远不直接调同步接口**，保证断网时行为与在线时完全一致。

**2. 变更队列与去重**

- `opId` 客户端生成（时间戳 + 设备号 + 序列），全局唯一，服务端唯一索引兜底；
- 服务端应用变更时把 `opId` 写入操作日志，重复推送返回上次结果（幂等）；
- 下行变更同样带 opId，客户端发现是自己推过的直接忽略，避免回环。

**3. 冲突解决策略（按数据类型分层）**

| 数据类型 | 策略 | 说明 |
|----------|------|------|
| 追加型（扫码记录、日志） | 天然无冲突 | 只做去重，永不覆盖 |
| 计数/数量型 | 服务端聚合为准 | 本地显示「已回传」与「待回传」分开 |
| 字段独立型（备注、地址） | 字段级合并 | 不同字段各写各的，同字段后写让步 |
| 状态机型（任务状态） | 服务端裁决 | 非法流转拒绝，返回当前权威状态 |
| 关键业务冲突 | 进异常队列人工判 | 双方数据都保留，绝不静默丢弃 |

实现上可用 `version` 字段做乐观锁：推变更时带上读到的版本，版本不匹配服务端返回当前值，客户端按上表策略处理（自动改或转人工）。

**4. 重连补偿**

- 网络恢复事件触发一次 sync，之后按「在线：10s 一次；离线：停止」的节奏调度；
- push 失败指数退避（2s→4s→…→60s 封顶），**永远限制批量大小**，断网三天的设备分几十批慢慢补，每批带断点；
- pull 按游标增量，服务端保留变更日志的窗口（如 7 天）；超出窗口或游标失效时降级为「全量快照 + 本地未同步数据重新排队」；
- 冲突记录不阻塞正常同步：`CONFLICT` 的行停在本地等人处理，其余记录继续流转。

**5. 边界处理**

- 存储上限：outbox 和本地日志设配额，超限时提示并引导优先回传；
- 时间：设备时钟可能不准，排序以服务端接收序 + 单调序列为准，时间戳只作参考；
- 测试：用「网络开关 + 时钟偏移 + 批量冲突」三个维度做自动化模拟，同步逻辑必须能离线回归。

## 落地效果（示意）

| 场景 | 在线优先（常见问题） | 离线优先（预期，示意） |
|------|----------------------|------------------------|
| 断网作业 | 提示失败，人工纸单记录 | 照常作业，变更进 outbox |
| 恢复网络 | 整页刷新，可能覆盖本地 | 分批补传，按规则裁决冲突 |
| 断网很久后上线 | 一次性回灌超时失败 | 游标增量 + 断点续传 |
| 重复推送 | 产生重复业务数据 | opId 幂等，重复无副作用 |

补传成功率、冲突队列积压量是上线后要盯的两个指标，需要按周统计确认策略是否要调整。

## 小结

离线优先不是「加个缓存」，是把因果关系反过来：**本地是主、网络是从**。落地动作就四步——业务数据进本地库且本地写即成功，写操作同事务进变更队列，按数据类型预先定好冲突规则（幂等、聚合、合并、人工四选一），恢复后按游标和批次补偿而不是全量覆盖。冲突规则这一步最容易被跳过，也是现场数据出问题后最难补救的一步：先在接口文档里把每张表的冲突策略写清楚，再动手写同步引擎。
