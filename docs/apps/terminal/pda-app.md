# PDA 移动端应用开发

## 背景与问题

制造业现场的收货、上料、盘点、质检，大多靠 PDA 扫码完成。这类项目和普通 Web 开发差别很大，坑基本集中在四件事上：

- **扫码不是输入框**：仓库灯下条码反光、标签褶皱，扫出来带不带前缀、结尾有没有回车，各家枪头行为不一致；扫太快还会丢字符。
- **网络不等于办公室**：钢结构厂房里 Wi-Fi 漂移是常态，冷库、立体库边缘信号更差。人正在扫码录数据的时候断网，不能让他白干。
- **数据要和后台对上**：PDA 上操作的是任务、单据、物料，后台接口往往是给 Web 端设计的，直接搬过来会发现缺批量、缺幂等、缺状态机。
- **现场部署没人帮你点**：PDA 分散在各个班组，装包、升级、登录态都得考虑现场维护成本。

写过 Web 的人接手 PDA，最容易犯的错是「先把界面做出来再说」，结果上线后被断网和扫码识别率反复打回。

## 方案设计

**技术选型**：按团队情况选，不追新。

- 有 Android 原生需求（扫码广播、开机自启、设备管理）→ Kotlin；
- 团队是 Web 背景、业务以表单流转为主 → H5 + 浏览器内核（或 Capacitor 打包）；
- 已有 React/Vue 积淀且要双端 → Flutter / RN 都够用，现场项目差异不大。

**整体分层**：

```
UI 层（任务界面、扫码交互）
  ↓
本地数据层（SQLite / Room：任务缓存 + 待同步队列）
  ↓
同步层（批量提交、幂等、冲突检测）
  ↓
网络层（统一超时/重试/离线降级）
  ↓
后台接口（任务下发、结果回传、主数据查询）
```

核心原则两条：

1. **离线可完成当前任务**：领到任务后，扫码校验、必填校验、状态推进全部走本地数据，断网只是暂时不能回传。
2. **接口按现场动作设计**：不暴露 CRUD，暴露「领任务」「提交结果」「查询主数据」这类带状态语义的接口，入参支持批量、带幂等键。

**扫码方案**：优先用系统扫码广播（ACTION_DECODE），拿到结果后自己拼串解析；没有广播的设备用 Camera/连续扫码库。解析逻辑做成一个纯函数，方便把现场遇到的怪码离线复现。

## 关键实现

**1. 扫码解析与防抖**

```kotlin
// 伪代码：统一入口，屏蔽枪头差异
fun parseScan(raw: String): ScanResult {
    val s = raw.trim().removeSuffix("\r").removeSuffix("\n")
    // 前缀如 "]C1"（Code128 GS1）按业务决定保留或剥离
    val code = if (s.startsWith("]C1")) s.substring(3) else s
    return if (code.length < 6) ScanResult.Invalid(raw) else ScanResult.Ok(code)
}
```

连续触发用时间窗去抖（150~300ms 内的重复上报合并），扫完一条锁输入 300ms，防止同一张标签被扫两次。

**2. 本地缓存 + 待同步队列**

任务明细落到 SQLite；每次用户动作先写本地表 `pending_op`（op_id、类型、payload、created_at、retry），**写完立刻刷新 UI**，再异步尝试回传：

```sql
CREATE TABLE pending_op (
  op_id     TEXT PRIMARY KEY,   -- 客户端生成，兼做幂等键
  task_id   TEXT NOT NULL,
  op_type   TEXT NOT NULL,
  payload   TEXT NOT NULL,
  created_at INTEGER NOT NULL,
  retry     INTEGER DEFAULT 0
);
```

回传成功删记录，失败保留并累加 `retry`，超过阈值标 `stuck` 提示人工处理。

**3. 弱网处理**

- 请求统一 5s 超时 + 指数退避重试，禁止在 UI 线程死循环重连；启动时和网络恢复时（ConnectivityManager 回调）触发一次队列 flush；
- 主数据（物料、库位）按「上次同步时间戳」增量拉取，本地只读也能校验；
- 顶部常驻网络状态条，离线时回传按钮置灰但不隐藏，让用户知道「存下了，还没传」；

**4. 与后台接口设计**

- `POST /tasks/claim` 领任务：服务端锁任务并返回快照，客户端整包缓存；
- `POST /task-results/batch` 回传：数组入参，每条带 `op_id`，服务端按唯一索引去重，**重复提交返回成功而不是报错**；
- 状态推进用服务端状态机校验（如「已扫描→已提交」），非法流转直接拒绝，防止离线期间任务被别人做过；
- 大结果（含照片）先传文件拿 file_id，再提交业务，避免一个接口又传文件又写库。

**5. 现场部署**

- 内部分发（不走应用市场）：签名 APK + 版本检查接口，启动时强弱更新分开：数据结构不兼容强更，UI 改动可延后；
- 配置（服务器地址、车间号）做成首启引导页，可扫码导入，避免现场手敲 IP；登录态用长效 refresh token，班组长设备可记住密码但设自动锁屏；
- 只留操作日志 + 崩溃堆栈（不上报隐私），现场扯皮时能还原「谁在哪一步扫了什么」；

## 落地效果（示意）

用示意数据说明这套做法的收益方向（非真实生产统计）：

| 维度 | 上线前常见状态 | 采用本方案后（示意） |
|------|----------------|----------------------|
| 断网时操作 | 页面报错，人工登记事后补录 | 照常扫码，联网后自动回传 |
| 重复扫码/提交 | 后台出现重复记录，需人工对账 | 幂等键去重，重复提交无副作用 |
| 现场升级 | 逐台拷包、版本不一致 | 版本检查 + 增量更新包 |
| 怪码问题 | 「扫不出来」无法定位 | 原始串落日志，可离线复现解析 |

具体提升幅度取决于现场网络与班组习惯，需要上线后按周观察回传成功率、卡单数量再评估。

## 小结

PDA 项目的难点不在界面，在**数据流**：扫码要兼容设备差异，断网要保证已采数据不丢，接口要按现场动作而不是按表结构设计，部署要考虑没人盯着升级。先按「本地写成功即算完成、回传只是同步动作」把架构定下来，弱网、幂等、批量这些问题会在同一套机制里一起解决；反过来先堆功能，后期每一条都要返工。
