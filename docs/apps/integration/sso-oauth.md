# 单点登录与授权打通

## 背景与问题

公司内部系统多了之后，每个系统各管各的登录：OA 一套账号、报表一套账号、几十个内部小工具又是几十套。结果是：

- 同事入职要开通 N 个系统，离职要挨个关，漏一个就是安全黑洞；
- 密码记不住，弱密码和浏览器明文保存泛滥；
- 想做「统一权限」根本无从下手，因为身份都不统一；
- 用户体验差，一天要登录七八次。

目标很明确：**一次登录，全部通行**。技术选型上，OAuth2 是最常被问到的——但要先分清它是什么：OAuth2 解决的是**授权**（让 A 系统安全地访问 B 系统的资源），OIDC 在它之上补了**认证**（你是谁）。做单点登录，实际落地通常是「OIDC/OAuth2 授权码流程」，把它当成登录协议用。

## 方案设计

架构上引入**认证中心（IdP）**，各业务系统变成**客户端（RP）**：

```
用户 ──▶ 业务系统A(未登录) ──302──▶ 认证中心
                                      │ 无会话
                                      ▼
                                  登录页(输账号密码)
                                      │ 验证通过
用户 ◀── 回跳 A，携带 code ───────────┘
A ──后台用 code 换 token──▶ 认证中心 ──▶ 得到 access_token / id_token
```

关键决策：

| 决策点 | 选择 | 理由 |
|--------|------|------|
| 主流程 | 授权码模式（Authorization Code） | 密码不经过第三方客户端，最安全，Web 标配 |
| 密码模式 | 仅限受信的老旧服务端程序 | 有历史系统改造期的过渡用途，新系统禁用 |
| 会话 | 认证中心持全局会话，客户端持本地会话 | 免登录 + 登出联动 |
| Token | 短期 access_token + 可撤销 refresh_token | 减少泄露窗口，又不频繁打扰用户 |

**授权码 vs 密度模式**：

- **授权码模式**：前端拿到的是 code，换 token 在后端完成，token 不过浏览器，防截获——绝大多数场景用这个；
- **密码模式**（`grant_type=password`）：客户端直接拿用户名密码换 token，方便但危险——客户端一旦有密码就能绕过一切，只在**自家受信的遗留系统过渡**时用，且要限制客户端范围。

## 关键实现

**1. 授权码流程的换 token**（客户端后端）：

```java
// 1. 回调拿到 code，立即用它换 token（code 一次性、几十秒过期）
TokenResponse t = idpClient.exchangeCode(code, redirectUri, codeVerifier);
// 2. 解析 id_token（验签 + 验 aud），取出用户身份
UserInfo user = parseAndVerifyIdToken(t.getIdToken());
// 3. 自己系统里建立会话，下发本系统的登录态 Cookie
session.create(user);
```

`state` 参数必须生成并回校验（防 CSRF），`code_verifier`（PKCE）建议加上，防 code 中间人截获。

**2. Token 生命周期**：

- `access_token`：**短命**（如 15 分钟–2 小时），只用于调接口，不存库只存内存/加密缓存；
- `refresh_token`：**长命 + 可撤销**，存服务端并绑定设备/客户端，用户改密码或管理员踢人时作废；
- 到期前静默刷新，用户无感；刷新失败即视为登出，重走授权流程。

核心原则：**泄露一个短期 token 损失有限，长期凭据必须可撤销**。

**3. 多系统统一登录**：接入方只需三步——跳转认证中心（带 `redirect_uri`）、回调换 token、本地建会话。各系统**不存密码**，只存用户 ID 和从 `id_token` 同步过来的最小信息。新系统接入从「开发登录模块」变成「配置几个回调地址」。

**4. 登出与会话**——最容易被忽略：

- **全局登出**：用户在认证中心登出 → 删除全局会话 → 通过 front-channel（回跳各客户端的 logout 端点）或后台通知，让各业务系统的本地会话一起失效；只删本地 Cookie 的话，其他系统还能用，等于没登；
- **会话分区**：认证中心与各客户端会话独立过期，客户端本地会话建议短于全局会话，到期静默重定向续期；
- **服务端 Token**：涉及写操作的场景，重要操作除 Cookie 外校验 refresh 状态或加二次确认，防止登出后残留 token 继续调用。

## 落地效果（示意）

- 员工只需记一套账号，新系统接入只需配置回调，不再逐系统开通密码；
- 授权码 + 短期 token 上线后，token 泄露的影响窗口从「长期有效」收敛到分钟级；
- 全局登出打通后，禁用一个账号能让所有关联系统在会话/Token 过期后同步失效，离职收口不再靠人工逐个关。

（以上为方案效果示意，非生产统计数据。）

## 小结

单点登录的骨架是：**一个认证中心 + 各系统做客户端**。主流程走授权码模式，密码模式只留给受信遗留系统过渡；token 短命化 + refresh 可撤销控制泄露面；登出必须联动全局会话，否则「统一登录」只是统一了进来、没统一出去。身份统一之后，权限、审计、离职收口才有落点。
