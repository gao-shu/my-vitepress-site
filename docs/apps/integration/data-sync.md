# 系统间数据同步方案

## 背景与问题

多系统并存是常态：ERP 有主数据，CRM 要一份，数据仓库要一份，报表平台还要一份。数据同步做不好，会反复出现这几类问题：

- **两边对不上**：A 系统显示已发货，B 系统还是待发货，客服两边查；
- **同步把库拖死**：每天夜里全量 `SELECT *` 几百万行，业务库 IO 飙高，早高峰变慢；
- **字段语义不一致**：A 的 `status=1` 是启用，B 的 `status=1` 是停用，直接搬就出事故；
- **中途失败留脏数据**：同步到一半断了，B 系统留下半截数据；
- **没人知道丢没丢**：同步任务「成功」结束，但少了几条，一周后才被业务发现。

同步方案选型，本质是在**实时性、侵入性、资源开销**三者之间做取舍。

## 方案设计

先分清两种模式：

| 模式 | 做法 | 适用 |
|------|------|------|
| 全量同步 | 按时间窗或分页拉取全表，覆盖写目标 | 首次初始化、小表、纠错重刷 |
| 增量同步 | 只取上次同步后变化的数据 | 日常运行，绝大多数场景 |

**选型决策**：

- **CDC（变更数据捕获）**：源库开 binlog / 使用 Debezium 等解析变更流。实时性最好、对业务库只读日志不加查询压力，但要维护解析组件和位点。适合核心表、要求近实时的场景；
- **定时增量任务**：按 `update_time > 上次水位` 拉取，加游标分页。实现简单、谁都能维护，但有延迟（取决于调度周期），且依赖表上有可靠的更新时间字段。适合大多数中低频场景；
- **定时全量**：只用于初始化和兜底对账，大表必须分页 + 限速。

一个系统里通常组合使用：主数据用 CDC 近实时，配置类小表定时全量，报表明细走数仓 ETL。

**整体流程**固定为四段：**抽取 → 映射清洗 → 写入 → 对账补偿**。四段都要可观测，任何一段都可能成为丢失点。

## 关键实现

**1. 增量水位与分页**：水位用「时间戳 + 主键」双条件，防止同一秒内多条记录被漏掉：

```sql
SELECT * FROM orders
WHERE (update_time > #{lastTime}
   OR (update_time = #{lastTime} AND id > #{lastId}))
ORDER BY update_time, id
LIMIT 500;
```

同步完成后再把水位写回 checkpoint 表。**先拉数据、后写水位**，失败了大不了重复拉，不能先写水位导致漏数据。

**2. 字段映射与清洗**：中间加一层转换器，不要源表直写目标表——

```java
OrderMsg msg = OrderMsg.builder()
    .id(row.getId())
    .status(STATUS_MAP.get(row.getStatus()))   // 枚举值显式映射，禁止裸搬
    .amount(row.getAmount().movePointRight(2).longValue()) // 单位统一到分
    .build();
```

清洗规则集中在转换层：枚举映射、单位换算、空值默认、非法数据拦截并进异常表。**脏数据隔离，不阻塞主流程，也不污染目标库**。

**3. 写入策略**：目标端用 `INSERT ... ON DUPLICATE KEY UPDATE`（或 upsert）实现幂等——重复同步同一条不会产生重复数据，中途失败重跑即可。大批量分批提交，避免长事务锁表。

**4. 对账与补偿**——同步的最后一道防线：

- **条数对账**：定时比对源/目标在时间窗口内的记录数、按状态分组的条数；
- **抽样比对**：全量比对成本高时，按主键抽样比对关键字段哈希（`MD5(concat(ws, status, amount))`）；
- 发现差异 → 生成**修复任务**：从源端重取该批数据覆盖写入（upsert 让补偿天然幂等）。

对账是唯一能回答「到底丢没丢」的机制，前面所有环节都可能出错，对账负责兜底发现。

**5. 失败处理**：同步任务必须记录每批次的水位、条数、耗时、异常；失败告警但**水位不前进**，下次调度自动重跑，配合限次数防死循环。

## 落地效果（示意）

- 主数据从定时轮询改为 CDC 后，跨系统状态不一致的窗口从「小时级」缩小到「秒级」，客服两头对不上的工单明显减少；
- 夜间全量改为增量 + 分页限速后，业务库不再出现同步时段的 IO 尖刺；
- 对账任务上线后，「静默丢数据」从靠业务发现变成第二天自动出修复单，且修复动作幂等可反复执行。

（以上为方案效果示意，非生产统计数据。）

## 小结

数据同步没有一招通吃：实时核心表上 CDC，一般表走定时增量，全量只做初始化和兜底。工程上的关键是四件事——**水位不前移就重跑、映射层隔离字段差异、目标端 upsert 保幂等、对账补偿兜住一切漏网之鱼**。同步「跑成功」不等于数据「对」，能对账的同步才敢说可靠。
