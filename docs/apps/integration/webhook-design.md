# Webhook 接入与可靠投递

## 背景与问题

Webhook 是「我有事通知你」的反向模式：对方注册一个回调地址，你的系统状态一变就 POST 过去。它比轮询省资源，但把可靠性责任推给了双方，坑比看上去多：

- **丢事件**：回调发出去对方正好重启，HTTP 超时失败，事件就没了；
- **重复事件**：网络抖动触发重试，对方收到两条一样的订单通知，重复发货；
- **乱序**：订单创建、支付、关闭三个事件并发发出，对方先收到「关闭」再收到「创建」，状态错乱；
- **坏接收方拖垮发送方**：某个客户的回调地址挂了，重试队列堆积，影响正常投递；
- **签名校验缺失**：回调接口裸奔，谁都能伪造一条「支付成功」打进来。

Webhook 设计的核心只有一句话：**发送方保证「至少投递一次」，接收方保证「幂等处理」，两边都不能省**。

## 方案设计

发送侧（我的系统对外发回调）：

1. **事件表落库**：业务事务里写业务数据 + 事件记录，先落库再异步投递，进程挂了事件不丢；
2. **投递服务**：从事件表取待发记录，POST 到客户地址，记录每次投递结果；
3. **重试策略**：指数退避（如 10s、1min、10min、1h、6h），超过 N 次进入**死信**；
4. **死信与人工补偿**：死信进告警（钉钉/邮件），支持后台手动重放或导出；
5. **签名**：每次请求带 `X-Signature: HMAC-SHA256(body, secret)`，接收方据此验真。

接收侧（我接别人的回调）：

1. 先验签、再校验时间戳（防重放），最后才进业务；
2. **以事件 ID 做幂等**，处理前查/写去重表；
3. 快速返回 200，重活丢到异步队列，别让对方等到超时重试；
4. **乱序控制**：按业务单据维护版本号或状态机，旧版本事件直接丢弃。

```
业务事务 ──▶ 事件表 ──▶ 投递器 ──HTTP──▶ 客户回调
                        │ 失败
                        ▼
                  重试队列(退避) ──超限──▶ 死信表 ──告警──▶ 人工补偿
```

## 关键实现

**1. 幂等去重**——最简单可靠的做法是唯一键：

```sql
CREATE TABLE webhook_event (
  event_id   VARCHAR(64) PRIMARY KEY,   -- 全局唯一事件 ID
  event_type VARCHAR(32) NOT NULL,
  payload    JSON NOT NULL,
  status     TINYINT DEFAULT 0,         -- 0待发 1成功 2重试中 9死信
  retry_cnt  INT DEFAULT 0,
  next_retry_at DATETIME
);
```

接收方用 `event_id` 做 `INSERT IGNORE` 或 Redis `SETNX`，插不进去说明处理过，直接返回 200。

**2. 投递与退避**：投递器单条处理——查状态为待发/到点重试的事件 → POST（超时设 5s）→ 成功标记成功，失败 `retry_cnt++` 并按下一次退避时间写回 `next_retry_at`。注意**按事件串行**，同一客户的多个事件排序发出，能天然缓解乱序。

**3. 签名校验**：

```java
String expect = Hex(HmacSHA256(rawBody, secret));
if (!MessageDigest.isEqual(expect.getBytes(), headerSig.getBytes())) {
    throw new SignatureException("invalid signature");
}
```

必须用原始 body 校验，不能先反序列化再重新序列化（字段顺序会变）。另外记录 `X-Timestamp`，超过 5 分钟拒绝。

**4. 乱序处理**——两个手段叠加：

- 事件体带 `eventType` + `occurredAt` + 业务单据的 `version`（乐观锁版本）；
- 接收方按状态机校验：`已关闭 → 已支付` 这种逆向流转直接忽略并记日志，不硬写库。

**5. 死信与人工补偿**：死信表配管理页——展示事件内容、失败原因、历史投递记录，支持「立即重放」「修改地址后重放」「标记跳过」。补偿是兜底手段，**重放也必须幂等**，因为接收方可能已经收到过了。

## 落地效果（示意）

- 投递失败后自动退避重试，接收方短暂停机不再导致事件丢失；
- 死信 + 人工重放页面把「客户说没收到通知」的排查从翻日志变成看表点按钮；
- 接收侧以事件 ID 去重后，重复投递对业务零影响；按版本号过滤后，乱序事件不再打乱单据状态。

（以上为方案效果示意，非生产统计数据。）

## 小结

Webhook 的可靠性是分工契约：发送方靠**事件落库 + 指数退避重试 + 死信兜底**做到不丢，接收方靠**验签 + 事件 ID 幂等 + 状态机过滤**做到不重不乱。只做一半，系统上线初期看着没问题，等一次网络抖动或对方一次重启，就会用数据事故把课补上。
