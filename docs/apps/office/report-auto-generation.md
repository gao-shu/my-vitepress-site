# 日报周报自动生成

## 背景与问题

每个团队都有一份"没人爱写但没人敢不写"的日报周报。业务、运营、交付同学每周花半小时拼数据、凑字数，管理层收到的还常常是格式不一、数据对不上的版本。手动汇总的问题其实就三类：

1. **数据源分散**：数字在 ERP/CRM/表格里，结论在聊天记录里，人肉搬运必然有延迟和抄错。
2. **口径不统一**：张三的"完成率"按单量算，李四的按金额算，周会上先吵口径再吵结论。
3. **时效性差**：周报周一才发，参考价值已经打折。

自动生成日报周报的目标不是"替代人写"，而是**把数据和结构化的部分机器做掉，把判断和补充留给人**。完全无人值守的报告没人看，完全手写的报告没价值——平衡点是"机器初稿 + 人工确认"。

## 方案设计

流水线分五段：

```
数据源接入 → 指标计算（统一口径） → 模板渲染 → AI 摘要 → 人工确认 → 定时推送
```

关键决策：

- **口径在指标层定义，不在报表层定义**。每个指标写成一段可复用的查询/计算逻辑（SQL 或代码函数），报表只是引用指标。口径变更改一处，所有报表同步生效。
- **模板与代码分离**。报表结构放模板文件（Jinja2/FreeMarker 皆可），运营改文案不用改代码。
- **AI 只做摘要，不做数据**。数字必须来自指标层，AI 负责把指标结果写成人话（"本周完成率环比上升，主要来自 X 类订单"），并且要求 AI 只能引用给定数据、不得自行发挥数字。
- **人工确认是必经环节**，不是可选项：发送前给责任人 30 分钟到几小时的确认窗口，可改可否决。

## 关键实现

**1. 数据源接入与指标层**

```python
# metrics.py —— 口径集中定义
def order_completion_rate(date_range):
    """完成率口径（唯一定义处）：完成单量 / 总单量，按单量计"""
    df = query_orders(date_range)
    return {
        "total": len(df),
        "done": int((df.status == "DONE").sum()),
        "rate": round((df.status == "DONE").mean(), 4),
    }

METRICS = {
    "order_completion_rate": order_completion_rate,
    "revenue": revenue_metric,
    "ticket_backlog": ticket_backlog_metric,
}
```

数据源接进来先落一张宽表/中间表，报表层永远查中间表，不直接打业务库——周报跑在业务高峰就是事故。

**2. 模板渲染**

```jinja2
{# weekly_report.md.j2 #}
# 运营周报（{{ week_start }} ~ {{ week_end }}）

## 核心指标
| 指标 | 本周 | 上周 | 环比 |
|------|------|------|------|
{% for m in metrics %}
| {{ m.name }} | {{ m.cur }} | {{ m.prev }} | {{ m.delta }} |
{% endfor %}

## AI 摘要
{{ ai_summary }}

## 人工补充
{{ manual_notes | default("（待补充）") }}
```

**3. AI 摘要：限定输入输出**

```python
def gen_summary(metrics: dict) -> str:
    prompt = (
        "根据以下指标数据写 3 条以内的周报摘要，只陈述数据支持的结论，"
        "不得编造数据之外的信息，不写套话：\n"
        + json.dumps(metrics, ensure_ascii=False)
    )
    return llm.chat(prompt, max_tokens=400)
```

再加一道**护栏校验**：摘要里出现的数字必须能在指标数据里找到（简单做法是抽取摘要中的数字串与指标值比对），对不上就打回重写或降级为"仅展示指标表"。

**4. 定时生成与人工确认**

```python
# 调度：周五 17:00 生成初稿，周六 12:00 确认截止，之后自动推送
@cron("0 17 * * 5")
def draft_weekly():
    metrics = collect_metrics(this_week())
    draft = render(metrics, ai_summary=gen_summary(metrics))
    save_draft(draft)
    notify_owner(draft, deadline="Sat 12:00")   # @责任人确认

@cron("0 12 * * 6")
def publish_weekly():
    draft = load_draft()
    if draft.status == "approved" or not draft.owner_response:
        push(draft.final_content, channels=[feishu_group, email])
    # 责任人明确否决则跳过本轮并记录原因
```

确认环节要处理两种状态：**通过**（直接发）和**超时未处理**——超时策略团队自己定（默认发或默认不发都行，但要写死并告知所有人，别每次临时讨论）。

**5. 推送**

复用通知网关：群消息发卡片摘要 + 文档链接，邮件发全文；长报告落在线文档（飞书文档/语雀），推送里只放结论和链接，别把两千字塞进群消息。

## 落地效果

- 报告从"人肉搬运 + 格式对齐"变成"指标自动生成 + AI 成稿"，责任人只需审校和补几句判断，准备时间从原来的小时级压缩到分钟级审校。
- 口径集中到指标层后，周会上"数字对不上"的争论明显减少——所有报表引用同一份定义。
- 人工确认环节拦住过数据异常的初稿（如上游接口抖动导致的异常值），避免了错误结论直达管理层。

具体节省时长与报告量级因团队而异，建议上线前先并行跑两轮（人写 + 机器生成）做对照。

## 小结

日报周报自动化的正确姿势是**"数据机器做、判断人来做"**：指标层统一口径，模板分离结构与文案，AI 只在给定数据内写摘要并加校验护栏，最后保留人工确认这道闸。省下来的是搬运和排版的时间，留下的仍然是人对业务的判断——这既是技术方案，也是这套东西能被团队真正用下去的原因。
