# 物联网数据平台搭建

采集打通之后，数据会涌过来：几千台设备、每台几十个点、秒级上报。直接怼 MySQL 会崩，直接上「大平台全家桶」又容易过度设计。这篇讲一个务实的物联网数据平台怎么搭——设备怎么接、数据存哪、怎么转发、下游 MES/BI 怎么消费。

## 背景与问题

- 接入层混乱：每个采集程序各自直连数据库，设备一多连接数爆炸，谁改了协议没人知道。
- 存储选型纠结：关系库存时序数据，写得慢、查得慢、删得痛苦；时序库又是新东西，团队没人会运维。
- 数据流向写死：采集程序里写死「同时写库 + 发 MQTT + 调接口」，下游加一个消费方就要改采集代码。
- 消费方各要各的：MES 要实时事件（设备状态变了立刻响应），BI 要聚合报表（班次/日电量），看板要秒级曲线——一个接口伺候不了所有人。
- 设备管理缺位：设备上下线、固件版本、点表版本没有台账，出问题不知道现场跑的是哪套配置。

## 方案设计

### 设备接入层

```
采集适配（Modbus/S7/MQTT…） → 接入网关（鉴权/会话/限流） → 消息总线（MQTT/Kafka）
                                                                    ↓
                                             规则引擎（过滤/计算/路由） → 各下游
```

- 接入网关统一入口：设备用 `deviceId + token` 鉴权，一条连接一个会话，上报频率限流；网关只做接入和转发，不写业务逻辑。
- 消息总线解耦：上报数据一律进消息队列（局域网小规模 MQTT Broker，规模大或要回放上 Kafka），**采集端只管发，谁消费谁订阅**。
- 设备影子/注册表：设备元数据（型号、点表版本、负责人）存关系库，最新状态存影子（内存 + 持久化），支持「期望状态」下发与离线补同步。

### 时序 / 关系存储选型

| 数据 | 存储 | 理由 |
|------|------|------|
| 原始采样点 | 时序库（InfluxDB/TDengine/QuestDB） | 高频写、按时间范围查、自动过期 |
| 设备/点表/用户/告警规则 | 关系库（MySQL/PG） | 事务与关联查询 |
| 聚合结果（班次/日/月） | 关系库或 OLAP | 供 BI 直接查，不扫原始点 |
| 原始点保留 | 7~30 天滚动 | 过期自动删，聚合长期留 |

务实选择：**数据量小（万级点、秒级）可以先 PG + 分区表 + 自动归档**，别为了「先进」上全家桶；点位上十万、要秒级曲线和回放，再上时序库。原则是「原始点可丢、聚合结果不可丢」，聚合任务必须幂等可重算。

### 规则转发

- 规则引擎消费消息总线，支持四类动作：**过滤**（丢弃质量位为 bad 的点）、**计算**（阈值判断、瞬时转累计、滑动均值）、**路由**（按设备/指标分主题）、**动作**（写时序库、发告警、调 Webhook、转发 MQTT）。
- 规则配置化存库，热更新，不把「超 80 度发微信」写死在采集代码里。
- 转发带重试与死信：下游接口挂了进重试队列，连续失败进死信主题人工排查，绝不阻塞主链路。

### 与 MES / BI 的数据消费

- **实时事件**（状态变化、告警、阈值越限）：走消息主题 + Webhook/MQTT 推给 MES，MES 据此触发报工、停机记录。
- **查询接口**（当前值、最近 N 条曲线）：平台出统一查询 API，按设备 + 时间范围返回，看板和 MES 共用。
- **BI 分析**：BI 不查原始点，读聚合表（班次产量、能耗日报、设备 OEE 中间表）；聚合任务按班次边界触发，幂等可重算。
- 口径约定：**平台是时序数据的唯一出口**，MES/BI 不直连时序库，避免各查各的算出三个数。

## 关键实现

规则转发配置（示意）：

```json
{
  "name": "温度越限告警",
  "match": { "deviceType": "oven", "point": "temp" },
  "filter": "quality == 'good'",
  "actions": [
    { "type": "tsdb", "measurement": "oven_temp" },
    { "type": "condition", "expr": "value > 80 for 30s" },
    { "type": "webhook", "url": "http://mes/api/alarms", "retry": 5 }
  ]
}
```

要点：

- 聚合任务按 `设备 + 班次 + 日期` 做幂等键，重跑当天聚合不产生重复行。
- 接入网关与消息总线分离：网关挂了 broker 里还有缓冲，网关可多实例水平扩。
- 查询 API 带降级：热数据走时序库，冷数据走聚合表，超时降级返回聚合曲线，看板不白屏。
- 设备上下线以保留消息（LWT）广播，注册表状态与影子同步更新，台账永远知道谁在线。
- 全链路带 `deviceId + 时间戳` 追踪，一条数据从设备到 BI 卡在哪一跳可查。

## 落地效果（示意）

以下为模式效果示意，非生产数据：

- 接入层收敛到网关 + 消息总线后，采集端不再直连库，新增一种协议只加适配器不动下游。
- 原始点设定期限自动过期、聚合长期保留，库体积稳定，不再出现「越跑越慢」。
- 规则配置化后，「加一个告警转发」从改代码发版变成改一条规则热更新。
- MES 走事件、BI 走聚合、看板走查询 API，三方取数口径一致，对数会议减少。

## 小结

物联网平台的骨架是三层：**接入层统一鉴权与会话、消息总线解耦生产与消费、规则引擎负责过滤计算与转发**。存储按「原始点可丢、聚合不可丢」分工，时序库与关系库各司其职；消费侧按场景分发——MES 要事件、看板要曲线、BI 要聚合，并守住「平台是时序数据唯一出口」这条口径红线。规模没到之前，宁可用 PG 分区表起步，也别先搬全家桶。
