# Modbus/S7 等协议对接实践

车间里真正耗时间的不是写业务代码，是把那些七七八八的设备对上来：这台是 Modbus RTU、那台是 S7、还有个仪表只会 ASCII 自定义帧。协议对接的活儿 80% 在点表和调试上。这篇把常见协议的选型、点表配置、网关与脚本对接、调试排障串起来，少踩现场的坑。

## 背景与问题

- 协议一堆，选型靠猜：Modbus、S7、MC、FINS、OPC UA、MQTT，名字都听过，真到现场不知道哪条能通。
- 点表是黑洞：寄存器地址 40001 到底是 0 还是 1 起始、保持寄存器还是输入寄存器、字节序是大端还是小端——读出来数值对不上，能查一整天。
- 对接方式摇摆：用现成网关（KA、ThingsBoard、开源采集器）还是自己写脚本，边界在哪没想清，最后两头都半吊子。
- 调试没趁手工具：现场只能 printf 看日志，报文看不懂、不知道是没发出去还是设备没回。
- 常见异常反复踩：超时、垃圾帧、从站忙、半包粘包，每个都要现场现写处理。

## 方案设计

### 常见工业协议对比

| 协议 | 链路 | 特点 | 典型场景 |
|------|------|------|----------|
| Modbus RTU | RS485 串口 | 简单、一主多从、无会话 | 仪表、变频器、能源表 |
| Modbus TCP | 以太网 | RTU 报文套 TCP，端口 502 | PLC、网关、新仪表 |
| S7 | 以太网 102 | 西门子私有，读写 DB 区高效 | 西门子 S7-200/300/1200/1500 |
| MC/FINS | 以太网 | 三菱/欧姆龙各自私有 | 日系 PLC |
| OPC UA | 以太网 | 标准化、带建模与安全 | 新产线、系统间集成 |
| MQTT | 以太网 | 轻量发布订阅、走 IP | 采集器上云/上平台 |

选型顺序：**先看设备支持什么**（设备是甲方），再看现场链路（有没有网口），最后才谈偏好。老仪表一律 Modbus，西门子网口选 S7，能上 OPC UA 的新设备优先 OPC UA。

### 点表配置

点表是对接的唯一事实来源，做成配置而不是硬编码：

```
device, point, proto, addr, type, scale, unit, rw
pump01, temp,   modbus-tcp, 40001, float32, 0.1, ℃, r
pump01, run,    modbus-tcp, 00005, bool,   1,   -, r
line01, speed,  s7, DB12.DBD4, real, 1, rpm, rw
```

- 地址写**绝对地址 + 协议方言**：Modbus 明确 4x/3x 区与 0/1 基址；S7 明确 DB 号与偏移（注意优化访问 DB 要关闭）。
- 数据类型与字节序显式声明：`float32` 要带端序（ABCD/CDAB…），先用已知值校准一遍再上线。
- 缩放（scale）在采集侧统一处理，业务侧只拿工程值。
- 点表支持导入导出（Excel/CSV），现场改点不用改代码。

### 网关 / 脚本对接

- **网关路线**（现成采集软件/协议网关）：设备种类多、点位多、不想养代码时用，配置即可出数；代价是灵活性差，特殊帧、私有协议支持不了。
- **自研脚本路线**（Python/Java + 库）：私有协议、特殊逻辑（按配方切点表、条件写入）、要和业务深度联动时用；代价是断线重连、缓冲、部署运维都得自己做。
- 务实边界：**标准协议走网关快速出数，私有/异构需求走自研脚本**，两条路输出统一成同一格式（点位 + 时间戳 + 值）进上层，别搞两套数据模型。

### 调试工具与常见异常

- 工具箱必备：Modbus Poll / Modbus Slave（主从互测）、Wireshark（抓 TCP 看报文）、串口助手（看原始字节）、`nc`/`telnet` 试端口通不通。
- 万能排查顺序：**物理链路 → 端口/从站地址 → 报文格式 → 字节序 → 缩放**，五步走完九成问题定位。
- 常见异常对照：

| 现象 | 多半原因 |
|------|----------|
| 超时无响应 | 从站地址错、波特率/接线错、端口不通 |
| 回 `Exception Code 02/03` | 地址越界、功能码不支持（读错了区） |
| 数值大得离谱或负数 | 字节序/字序错、缩放没乘 |
| 读到值但像「上一拍」 | 主从缓冲未刷新、读的是保持区镜像 |
| 间歇性超时 | 总线干扰、终端电阻缺失、轮询过快 |
| 半包/粘包（TCP 自定义帧） | 按帧头帧尾重组，不能按固定长度读 |

## 关键实现

统一适配层，业务只认 `read/write`，协议差异收敛在适配器里：

```java
public interface DeviceAdapter {
    Map<String, Object> read(List<Point> points) throws CommException;
    void write(Point point, Object value) throws CommException;
}

// Modbus 适配器要点：连续地址合并读，减少往返
public class ModbusTcpAdapter implements DeviceAdapter {
    public Map<String, Object> read(List<Point> points) {
        List<Point> sorted = mergeContiguous(points);      // 合并连续寄存器
        byte[] raw = client.readHolding(sorted.first(), sorted.count());
        return decode(raw, points);                        // 端序 + 缩放在这里
    }
}
```

- 解码统一走一个 `decode(raw, points)`：按点表声明的类型和端序解析，再乘缩放——**字节序问题只允许在这一处排查**。
- 写操作带回读校验：写完隔一拍读回，值不一致记 Warn，防止「以为写成功了」。
- 调试开关：可临时打开原始报文 hex 日志，按设备维度过滤，现场排障不用改代码重发版。
- 异常分类处理：超时退避重连、Exception Code 记入点表质量位（`bad`），不让一个坏点污染整帧。

## 落地效果（示意）

以下为模式效果示意，非生产数据：

- 点表配置化后，现场加点改地址变成改一行配置，不用改代码重新部署。
- 统一适配层把 Modbus/S7 差异挡在业务层之外，上层采集循环只有一份。
- 排障顺序固化后，「数值不对」类问题从翻代码变成对点表五步走，定位时间明显缩短。
- 标准协议走网关、私有协议走脚本的分工，让首批设备快速出数，长尾私有设备也能接。

## 小结

协议对接的核心是三件事：**选型看设备不看偏好、点表是唯一事实来源（配置化 + 显式端序缩放）、调试按「链路 → 地址 → 报文 → 字节序 → 缩放」五步走**。网关与自研脚本不是二选一，是按协议标准化程度分工。把字节序和地址这类经典坑收敛到一个解码函数里，现场排障才能从考古变成查表。
