# PLC 数据采集方案

设备数据要进系统，第一步是把 PLC 里的点位读出来。这活儿看着简单——不就是读寄存器吗——真正做下去，坑都在链路和节奏上：网口串口怎么选、协议怎么定、读多快、断线了数据丢不丢、写库扛不扛得住。这篇把一条采集链路从选型到落库过一遍。

## 背景与问题

- 现场 PLC 品牌杂：西门子 S7、三菱、欧姆龙、 Modbus 从站的仪表和变频器混在一个车间，一个采集程序要伺候多种协议。
- 网口与串口并存：新设备带网口，老设备只有 RS485，还有一批 PLC 程序被人加密或不给改，只能外部读。
- 采集频率没有账：有人 100ms 全量轮询 500 个点，PLC 扫描周期被拖慢，设备报警；有人 5 秒读一次，曲线全是锯齿没法看。
- 断线即丢数：交换机重启、设备断电、串口被拔，重连之后中间那段数据没了，产量和曲线对不上。
- 写库压垮业务库：采集高频写 MySQL 明细表，一周把业务库磁盘和索引干废，白天业务系统跟着卡。

## 方案设计

### 网口 / 串口采集

| 链路 | 适用 | 注意 |
|------|------|------|
| 以太网（TCP） | S7、三菱 MC、大部分新 PLC | 端口固定（如 S7 的 102），一台采集机可带多台设备 |
| RS485 串口 | Modbus RTU 仪表、变频器、老设备 | 一主多从，注意从站地址冲突、波特率一致性 |
| USB 转串口 | 调试与小规模接入 | 现场不推荐长期跑，接触不良 |

原则：**能走网不走串**；串口链路上从站不超过 16 个、总线长度和终端电阻按规范来；采集程序里网口和串口抽象成同一个 `Channel` 接口，业务层不感知链路差异。

### 协议选型

- 西门子 PLC（S7-1200/1500）：S7 协议走网口，`libnodave` / `S7.Net` 成熟，不用在 PLC 侧写通信块也能读（注意 DB 块「优化访问」要关闭或按符号寻址）。
- Modbus（RTU/TCP）：事实标准，仪表、能源表、第三方设备首选；TCP 版直接对 502 端口，RTU 走串口。
- 三菱/欧姆龙：MC 协议、FINS，各用对应库。
- 不确定就先做协议网关：采集程序只对内输出统一格式，协议差异收敛在适配层。

### 采集频率与断线重连

- 分级采集：状态位/报警位 200ms~1s，工艺参数 1s~5s，产量/累计量 5s~30s。**不是所有点都要快**。
- 轮询而非订阅：多数 PLC 不支持主动上报，按点表分组轮询，一组读失败跳下一组，别让一个坏点卡死整轮。
- 断线重连：指数退避（1s → 2s → 4s → … → 上限 30s），重连成功后立即做一次全量读（拿到当前真值），链路状态以事件形式抛给上层置状态灯。

### 边缘缓冲与写业务库

```
PLC → 采集适配层（协议） → 内存环形缓冲 → 落地缓冲（本地文件/SQLite） → 批量写入存储
```

- 断网/写库失败时数据先进本地缓冲，恢复后按时间序补传，补传带幂等键防止重复入库。
- 写库必须**批量 + 异步**：攒 1~5 秒或 500 条一批插入，绝不用单条 insert 硬怼。
- 明细高频数据进时序库或分区表，业务库只存聚合结果（班次产量、当前状态）。

## 关键实现

采集主循环（轮询 + 断线退避，示意）：

```java
while (!stopped) {
    try {
        if (!channel.isConnected()) {
            channel.connect();               // 内含指数退避
            buffer.markReconnect();          // 标记断点，用于补传与缺数标注
        }
        for (PointGroup g : pointTable.groups()) {
            Map<String, Object> vals = channel.read(g);   // 一组读失败跳过
            buffer.offer(vals, System.currentTimeMillis());
        }
    } catch (CommException e) {
        channel.disconnect();
        backoff.await();                     // 1s 起，上限 30s
    }
}
```

要点：

- 点表按「设备 + 区域 + 数据类型」分组，一组一次多点连续读（Modbus 连续读保持寄存器，S7 批量读 DB），**减少往返次数比提高频率更重要**。
- 缓冲消费端批量落库，写失败不抛回采集线程，只记重试计数——采集和落库解耦，落库慢不能拖垮采集节奏。
- 断线期间的数据缺口在时序数据里显式打 `gap` 标记，别用插值假装有数，复盘时会误导人。
- 原始报文可开关记录，现场出现「点位值不对」时能回放对帧。

## 落地效果（示意）

以下为模式效果示意，非生产数据：

- 分级采集后，全量点位数不变的情况下，PLC 侧通信负载明显下降，设备侧不再报通信慢。
- 断网半小时，本地缓冲补传完整，曲线只在断点处有标记，产量统计没有缺漏。
- 批量写库把单条插入的高频写变成低频大批量，业务库磁盘和慢查询恢复平稳。
- 点表分组轮询后，单个故障从站不再拖死整条链路，其余设备数据照常。

## 小结

PLC 采集的四条硬约束：**协议按品牌选型并收敛到统一适配层、频率按点位分级而不是一刀切、断线退避重连加本地缓冲补传、落库批量异步与采集解耦**。做采集最忌讳「只考虑正常链路」，现场的常态就是断线、干扰、从站失联——把断线当正常路径写，系统才跑得久。
