# MES 核心问题清单

> **一句话定位**：MES 把 ERP 的"计划"变成车间的"动作"，再用数据证明这个动作**做对了没有**。
>
> **本文用途**：工单、报工、追溯、防错、OEE 五条主线上的核心问题与解法。配套：[ERP](/scenarios/enterprise-digital/erp) · [WMS](/scenarios/enterprise-digital/wms) · [IIoT](/scenarios/enterprise-digital/iiot)。

## 一、MES 在管什么

一句话：**管工单在人机料法环上的执行过程**。

```text
ERP 工单下达
   │
   ▼
MES：工艺路线 → 工序派工 → 领料上线 → 报工（投入/产出/报废）
                                          │
                                          ├─► 质检（首检/巡检/终检）
                                          ├─► 设备状态与参数采集（IIoT）
                                          └─► 完工入库 → 回写 ERP
```

和 ERP 的边界，面试一定要讲清：

| 事项 | ERP | MES |
|---|---|---|
| 生产什么、要多少 | ✅ 决定 | 接收 |
| 怎么做（工序顺序、参数） | 存工艺路线主数据 | ✅ 执行与校验 |
| 做了多少、谁做的 | 接收结果 | ✅ 采集 |
| 物料消耗 | 接收成本 | ✅ 实际领用与倒冲 |
| 库存账 | ✅ 账面 | 报工触发入库申请 |

## 二、核心问题清单

| # | 核心问题 | 为什么难 | 典型后果 |
|---|---|---|---|
| 1 | **工单状态机失控** | 状态多、跃迁非法、返工回流 | 已关闭的工单还能报工 |
| 2 | **报工与倒冲不准** | 投入产出不平、损耗率、超报 | 库存虚高、成本失真 |
| 3 | **在制品（WIP）对不上** | 工序间转移批量、跳序、返工 | 车间堆满料，系统说没有 |
| 4 | **质量追溯断链** | 关键工序漏扫码、批次关系缺失 | 召回时查不到源头 |
| 5 | **防错防呆缺失** | 上料校验、工序跳过拦截 | 装错料，批量报废 |
| 6 | **OEE 算不准** | 停机原因归类、节拍标准、状态判定 | 数据好看但没人信 |
| 7 | **排产靠 Excel** | 有限产能、换型时间、优先级 | 计划天天改，交期天天延 |
| 8 | **计件工资争议** | 合格/不合格、返工是否计件 | 工人觉得算错，闹 |
| 9 | **工艺参数管控** | 参数下发、超差报警、版本 | 参数被改无人知 |
| 10 | **现场抵触** | 增加操作步骤、PDA 难用 | 系统上线，数据靠补录 |

## 三、五个深水区逐个拆

### 1. 工单状态机：所有 MES 的地基

**状态定义**（最小可用集合）：

```text
CREATED（已创建）
  → RELEASED（已下达）        ERP 下达或计划员释放
  → IN_PROGRESS（生产中）      首道工序开工
  → PAUSED（暂停）             缺料/设备故障/换线
  → IN_PROGRESS（恢复）
  → COMPLETED（已完工）        末道工序报工完成
  → CLOSED（已关闭）           财务结算 / 归档
  ↘ CANCELLED（已取消）        下达后未生产可取消
```

**合法跃迁表**（这才是代码要落的东西）：

| 当前状态 | 事件 | 目标状态 | 守卫条件 |
|---|---|---|---|
| CREATED | release | RELEASED | 工艺路线已审核、物料已齐套 |
| RELEASED | start | IN_PROGRESS | 首工序已派工、已领料 |
| IN_PROGRESS | pause | PAUSED | 记录暂停原因 |
| PAUSED | resume | IN_PROGRESS | — |
| IN_PROGRESS | complete | COMPLETED | 所有工序已报工且数量校验通过 |
| COMPLETED | close | CLOSED | 已入库、成本已归集 |
| COMPLETED / CLOSED | reopen | IN_PROGRESS | 需审批，记录原因（返工返修） |
| CREATED / RELEASED | cancel | CANCELLED | 无报工记录 |

**实现方式**：枚举 + 转移表（`Map<State, Map<Event, Transition>>`），不要写成一堆 `if (status == X && action == Y)`。每次跃迁写 `workorder_status_log`（from / to / event / operator / time / reason）。

**返工怎么办**：不要新开状态，用**返工工单**关联原工单（`rework_of` 字段），原工单回到 `IN_PROGRESS`，返工工序走独立工序序列。

> **面试口径**：状态机的关键不是状态有几个，是"谁能推进状态、推进前要满足什么条件"。我一般用状态转移表驱动，非法跃迁统一在入口拦截抛异常，并且每次跃迁留日志——这样出问题能还原"谁在什么时候把单子推到了这个状态"。返工绝对不能靠改数量糊过去，要开返工单留痕。

### 2. 报工与倒冲：库存虚高的第一元凶

**报工要记三个数**：

```text
投入数量（input_qty）  ← 实际领用
产出数量（output_qty） ← 合格品
报废数量（scrap_qty）  ← 不良品
约束：input_qty ≈ output_qty + scrap_qty + 在制
```

**并发超报怎么防**：两个班组长同时报同一张工单，加起来超过计划量。

```sql
UPDATE mes_workorder
SET reported_qty = reported_qty + #{n}, version = version + 1
WHERE id = #{id} AND reported_qty + #{n} <= plan_qty;
-- affected = 0 → 超报，拒绝（或走高版本审批）
```

**倒冲（Backflush）**：不做出库单，报工时按 BOM 标准用量自动扣料。

```text
应扣量 = 报工合格数 × BOM 单位用量 × (1 + 损耗率)
```

三个坑：

1. **损耗率不准** → 长期跑下来账面库存虚高或为负。要定期用实际盘点校正损耗率。
2. **倒冲时库存不足** → 不能直接报错卡住产线，也不能扣成负数。做法是"先记账后补料"：允许生成欠料记录，同时告警，月末盘点平账。
3. **替代料** → 倒冲要用实际投料记录，不能用 BOM 默认料。

> **面试口径**：倒冲本质是"用标准用量替代实际称重"，省了操作但牺牲了精度。所以它只适合包装料、辅料这种价值低用量稳的物料；主料、贵重料必须实际扫码投料。这个边界划错了，库存和成本一定崩。

### 3. 在制品 WIP：车间里最玄学的数字

**问题**：系统里在制 500 件，车间实际堆着 800 件，差在哪？

**根因通常是三种**：

| 根因 | 表现 | 解法 |
|---|---|---|
| 工序间转移没记录 | 上工序报完工，下工序没报接收 | 强制"交接确认"，转移即记录 |
| 跳序生产 | 后道工序先干，前道没报 | 前置工序未完成则拦截（可配置放行） |
| 报废没登记 | 坏了直接扔，只在完工时少报 | 报废必须单独登记，不能靠差额 |

**校验公式**（每天跑一遍）：

```text
期初在制 + 本期投入 − 本期产出 − 本期报废 = 期末在制
不平衡 → 生成异常任务，落到具体工序
```

> **面试口径**：WIP 对不上，99% 不是算法问题，是现场有动作但系统没记录。技术上能做的是"让漏记录变成走不通"——不做交接确认就无法开始下道工序。这属于用流程倒逼数据质量，比事后对账有效得多。

### 4. 质量追溯：从"能查"到"查得全"

**追溯模型**：记录**消耗关系**，不是最终归属。

```sql
mes_trace_relation(
  parent_type, parent_no,    -- 产出：成品批次 / 序列号
  child_type,  child_no,     -- 投入：原料批次 / 半成品批次
  qty,                       -- 消耗数量
  workorder_no, process_no,  -- 哪张工单、哪道工序
  operator, equipment_no,    -- 谁做的、哪台设备（4M1E）
  create_time
)
```

**两个方向的查询**：

| 方向 | SQL 思路 | 场景 |
|---|---|---|
| 反查（成品→原料） | `WHERE parent_no = ?` 递归向上 | 客户投诉，找根因 |
| 正查（原料→成品） | `WHERE child_no = ?` 递归向下 | 供应商来料问题，圈定召回范围 |

**必须强制的扫码点**（少一个链路就断）：

1. 投料（原料批次 ↔ 工单）
2. 关键件装配（序列号 ↔ 半成品）
3. 包装（成品批次 ↔ 内包序列号）
4. 完工入库（成品批次 ↔ 库位）

**性能**：追溯表会是全厂最大的表之一。按月分区 + `(parent_no, create_time)` / `(child_no, create_time)` 双向索引；递归查询限制深度和节点数（防止爆炸式展开）。

> **面试口径**：追溯能不能做成，不看技术看现场——关键工序必须强制扫码，否则数据链一断，追溯就是摆设。技术上我一般做"关系表 + 双向索引 + 递归查询上限"，并且把追溯链可视化，让人能一眼看出哪一步缺数据。

### 5. OEE：为什么车间的 OEE 数据没人信

**公式**：

```text
OEE = 可用率 × 性能 × 良率

可用率 = 实际运行时间 / 计划生产时间
性能   = (理论节拍 × 实际产量) / 实际运行时间
良率   = 合格品数 / 总产出
```

**三个数字都容易造假**：

| 指标 | 造假方式 | 后果 |
|---|---|---|
| 可用率 | 停机不登记原因，算成"计划停机" | OEE 虚高 |
| 性能 | 理论节拍定得松 | 性能永远 95%+ |
| 良率 | 返工品算合格 | 掩盖质量问题 |

**判定设备状态的可靠做法**：不靠人填，靠 **IIoT 采信号**——运行/待机/故障/停机四态用 PLC 的运行信号 + 电流阈值 + 报警码判定，人工只补"停机原因"（因为原因无法自动获取）。

> **面试口径**：OEE 的价值不在于那个百分比，在于三个乘数能定位问题——可用率低是设备维护问题，性能低是节拍/换型问题，良率低是工艺质量问题。所以做 OEE 一定要能下钻到"哪台设备、哪个班次、哪段时间、什么原因"。数据靠人填的 OEE 不可信，状态必须来自设备信号。

## 四、面试高频追问

**Q1：MES 和 ERP 的工单谁管？**
A：ERP 管"要生产什么"（需求与计划），MES 管"实际怎么生产"（工序级执行）。一张工单在 ERP 是"数量 + 交期"，在 MES 拆成"多道工序 + 多个报工记录"。关联用同一个 `workorder_no`，MES 完工后把实际数量、实际工时、实际用料回写 ERP。

**Q2：报工为什么要幂等？**
A：PDA 网络抖动、用户重复点击、消息重投都会导致重复报工，库存和产量翻倍。做法是客户端生成 `request_id` 唯一索引，服务端重复请求直接返回上次结果；数量类更新用条件更新防超报。

**Q3：工序可以跳着做吗？**
A：业务上不该跳，但现场一定有例外（急单、试制）。做法是"默认拦截 + 白名单放行 + 留痕"，不要为了合规把产线卡死，也不要为了灵活全部放开。

**Q4：追溯要查 3 年前的批次，怎么保证性能？**
A：历史数据归档到独立的追溯库（可以放宽查询性能要求），主库只留近 12 个月；按时间分区 + 覆盖索引；查询限制展开深度；对外提供异步导出，不要求秒级。

**Q5：多工厂多车间怎么建模？**
A：`factory → workshop → line → work_center → equipment` 五级树，工单绑定到 `work_center`；权限按树节点授权；报表按层级汇总。不要把车间写死成枚举。

**Q6：MES 上线后工人不愿用怎么办？**
A：三个原则——① 减少输入，能扫码就不手输，能默认就不选；② 系统先给好处（计件工资实时可查、报工不用手写单）；③ 关键节点强制，非关键节点宽松。硬推 100% 全流程采集的项目基本都失败。

**Q7：工艺路线和 BOM 的关系？**
A：BOM 说"用什么料、用多少"，工艺路线说"按什么顺序做、在哪个工位做、用什么参数"。两者独立建模，在工单下达时一起快照，避免主数据变更污染在制工单。

## 五、30 秒速答卡

> MES 的价值是把 ERP 的计划落到工序级，并且留下可追溯的证据。技术上四件事最关键：工单状态机用转移表驱动、非法跃迁在入口拦截、每次跃迁留日志；报工要幂等并且用条件更新防超报，倒冲只适合低值辅料，主料必须实际扫码；追溯靠"消耗关系表"记录 4M1E，关键是关键工序强制扫码，否则链路会断；OEE 的设备状态必须来自 IIoT 信号而不是人工填报，人工只补停机原因。
