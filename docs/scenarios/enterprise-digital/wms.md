# WMS 核心问题清单

> **一句话定位**：WMS 只回答三个问题——**东西在哪、有多少、怎么最快拿出去**。所有模块都是为这三件事服务的。
>
> **本文用途**：把 WMS 最容易做错、也最容易被面试追问的 10 个点列清楚。配套：[ERP](/scenarios/enterprise-digital/erp) · [MES](/scenarios/enterprise-digital/mes) · [IIoT](/scenarios/enterprise-digital/iiot)。

## 一、WMS 在管什么

传统进销存只管"这个物料有多少"，WMS 多管了两个维度：**位置**和**状态**。

```text
数量 × 位置 × 批次 × 状态 = 真实库存
```

主链路：

```text
ASN 预约 → 收货 → 质检 → 上架 ─┐
                                ├─► 库内作业：移库 / 盘点 / 补货
订单池 → 波次 → 拣货 → 复核 → 装车发运 ←┘
```

## 二、核心问题清单

| # | 核心问题 | 为什么难 | 典型后果 |
|---|---|---|---|
| 1 | **库存准确性** | 四维库存 + 并发扣减 + 账实对账 | 明明有货拣不出，客户投诉 |
| 2 | **库位体系建设** | 编码规则、容量、混放策略、ABC 分区 | 乱放、爆仓、找货靠人脑 |
| 3 | **波次与拣货路径** | 订单池策略 + 路径优化 + 分播方式 | 拣货员一天走 20 公里，效率腰斩 |
| 4 | **批次效期管理** | FEFO、临期预警、正反追溯 | 过期品发出去，召回找不到源头 |
| 5 | **多单位与拆零** | 基本/采购/销售单位 + 箱规 + 尾箱 | 1 箱 24 个，拣 30 个怎么算 |
| 6 | **盘点期间业务冲突** | 盘点要冻结，出库不能停 | 盘着盘着又出库，差异算谁的 |
| 7 | **RF/PDA 弱网** | 仓库 WiFi 死角、离线作业 | 扫了半天没提交，重复作业 |
| 8 | **WMS 与 ERP 库存归属** | 双份库存、同步延迟 | 两边数据打架，谁都不认 |
| 9 | **越库与预约** | 月台时段、直发不入库 | 到货排队，月台堵死 |
| 10 | **作业绩效** | 计件、工时、KPI 口径 | 干多干少一个样，激励失效 |

## 三、五个深水区逐个拆

### 1. 库存准确性：四维库存怎么建模

**库存不是一个数字**，是一个坐标点。最小粒度表：

```sql
-- 库存主表：一个"库存单元"= SKU + 库位 + 批次 + 状态 + 货主
wms_stock(
  id, sku_id, location_id, batch_no, stock_status, owner_id,
  qty_total,       -- 总量
  qty_allocated,   -- 已分配（订单占用）
  qty_locked,      -- 已锁定（作业中，如拣货中）
  qty_frozen,      -- 冻结（质检中、待判）
  qty_available,   -- 可用 = total - allocated - locked - frozen
  version          -- 乐观锁
)
```

三个必须守住的规则：

1. **可用量是算出来的，不是改出来的**。任何作业只改 total / allocated / locked / frozen，available 永远由公式派生，避免"四个数各自被改、互相不匹配"。
2. **每次变动都写流水**，`wms_stock_flow` 只 append，字段包含前后值、单据号、操作人。对账靠流水回放。
3. **扣减用条件更新**，靠影响行数判断成败：

```sql
UPDATE wms_stock
SET qty_allocated = qty_allocated + #{n}, version = version + 1
WHERE id = #{id} AND qty_available >= #{n};
-- affected rows = 0 → 库存不足，抛业务异常，不要重试到成功
```

> **面试口径**：库存准确性靠"模型正确 + 流水可回放 + 对账兜底"三件套。技术上最容易犯的错是把可用量当字段去更新，最后四个数量互相矛盾。另外扣减一定要用 `WHERE available >= n` 这种条件更新，靠影响行数判断，不能先 select 再 update——那是超卖的根源，详见[库存并发扣减](/scenarios/inventory-deduction)。

### 2. 库位体系：编码一乱，全盘皆输

**库位编码建议分段语义化**：

```text
A-01-03-02
│  │  │  └─ 层（2 层）
│  │  └──── 列（3 列）
│  └─────── 排（1 排）
└────────── 库区（A 区 = 常温整箱区）
```

**上架策略按优先级依次判断**：

| 优先级 | 策略 | 适用 |
|---|---|---|
| 1 | 指定库位 | 客户指定、危化品专库 |
| 2 | 同批次合并 | 已有该 SKU 同批次，优先合并减少碎片 |
| 3 | ABC 分区匹配 | A 类高频品放近端拣货位 |
| 4 | 容量与承重校验 | 体积/重量不超限 |
| 5 | 空库位按路径最近 | 兜底 |

**核心矛盾**：**存储效率 vs 拣货效率**。整箱存储要紧密堆放省空间，拣货要留通道、要靠近出货口。解决办法是**分区**——存储区（高密度）+ 拣货区（低容量高频补货），两区之间做补货任务。这个"前后仓"模型是 WMS 的经典结构。

> **面试口径**：库位分配不是找个空位放进去，是在"空间利用率"和"行走距离"之间做权衡。工程上的标准做法是分区加分策略评分，策略要可配置——因为不同仓库的最优解完全不同，硬编码的策略上线就得改代码。

### 3. 波次与拣货：效率差距全在这里

**波次（Wave）的作用**：把 N 张小订单合成一次拣货任务，减少重复跑动。

**波次策略维度**：

- 承运商 / 时效（今日达 vs 普通）
- 订单区域（同一片区一起拣）
- 商品重合度（同一 SKU 的多张单合并）
- 体积重量（不超过一个拣货车）

**两种分播方式，取舍很关键**：

| 方式 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| 先拣后分（播种式） | 一次拣出总量，再到分播墙按订单分 | 行走距离最短 | 需要分播区，易错单 |
| 边拣边分（摘果式） | 推着车按订单逐个拣 | 不易错、无需分播 | 行走距离长 |

**路径优化**：仓库巷道本质是网格图，标准解法是 S 形（蛇形）穿越，比"按库位号顺序"少走 30%~50%。真要最优解用 TSP 近似算法，但实际项目中 S 形 + 巷道分组已经够用——**算法复杂度换来的收益在人工仓里不明显**。

> **面试口径**：波次设计的核心指标是"每单行走距离"和"每车拣货件数"。技术上不是算法难，是约束多——拣货车容量、订单时效、分播墙格口数量。所以我倾向先做可配置的规则引擎（策略模式 + 规则表），跑一段时间用真实数据调参，而不是一上来写复杂的最优路径算法。

### 4. 批次效期：FEFO 与双向追溯

**FEFO vs FIFO**：

- FIFO（先进先出）：按入库时间，先入库先出。
- FEFO（先到期先出）：按失效日期，**快过期的先出**。食品、药品、化工必须用 FEFO。

**分配算法**（拣货时选批次）：

```sql
SELECT * FROM wms_stock
WHERE sku_id = #{sku} AND stock_status = 'AVAILABLE' AND qty_available > 0
ORDER BY expire_date ASC, inbound_time ASC   -- FEFO
LIMIT ...;
```

同时要加两条守卫：`expire_date > 当前日期 + 最小剩余保质期`（不能把明天过期的发给客户）、`质检状态 = 合格`。

**双向追溯**：

| 方向 | 查询 | 场景 |
|---|---|---|
| 反查（向上） | 成品批次 → 用了哪些原料批次、哪张工单、哪个供应商 | 客户投诉，找根因 |
| 正查（向下） | 原料批次 → 流向了哪些成品、发给哪些客户 | 供应商来料有问题，召回 |

追溯表的设计要点：**记录"消耗关系"而不是"最终结果"**。`trace_relation(parent_batch, child_batch, qty, workorder_no, time)`，一次写入，正反两个方向都能查。

> **面试口径**：追溯的难点不是建模，是数据完整性——上了线才发现某个工序没扫码，链路就断了。所以追溯方案落地时，必须在**关键工序**（投料、关键件装配、包装）强制扫码校验，宁可慢一点也不能漏点。

### 5. 弱网与幂等：PDA 是 WMS 的命门

仓库 WiFi 一定有死角（金属货架、冷库）。PDA 必须支持**离线作业**。

**离线架构**：

```text
PDA 本地 SQLite 队列
  → 任务包预先下发（今天要拣的 200 单）
  → 离线扫码，本地扣减本地库存快照
  → 恢复网络后批量上传，服务端幂等校验
```

**幂等的关键**：每条作业带客户端生成的 `request_id`（UUID），服务端建唯一索引。重复上传直接返回上次结果。

```sql
UNIQUE KEY uk_request (request_id)   -- 重复插入失败 → 查已有记录返回
```

**冲突处理**：离线期间服务端库存可能已变（别人拣走了）。策略是**提交时校验 + 差异进异常池**，不阻塞作业——现场作业不能因为后台数据打架就停摆，先按实物走，事后人工平账。

> **面试口径**：弱网场景的第一原则是"作业优先"，宁可事后对账，不能让拣货员卡在那里。技术上就是本地队列 + 客户端幂等键 + 提交时校验，冲突不阻断只记录。这块和[接口幂等性设计](/scenarios/api-idempotent)是同一套思路。

## 四、面试高频追问

**Q1：库存超卖怎么彻底解决？**
A：分场景。单库单实例用条件更新（`WHERE available >= n`）就够；多实例高并发用 Redis 预扣 + 异步落库；跨仓跨系统必须做预占（reserved）并设置超时释放。没有万能方案，看并发量级和一致性要求。

**Q2：为什么不用数据库行锁？**
A：`SELECT FOR UPDATE` 在热点 SKU 上会把并发串行化，RT 从 5ms 涨到几百毫秒，还容易死锁。条件更新是乐观策略，冲突时影响行数为 0，应用层决定重试还是拒绝，可控性更好。

**Q3：库存流水表越来越大怎么办？**
A：按月分区（`PARTITION BY RANGE(create_time)`），冷数据归档到历史库。查询走"库存主表看现在、流水表看历史"，列表页强制带时间范围。

**Q4：盘点怎么做到不停业？**
A：动碰盘点（有作业的库位才盘）+ 循环盘点（按 ABC 分批，A 类每月、C 类每季）。必须全盘时，用**库存快照**：冻结时点生成快照表，盘点期间正常出入库，差异 = 实盘 − 快照 ± 期间变动，这样不用停业务。

**Q5：库位分配要不要用算法？**
A：人工仓优先用规则 + 评分，机器人和立体库才值得上优化算法。判断标准是"行走成本占比"——人工仓里走路的成本远高于算法成本，但规则优化（分区、就近）已经能拿到大部分收益。

**Q6：WMS 和 ERP 的库存对不上，先查什么？**
A：按这个顺序——① 单位换算（箱/个）；② 回写消息是否丢失（查消息表和消费记录）；③ 是否有绕过 WMS 直接改 ERP 库存的操作；④ 在途/在检库存是否被一边计入一边没计。90% 的差异出在前两项。

**Q7：多货主（3PL）怎么隔离？**
A：库存表加 `owner_id`，所有查询强制带 owner 条件；权限到货主级；货主间不允许跨用库存；计费按货主独立算（仓储费、操作费）。

## 五、30 秒速答卡

> WMS 的本质是把库存从"一个数字"变成"数量 × 库位 × 批次 × 状态"的四维模型，核心指标是库存准确率和人均拣货效率。技术上三件事最关键：一是库存变动只走条件更新加流水，可用量永远派生不直接改；二是波次和上架策略要做成可配置规则，不同仓库最优解不同；三是 PDA 必须支持离线，本地队列加客户端幂等键，冲突不阻断作业只进异常池。跟 ERP 的关系是实物以 WMS 为准、账面以 ERP 为准，靠消息回写加每日对账。
