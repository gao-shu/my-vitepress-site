# IIoT 核心问题清单

> **一句话定位**：IIoT 干三件事——**采得上、存得住、用得了**。90% 的项目死在第一件。
>
> **本文用途**：协议、点表、采集、存储、断线、告警六条主线上的核心问题与解法。配套：[ERP](/scenarios/enterprise-digital/erp) · [WMS](/scenarios/enterprise-digital/wms) · [MES](/scenarios/enterprise-digital/mes)。

## 一、IIoT 在做什么

```text
设备（PLC / 仪表 / 机床 / 机器人）
   │  协议：Modbus / S7 / OPC UA / 私有协议
   ▼
边缘网关（采集、解析、缓存、规则判断）
   │  MQTT / HTTP / Kafka
   ▼
平台（接入、时序存储、告警、规则、API）
   │
   ▼
消费方：MES（设备状态/产量）、看板、BI、预测性维护
```

**关键认知**：IIoT 不是"读个数据存起来"。它是**工业现场与 IT 系统之间的翻译层 + 缓冲层 + 兜底层**。现场的协议脏、网络差、时钟乱，这些都要在这一层消化掉，不能漏给上层。

## 二、核心问题清单

| # | 核心问题 | 为什么难 | 典型后果 |
|---|---|---|---|
| 1 | **协议碎片化** | Modbus/S7/OPC UA/私有，每家都不一样 | 接一台设备写一套代码 |
| 2 | **点表管理** | 上万点位、地址/类型/字节序/缩放 | 配错一个位，数据全错 |
| 3 | **采集频率与数据量** | 毫秒级 vs 分钟级，写放大 | 存储爆炸，查询卡死 |
| 4 | **网络不稳断线** | 车间网、无线、4G 都会断 | 数据缺口，事后查不到 |
| 5 | **数据质量** | 空值、0 值、跳变、时钟漂移 | 报表全是脏数据 |
| 6 | **边缘与云协同** | 规则下发、断网自治、OTA | 断网就停产 |
| 7 | **指令下行安全** | 写 PLC 有物理风险 | 误操作停机或损坏设备 |
| 8 | **海量连接** | 几千设备长连接、心跳、会话 | 网关内存爆、连接掉 |
| 9 | **告警风暴** | 抖动、级联、重复 | 报警没人看，等于没有 |
| 10 | **工控安全** | 生产网不能直接连外网 | 要么不通，要么裸奔 |

## 三、五个深水区逐个拆

### 1. 协议选型：先看设备，再看场景

| 协议 | 传输 | 特点 | 适用 |
|---|---|---|---|
| **Modbus RTU** | RS485 串口 | 简单、便宜、主从轮询 | 老设备、仪表、电表 |
| **Modbus TCP** | 以太网 | 同上，走 TCP 502 | 支持网口的 PLC、仪表 |
| **S7（西门子）** | 以太网 | 西门子私有，需按 DB 块地址读 | 西门子 S7-200/300/1200/1500 |
| **OPC UA** | TCP/HTTPS | 标准、自带信息模型、有安全机制 | 新设备、跨厂商集成 |
| **MQTT** | TCP | 轻量、发布订阅、QoS 可选 | 设备→平台的上行通道 |
| **Profinet / EtherCAT** | 实时以太网 | 硬实时，微秒级 | 产线控制层，一般不由 IT 直采 |

**选型判断顺序**：

1. 设备自带什么口？（网口优先，串口兜底）
2. 厂家开放什么协议？（先查手册，别自己猜寄存器）
3. 数据要什么实时性？（控制级 vs 监控级，差一个数量级）
4. 一台网关带多少点？（RTU 轮询受波特率限制，点多必须拆）

**踩坑提醒**：Modbus 串口一条总线挂太多从站，轮询一轮就要几秒——这不是软件问题，是物理限制。点位多就多条总线、多个网关。

### 2. 点表管理：配错一个位，全场数据作废

**点表要描述的东西**：

```text
设备 → 点位（tag）
  ├── 地址：40001（Modbus 保持寄存器）、DB1.DBD0（S7）
  ├── 数据类型：bool / int16 / uint16 / int32 / float32
  ├── 字节序：ABCD / CDAB / BADC / DCBA   ← 32 位最易错
  ├── 缩放：raw × 0.1 → 实际值（温度、压力）
  ├── 单位与量程：℃，0~150
  ├── 采集周期：1000ms
  └── 死区（deadband）：变化超过阈值才上报
```

**字节序为什么是重灾区**：Modbus 寄存器是 16 位，一个 32 位浮点要占两个寄存器。四个字节怎么排，不同厂家完全不同：

```text
ABCD（大端）  CDAB（字交换，最常见）  BADC  DCBA（小端）
```

表现就是"读出来是 1.2e-38 这种乱数"。**处理办法**：点表里显式配 `byte_order`，采集层统一转成 Java 的 `float`，绝对不在业务层做转换。

**点表必须配置化，不能硬编码**：

```sql
iot_point(
  id, device_id, tag_code, address, data_type, byte_order,
  scale, offset, unit, min_val, max_val,
  collect_interval, deadband, enabled
)
```

改点表不用改代码、不用重启采集进程——这是能否交付 100 台设备的分水岭。

> **面试口径**：IIoT 项目里最耗时的不是写协议，是核对点表。我的做法是把点表做成配置表 + 校验工具：配完先在网关上模拟读一遍，把原始值和换算值并排显示给现场工程师确认，确认后再启用。硬编码点表的项目，第二个车间就要重写。

### 3. 采集分层与存储：别把秒级数据当毫秒级存

**分层原则**：

| 层级 | 频率 | 用途 | 存哪 | 保留 |
|---|---|---|---|---|
| 实时值 | 秒级 | 看板、当前状态 | Redis / 内存 | 只留最新 |
| 明细 | 秒~分钟 | 趋势、追溯 | 时序库 | 3~12 个月 |
| 聚合 | 分钟~小时 | 报表、OEE | 关系库 | 长期 |
| 事件 | 触发式 | 报警、停机 | 关系库 | 长期 |

**写放大的来源**：1000 个点位 × 1 秒 = 8.6 万点/秒。如果每条一个 INSERT，数据库直接被打死。

**三个优化手段**：

1. **批量写**：边缘侧攒 500~2000 条一批，或者按 200ms 窗口批量提交。
2. **死区过滤**：值没变就不上报（`ABS(new - last) > deadband`），实际数据量常能降 70% 以上。
3. **列式/时序存储**：按设备 + 时间戳建索引，压缩编码（delta-of-delta + 字典编码）。

**时序库选型**：

| 方案 | 优势 | 短板 | 适合 |
|---|---|---|---|
| **TDengine** | 国产、压缩比高、SQL 友好、超级表模型贴合设备场景 | 生态相对小 | 设备数量多、写入量大 |
| **InfluxDB** | 生态好、查询语言成熟 | 集群版收费，版本差异大 | 中小规模、快速起步 |
| **TimescaleDB** | PG 扩展，SQL 能力完整，可 JOIN 业务表 | 超大数据量需调优 | 已有 PG 技术栈 |
| **ClickHouse** | 分析查询极快 | 不适合单点更新/高频小写入 | 事后分析、大屏聚合 |

> **面试口径**：选时序库先算三个数——设备数 × 点位数 × 采集频率 = 每秒写入点；再算单点字节数 × 保留时长 = 存储量。算完这两个数，选型基本没悬念。我倾向 TDengine 或 TimescaleDB，前者省存储，后者省学习成本。

### 4. 断线不丢数：边缘缓冲 + 补传去重

**问题**：车间网络断 30 分钟，这 30 分钟的产量、温度曲线全没了。事后查质量事故，正好缺这一段。

**标准解法**：

```text
边缘网关
  ├── 采集 → 本地环形缓冲（SQLite / RocksDB / 内存队列）
  ├── 网络正常 → 实时上报
  ├── 网络断 → 写本地，标记 seq（单调递增）
  └── 恢复 → 按 seq 补传，服务端幂等去重
```

**去重键**：`(device_id, tag_code, ts)` 建唯一索引，重复插入忽略。

**时间戳必须由边缘生成**，不能用平台接收时间——补传时数据是"旧"的，用接收时间会全部错位。

**边缘自治**：断网时网关要能继续跑规则（本地告警、本地联锁），不能因为连不上云就罢工。这是"边缘计算"存在的真实理由。

> **面试口径**：断线不丢数的关键有两处——一是边缘要能缓存足够长的数据（按最坏断网时长估算容量），二是补传必须幂等，因为补传过程本身也会超时重试。时间戳一定要在采集侧打，这是很多人踩过的坑。

### 5. 告警收敛：从"报警没人看"到"报警就是命令"

**告警风暴的三种成因**：

| 成因 | 表现 | 解法 |
|---|---|---|
| 抖动 | 温度在阈值附近反复进出，一天 200 条 | 连续 N 次超阈值才触发 + 静默期 |
| 级联 | 一个网关掉线，底下 500 个点位全报 | 拓扑抑制：父节点告警时抑制子节点 |
| 重复 | 同设备同指标多渠道重复推 | 去重键 `(device, metric, 窗口)` 合并 |

**分级**：P0 停机/安全 → 电话+短信；P1 影响产能 → 企微/钉钉；P2 需关注 → 站内信日报。

**状态机**：

```text
NORMAL → FIRING（触发）→ ACKNOWLEDGED（已确认）→ RESOLVED（恢复）
                              ↓
                         升级（超时未确认 → 通知上级）
```

必须有"已确认"这一环，否则值班的人只能看着，不能表态。

> **面试口径**：告警系统的核心指标不是"数量"，是"有效告警率"和"平均响应时间"。做完之后要去统计有多少告警被人为忽略，被忽略的那部分就是噪声，要么改阈值要么抑制。

## 四、面试高频追问

**Q1：几千台设备的长连接怎么撑？**
A：Netty 做接入层，`boss/worker` 线程数按核数配；设备会话放 Redis（`device:{id} → node`），节点无状态可水平扩；心跳用 MQTT 的 keepalive 或自定义 ping/pong，超时 2.5 倍时间判定离线；离线事件走延迟队列，不要靠定时扫全表。

**Q2：MQTT 的 QoS 怎么选？**
A：QoS 0 最多一次（丢了不管，适合高频非关键）；QoS 1 至少一次（可能重复，业务侧要做幂等，最常用）；QoS 2 恰好一次（握手多、开销大，关键指令才用）。绝大多数遥测数据用 QoS 1 + 服务端幂等就够了。

**Q3：设备时间不准怎么办？**
A：三件事——采集侧尽量用统一授时（NTP / 网关对时）；时间戳以边缘采集时刻为准；平台侧做时钟偏移检测（和服务器时间差超过阈值就告警并记录偏移量），必要时按偏移量校正。

**Q4：一个点位读出来是乱数，怎么排查？**
A：按顺序——① 地址对不对（Modbus 的 40001 是"第 1 个保持寄存器"，但报文里从站地址要减 1）；② 数据类型对不对（把 float 当 int32 读）；③ 字节序对不对（CDAB 最常见）；④ 缩放因子是否漏乘。工具上先用 Modbus Poll 之类的现成工具验证，确认能读到正确值再写代码。

**Q5：IIoT 和 SCADA 什么关系？**
A：SCADA 偏控制与监控（实时性强、闭环），IIoT 偏数据汇聚与分析（跨系统、上云）。技术上 IIoT 常从 SCADA 或 OPC UA 服务器取数据，不直接碰底层 PLC，这样既安全又不干扰控制。

**Q6：怎么保证不下行错指令？**
A：三道闸——① 网络隔离，生产网与办公网单向或经 DMZ；② 指令白名单，只允许预定义的指令模板，不允许任意寄存器写入；③ 二次确认 + 超时回读校验，写完读回值比对，不一致立即告警。写 PLC 是物理世界操作，必须当成高风险动作设计。

## 五、30 秒速答卡

> IIoT 我理解是三个"翻译"：协议翻译（Modbus/S7/OPC UA 到统一模型）、时间翻译（边缘打时间戳、批量对齐）、语义翻译（原始值到带单位的工程量）。技术上最关键的四个点：点表必须配置化并显式配字节序，不然每家设备都要改代码；采集要分层，秒级实时值进 Redis、明细进时序库、聚合进关系库，配合死区过滤和批量写控制写放大；断网必须边缘缓存加补传幂等，时间戳在采集侧生成；告警要做抖动过滤、级联抑制和确认升级，否则报警等于没有。
