03 · AI 协作体系建设 ​

本章是整套 SOP 的核心。目标不是配齐所有能力，而是把 Rules、Agent、Skills、MCP、Hooks 的职责钉死，让每一条约束、每一个角色、每一份方法都放对位置。

场景与问题 ​

有三种很典型的「建了体系但没用」：

  • 一份大杂烩规则：技术栈、目录约定、业务流程、本次需求、安全红线全在一个文件里，两百多行。AI 每次只执行末尾几条，前面等于不存在。
  • Agent 拆得很热闹：架构、后端、前端、测试、Reviewer 全配上，结果一个「改个字段校验」的任务要在五个角色之间传三轮，比自己改慢十倍。
  • Skill 和 Rules 互相打架：Skill 里写着「按本项目三层架构实现」，换到另一个项目就带着上一个项目的业务事实跑，输出全是错的。

共同根因是第 01 章那张职责表没落地。本章把五个机制分别展开，给出编写模板 + 填好的示例 + 验收方式，全部与具体工具无关。

零、先定最小集，再谈完备 ​

阶段必须建按需才建明确不建
项目接入后全局 Rules 一份、项目认知报告、一条开发主链—全套 Agent、Skill 大全
第一次迭代该任务的 Spec复用第二次出现的同类操作为了「体系完整」补文件
重复 3 次以上—对应的 Skill只出现过一次就沉淀
确有并行收益—拆子 Agent单文件改动也搞多 Agent
检查反复漏—Hook 脚本化靠 Prompt 反复提醒

判断顺序：先 Rules，再 Spec，再 Skill，最后才考虑 Agent 和 MCP。反过来做，你会得到一堆没人用的配置。

一、Rules：约束所有任务 ​

分层 ​

层级管什么示例变更频率
全局技术栈、构建测试命令、禁改区、安全红线「不得自行新增依赖」低
项目级分层约定、命名、错误码、接口风格「Controller 不写业务逻辑」中
目录级某个模块特有的约束「legacy/inventory 无测试覆盖，禁止改动」中
技术规范语言/框架的具体写法「MyBatis 不用注解写动态 SQL」低
安全规范凭据、外发、权限「生产连接串禁止写进任何上下文文件」极低
业务约束跨任务成立的业务红线「出库分配必须 FEFO，不得按 FIFO」低

三条不要写进 Rules

① 本次任务要做什么（那是 Spec）；② 完整业务流程说明（那是项目认知报告）；③ 分阶段的操作步骤（那是 Skill 或开发流程）。Rules 只回答「无论做什么任务都必须遵守什么」。

编写标准 ​

  1. 每条规则可验证 —— 能指向一个命令、一个 diff 特征或一个检查点，不能是「代码要写好」这种形容词。
  2. 每条禁止项配一个反例，让 AI 知道边界在哪。
  3. 写明来源（来自哪份文档、哪次事故、哪条约定），否则半年后没人敢删。
  4. 全局规则控制在 30 行以内；超了就是混进了别层的东西。
  5. 用「必须 / 禁止」陈述句，不用「建议 / 尽量」。

markdown

二、Agent：角色与任务执行 ​

角色清单 ​

不要求每个项目都配全，绝大多数项目只需要「主 Agent + 按需的 1–2 个子角色」。

角色职责（一句话）输入输出权限边界协作方式
主 Agent拆解任务、传递上下文、收口结果，不写业务代码需求 + Spec + 项目认知报告任务分工表 + 汇总可读全仓；写仅限任务文档向人交付，不自行宣布完成
架构 Agent出方案与代价对比，不动代码需求 + 现状架构方案 + 取舍 + 不做清单只读人拍板后才进入实现
后端 Agent按 Spec 实现后端改动Spec + 相关规则 + 调用链代码 diff + 测试写后端目录提交给 Reviewer 与测试
前端 Agent按接口契约实现页面Spec + 接口契约代码 diff写前端目录与后端并行，共用契约
测试 Agent补用例、跑命令、汇总结果Spec 的验收段 + diff测试结果（含失败项）写测试目录；不改实现不修 bug，只报
Reviewer Agent审 diff、提问题仅 diff + Spec，不给推理过程问题清单只读不判定通过

为什么 Reviewer 不能判定通过

执行者不能当验收人。Reviewer Agent 只输出「问题清单和依据」，逐条对照验收清单判定是否完成，是人的动作。把这一条写进权限边界，比在 Prompt 里提醒十遍都有效。

什么时候才拆子 Agent ​

适合并行必须串行
前后端共用已冻结的接口契约需求澄清 → 架构设计（人未拍板不能开实现）
多个互不重叠模块的同类改动数据库变更 → 依赖它的接口实现
测试补充与文档整理实现 → Review → 验收
独立模块的只读分析同一文件的多处修改

一条硬规则：没有冻结的 Spec 就不要并行。并行拆得越细，上下文对齐成本越高；单文件改动搞多 Agent，纯属用流程制造开销。

填好的示例（Reviewer Agent） ​

markdown
# Reviewer Agent

## 职责
只审本次 diff，输出可追溯的问题清单。

## 不负责
- 不修代码、不改 diff、不补测试。
- 不判定「可以合并 / 已完成」，那是人的动作。
- 不评价整体架构好坏，只审这次改动是否越界。

## 输入（缺一不可）
| 材料 | 来源 | 缺失时 |
|------|------|--------|
| 本次 diff | git diff | 停手索要 |
| 对应 Spec | docs/ai-context/specs/ | 停手索要 |
| 全局 Rules 与项目认知报告第 8 节 | 仓库 | 停手索要 |

## 输出
- 问题清单：编号 / 位置（文件:行）/ 违反了哪条规则或 Spec / 依据 / 严重级别。
- 必须附带的证据：每个问题都要能指到具体行号，不接受「整体感觉」。

## 权限边界
- 可读：全仓只读
- 可写：无
- 禁止：修改任何文件、执行写操作、给出通过结论

## 协作方式
- 向人交付问题清单，人逐条裁定「改 / 不改 / 记入技术债」。
- 触发升级：发现禁改区被改动、发现凭据外泄、发现与 Spec 冲突且影响线上行为。
- 与测试 Agent 的交接物：测试未覆盖的边界条件，转交测试角色补用例。

## 停手条件
- diff 与 Spec 明显不是同一个任务时停下，不强行审。
- 无法判断某条规则是否适用时，标「需人确认」，不自行解释规则。

## 完成判定
- 由人对照验收清单判定；本 Agent 只输出清单，不宣布完成。

三、Skills：可复用的方法 ​

与 Rules 的根本区别 ​

RulesSkills
是否自动生效是，每个任务都带否，触发条件满足才启用
内容约束（不能做什么）方法（怎么一步步做）
归属跟仓走，只属于这个项目跟人走，可跨项目复用
能不能放业务事实可以（但只写约束，不复制说明）禁止

一句话：Skill 里出现具体表名、客户名、业务字段，就是写错了地方。

通用 Skill 分类 ​

类别触发条件典型产出
项目分析接手陌生仓库事实清单 + 待确认清单
需求分析拿到一段模糊需求澄清问题列表 + 范围草案
架构设计需要定模块边界方案与取舍对比（不拍板）
数据库设计新增表/改字段表设计 + 迁移与回滚要点
API 设计新增/改接口接口契约（路径、入出参、错误码）
后端开发有冻结 Spec小步 diff + 单测
前端开发有接口契约页面 diff + 交互说明
测试实现完成用例 + 实际命令输出
Bug 排查有完整报错与复现步骤根因假设 + 证据排除记录
代码审查有 diff问题清单（不判定通过）
文档生成交付前README / 变更记录 / 交接说明
项目交付验收通过后交付报告

设计标准 ​

  1. 触发条件写「什么时候不用」，比只写什么时候用更能防止滥用。
  2. 执行流程每一步都有可检查的中间产出，不能是「分析一下」这种黑盒。
  3. 写清失败与降级：缺输入、命令跑不通、AI 输出不可信时怎么办。
  4. 必须有复用记录：至少在两个项目里跑过，才升级为通用能力。
  5. Skill 不写业务事实、不写工具按钮、不复制 Rules 全文。

填好的示例（Skill · 老项目局部改动） ​

markdown
# Skill · 老项目局部改动

## 触发条件
- 用：在已有仓库上做一个范围明确的小改动（加过滤、加字段、修一个 bug）
- 不用：新模块开发、架构调整、跨多个系统的改造

## 输入
| 材料 | 必须 | 缺失时 |
|------|------|--------|
| 项目认知报告 | 是 | 停手，先做接入（第 02 章） |
| 本次 Spec（含验收与"不做"） | 是 | 停手索要，不按口头需求开工 |
| 涉及的调用链 | 是 | 用扫描 Prompt 补一条链 |
| 全局 Rules | 是 | 停手索要 |

## 执行流程
| 步 | 动作 | 中间产出 | 检查点 |
|----|------|---------|--------|
| 1 | 复述改什么、不改什么 | 三句话复述 | 人确认 |
| 2 | 定位会碰的文件，列清单 | 文件清单（不超过 N 个） | 人确认范围 |
| 3 | 写/确认 Spec | specs/<短名>.md | 人冻结后才继续 |
| 4 | 小步实现，一次一个改动单位 | diff | 人看 diff |
| 5 | 跑 Spec 里的验收命令 | 命令输出原文 | 结果对照验收段 |
| 6 | 查「改前行为」是否保持 | 回归对照结果 | 人确认 |
| 7 | 交 Reviewer | 问题清单 | 人裁定 |

## 输出
- diff + 命令输出原文 + 回归对照结果 + 未解决问题清单。

## 验收标准
- [ ] Spec 中每条验收都有对应的实际输出
- [ ] 未点名的行为与改前一致（至少验证一条）
- [ ] diff 未触及禁改区，pom.xml / 依赖文件无变更
- [ ] 已有 URL 与接口签名未变

## 失败与降级
| 情况 | 处理 |
|------|------|
| 调用链超出本次范围 | 缩回范围，把超出的记入待办，不扩大改动 |
| 验收命令跑不通 | 原样贴报错，标「环境待确认」，不写成「通过」 |
| 发现需要先改架构 | 停手，退回技术设计流程，不在本任务里顺手重构 |

## 不写入本 Skill 的内容
- 具体表名、字段、客户名 → 项目认知报告
- 禁改区清单 → Rules
- 本次改哪个接口 → Spec

四、MCP：外部能力连接 ​

MCP 只解决一件事：让 AI 拿到仓库之外的能力或数据。它不决定开发流程，也不替代项目认知报告。

适合接不适合接
只读的测试库元数据、表结构查询生产库（外发与权限风险）
内部文档/知识库检索把整个业务知识库塞进每次会话上下文
构建与 CI 状态查询用 MCP 代替本地跑命令
工单/需求系统的只读同步让 AI 直接写回需求系统

接入前三项检查，缺一不接：

  1. 必要性：不接这个数据源，任务是不是真做不了？能靠仓库内文件解决的，不接。
  2. 边界：数据能不能外发、凭据放哪、权限最小化到什么程度、只读还是可写。
  3. 降级：服务不可用时，流程是停下来还是走本地文件；不能出现「MCP 挂了整套 SOP 就跑不动」。

五、Hooks：确定性自动化 ​

判断标准很简单：凡是「漏了就出事」且「能写成脚本判定」的检查，一律交给 Hooks，不交给 AI 自觉。Prompt 提醒会被长会话稀释，脚本不会。

检查为什么必须脚本化失败动作
格式 / lint / 构建每次提交都要过，AI 会忘阻断提交
单测与最小冒烟「已完成」必须有证据阻断并贴出输出
密钥 / 凭据扫描外发不可逆转阻断 + 报告
依赖文件变更检测防止 AI 自行引包阻断，需人确认
禁改区 diff 检测无测试覆盖的老代码不能被顺手改阻断
提交信息规范便于回溯与回滚提示或阻断

Hooks 不判断业务对错（例如「这个过滤逻辑符合 FEFO 吗」），那是 Spec 验收和人的判断。它只做确定性事实检查。

六、一个需求，五个机制各做什么 ​

需求：WMS 出库列表增加「效期不足 30 天」过滤（老项目，第三次做同类局部改动）。

机制这一刀里管什么不管什么
Rules禁改 /api/stock/outbound 签名、禁止把 qty 当账面量、禁改 legacy 目录、禁止新增依赖这个过滤怎么实现
Agent主 Agent 拆任务；后端 Agent 实现；Reviewer 只出「问题清单」判定能不能合
Skills复用「老项目局部改动」Skill 的 7 步流程与回归对照存 biz_stock 字段含义
MCP若需核对测试库表结构，只读接入；不可用时降级到本地 DDL 文件决定开发顺序
Hooks提交前跑 mvn test、密钥扫描、禁改区 diff 检测判断 FEFO 有没有被破坏
人确认规则 R02 未被改动、逐条对照验收清单判定完成写实现代码

看出职责边界的意义：如果把「必须 FEFO」写进 Skill，换到 ERP 项目就会带着 WMS 的业务事实跑；如果让 Reviewer 判定通过，验收就外包给了执行者。

七、工具适配边界声明 ​

本章所有文件名、目录名、层级划分都是通用示意，只表达「哪类内容放哪」，不代表任何 AI 编程工具的官方约定。

  • Cursor、WorkBuddy、Claude Code 等工具的目录结构、配置语法、加载优先级、调用方式，以对应版本的官方文档为准。
  • 不同工具对 Rules / Agent / Skills 的支持程度不同：有的没有目录级规则，有的 Skill 不进仓库，有的不支持 Hook。适配时按能力映射，缺的能力不要用别的能力硬凑。
  • 本 SOP 不编造未经验证的工具特性。具体落地办法在 M3 工具适配指南中单独给出（Cursor、WorkBuddy 各一篇），通用章节里不混写。

八、建设验收清单 ​

  • [ ] 全局 Rules 不超过 30 行，每条都配了验证方式，禁止项都有反例
  • [ ] 任取一条规则，能说清它属于哪个层级、来源在哪
  • [ ] Rules 里没有出现「本次」「这个需求」「先做…再做…」这类任务/流程措辞
  • [ ] 实际启用的 Agent 有书面职责与权限边界，Reviewer 明确不判定通过
  • [ ] 每个 Skill 都写了触发条件、什么时候不用、失败降级、复用记录
  • [ ] Skill 中没有具体表名、客户名、业务字段
  • [ ] MCP 接入逐条过了必要性 / 边界 / 降级三项检查
  • [ ] 所有「漏了就出事」的检查已进 Hooks，不靠 Prompt 提醒
  • [ ] 启动必备清单没有超过 5 项（防过度设计）

九、常见问题 ​

Q：只有一个 Agent 算不算建了协作体系？ 算。单 Agent + 一份可验证的 Rules + 一条主链就是最小可用体系。角色数量不是成熟度指标。

Q：Rules 和项目认知报告都提到 FEFO，算重复吗？ 不算，但职责不同：报告里写「规则是什么、来源在哪」，Rules 里只写「必须保持、怎么验证」。不要两边都贴整段业务说明。

Q：Skill 什么时候从项目专属升级成通用？ 同类操作在第二个不同项目里跑通、且删掉所有业务事实之后仍然可用，才升级。只出现过一次就沉淀，通常会沉淀出一份没人用的模板。

Q：工具不支持 Hooks 怎么办？ 把检查降级为 CI 步骤或提交前手动脚本，并在验收清单里点名「必须跑」，不要假装 AI 会记得。适配层能力缺失要如实记录，不要用别的能力硬凑。

关键要点 ​

  • 建设顺序：Rules → Spec → Skill → Agent / MCP；启动必备不超过 5 项。
  • Rules 管约束且自动生效，Skill 管方法且触发才用；Skill 里禁止出现业务事实。
  • Agent 必须有权限边界，Reviewer 不判定通过，验收始终在人。
  • 没有冻结的 Spec 不并行；单文件改动不拆多 Agent。
  • 确定性检查交给 Hooks，MCP 接入前过必要性 / 边界 / 降级三关。
  • 所有目录与语法均为示意，具体工具以官方文档为准，M3 单独适配。

小结 ​

协作体系的成熟度不看配置数量，看职责有没有混。一份 30 行可验证的 Rules、一个明确的 Reviewer 边界、一份在两个项目里验证过的 Skill，比十个 Agent 加两百行规则有用得多。建完这一层，就具备进入需求、设计、开发、测试主链的条件了 —— 那是 M2 的范围。
