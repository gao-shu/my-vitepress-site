02 · 项目接入与初始化 ​

新项目和老项目的第一步完全不同，但从「项目认知报告」产出之后，走的是同一条开发主链。本章的交付物是一份能直接复制使用的《项目认知报告》模板。

场景与问题 ​

接手一个陌生的老仓库时，最常见的翻车方式是：把 AI 拉进会话，问一句「这个项目是干什么的」，拿到一段流利的概述，然后就开始改代码。那段概述里通常混着三样东西 —— 从代码里读出来的事实、模型根据常见框架脑补的推测、以及它把两者缝合时编出来的过渡句。你没法分辨哪句是真的。

新项目反过来：什么都没有，于是有人一上来就让 AI「生成完整项目结构」，结果得到一个包含网关、缓存、消息队列、多模块的骨架，实际只需要三张表两个接口。

两种失败的共同点：没有一份把「已知事实」和「待确认」分开的书面结论。接入阶段要产出的不是理解的感觉，而是一份能被打勾、能被下一轮会话直接引用的档案。

二、新项目接入 SOP ​

步输入动作输出停手条件
1一句话想法写清：给谁用、解决什么问题、怎样算有用、明确不做什么目标与范围（不超过 10 行）「怎样算有用」说不出来就停
2目标、团队栈、部署条件选技术栈，写选择理由与放弃理由技术栈决策表别选没跑通过的组合
3目标 + 栈定模块边界、系统级约束（模块、表、接口、状态机）架构一页纸停在边界，不写字段校验
4架构规划目录、包命名、配置与文档位置目录结构 + AI 协作文件位不预建空目录
5架构定数据库规范（命名、主键、审计字段）与接口规范（路径、错误码、分页）规范两页规范能举例，不只是形容词
61–5 的产出填《项目认知报告》，人写已知事实报告 v0.1所有「来源」列都填得出来
7报告建最小协作体系（见第 03 章）全局 Rules + 一条主链别一次配齐 Agent/Skill

顺序不能反

先定边界，再定文件，再让 AI 写代码。反过来做，AI 会用「它认为合理」的结构替你做架构决策，而且这个决策只存在那轮对话里。

三、老项目接入 SOP ​

步输入动作输出停手条件
1仓库自动扫描目录树、构建文件、配置文件、入口类结构清单只读，不改任何文件
2结构清单识别语言/框架/版本、依赖清单、外部服务技术栈表（带证据路径）版本号必须来自配置文件
3全仓分析分层、模块依赖、调用方向架构现状图只描述现状，不写「应该」
4架构图定位核心业务模块与关键调用链模块清单（标热度）挑本次会碰的 1–2 条链
5数据库脚本/ORM梳理表、主外键、索引、字段含义数据模型摘要字段含义不确定就标「待确认」
6代码 + 文档抽取业务规则，逐条标注来源与置信度规则清单（事实/待确认两态）禁止把推测写成事实
7提交历史、注释、TODO识别历史技术债与隐含约定技术债 + gotchas 候选gotchas 最终由人写
81–7 草稿人审去伪：删掉模型脑补、补全来源、写 gotchas《项目认知报告》v0.1还有一条「来源」为空就不许进第 9 步
9报告从现状提炼最小项目专属配置项目 Rules + 禁改区不照抄理想规范

老项目五条硬禁令：不重构架构 · 不改已有 URL/接口签名 · 不加依赖 · 不批量格式化 · 不把扫描推测当事实写进档案。

可复制：老项目扫描 Prompt ​

text
你现在的任务只有一个：扫描并如实记录，不要提出任何改进建议，不要修改任何文件。

背景：这是一个我需要接手的已有仓库，我还没理解它。
目标：产出「事实清单」，供我人审后写进《项目认知报告》。

约束：
- 每条结论后面必须附上证据的文件路径或行号。
- 读不到的、推断的、根据常见框架猜测的，一律单独放进「待确认」段，
  不要和事实混在一起，不要为了段落完整而补过渡句。
- 本轮只覆盖【填写：本次会碰的模块或调用链】，不要试图描述整个系统。
- 不要输出「建议」「优化」「应该」任何字样。

输出格式（严格按这四段）：
1. 事实（编号 + 结论 + 证据路径）
2. 待确认（编号 + 不确定点 + 需要我提供什么）
3. 这次会碰的调用链（入口 → 中间层 → 数据层，逐层给文件）
4. 本轮未覆盖范围（一句话）

填写示例（片段 · WMS 批次效期场景） ​

模板不是空标题，下面是第 4、8、9 节填好之后的样子，可直接照着写：

markdown
## 4. 核心业务规则
| 编号 | 规则 | 状态 | 来源 | 备注 |
|------|------|------|------|------|
| R01 | 出库按 FEFO（先到期先出）分配批次，不是 FIFO | 事实 | BatchAllocService.java:87 | 与常见 WMS 不同，别让 AI 想当然 |
| R02 | 效期不足 30 天的批次禁止出库，需走特批 | 事实 | BatchAllocService.java:112；生产确认 | 阈值配置在 biz_config 表 |
| R03 | 同一批次不允许跨库位拆分 | 待确认 | 需仓储主管确认 | 阻塞出库单拆分设计 |

## 8. 禁改区与安全边界
- 禁改文件 / 目录：legacy/inventory/ 下的旧结算逻辑（无测试覆盖）
- 不得外发的内容：客户物料编码、供应商价格
- 凭据与环境隔离要求：生产库连接串只存在运行环境，禁止写进任何上下文文件
- 依赖变更审批：新增依赖需人确认，AI 不得自行引入

## 9. gotchas（必须人写）
- biz_stock 表的 qty 字段是「可用量」不是「账面量」，冻结量另算；按账面量写查询会超卖。
- 老接口 /api/stock/adjust 不校验幂等键，重复调用会重复扣减，调用方自己保证。
- 本地跑单测必须连测试库，纯内存 H2 跑不起来，别改配置去适配 H2。

七、接入完成验收清单 ​

接入阶段算做完，必须能逐条打勾：

  • [ ] 《项目认知报告》已落仓库，版本号、日期、维护人、认知范围齐全
  • [ ] 每条事实都有来源；所有推测都进了「待确认」，正文里没有「应该是」「一般是」这类措辞
  • [ ] gotchas 由人写，且至少写了一条踩坑经验（新项目可写「暂无」，但接入后须补）
  • [ ] 构建命令、测试命令、最小冒烟验证在本机实际跑通过一次
  • [ ] 禁改区与安全边界写明，并已同步进项目 Rules
  • [ ] 明确写出「未覆盖范围」，且会话里重申过这条边界
  • [ ] 接入结论里写清「可以开始哪类任务 / 暂不允许哪类任务」
  • [ ] 老项目：确认没有任何架构级改动被引入，git diff 只有文档

不得以 AI 自述作为验收

「我已扫描完成」「项目结构已理解」不构成验收。上面每一条都要能指到一个具体文件或一次实际命令输出。

八、常见问题 ​

Q：报告要写多长？ 一个中等规模老项目，接入版 80–150 行足够。写超了通常说明把业务流程说明整段搬进来了，那应该另放文档，报告里只留索引。

Q：扫描一次就能理解整个系统吗？ 不能。老项目第一轮的认知范围只覆盖「本次会碰的一条调用链」，报告里必须写明未覆盖范围。系统级理解是多次迭代累积出来的，不是一次扫描的成果。

Q：新项目也要写 gotchas？ 接入时写「暂无」即可，但第一个坑出现后立刻补。它的价值在于让「坑」有唯一存放位置，避免散落在聊天记录里。

Q：这份报告和 README 什么关系？ README 给人看（怎么跑、怎么贡献）；项目认知报告给 AI 看（事实边界、禁改区、gotchas）。不要合并，合并后的结果通常两边都不好用。

关键要点 ​

  • 新项目先定边界再建文件；老项目先扫描建档，禁止直接重构。
  • 事实 / 待确认 / 人写 gotchas 三态分离，是防止 AI 编造的核心手段。
  • 每条结论必须带来源；扫描 Prompt 里明确规定「不许补过渡句、不许写建议」。
  • 《项目认知报告》是唯一事实源，Rules 不复制业务规则，Spec 不合并进长期文档。
  • 接入验收看证据（文件 + 命令输出），不看 AI 自述。

小结 ​

接入阶段真正的产出不是「我大概懂了这个项目」，而是一份能被下一轮会话直接引用、能被逐条打勾的档案。新项目和老项目只是获取这份档案的路径不同 —— 一个靠人写已知目标，一个靠扫描加人审去伪。档案落地之后，两条路就合成一条，进入第 03 章建最小协作体系。
