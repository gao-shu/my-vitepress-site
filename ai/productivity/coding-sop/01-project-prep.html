01 项目准备 ​

让 AI 先搞懂项目：新项目怎么初始化、老项目怎么接手、怎么摸清结构与调用链、怎么建立最小且长期生效的协作配置。准备到「能说清改哪里、会影响谁」就够了，不要先建一堆文档。

一、什么时候用 ​

场景怎么做
全新项目，代码还没开始写新项目初始化
已有脚手架，尚未正式开发检查现有结构，补项目约定
接手别人开发的项目老项目接管
已开发一段时间，AI 经常理解错补上下文与规则，不必重做接入
小型一次性项目只做最小必要准备

项目准备的核心任务只有三个：让 AI 知道项目是什么、知道如何开发与验证、知道哪些事情不能擅自做。

不是每次开发都要重新准备一遍。 结果沉淀在仓库里，后续会话直接读。

实际开发的四步流程 ​

text
① 准备项目    让 AI 理解项目，读取规则和必要上下文（本页）
② 描述任务    说清目标和约束，让 AI 分析、拆解、编码（第 02 页）
③ 遇到问题    让 AI 定位根因、修复并验证（第 03 页）
④ 完成验收    检查功能、测试、构建和交付结果（第 04 页）

复杂功能 / 老项目完整接入 + 四层上下文分析

二、操作步骤 ​

2.1 新项目初始化（七步） ​

步骤AI 要做什么产出
1明确项目目标、用户和核心功能项目目标
2确认技术栈与运行环境技术约定
3检查或建立项目目录结构项目骨架
4确定开发、构建和测试命令命令清单
5确定代码规范和修改边界项目规则
6检查开发环境是否可用环境检查结果
7整理必要的项目上下文项目说明

先定边界，再定文件，最后才让 AI 写代码。顺序反了，AI 会用「它认为合理」的结构替你做架构决策，而且这个决策只存在那轮对话里。

2.2 老项目接管（九步） ​

步骤检查内容产出
1项目目录与模块划分项目结构
2技术栈、依赖和版本技术环境
3启动、构建和测试方式命令清单
4核心业务模块与调用关系业务地图
5数据库、接口和外部依赖关键依赖清单
6代码规范和已有规则开发约定
7当前已知问题和风险风险清单
8与当前任务相关的代码位置任务上下文
9汇总并检查认知准确性项目接入报告

新项目可以设计结构，老项目必须尊重现状。 不要求一次理解整个系统：先掌握整体结构，再围绕实际任务深入对应模块。

七条硬禁令（突破需说明原因、影响范围并取得授权）：

  1. 不擅自重构原有架构。
  2. 不随意修改已有接口签名。
  3. 不随意升级依赖和框架版本。
  4. 不批量格式化无关文件。
  5. 不把推测出来的业务规则当作真实规则。
  6. 不擅自删除已有功能。
  7. 不修改生产数据或执行不可逆操作。

2.3 项目分析：四层收敛 ​

无效扫描的根因是范围没有分层。按外到内四层收敛，每层有停止条件，上一层没完成不进下一层。

层次产出可以停的条件典型耗时
项目地图模块清单 + 入口 + 构建方式能说出「项目由哪几块组成」3–5 分钟
模块地图本次任务涉及的目录与子模块能指出「改动落在哪个包」2–3 分钟
调用链入口 → 服务 → 数据完整路径能画出「请求经过哪几层」5–10 分钟
相关文件待读待改文件清单（含不改但受影响的）每个文件都能说出为何关心1–2 分钟

明确跳过：node_modules/、target/、dist/、.git/、依赖目录、生成代码、大体积二进制。扫进去只会消耗上下文。

追踪调用链时，六类路径都要覆盖：同步调用、前端调用、异步任务（定时 / @Async）、消息消费、配置开关、动态 SQL。只跟同步链会漏掉大量场景。

链条要追到数据落点才算完：数据改在哪张表、事务边界在哪、异常最终怎么处理。

数据库结构以迁移脚本或实际库为准，不以实体类为准；接口要同时看前端 api/*.ts 与后端 DTO；缓存、MQ、第三方接口即使是间接依赖也要指出。

2.4 建立最小协作配置 ​

启动只建五项：项目认知资料、一份全局 Rules、一条开发主链、任务输入与验收习惯、进度记录方式。不需要全套 Agent、Skill 库、MCP、Hooks。

机制回答什么归属能不能放业务事实
Rules所有任务必须遵守什么跟仓库走只写约束句，不复制说明
Agent谁来做、权限到哪跟仓库或人走不存事实
Skills重复出现的方法怎么一步步做跟人走，可跨项目禁止

Rules 写什么：技术栈与版本、构建测试命令、命名分层、禁改目录、安全红线、跨任务成立的业务约束。不写本次任务、完整业务流程、分阶段操作步骤。每条要可验证，禁止项要配反例，全局控制在 30 行内，用「必须 / 禁止」而非「建议 / 尽量」。

Agent 的关键边界：执行者不能当验收人。审查者只输出「问题清单和依据」，完成判定由人做。没有冻结的 Spec 就不要拆并行角色。

Skill 的三个条件同时满足才建：同类操作出现三次以上、有稳定步骤和检查点、至少两个任务验证有效。Skill 里出现具体表名、客户名、业务字段，就是写错了地方。

MCP / Hooks 不越界：MCP 只解决仓库外的能力或数据，接前过必要性 / 边界 / 降级三项检查；凡是「漏了就出事且能脚本判定」的检查（构建、单测、密钥扫描、禁改区 diff）交给脚本，不靠提示词提醒。

工具适配边界：上面所有文件名和目录都是通用示意。Cursor、WorkBuddy 等工具的具体目录、配置语法、加载方式，以各自当前版本官方文档为准，不把某个工具的目录当成行业规范。

2.6 什么时候可以开始开发 ​

  1. 知道项目是什么。
  2. 知道项目如何运行。
  3. 知道如何编译和测试。
  4. 知道开发时要遵守哪些规则。
  5. 当前任务相关信息能够继续获取。
  6. 未确认的信息已经明确标注。

不需要等整个项目完全理解后才开始开发。 新功能只需在开始该任务前补对应业务上下文。

三、提示词 ​

3.1 新项目初始化 ​

text
现在准备开始一个新项目。

你的任务是协助我完成项目初始化，但暂时不要直接大规模编写业务代码。

第一步：明确项目目标
请先了解：
1. 项目要解决什么问题？
2. 主要用户是谁？
3. 核心业务功能有哪些？
4. 当前已经确定的技术选型是什么？
5. 有哪些明确的开发约束？

如果现有信息足够，不要重复询问。
如果存在关键缺失，一次性列出需要我确认的问题。

第二步：检查现有环境
检查当前工作目录：
- 是否已经存在项目文件？
- 是否已经有技术脚手架？
- 是否存在 Git 仓库？
- 是否已有项目规则文件？
- 是否已经安装必要依赖？

不要覆盖或删除已有内容。

第三步：提出初始化方案
给出：
1. 推荐目录结构。
2. 技术栈与依赖建议。
3. 开发、构建、测试命令。
4. 必要的项目规则。
5. 当前阶段需要创建的文件。

第四步：控制初始化范围
只创建当前阶段真正需要的内容。
不要预建大量空文档。
不要为了使用 Agent、Skills 或 MCP 而强行增加配置。

第五步：执行环境检查
在获得必要授权后，执行初始化和环境检查。

最终向我报告：
- 已完成的初始化内容。
- 项目目录结构。
- 技术栈。
- 开发和测试命令。
- 尚未解决的问题。
- 下一步建议。

特别要求：
不要把尚未确认的技术选型写成既定事实。
不要在没有确认的情况下执行高风险操作。

3.2 老项目接管 ​

text
你现在需要接管一个已经存在的软件项目。

本轮任务是：理解项目现状，建立后续开发所需的上下文。

暂时不要修改业务代码，不要进行重构，不要安装新依赖。

请按以下顺序检查：

一、项目基本情况
- 项目技术栈及版本。
- 前后端架构。
- 模块划分。
- 目录结构。
- 主要依赖。

二、运行与开发方式
- 如何启动项目？
- 如何构建项目？
- 如何执行测试？
- 是否存在数据库及相关配置？
- 是否存在 Docker 或其他运行环境？

三、业务结构
- 核心业务模块有哪些？
- 模块之间如何调用？
- 关键接口在哪里？
- 重要数据实体有哪些？
- 是否存在第三方系统集成？

四、开发规范
- 是否存在 AGENTS.md、CLAUDE.md、.cursor/rules 等规则文件？
- 是否存在项目自己的代码规范？
- 是否有特殊的命名、目录或架构约束？

五、风险与注意事项
- 哪些模块不应该随意修改？
- 哪些操作可能影响生产数据？
- 是否存在已知问题？
- 哪些信息无法从代码中确认？

六、输出项目接入报告

请使用以下格式：
1. 项目基本信息
2. 技术栈与版本
3. 目录与模块结构
4. 项目启动、构建和测试方式
5. 核心业务模块
6. 重要接口与数据实体
7. 开发规范
8. 外部依赖
9. 已知风险与注意事项
10. 尚未确认的信息

每项信息标记为：
- 已确认：有代码、配置或文档证据。
- 待确认：目前无法从现有资料确定。
- 人工补充：需要项目维护人员提供。

执行约束：
1. 本轮只读分析，不修改任何文件。
2. 不扫描无关目录和大型依赖目录。
3. 优先检查项目入口、配置、README、模块结构和关键业务代码。
4. 不要把猜测当成事实。
5. 不要为了生成报告而重复读取大量相同内容。
6. 如果项目规模较大，先输出整体地图，再针对重要模块深入。
7. 不需要一次性理解整个项目的所有业务细节。

最后告诉我：
- 当前是否已经具备开发条件？
- 如果开始一个新功能，还缺少哪些必要信息？
- 哪些内容建议写入项目规则文件？
- 哪些内容应该等具体开发任务出现时再分析？

text
你的任务只有一个：产出一份项目地图。不要修改任何文件，不要提改进建议。

背景：我需要了解一个已有项目的整体结构，还没有开始任何开发。

四、验收标准 ​

项目接入检查 ​

  • [ ] 新项目目标与技术栈明确，开发命令已实际跑通；或老项目有一份可靠的接入报告。
  • [ ] 每条认知结论都有来源；推测都进了「待确认」，正文没有「应该是」「一般是」。
  • [ ] gotchas 由人写，不是 AI 代笔。
  • [ ] 构建命令、测试命令、最小冒烟验证在本机实际跑通过一次。
  • [ ] 禁改区与安全边界写明，并已同步进规则文件。
  • [ ] 明确写出「未覆盖范围」。
  • [ ] 老项目：确认没有任何架构级改动，git diff 只有文档。
  • [ ] 没有创建无意义的空文档或复杂配置。

上下文是否足够的五问 ​

  1. 我知道要改哪几个文件吗？
  2. 我知道改完之后谁会受影响吗？
  3. 我知道涉及哪张表、哪个接口吗？
  4. 我知道现有实现为什么这么写吗？
  5. 我知道哪些地方不能碰吗？

有两条答不上来，回到对应层补，不要带着缺口开始改代码。

配置检查 ​

  • [ ] 全局规则不超过 30 行，每条都有验证方式，禁止项都配了反例。
  • [ ] 规则里没有「本次」「这个需求」「先做……再做……」这类任务措辞。
  • [ ] 启用的角色有职责与权限边界，审查者明确不判定通过。
  • [ ] Skill 里没有具体表名、客户名、业务字段。
  • [ ] 能脚本化的检查已进入脚本，不靠提示词提醒。

准备阶段最容易犯的错 ​

  • 让 AI 一次性扫描整个仓库：上下文被无关代码占满，关键信息反而被稀释。
  • 初始化阶段创建大量文档：生成没人维护的空文件。
  • 接手老项目时顺手重构：加一个功能却引入大量无关变更。
  • 把「看懂了」当成「验证过了」：靠命名和注释推测业务规则。
