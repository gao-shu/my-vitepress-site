项目分析与上下文准备 ​

上一章解决了「怎么把任务交代清楚」，本章解决「AI 接到任务后，怎么快速找到该看的地方」。核心方法是分层收敛：先拿项目地图，再定位模块，然后追调用链，最后才读具体文件——而不是让 AI 把整个仓库读一遍。

一、什么时候使用 ​

以下情况必须先做上下文准备，再让 AI 动手：

  • 第一次进入一个仓库，或接手别人写的项目。
  • 修改一个自己三个月前写的功能，记忆已经模糊。
  • 需求涉及「加个字段」「加个接口」但你不确定会波及哪里。
  • 修复一个涉及多个模块、调用链不清晰的 Bug。
  • 同一问题改了三次都没改对——通常说明影响范围判断错了。

以下情况可以跳过：

  • 改文案、调颜色、改常量值。
  • 修改自己刚写的、还在上下文里的代码。
  • 已有明确 Spec 且改动只在一个自包含文件内。

判断标准：你能不能用一句话说清「改哪里」和「会影响谁」。 说不出「会影响谁」，就要先做上下文分析。

二、上下文准备的四层范围 ​

无效扫描的根本原因是范围没有分层——AI 拿了整个仓库当上下文，结果里面 95% 与任务无关，真正相关的那几个文件被淹没。

正确的收敛路径是从外到内、四层递进：

text
第 1 层  项目地图      整体结构、模块划分、入口在哪
            ↓ 收敛
第 2 层  模块地图      本次任务落在哪个模块、涉及哪些子目录
            ↓ 收敛
第 3 层  调用链        这个模块里，入口 → 服务 → 数据的完整路径
            ↓ 收敛
第 4 层  相关文件      真正要读、要改的那几个文件

2.1 每层的产出与停止条件 ​

层次产出什么时候可以停典型耗时
项目地图模块清单 + 入口清单 + 构建方式能说出「这个项目由哪几块组成」3–5 分钟
模块地图本次任务涉及的目录与子模块能指出「改动落在哪个包里」2–3 分钟
调用链从入口到数据层的文件路径能画出「请求进来后经过哪几层」5–10 分钟
相关文件待读待改文件清单（含不改但受影响的）文件清单能逐个说出为什么关心它1–2 分钟

停止条件很重要。 没有停止条件的分析会一路滑向全仓扫描。

三、第一层：拿到项目地图 ​

目标是花最短时间知道「这个项目由什么组成、从哪里进入」。

3.1 该看什么 ​

要回答的问题去哪里找
有几个模块、怎么划分的pom.xml 的 <modules>、package.json 的 workspaces、settings.gradle
前端入口在哪src/main.ts、src/App.vue、src/main.js
后端入口在哪带 @SpringBootApplication 的类、main 方法
有哪些环境配置application*.yml、application*.properties、.env*
怎么构建、怎么跑测试package.json scripts、pom.xml、Makefile、CI 配置
哪些目录是产物或依赖target/、dist/、node_modules/、.git/

明确排除：node_modules/、target/、dist/、.git/、压缩包、大体积二进制、生成代码目录。这些目录 AI 扫进去只会消耗上下文和出错。

四、第二层：定位相关模块 ​

有了项目地图，下一步是把任务落到具体模块。

4.1 定位顺序 ​

按这个顺序找，先命中先停：

  1. 按业务名词搜——先搜中文业务词和领域英文词（出库、批次、outbound、batch），业务代码里字段名往往保留业务语义。
  2. 按技术入口搜——已知要改哪个接口，就从 Controller 或路由定义反查。
  3. 按数据实体搜——已知涉及哪张表，就搜表名和实体类名。
  4. 按目录结构推——按项目地图的模块划分，直接推断该落在哪个包里。

4.2 多模块项目的额外一步 ​

Java 多模块项目（ruoyi-admin / ruoyi-system / ruoyi-common / 业务模块）里，必须先确认三件事：

  • 本模块能否依赖目标模块——方向错了编译不过，先看 <dependency>。
  • 公共模块（common）里放什么——能放通用工具，但放业务逻辑会污染所有模块。
  • 控制器与实现是否同模块——有的项目 controller 在 admin 模块、实现放在业务模块的 service 包，改一边不等于改另一边。

4.3 可复制：相关模块定位提示词 ​

你的任务只有一个：定位本次任务相关的模块和文件，并说明定位依据。不要修改任何文件。

任务：<本次要做的事，一句话>

约束：
- 先给模块级判断，再给文件级清单，不要一上来就逐文件读。
- 使用搜索定位，不要遍历整个仓库。
- 跳过 node_modules、target、dist、build、.git 等目录。
- 找不到时明确说「未找到」，并列出你试过的关键词，不要编造路径。
- 每个文件都要说明「为什么关心它」（是入口、是实现、是数据、是调用方还是配置）。

请输出：
1. 任务归属模块（模块名 + 判断依据）
2. 相关文件清单（路径 | 角色 | 为什么关心它 | 证据行号）
3. 可能受影响的调用方（路径 | 调用方式 | 风险点）
4. 不在本次范围内的相邻模块（说明为什么排除）
5. 目前仍不确定的部分（需要我提供什么信息）

五、第三层：追踪调用链与数据流 ​

这一层是最容易漏、也最容易出问题的地方。

5.1 必须覆盖的路径类型 ​

只跟同步调用链会漏掉大量场景：

路径类型典型位置漏掉的后果
同步调用Controller → Service → Mapper相对少见漏
前端调用Vue 页面 → API 定义 → 后端接口前端传参变了后端没同步
异步任务@Scheduled、@Async、线程池定时跑的任务用的是旧逻辑
消息消费MQ 消费者、事件监听器消息格式改了消费端没改
配置驱动开关、字典、配置表功能被开关关着，测不出来
反射 / 动态 SQLMyBatis XML、动态路由改的 SQL 根本没人调用

5.2 追踪的终点 ​

链条要一直追到数据落点才算完：

六、第四层：核对数据库、接口与外部依赖 ​

分析不能只看代码。有三处「代码里看不到」的东西必须专门核对。

6.1 数据库结构 ​

  • 表结构以迁移脚本或实际库为准，不要以实体类为准——实体类可能漏字段、可能与线上不一致。
  • 看索引：这次改动如果加了查询条件，是否命中索引；有没有唯一约束会被新逻辑破坏。
  • 看约束：外键、唯一键、非空约束，新代码是否违反。
  • 看数据量级：一张几万行的表和一张几十万行的表，加个查询条件的后果完全不同。

核对方式：优先读 resources/db/migration/ 或 sql/ 目录下的迁移脚本；能连测试库则直接查 information_schema，但只读、且先确认是测试库。

6.2 接口契约 ​

前端与后端是一对，改一边必须看另一边：

  • 前端 API 定义文件（api/*.ts、src/api/**）里的路径、参数、返回结构。
  • 后端 Controller 的入参 DTO、返回包装类、错误码。
  • 是否有接口文档、是否有契约测试。

常见问题：前端传 status 字符串，后端收的是枚举数字；前端返回体读 data.list，后端改成了 data.records；错误码从 400 改成 409，前端只按 body.code 判断。

6.3 外部依赖 ​

  • Redis 缓存：改了数据但不失效缓存，是「代码没问题但功能不对」的典型原因。
  • MQ：消息体格式、幂等键、重试与死信策略。
  • 第三方接口：签名方式、超时、重试、限流，失败时是降级还是抛错。

6.4 可复制：依赖与影响面核对提示词 ​

你的任务只有一个：核对本次改动会波及的数据库、接口、缓存和外部依赖。不要修改任何文件。

改动点：<文件:行号 + 改了什么>

约束：
- 数据库结构以迁移脚本或实际库为准，实体类只作参考。
- 只读核对，不要执行任何写操作，不要连接生产库。
- 缓存、消息、第三方接口都要覆盖，即使本次没直接改到——间接依赖必须指出。
- 每条结论给出证据来源（文件路径、SQL 结果或配置项）。

请输出：
1. 直接影响（被修改的表、接口、缓存键、消息体）
2. 间接影响（调用方、被缓存的数据、定时任务、报表统计）
3. 数据一致性风险（缓存未失效、索引缺失、约束冲突、并发覆盖）
4. 接口兼容性风险（字段增删改、状态码变化、返回结构变化）
5. 需要人工确认的事项（列出具体问题，不给猜测结论）

七、影响范围判断 ​

判断影响范围不是靠感觉，而是靠四类证据。

证据类型怎么查说明什么
反向调用全仓搜方法名、接口路径、字段名谁会受影响
数据落点追踪到表，看谁写这张表哪些功能依赖这张表

八、上下文是否足够的判断标准 ​

在动手改代码前，用这五个问题自检：

  1. 我知道要改哪几个文件吗？ 说不出来就是上下文不足。
  2. 我知道改完之后谁会受影响吗？ 只知道改哪、不知道影响谁，不够。
  3. 我知道这次改动涉及哪张表、哪个接口吗？ 不清楚数据落点，不够。
  4. 我知道现有实现为什么这么写吗？ 不明原因就容易把有意设计当冗余删掉。
  5. 我知道哪些地方不能碰吗？ 没有禁改区概念，就容易顺手重构。

五问中有两条答不上来，回到上一层补，不要带着缺口开始改代码。

九、复用已有项目知识，不要重复扫描 ​

如果第 01 章的接入工作已经做过，项目里应该已经有认知资料。先读它，再扫描。

已有资料复用方式不要重复做的事
项目认知报告直接读第 3、4、5 节（目录、规则、数据接口）重新扫目录结构
项目规则文件直接作为约束，不再重复交代每次会话重新贴约束
模块地图文档直接定位模块重新搜入口
gotchas 记录直接读，避免重复踩坑重新发现已知坑

如果接入资料与当前代码不一致（有人改了代码没更新文档），以代码为准，并把差异记下来——这本身是一条值得更新的经验。

十、常见错误 ​

错误 1：一次性让 AI 读整个仓库 ​

问题：上下文被无关代码占满，关键信息反而被稀释；分析结果看起来面面俱到，实际不可用。

正确做法：严格按四层收敛，每层有停止条件，输出进入下一层前先确认。

错误 2：只跟同步调用链 ​

问题：漏掉定时任务、消息消费、配置开关，改了主流程但旧路径还在跑。

正确做法：把六类路径逐条确认，答不上来的标为待确认。

错误 3：以实体类推断数据库结构 ​

问题：实体类漏字段、加了 @TableField(exist = false) 的非持久化字段，读到假的表结构。

正确做法：以迁移脚本或实际库为准，实体类只作参考。

错误 4：把「看懂了」当成「验证过了」 ​

问题：AI 读完代码说「已理解业务逻辑」，实际是从命名和注释推测的。

正确做法：所有理解必须带证据路径；靠推测得出的业务规则一律标为待确认，不能当事实往下走。

错误 5：影响范围只写一句话 ​

问题：「影响列表查询相关逻辑」这种描述无法作为核对清单，改漏了也发现不了。

正确做法：输出逐文件清单，每个文件标明角色和原因，区分「必须同步」与「需要回归」。

十一、本章完成检查 ​

开始写代码前，确认下面这些都已经落到纸上：

  • [ ] 有一份项目地图（模块、入口、构建命令），新接手项目时至少扫过一次。
  • [ ] 明确本次任务落在哪个模块、涉及哪些子目录。
  • [ ] 至少追出一条完整调用链，从入口到数据落点。
  • [ ] 确认了同步、异步、消息、定时、配置开关、动态 SQL 六类路径中没有未覆盖的。
  • [ ] 核对了数据库结构来源（迁移脚本或实际库）。
  • [ ] 核对了前端 API 定义与后端接口契约。
  • [ ] 确认了 Redis 缓存、MQ、第三方接口的间接影响。
  • [ ] 有一份逐文件的影响清单，标明直接修改 / 必须同步 / 需要回归。
