交付验收与经验复用 ​

这是整套 SOP 的最后一环。AI 说「写完了」不算完成——完成要能逐条核对、有命令输出、有 diff 证据。验收通过后，还要判断这次的经验值不值得沉淀，让下一次开发真的能少走弯路。

一、什么时候使用 ​

以下时机进入本章：

  • 一个子任务或整个任务执行完毕，准备标记完成。
  • AI 报告「已完成」，你需要判断是不是真的完成。
  • 准备提交、合并或部署之前。
  • 一次开发结束后，判断哪些经验值得留下来。

不要等到全部代码写完才第一次验收。第 06 章的每个检查点都应该用本章的清单做局部验收——越晚发现问题，回滚成本越高。

一条底线：完成由人判定，不由 AI 宣布。 AI 负责提供证据，人负责逐条核对。

二、四层验收 ​

层次回答什么主要证据
功能验收要求的功能实现了吗页面操作、接口返回、业务规则核对
兼容验收原有功能被影响了吗回归对照、接口契约比对
技术验收编译和测试通过了吗命令输出原文
交付验收结果可追溯、可接手吗diff、交付报告、遗留清单

四层不是每次都要同等强度。按第 02 章的任务分级裁剪：

  • L1 简单任务：功能 + 局部检查 + 说明修改结果。
  • L2 普通任务：四层都过，但兼容验收只看相关模块。
  • L3 复杂任务：四层全过，兼容验收覆盖上下游，技术验收包含全量测试。

三、第一层：功能验收 ​

3.1 逐条对照，不要凭印象 ​

把第 02 章任务输入里的「验收标准」逐条抄过来，每条后面填结果：

text
| 验收项 | 预期 | 实际 | 证据 | 结论 |
| ------ | ---- | ---- | ---- | ---- |
| 不同状态筛选结果正确 | WAITING 只返回等待单 | 返回 3 条 WAITING | 单测输出 + 页面截图 | 通过 |
| 分页不受影响 | 第 2 页数据正常 | 页码正确、总数一致 | 接口返回原文 | 通过 |
| 不符合条件订单不能关闭 | 已发订单被拒 | 返回 409 | 接口冒烟 | 通过 |

「看起来没问题」不是证据。 每条结论都要能指到一个具体命令输出、接口返回或页面行为。

3.2 业务规则要单独核对 ​

功能验收里最容易漏的是业务规则——代码跑通了，但规则理解错了。

核对方法：从项目认知资料里取出本次相关的规则（例如「出库必须 FEFO」「关闭订单必须释放库存」），逐条确认实现是否保持。有疑问的交给业务确认，不要让 AI 自行解释。

四、第二层：兼容验收 ​

4.1 Git Diff 检查清单 ​

逐项检查 diff，任何一项不通过都不能算完成：

  • [ ] 改动文件都在第 04 章的「允许修改」范围内。
  • [ ] 没有触碰禁改区。
  • [ ] 依赖文件（pom.xml、package.json、requirements.txt）没有意外变更。
  • [ ] 没有批量格式化无关文件。
  • [ ] 没有硬编码特判、吞异常、放宽断言。
  • [ ] 没有删除或注释掉现有测试。
  • [ ] 没有把临时调试代码（打印、TODO、注释掉的分支）留在里面。
  • [ ] 提交信息说清了改什么、为什么。

4.2 接口与数据兼容 ​

检查对象核对什么
已有接口路径、方法、入参、返回结构、错误码是否变化
已有字段是否删除、改名、改类型、改含义
数据库是否改字段类型、是否加非空约束、迁移是否可重复执行
缓存数据变更后缓存键是否失效
上下游第 03 章影响清单里的调用方是否逐个核对
前端契约api/*.ts 与后端 DTO 是否一致

兼容性结论要写成「没变 / 变了但已确认兼容 / 变了需要通知下游」三种之一，不能写「应该没问题」。

五、第三层：技术验收 ​

5.1 证据要求 ​

项合格证据不合格写法
编译命令原文 + 成功输出「编译通过」
单测命令原文 + 通过数 / 失败数「测试都过了」
接口冒烟请求与返回原文「接口正常」
类型检查命令原文 + 输出「类型没问题」
无法执行的检查原因 + 替代检查不写，或写成通过

5.2 任务级别对应 ​

text
L1：编译或局部检查 + 修改说明
L2：相关模块单测 + 接口冒烟 + 关键回归
L3：全量测试 + 接口冒烟 + 上下游回归 + 数据迁移检查

5.3 可复制：验收自查提示词 ​

text
请对本轮改动做验收自查，不要修改任何文件，也不要宣布完成。

输入：
- 任务验收标准：<来自任务输入的验收段>
- 修改范围与不做项：<来自 TASK-PLAN.md>
- 本轮 diff：<git diff>
- 已执行的命令与输出：<原样>

请按四层输出：

1. 功能验收（逐条对照验收标准，每条给证据或标「缺证据」）
2. 兼容验收（逐项检查 diff、接口、字段、上下游，给出「没变 / 已确认兼容 / 需通知下游」）
3. 技术验收（已执行命令清单与输出关键行；未执行的明确标出，不得写成通过）
4. 交付验收（改动文件清单、遗留问题、是否可接手）

约束：
- 不编造测试输出，不把未执行的检查写成通过。
- 发现问题直接列出，不要替它找理由。
- 最后输出「可以进入人工验收 / 尚缺以下证据」二选一，不要输出「任务完成」。

6.2 遗留问题不能藏 ​

遗留问题写清楚，比假装没有更有价值。每条包含：问题是什么、影响什么、建议怎么处理、谁来决定。

「下次再说」不是处理方式——要么建明确的待办，要么写进认知资料的 gotchas，要么在交付报告里留痕。

七、经验沉淀 ​

7.1 先问三个问题 ​

不是每次开发都要沉淀。三个问题全答「是」才动手：

  1. 这个问题还会再出现吗？ 一次性问题不沉淀。
  2. 不沉淀的代价是什么？ 代价很小就不沉淀。
  3. 有没有第二个项目能验证它？ 没验证过的方法只是设想。

7.2 沉淀到哪里 ​

经验类型去哪里例子
跨任务成立的约束Rules「禁止新增依赖」「出库保持 FEFO」
踩过的坑、不看代码想不到的gotchas / 项目认知资料「qty 是可用量不是账面量」
重复三次以上的做法Skill「老项目局部改动」「测试失败修复循环」
项目特有的事实项目认知资料模块划分、字段含义、历史决策
一次性的排查过程不沉淀，留在交付报告某次特定的偶发问题
工具配置细节工具适配说明某个工具的具体目录与语法

7.3 沉淀格式：规则更新 ​

text
触发：什么问题、在第几次出现
新增规则：Cxx / Pxx，一句话
验证方式：哪个命令或 diff 特征
反例：曾经或可能出错的写法
来源：哪次事故 / 哪次复盘
变更记录：日期 + 原因

7.4 沉淀格式：Skill 更新 ​

在 Skill 的「复用记录」表加一行，写清日期、项目、结果、据此改了什么。至少两个项目验证过才升级为通用方法；只有一个项目的先留在项目内。

八、什么不要沉淀 ​

明确禁止清单，避免把长期资产变成垃圾场：

  • 一次性 bug 的临时绕法（当时有效，过后误导）。
  • 未验证有效的「看起来不错的方法」。
  • 具体表名、客户名、业务字段写进 Skill（它跟人走，会污染下个项目）。
  • 本次任务范围写进 Rules（规则会膨胀）。
  • 整段业务流程说明写进 Rules（它属于认知资料）。
  • 已经过时的技术栈版本、构建命令。
  • 重复已有提示词库的大段模板。
  • 「尽量」「建议」这类无法验证的软规则。

九、让下一次能直接复用 ​

沉淀的终点是「下一次不用重新交代」。验收时问自己五个问题：

  1. 下次开新会话，AI 能不能只读项目资料就知道禁改区和命令？
  2. 同类任务再来，能不能直接套用已有的 Skill，不用从头讲步骤？
  3. 上次踩的坑，下次还会不会踩？
  4. 同类 bug 再出现，能不能直接用第 07 章的闭环 + 提示词库的手法？
  5. 新人接手，能不能靠交付报告看懂这次改了什么、为什么？

五条里有两条答不上来，说明沉淀没做到位。

十、常见错误 ​

错误 1：以 AI 自述作为验收 ​

问题：「已完成」「已补充测试」不是证据，上线后才发现问题。

正确做法：每条验收都要有命令输出、diff 或页面行为。

错误 2：只看功能，不看兼容 ​

问题：新功能正常，老功能被改坏。

正确做法：兼容验收独立一层，逐项核对接口、字段、上下游。

错误 3：把没跑的测试写成通过 ​

问题：交付报告失真，问题延后暴露。

正确做法：已验证 / 未验证 / 受限 / 不适用四态区分，原因写清楚。

错误 4：遗留问题写「下次处理」 ​

问题：没有具体位置和责任人，等于没写。

正确做法：建待办、写 gotchas，或明确谁来决定。

错误 5：把一次性经验写成 Rules ​

问题：规则越来越长，真正的红线被稀释。

正确做法：三问筛选，一次性过程留在交付报告。

错误 6：把业务字段写进 Skill ​

问题：Skill 跟人走，带着 A 项目的字段跑到 B 项目。

正确做法：Skill 只放方法，业务事实留项目认知资料。

错误 7：没有回归对照证据 ​

问题：无法证明「没改坏别的」。

正确做法：回归表至少有一条「改前行为保持」的证据。

十一、本章完成检查 ​

  • [ ] 四层验收逐条完成，每条都有证据。
  • [ ] 功能验收逐条对照任务输入里的验收标准。
  • [ ] diff 检查清单全部打勾，没有硬编码、吞异常、放宽断言。
  • [ ] 接口、字段、数据库、缓存、上下游的兼容性结论明确。
  • [ ] 技术验收的命令与输出原文已记录。
  • [ ] 未验证项按四态区分，没有写成通过。
  • [ ] 回归对照包含「已修复」与「改前行为保持」两类证据。
  • [ ] 交付报告完整，遗留问题逐条列出且有处理方式。
  • [ ] 沉淀经过三问筛选，放到了正确的位置。
  • [ ] 沉淀内容没有踩「什么不要沉淀」清单里的任何一条。

全专题收尾 ​

到这里，九个页面构成了一条完整链路。这套 SOP 能否支撑真实项目，取决于你能否对下面三个问题回答「是」：

  1. 能不能少问？ 用户只交代目标和边界，AI 自己查项目、判断缺口、集中提阻塞问题。
  2. 能不能少错？ 先理解再执行、方案先行、小步改动、每步有证据，不靠反复试错。
  3. 能不能连续完成？ 有计划、有状态、有恢复、有检查点，不需要每步等待确认。

如果这三条里还有做不到的环节，回到对应章节补，不要靠增加文档数量来制造「完整」的感觉。
