开发中 ​

一项开发任务从准备到交付的九个阶段。找到你现在所处的阶段，复制对应命令，按结果往下走。

快速定位 ​

我现在要做什么使用
开新项目 / 接手老项目01 项目准备
判断需求能不能做、把需求说清02 需求分析
写代码前定方案、评方案03 架构设计
按方案连续编码04 功能开发
检查写完的代码、按问题整改05 功能审查与完善
修业务逻辑错误、查 BUG 根因06 逻辑与 BUG 修复
改善结构、不动行为07 代码优化与重构
设计用例、执行测试、分析结果08 代码测试
交付验收、沉淀经验、清理遗留09 交付复用

原则：简单任务可跳过部分阶段，复杂任务完整走。测试必须有实际执行证据。

01 · 项目准备 ​

让 AI 先懂项目、定好边界，再动手写代码。

什么时候使用 ​

  • 全新项目要初始化
  • 接手别人开发的项目
  • AI 经常理解错、改错地方

操作 ​

① 新项目初始化 ​

text
现在准备开始一个新项目，请协助初始化，但暂时不要大规模编写业务代码。

1. 先确认：项目要解决什么问题、主要用户、核心功能、技术选型、开发约束。信息够就不要重复问，关键缺失一次性列出。
2. 检查当前目录：是否已有项目文件、脚手架、Git 仓库、规则文件、必要依赖。不要覆盖或删除已有内容。
3. 给出初始化方案：目录结构、技术栈与依赖、开发/构建/测试命令、必要规则、当前阶段要创建的文件。
4. 只创建当前真正需要的内容，不预建空文档，不为用 Agent / Skill / MCP 强行加配置。
5. 等我确认后再执行初始化和环境检查。

不要把未确认的技术选型写成既定事实，不要执行未经确认的高风险操作。

按顺序检查：技术栈与版本、前后端架构、模块划分；如何启动/构建/测试、有无数据库和 Docker；核心业务模块、模块间调用、关键接口、重要数据实体、第三方集成；已有规则文件和代码规范；哪些模块不能随意改、哪些操作影响生产数据、已知问题、代码里查不到的信息。

输出项目接入报告，每项标注：已确认（有证据）/ 待确认 / 人工补充。
最后说明：是否具备开发条件，开始新功能还缺什么信息，哪些建议写入规则。

02 · 需求分析 ​

把需求说清楚，并先判断可行性和风险——有重大问题先沟通，确认没问题再往下做。

什么时候使用 ​

  • 收到新功能、改动、Bug 需求
  • 需求描述模糊、怕 AI 理解错
  • 不确定现有架构能不能实现

操作 ​

① 需求可行性分析 ​

text
请分析下面这个需求，本轮只分析和沟通，不要修改任何代码，也不要开始实现。

需求：<描述>

请输出：
1. 需求复述（三句话内），确认你理解对了
2. 可行性判断：基于当前项目结构、数据库、接口和现有能力，能不能做、要改哪些地方
3. 风险与阻塞：业务规则不清、数据一致性、权限、兼容性、不可逆操作等
4. 缺失信息：分「能从项目查到的」「必须问我的」两类；能从项目查到的你自己查，只把真正阻塞的集中问我
5. 初步影响范围：大致涉及哪些模块和文件

如果可行性有问题或存在重大风险，先列出来等我确认，不要给出实现方案。
确认无阻塞后，再问我是否进入方案设计。

② 需求完善与任务输入 ​

text

需求：<描述>

按四段整理：
1. 目标：具体要实现什么
2. 约束：允许改什么、不能改什么、必须保持兼容什么
3. 验收：怎样算完成（写成能核对的行为、命令或 diff 特征，不写「完成开发」）
4. 任务分级：按修改范围、业务复杂度、数据影响、接口兼容、回归风险判断，说明是简单 / 普通 / 复杂

缺失信息按「能从项目查到的自己查、影响正确性的集中问我」处理，不要让我重写能从代码查到的内容。

03 · 架构设计 ​

在写代码前定方案，结合现有项目结构、数据库、接口和兼容性，避免方向错了返工。

什么时候使用 ​

  • 涉及多文件或数据结构改动
  • 有多种实现路径要取舍
  • 改错了要回滚多个文件

操作 ​

① 技术方案设计 ​

text
请基于当前项目产出技术方案和风险清单。本轮只出方案，不要修改代码、不要创建文件。

任务：<一句话>
已有上下文：<涉及模块、调用链、数据表、接口、禁改区，或让 AI 自己读项目补全>

输出：
1. 需求复述（三句话内）
2. 现有结构影响：要改哪些模块、数据库、接口，与现状怎么衔接
3. 本次不做项
4. 方案比较（可选方案，逐项对比改动范围、数据影响、兼容性、回滚成本、验证难度）
5. 推荐方案与理由（业务正确性 → 兼容性 → 改动范围 → 复用 → 可验证）
6. 修改范围三栏：允许修改 / 禁止修改 / 必须保持兼容（落到具体路径）
7. 风险清单：风险 → 触发条件 → 影响 → 处理 → 谁确认
8. 子任务拆解：编号 / 任务 / 文件 / 依赖 / 完成标准 / 验收方式
9. 需我拍板的问题（没有就写「无，可以开始」）

不要编造项目里不存在的组件或服务，无法判断的标「待确认」。

② 方案评审 ​

text
请评审下面这份技术方案，本轮只评审，不改方案、不改代码。

<粘贴方案>

检查：
1. 是否考虑了现有项目结构、数据库现状、接口契约和兼容性
2. 修改范围三栏是否落到具体文件、有无越界风险
3. 数据结构变更能否回滚、会不会影响已有数据
4. 风险清单是否每条都有处理动作和确认人
5. 子任务是否可独立验收、完成标准是否可核对
6. 有没有需要人拍板却没列出来的决策

输出：问题清单（带依据）+ 建议调整项 + 结论（可进入开发 / 需修改后再评）。

04 · 功能开发 ​

按已确认的方案连续编码，每步守住修改范围，不扩大需求。

什么时候使用 ​

  • 方案已定、子任务已拆
  • 要让 AI 连续做多个步骤
  • 中途可能中断、需要恢复

操作 ​

① 功能开发（守范围） ​

text
请按已确认的方案开始开发，严格遵守下面的执行规则。

已提供：任务计划、修改范围三栏、不做项、验收标准。

执行规则：
1. 每轮只做一个子任务，按依赖顺序，不跳
2. 严格遵守修改范围，超出范围或要动禁改区 / 依赖 / 公共模块，先停下来说明，不要「顺手改」
3. 每个子任务完成后跑对应的验证命令，原样记录输出
4. 验证通过再进入下一个；失败先说明本轮假设为什么错了，同一错误建议最多试几轮，仍失败就停手标阻塞
5. 到检查点停下来等我确认，不要自行通过
6. 不要自己宣布整个任务完成，最终验收由我判定

如果以上规则可行，从第一个子任务开始。

05 · 功能审查与完善 ​

先检查已完成的代码是否符合规范，再决定要不要改——审查阶段不擅自重写。

什么时候使用 ​

  • 一个功能或子任务写完
  • AI 报告「已完成」，要判断是否真完成
  • 想补边界、异常、权限但不确定改哪里

操作 ​

① 功能规范审查 ​

text
请对本次已完成的代码做规范审查。本轮只审查、只输出问题清单，不要修改任何文件，也不要重写代码。

输入：任务验收标准、修改范围与不做项、本轮 diff。

按清单检查，每条给「文件:行号 | 问题 | 依据」：
1. 功能是否符合验收标准、业务规则是否实现完整
2. 边界条件：空值、零值、重复、越权
3. 异常处理与事务边界
4. 接口、字段、数据兼容性
5. 权限与数据范围
6. 测试断言是否被放宽或删除
7. 改动范围：无关格式化、未用 import、调试打印、注释掉的分支、遗留 TODO

最后输出「问题清单」和「需我确认的疑点」两部分。不要写「整体没问题可以合并」这类结论，是否修改由我决定。

要求：

4. 不删除或放宽现有测试，不硬编码绕过，不吞异常

输出：逐项整改结果 + 验证证据 + 未处理项及原因。

06 · 逻辑与 BUG 修复 ​

处理两类问题——结果与预期不符的逻辑错误，和有报错的 BUG，统一走「先定位根因、再最小修复、最后验证」。

什么时候使用 ​

  • 编译失败、单测失败、接口报错
  • 功能结果与预期不符
  • 改完 A 坏了 B、偶发失败

操作 ​

① 业务逻辑修复（结果与预期不符） ​

text
请处理一个业务逻辑错误，先定位根因，不要直接改代码。

现象：<期望 vs 实际>
复现步骤：<步骤>
相关改动：<git diff 或提交记录，可让 AI 自己查>

本轮只做：
1. 列事实（只写有证据的：现象、实际 SQL / 参数、配置值）
2. 列几条根因假设，每条写支持和反对的证据
3. 用最小只读动作验证并逐个排除
4. 给出确认的根因（证据不足写「未确认」）、最小修改文件清单、绝对不能改的地方

判断根因的标准：修掉它能解释原始现象。证据不足不要选最像的当结论，不要输出修复代码。等我确认后再修复。

② BUG 根因分析与修复 ​

text
请按闭环方式修复一个 BUG。

问题：<现象 + 完整报错原文>
复现步骤：<步骤>
允许修改范围：<文件清单，或让 AI 先给建议>
验证命令：<具体命令>

要求：
1. 先收齐证据：复现步骤、完整堆栈、期望行为、环境、最近改动
2. 先分析根因再改，证据不足标「未确认」，不要猜着改
3. 只改导致根因的那一处，不顺手重构、不格式化、不改无关文件
4. 每轮改完跑验证命令，原样贴出命令和输出关键行
5. 失败先说明假设为什么错了；同一错误建议最多试几轮，仍失败就停手
6. 不删断言、不放宽测试、不硬编码特判、不吞异常、不加数据特判

输出：根因与修复对应关系 + 修改文件 + 每轮命令与输出 + 通过 / 未通过清单 + 未解决问题。

07 · 代码优化与重构 ​

改善代码内部结构，不改变外部行为。要改行为就另开任务，不混在重构里。

什么时候使用 ​

  • 功能正确但结构混乱、重复多
  • 技术债影响后续开发
  • 审查发现的改进点

操作 ​

① 代码优化 ​

text
请对下面这段代码做优化，目标是不改变外部行为的前提下改善可读性和结构。

代码：<粘贴代码或文件>

要求：
1. 先列出要补哪些行为测试来锁定当前行为，等我确认后再动手
2. 接口签名、返回结构、数据结构、字段含义、状态流转保持不变
3. 一次只改一个关注点，每步跑测试
4. 不夹带格式化、注释改写、无关调整
5. 不新增依赖，不改业务规则

输出：优化计划 + 行为测试清单 + 每步验证方式。本轮先不要改代码。

② 重构不改行为 ​

text
请重构下面这段代码，严格保持外部行为不变。

代码：<粘贴>

必须保持不变：接口 / 返回结构 / 数据结构 / 字段含义 / 状态流转 / 错误码。

要求：
1. 先确认已有行为测试覆盖正常路径和关键边界；不足先补，补完给我确认
2. 小步改，每步跑一次行为测试

09 · 交付复用 ​

交付要让结果可追溯、可接手；验收后判断哪些经验值得留下；同时清理本次开发产生的遗留文件。

什么时候使用 ​

  • 任务完成、准备收工
  • AI 说「已完成」，要判断是否真完成
  • 本次开发产生了临时文件要清理

操作 ​

① 交付验收 ​

text
请对本轮改动做验收自查，不要修改文件，也不要宣布完成。

输入：任务验收标准、修改范围与不做项、本轮 diff、已执行命令与输出。

按四层输出：
1. 功能：逐条对照验收标准，每条给证据或标「缺证据」
2. 兼容：检查 diff / 接口 / 字段 / 上下游，给出「没变 / 已确认兼容 / 需通知下游」
3. 技术：已执行命令与输出关键行，未执行的明确标出、不得写成通过
4. 交付：改动文件清单、遗留问题、是否可接手

另查安全检查（敏感信息、破坏性操作、Git 状态）。
最后输出「可以进入人工验收 / 尚缺以下证据」二选一，不要输出「任务完成」。

③ 遗留文件清理 ​

text

检查范围：本次任务涉及的目录；参考本任务的起始提交或时间判断归属。

检查：
1. 临时文件、备份文件（.bak / .tmp / ~ / .orig 等）

最后 ​

开发中完成 ​

九个阶段走完，至少确认：

  • 需求先判可行性、有风险先沟通

  • 修复先定位根因，不猜着改

  • 遗留文件清理区分归属，需人确认才删
